# 05. 리소스 관리와 머티리얼 — 도서관과 대출증

> **이 문서 하나로**: 텍스처/셰이더/메시 같은 GPU 리소스를 누가 소유하고 어떻게 찾아 쓰는지, 머티리얼이 왜 포인터가 아니라 "키"로 리소스를 참조하는지를 실제 코드와 함께 이해합니다.
>
> 관련 소스: `Graphics/ResourceMgr.h/.cpp`, `Graphics/Material.h/.cpp`, `Graphics/Mesh.h`, `Graphics/Texture.h`

---

## 1. 큰 그림 — 도서관 비유

게임이 쓰는 GPU 리소스(텍스처, 셰이더, 메시, 머티리얼)는 생성 비용이 크고, 여러 곳에서 공유되며, 수명 관리를 잘못하면 참사(이미 해제된 텍스처 참조 등)가 낚니다. sgf는 이 문제를 **도서관 모델**로 풀었습니다.

- 모든 리소스는 도서관(`g_cResourceMgr`)이 소장한다. (소유권은 항상 도서관)
- 이용자는 책을 직접 들고 다니지 않고 **대출증 번호(키, `_u32`)**를 들고 다닌다.
- 책이 필요한 순간에만 번호로 찾아서(`Find`) 잠깐 쓴다.

```cpp
// Graphics/ResourceMgr.h
/*
 * [역할]
 * 모든 그래픽 리소스(텍스처/셰이더/메시/머티리얼)의 소유자.
 * 리소스는 생성 시 _u32 키를 발급받고, 사용처는 키로 참조한다.
 *
 * - 키 발급: jc::IdProviderReuse (D-12. 삭제된 키는 재사용)
 * - 경로 중복 방지: 같은 파일을 두 번 로드하면 기존 키를 그대로 반환
 * - 디폴트 리소스(FR-30): 부팅 시 흰색 텍스처/기본 셰이더/프리미티브 메시/
 *   기본 머티리얼을 미리 만들어, 리소스 없이도 바로 그릴 수 있게 한다
 */
```

## 2. 왜 포인터가 아니라 키인가

포인터를 직접 들고 다니면 두 가지 문제가 생깁니다.

1. **누가 주인인지 흐려진다**: 머티리얼 A와 B가 같은 Texture*를 들고 있을 때, 누가 delete해야 할까? 둘 다 안 하면 누수, 둘 다 하면 이중 해제.
2. **리로드가 어려워진다**: 텍스처를 교체(핫리로드)하려면 그 포인터를 들고 있는 모든 곳을 찾아다니며 교체해야 한다.

키 방식이면 소유권은 항상 ResourceMgr 하나이고, 키 뒤의 실제 객체를 바꿔치워도 사용처는 아무것도 모릅니다. 머티리얼도 같은 이유로 키를 씁니다.

```cpp
// Graphics/Material.h
/*
 * [머티리얼이란?]
 * "이 물체를 어떻게 칠할가"의 묶음. 셰이더 + 텍스처들 + 재질 상수(baseColor).
 *
 * [D-13. 리소스는 키로 참조]
 * Material은 Shader*/Texture* 포인터를 보관하지 않고 _u32 키만 보관한다.
 * 바인드 순간에만 ResourceMgr에서 찾아 쓴다. (수명/교체 문제 해결)
 *
 * [MaterialConstants — b2 상수버퍼]
 * baseColor 등 재질 값. 16바이트 정렬 규약을 지켜야 한다.
 */
```

## 3. 디폴트 리소스 — "빈손으로 와도 그려짐"의 비밀

02·03 문서의 예제들은 텍스처 파일 하나 없이도 색직 도형을 그렸습니다. 비밀은 부팅 시 `ResourceMgr::Initialize`가 미리 만들어둔 디폴트 세트입니다.

| 디폴트 리소스 | 용도 |
|---|---|
| **1×1 흰색 텍스처** | 단색 도형의 공용 텍스처. 덕분에 단색과 텍스처 도형이 같은 셰이더/배치로 합쳐진다 (02장 배칭) |
| **디폴트 2D/3D 셰이더** | DefaultShaders.h의 내장 HLSL 소스로 컴파일. 파일 없이 동작 |
| **2D 프리미티브 메시** (Rect/Circle/Triangle/Line, VertexPTC) | GameObject::SetMesh로 바로 사용 |
| **3D 프리미티브 메시** (Cube/Sphere/Capsule/Cylinder/Plane/Quad, VertexPNT) | 3D 물체 테스트/블로킹에 바로 사용 |
| **디폴트 머티리얼 2D/3D** | 디폴트 셰이더 + 흰 텍스처 + 흰색 baseColor 조합 |

그래서 "새 프로젝트 첫 화면에 도형 하나 띄우기"가 리소스 준비 코드 0줄로 가능합니다. 이건 학습 계단을 낮추려는 의도적 설계입니다(FR-30).

접근 함수들은 이름이 그대로 안내합니다.

```cpp
g_cResourceMgr.GetWhiteTextureKey();
g_cResourceMgr.GetPrimitiveMesh2DKey(PrimitiveMesh2DType::Rect);
g_cResourceMgr.GetPrimitiveMesh3DKey(PrimitiveMesh3DType::Cube);
g_cResourceMgr.GetDefaultMaterial2D();   // Material* 반환 (자주 쓰는 편의 함수)
g_cResourceMgr.GetDefaultMaterial3D();
```

## 4. 실제 흐름 — 텍스처 로드부터 그리기까지

예제 8의 흐름을 따라가면 전체 그림이 잡힙니다.

```cpp
// Docs/sgf/06_예제_코드_모음.md 예제 8 — 리소스 로드와 머티리얼 구성
void OnEnter() override
{
	// 1. 파일에서 텍스처 로드 → 키 발급 (같은 경로 재호출 시 기존 키 반환)
	_u32 texKey = g_cResourceMgr.LoadTextureFromFile("Assets/player.png");

	// 2. 머티리얼 생성 → 텍스처 \"키\"를 슬롯 0에 꽂는다 (포인터 아님!)
	Material* pMat = g_cResourceMgr.CreateMaterial2D();
	pMat->SetTextureKey(0, texKey);          // Material.cpp:61
	pMat->SetBaseColor(color::WHITE);        // 틴트 없음

	// 3. 오브젝트에 메시(공용 Rect) + 머티리얼 장착
	pSprite_ = dbg_new GameObject("player");
	pSprite_->SetMesh((Mesh*)g_cResourceMgr.Find(
		g_cResourceMgr.GetPrimitiveMesh2DKey(PrimitiveMesh2DType::Rect)));
	pSprite_->SetMaterial(pMat);
	pSprite_->GetTransform()->SetLocalScale(vec3(128, 128, 1));  // 단위 메시 → 픽셀 크기
	AddChild(pSprite_, 10);
}
```

읽을 때 집중할 지점 세 곳:

1. **로드의 결과는 포인터가 아니라 키**입니다. 이 키는 저장해두고 언제든 `Find`로 교환할 수 있습니다.
2. **같은 파일을 여러 씬에서 로드해도 안전**합니다. 경로 중복 검사가 기존 키를 돌려줍니다. "로드 매니저를 따로 만들어야 하나?" 고민할 필요가 없습니다.
3. **단위 메시 + scale**: 공용 Rect 메시는 크기 1짜리이므로 scale (128,128)로 128×128픽셀 스프라이트가 됩니다. 메시 복제 없이 크기만 다른 스프라이트 수백 개를 만들 수 있습니다.

그리기 시점에 일어나는 일(바인드 순간의 키 → 객체 변환):

```
Renderer2D Flush 시점
  ├─ material->GetShaderKey()   → ResourceMgr::Find → Shader*  → VS/PS 바인드
  ├─ material->GetTextureKey(0) → ResourceMgr::Find → Texture* → SRV 바인드
  └─ material->GetConstants()   → b2 상수버퍼 업로드 (baseColor)
```

포인터는 이 찰나에만 존재합니다. 보관되는 것은 언제나 키뿐입니다.

## 5. 수명 관리 — 누가 언제 치우나

- **등록**: `LoadTextureFromFile` 또는 `Add(resource)` → 키 발급. 이후 소유권은 ResourceMgr.
- **사용**: `Find(key)`로 그때그때 교환. 장기 보관은 키로.
- **해제**: `Remove(key)` → 객체 삭제 + 키 회수. 이후 같은 키가 재발급될 수 있으므로(IdProviderReuse) 해제한 키를 계속 들고 있으면 안 됩니다.
- **일괄 정리**: 종료 시 `Finalize`가 전부 정리. 씬 단위 임시 리소스는 OnExit에서 Remove하는 습관을 들이면 메모리가 씬 전환마다 깨끗하게 유지됩니다.

> **주의**: `Find`가 돌려준 포인터를 멤버로 장기 보관하지 마세요. 그 순간부터 키 방식의 이점(안전한 교체/해제)이 사라집니다. "보관은 키로, 사용은 그때그때 Find로"가 규약입니다.

## 6. MaterialConstants와 16바이트 규약

b2에 올라가는 재질 값(MaterialConstants)은 GPU 상수버퍼 규약상 **16바이트 배수**로 정렬되어야 합니다. 현재는 `float4 baseColor_` 하나라 자연스럽게 16바이트입니다. 필드를 추가할 때는 float4 단위로 채우거나 패딩을 고려하세요 — 이 규약을 어기면 C++ 구조체와 HLSL cbuffer의 메모리 배치가 어긋나 이상한 색이 나옵니다. (상세는 sgfr 12장 상수버퍼 편)

---

## 7. 요약 — 기억할 다섯 문장

1. 모든 GPU 리소스의 소유자는 `g_cResourceMgr` 하나다 — 사용처는 `_u32` 키(대출증)만 들고 다닌다.
2. 머티리얼도 셰이더/텍스처를 **키로만 참조**하고(D-13), 바인드 순간에만 Find로 실체를 찾는다 — 수명/교체 문제가 사라진다.
3. 같은 파일을 두 번 로드하면 기존 키가 반환된다 — 중복 로드 걱정 없이 필요한 곳에서 로드해도 된다.
4. 부팅 시 디폴트 세트(흰 텍스처/기본 셰이더/프리미티브 메시/기본 머티리얼)가 만들어져 **리소스 준비 0줄로 그리기 시작**할 수 있다.
5. 규약은 하나 — **보관은 키로, 사용은 그때그때 Find로**. Find 결과 포인터를 장기 보관하면 키 방식의 이점이 사라진다.
