# 02. 2D 렌더링 파이프라인 — 사각형 하나가 화면에 뜨기까지

> **이 문서 하나로**: sgf에서 2D를 그리는 세 가지 길(스태틱/다이나믹/메시)이 각각 언제·왜 쓰이는지, Fill(채움) 시스템이 어떻게 도형을 만들어내는지, 그리고 "같은 텍스처는 한 번에 그린다"는 배칭의 원리를 실제 코드와 함께 이해합니다.
>
> 관련 소스: `Graphics/Renderer2D.h/.cpp`, `Graphics/Fill.h`, `Graphics/BatchRenderer.h`, `Scene/Shape2D.h`

---

## 1. 큰 그림 — 왜 "그릴 때 바로 안 그리는가"

GPU에게 "그려라(DrawCall)"라고 말을 거는 비용은 생각보다 비쌉니다. 사각형 1,000개를 1,000번의 DrawCall로 그리면 CPU가 GPU에게 말을 거는 데 시간을 다 씁니다. 그래서 sgf의 2D 렌더러는 **배치(batch) 렌더러**입니다: 그리기 요청이 오면 CPU 배열에 정점을 차곡차곡 모아두었다가, 한 번에 GPU로 보냅니다.

이 원리는 2D/3D가 동일해서 공통 베이스 클래스로 올라가 있습니다. 베이스의 주석이 흐름을 요약합니다.

```cpp
// Graphics/BatchRenderer.h
/*
 * [왜 만드는가?]
 * Renderer2D와 Renderer3D는 "그릴 때 바로 그리지 않고 CPU 배열에 정점을
 * 모아두었다가 한 번에 GPU로 보내는" 배치(batch) 렌더링 원리가 동일하다.
 *
 * 공통 흐름:
 * - Initialize: 셰이더 컴파일(파생이 소스/선언 제공) + 상수 버퍼 생성
 * - Begin: 뷰프로젝션 저장 + 배치 초기화(파생 훅 OnBegin)
 * - End: 남은 배치를 모두 그림(파생 Flush) + 마무리
 * - Flush: 모아둔 배치를 즉시 GPU로 전송 (파생 구현)
 */
```

## 2. 2D를 그리는 세 가지 길

Renderer2D는 용도가 다른 세 가지 그리기 경로를 제공합니다. 이 문서에서 가장 중요한 표이니 먼저 감을 잡으세요.

| 경로 | 한 줄 요약 | 어울리는 것 | 비용 |
|---|---|---|---|
| **① 스태틱** (`DeclareStatic*` → `RenderStatic(id)`) | "버텍스를 한 번만 구워두고(bake) 매 프레임 재사용" | 움직이지 않는 UI 배경/패널/테두리 | 가장 저렴 (재계산 0) |
| **② 다이나믹** (`RenderDynamic(params)`) | "매 프레임 파라미터로 버텍스를 새로 만든다" | 게이지, 9-패치, 모양이 변하는 것 | 프레임마다 bake |
| **③ 메시** (`GameObject::SetMesh` + Transform) | "단위 도형 메시를 GPU 행렬 변환으로 배치" | 움직이는 캐릭터/오브젝트 | 버텍스 불변, 행렬만 갱신 |

헤더 주석도 같은 이야기를 합니다. 특히 "예약과 그리기의 분리"가 v3 설계의 핵심입니다.

```cpp
// Graphics/Renderer2D.h
/*
 * [예약/그리기 분리]
 * 게임 코드는 "그리기 예약"만 하고, 실제 GPU 드로우는 RenderScene 끝의
 * FlushStatic/FlushDynamic이 한 번에 처리한다. (트리 순회 순서 = 드로우 순서)
 *
 * 1. DeclareStatic(params): 선언 = 채움 1회 bake → 캐시 저장 → staticId (OnEnter에서 호출)
 * 2. RenderStatic(staticId): 예약 = 캐시 참조만 (매 프레임 OnRender에서 호출)
 * 3. RenderDynamic(params): 예약 = 파라미터 복사 (매 프레임, FlushDynamic이 bake)
 * 4. FlushStatic(): 스태틱 세그먼트 전부 드로우 (버킷 순서 Bottom→Default→Top)
 * 5. FlushDynamic(): 다이나믹 세그먼트 전부 드로우 (버킷 순서)
 */
```

왜 "예약"일까요? 게임 오브젝트 트리를 순회하며 `OnRender()`가 불릴 때 곧바로 GPU에 그리면, 텍스처가 바뀔 때마다 배치가 끊깁니다. 대신 **일단 전부 예약만 받아두고**, 씬 순회가 끝난 뒤 몰아서 그리면 같은 텍스처끼리 이어 붙여 DrawCall을 최소화할 수 있습니다. 식당에 비유하면 주문이 들어올 때마다 요리하는 게 아니라, 주문서를 모아 같은 메뉴끼리 한 번에 조리하는 방식입니다.

## 3. 길 ① 스태틱 — 한 번 굽고 평생 쓰기

움직이지 않는 것을 매 프레임 다시 계산하는 것은 낭비입니다. 스태틱 경로는 `OnEnter`(씬 진입 시 1회)에서 버텍스를 구워 캐시에 저장하고, 이후에는 id만 예약합니다.

```cpp
// Docs/sgf/06_예제_코드_모음.md 예제 2 — 실전 패턴
class MyScene : public Scene2D
{
	void OnEnter() override
	{
		GetCamera2D()->SetOrthographic2D(1280, 720);

		// OnEnter에서 1회 선언 → staticId 반환
		floorId_  = DeclareStaticRect(rect(0, 0, 1280, 100), color(40, 40, 60));
		boxId_    = DeclareStaticRect(rect(100, 200, 80, 80),  color(255, 200, 0));
		circleId_ = DeclareStaticCircle(vec2(600, 400), 50, color(100, 200, 255), 32);
	}

	void OnRender() override
	{
		// 매 프레임: id만 예약 → 렌더러가 캐시된 버텍스로 전송 (재계산 없음)
		RenderStatic(floorId_);
		RenderStatic(boxId_);
		RenderStatic(circleId_);
	}
};
```

### 3-1. 더 편하게 — Shape2D 노드

"선언하고 예약하는" 두 단계조차 반복이 귀찮다면, 그것을 자동으로 해주는 편의 노드가 Shape2D입니다.

```cpp
// Scene/Shape2D.h
/*
 * [사용법]
 * Shape2D* pShape = dbg_new Shape2D("패널");
 * pShape->SetRect(rect(10, 10, 100, 50), color::WHITE);
 * pScene->AddChild(pShape, 0);  // AddChild 직후 OnEnter가 1회 bake → 이후 자동 드로우
 *
 * [특징]
 * - 완전 정적: 절대좌표로 1회 bake — 움직이지 않는 UI(테두리/패널/HP바 배경)에 적합
 * - 움직이는 도형은 메시 자동 드로우 경로 (GameObject::SetMesh + Mesh 2D 팩토리) 사용
 */
```

**주의**: Shape2D는 절대좌표로 1회 구워지므로, 나중에 Transform을 움직여도 그림은 따라오지 않습니다. 움직여야 한다면 길 ③(메시)을 쓰세요. 이 구분(정적 = Shape2D, 이동 = SetMesh)이 sgf 2D의 제1 사용 수칙입니다.

## 4. 길 ② 다이나믹 — 매 프레임 모양이 변하는 것들

HP 게이지처럼 **모양 자체가 매 프레임 변하는** 것은 구워둘 수 없습니다. `RenderDynamic(params)`는 파라미터만 복사해두고, 프레임 끝의 `FlushDynamic()`이 그 시점의 파라미터로 버텍스를 만들어(bake) 그립니다.

그런데 "사각형, 원, 9-패치, 게이지, 말풍선..."처럼 만들어야 할 도형 종류는 계속 늘어납니다. 도형 종류마다 enum을 추가하면 엔진을 매번 수정해야 합니다. sgf는 이 문제를 **콜백 기반 Fill 시스템**으로 풀었습니다.

```cpp
// Graphics/Fill.h
/*
 * 2D 채움(Fill) — enum 금지, 콜백 기반 커스텀 채움 (엔진 무수정 확장)
 *
 * [왜 enum이 아닌가?]
 * enum + switch는 새 채움 추가 시 엔진 헤더 수정 + 재빌드가 필요하다.
 * 콜백(Fill::Custom(fn))은 사용자 코드 하나로 확장이 끝난다.
 *
 * [역할 분담]
 * - Fill: "무엇을" 그릴지 (콜백 + 기하 고유 파라미터)
 * - RenderParams: "어디에, 어떻게" (영역 + 매 호출 색/옵션 + 렌더 버킷)
 */
```

즉 Fill은 "이 영역을 어떻게 삼각형들로 채울 것인가"를 아는 **함수 객체**입니다. 엔진이 기본 제공하는 Fill(단색 Solid, 텍스처 Texture, 9-패치 NinePatch, 게이지 Gauge)도 전부 같은 콜백 규약으로 구현되어 있어, 사용자가 `Fill::Custom(fn)` 하나로 말풍선이든 그림자든 새 채움을 추가할 수 있습니다. 콜백이 만들어낸 결과(FillResult)는 쿼드가 아니어도 되며, `PushTriangles`가 임의의 삼각형 목록을 받아줍니다.

### 4-1. 렌더 버킷 — 트리 순서를 뛰어넘는 전역 레이어

"HP바는 무조건 최상단, 배경은 무조건 최하단"처럼 트리 구조와 무관하게 보장하고 싶은 순서가 있습니다. 그래서 모든 예약에는 버킷이 있습니다.

```cpp
// Graphics/Fill.h
// 렌더 버킷 — 트리 밴드와 무관한 씬 전역 순서 (플러시 순서: Bottom → Default → Top)
enum class RenderLayer
{
	Bottom,		// 씬 전역 최하단 (배경 원경 등)
	Default,	// 트리 밴드 (zOrder) — 기본값
	Top			// 씬 전역 최상단 (HP바/툴팁/이펙트/커서)
};
```

Flush는 Bottom 버킷 전부 → Default(트리 순서) → Top 버킷 전부 순서로 그립니다.

## 5. 길 ③ 메시 — 움직이는 것은 행렬로

움직이는 캐릭터를 스태틱으로 구울 수는 없고, 다이나믹으로 매 프레임 버텍스를 다시 만드는 것도 아깝습니다. 위치·회전·크기만 바뀐다면 **버텍스는 그대로 두고 월드 행렬만 바꾸는** 것이 정답입니다. 이것이 메시 경로입니다.

```cpp
// Docs/sgf/06_예제_코드_모음.md 예제 4 — 움직이는 도형
class Player : public GameObject
{
public:
	Player()
	{
		// 2D 프리미티브 메시 (디폴트 리소스 — 단위 크기, VertexPTC)
		SetMesh((Mesh*)g_cResourceMgr.Find(
			g_cResourceMgr.GetPrimitiveMesh2DKey(PrimitiveMesh2DType::Rect)));

		// 게임오브젝트가 기본 제공하는 머티리얼 — 채움색은 baseColor 틴트로
		GetMaterial()->SetBaseColor(color(255, 200, 0));
	}

	void OnUpdate(const jc::TimeSpan& _dt) override
	{
		// 움직임 = Transform 이동 (월드 행렬은 자동 계산 — 부모 변환 포함)
		GetTransform()->SetLocalPosition(GetTransform()->GetLocalPosition() + vec3(1, 0, 0));
	}
};
```

핵심 설계는 Mesh.h 주석에 있습니다.

```cpp
// Graphics/Mesh.h
/*
 *  [— 2D 프리미티브]
 *  Rect/Circle/Triangle/Line 같은 기본 도형 메시를 만들 수 있다. (모두 VertexPTC)
 *  단위 도형(중심 원점)이라 Transform의 scale/rotation으로 크기·회전을 제어한다.
 *  정점은 로컬 공간에서 불변 — 월드 변환은 Renderer2D가 GPU(b1 상수버퍼)로 수행한다.
 */
```

"단위 도형"이라는 말에 주목하세요. 크기 1짜리 사각형 메시 **하나**를 전 게임이 공유하고, 각자의 Transform(scale로 크기, rotation으로 회전, position으로 위치)으로 다르게 보이는 겁니다. 정점 데이터를 복제하지 않으니 메모리도 아끼고, 변환은 GPU가 b1(오브젝트 상수버퍼)의 월드 행렬로 처리하니 CPU도 한가합니다. 이 구조는 3D(03 문서)와 완전히 동일합니다 — 그래서 2D 메시 경로를 이해하면 3D는 공짜입니다.

## 6. 배칭 — 같은 텍스처는 한 번의 DrawCall로

세 경로 모두 마지막에는 같은 곳으로 모입니다: `PushTriangles`(임의 삼각형)와 `PushQuad`(사각형 특화)가 정점을 CPU 배열에 쌓습니다. 이때 규칙은 단 하나입니다.

- **직전 예약과 텍스처가 같으면** → 그냥 이어서 쌓는다 (배치 계속)
- **텍스처가 바뀌면** → 지금까지 쌓인 것을 먼저 그리고(Flush) 새 배치를 시작한다

단색 도형은 어떻게 되냐고요? 모든 단색 도형은 ResourceMgr의 **1×1 흰색 텍스처**를 쓰고 정점 색으로 칠합니다(uv는 흰 픽셀 고정). 즉 단색 사각형 100개 + 단색 원 50개는 전부 "흰색 텍스처" 배치 하나 = **DrawCall 1번**입니다. 스프라이트를 아틀라스(한 장에 모은 이미지)로 만들면 스프라이트들도 같은 원리로 합쳐집니다.

> **드로우콜을 줄이는 실전 수칙 3가지**
> 1. 움직이지 않는 것은 스태틱으로 (버텍스 재계산 자체를 없앤다)
> 2. 같은 텍스처(아틀라스)끼리 연속으로 그려지게 배치한다 (배치가 끊기지 않게)
> 3. 모양이 변하는 것만 다이나믹으로 (남용하지 않기)

## 7. 씬과의 연결 — 누가 Begin/Flush를 불러주나

사용자가 Begin/End를 직접 부를 일은 거의 없습니다. `Scene2D::RenderScene`이 매 프레임 자동으로 이렇게 감싸줍니다.

```
Scene2D::RenderScene()
  ├─ g_cRenderer2D.BeginScene(this)     ← 카메라의 뷰·투영 행렬 전달
  ├─ (루트부터 트리 순회하며 OnRender 호출 — 예약이 쌓인다)
  ├─ g_cRenderer2D.FlushStatic()        ← 스태틱 예약 전부 드로우
  ├─ g_cRenderer2D.FlushDynamic()       ← 다이나믹 예약 전부 드로우
  └─ g_cRenderer2D.EndScene()
```

즉시 모드(`Begin/End + DrawRect/DrawSprite`)도 남아 있는데, 이는 씬 밖(디버그 오버레이 등)을 위한 하위 호환 경로입니다. 새 코드는 씬 안에서 예약 API를 쓰는 것이 정석입니다.

## 8. 요약 — 기억할 다섯 문장

1. 2D 렌더러는 **배치 렌더러**다 — 그릴 때 바로 그리지 않고 모아서 한 번에 GPU로 보낸다.
2. 그리는 길은 셋이다: **움직이지 않으면 스태틱**(1회 bake), **모양이 변하면 다이나믹**(매 프레임 bake), **움직이면 메시**(버텍스 불변 + GPU 행렬 변환).
3. Fill은 "영역을 삼각형으로 채우는 방법"을 담은 **콜백**이라 enum/엔진 수정 없이 새 채움을 만들 수 있다.
4. 예약에는 버킷(Bottom/Default/Top)이 있어 트리 순서와 무관한 전역 최상단/최하단을 보장한다.
5. 배칭의 규칙은 하나 — **같은 텍스처는 이어 그린다**. 단색 도형은 전부 1×1 흰 텍스처를 공유하므로 자동으로 한 배치가 된다.
