# 04. 단계별 개조 계획 - sgf를 멀티스레드 렌더링으로

> 한 번에 다 바꾸면 반드시 망가집니다. 각 단계는 “돌아가는 상태”를 유지하면서 조금씩 전진합니다.
> 각 단계마다 “왜 이 순서인가”를 꿼 반드시 읽으세요.

---

## 단계 0. 준비 운동 (이미 v2에서 완료!)

- D3D 객체 분리: `SwapChain` / `DepthStencilSurface` / `RenderStates` / `GraphicDevice`(파사드)
- 렌더링 코드가 전부 `BeginFrame ~ EndFrame` 사이에만 존재하도록 정리됨 (`Application::Run` 참고)
- Scene이 “상태 변경(OnUpdate)”과 “그리기(OnRender)”를 이미 분리해서 제출

왜 중요한가: 멀티스레드화는 “경계가 깨끗한 코드”에서만 가능합니다. 경계가 없으면 자를 대고 자를 곳이 없습니다.

---

## 단계 1. 로딩 스레드 (난이도 하 / 효과 즉시)

**목표**: 텍스처/WAV 파일 읽기를 백그라운드로.

- `ID3D11Device`는 스레드 안전이므로 `Texture::CreateFromMemory`는 워커 스레드에서 호출 가능
- 규칙: 파일 읽기 + 리소스 생성까지만 워커에서. “다 되었다” 알림은 큐에 넣고 메인이 다음 프레임에 수거
- 이 단계만으로도 “로딩 중 프레임 덩퀌”이 사라짐

**검증법**: 큰 PNG 10장을 로딩하면서 FPS가 안 떨어지는지 확인.

---

## 단계 2. 프레임 데이터 더블 버퍼링 (난이도 중 / 구조의 핵심)

**목표**: “게임 상태”와 “그릴 목록”을 분리하고, 그릴 목록을 두 벌 만든다.

```cpp
// 프레임당 그릴 목록 (03 문서의 RenderCommand 벡터)
struct FrameRenderData
{
    jc::Vector<RenderCommand> commands;
    mat4 viewProjection;   // 그 프레임의 카메라 스냅샷
    color clearColor;
};

FrameRenderData frames_[2];   // 0번/1번 공책
_s32 writeIndex_ = 0;         // 로직이 쓰는 공책 번호 (렌더는 1 - writeIndex_)
```

핵심 규칙:
1. `Scene::OnRender`는 이제 `Renderer2D`가 아니라 `FrameRenderData`에 기록 (아직 싱글스레드로!)
2. 카메라 행렬도 “그리는 순간”이 아니라 “기록하는 순간”에 복사해 넣는다 (스냅샷)
3. 이 단계에서는 같은 스레드가 기록 후 바로 재생하므로 동작 변화 없음

왜 먼저 싱글스레드로 하나: **구조 변경과 스레드 도입을 분리해야 버그 원인을 하나씩 잡을 수 있습니다.**

**검증법**: 모든 튜토리얼이 이전과 완전히 똑같이 그려지는지 눈으로 비교.

---

## 단계 3. 렌더 스레드 분리 (난이도 상 / 이 연구의 본의)

**목표**: 공책 재생을 전담 스레드로 옮긴다.

```
메인 스레드 (프레임 N+1)        렌더 스레드 (프레임 N)
--------------------------------  --------------------------------
PumpMessage / Tick                (대기: 제출 신호)
Director.Update / OnUpdate        BeginFrame(frames_[read].clearColor)
frames_[write]에 커맨드 기록      커맨드 → Renderer2D 호출로 변환
Input.NextFrame / Sound.Update    EndFrame(vsync)  // Present
--------- 프레임 경계: 둘 다 도착하면 공책 교환(swap) + 신호 ---------
```

구현 순서:
1. 렌더 스레드 생성. `GraphicDevice`/`Renderer2D` 소유권을 렌더 스레드로 이전 (메인은 이제 Context 접근 금지!)
2. 프레임 경계 동기화: 이벤트 2개 (“제출됨” / “재생 완료”) + `WaitForSingleObject`
3. 창 크기 변경/종료 같은 예외 상황: 메인이 “멈춰!” 플래그를 원자적으로 세우고 렌더가 확인 후 응답

왜 Present를 렌더 스레드가 하나: VSync 대기 시간(최대 16ms!)을 메인 스레드가 안 기다려도 되기 때문입니다.
이게 멀티스레드 렌더링 이득의 상당 부분을 차지합니다.

**검증법**: 로직에 일부러 8ms 지연을 넣고(Sleep), 렌더에도 8ms 지연을 넣어도 60FPS가 유지되면 성공.

---

## 단계 4. (선택) 커맨드 기록 자체를 병렬화

씬이 아주 복잡해졌을 때만 필요합니다. 그릴 목록 작성을 영역별로 쪼개 여러 워커가 나눠 기록하고,
렌더 스레드가 순서대로 이어붙입니다. D3D11 지연 컨텍스트는 이 단계에서야 고려합니다.
2D 배치 엔진인 sgf에서는 당분간 불필요하다는 것이 결론입니다.
