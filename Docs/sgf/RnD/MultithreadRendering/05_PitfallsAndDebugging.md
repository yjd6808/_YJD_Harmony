# 05. 멀티스레드 렌더링의 함정과 디버깅 방법

> 이 문서는 멀티스레드 렌더링을 도입할 때 반드시 만나게 되는 문제들과,
> 그 문제를 찾아내는 방법을 정리한다. 순서대로 읽기를 권장한다.
> (용어가 낯설다면 먼저 `00_Glossary.md`를 읽자)

---

## 1. 가장 흔한 함정 5가지

### 함정 1: 데이터 경쟁 (Data Race)

- **무엇이 문제인가?**
  - 게임 스레드가 `m_PositionsX[i] = 100;` 이라고 쓰는 동안,
    렌더 스레드가 같은 값을 읽으면 "쓰다 만 값"을 읽을 수 있다.
  - 비유: 칬판에 글을 쓰는 중인데 누군가 옆에서 바로 읽으면
    절반만 쓰인 문장을 읽게 되는 것과 같다.
- **증상**: 물체가 가끔 한 프레임씩 이상한 위치에 그려진다. 재현이 안 된다.
- **근본 해결**: 같은 데이터를 동시에 만지지 않는다.
  `04_StepByStepMigrationPlan.md`의 **더블 버퍼링**(쓰는 버퍼와 읽는 버퍼를 분리)이 정답이다.

### 함정 2: D3D11 즉시 컨텍스트(Immediate Context)는 스레드 안전하지 않다

- `ID3D11DeviceContext`(즉시 컨텍스트)는 **단 하나의 스레드에서만** 써야 한다.
- 반면 `ID3D11Device`(리소스 생성 공장)는 여러 스레드에서 동시 사용 가능하다.
- **증상**: 두 스레드에서 Context를 만지면 운이 좋으면 깨지고,
  운이 나쁘면 "이따금 화면이 깨지는" 찾기 힘든 버그가 된다.
- **규칙**: 우리 엔진에서는 `GraphicDevice::Context()`를 렌더 스레드 전용으로 약속한다.
  다른 스레드는 지연 컨텍스트(Deferred Context)나 명령 큐를 쓴다. (`03` 문서 참고)

### 함정 3: 교착 상태 (Deadlock)

- **무엇이 문제인가?**
  - 게임 스레드는 "렌더 끝나면 진행해야지"하며 기다리고,
    렌더 스레드는 "게임이 데이터 줘야 시작하지"하며 기다리면 둘 다 영원히 멈춘다.
  - 비유: 좁은 길에서 마주친 두 사람이 서로 "네가 먼저 비켜"라며 버티는 상황.
- **예방 규칙**:
  1. 락(Lock)은 항상 같은 순서로 잡는다.
  2. 락을 잡은 채로 다른 락을 기다리지 않는다.
  3. "기다림"에는 반드시 타임아웃을 두고, 타임아웃 시 로그를 남긴다.

### 함정 4: 프레임 지연으로 인한 입력 반응 느려짐 (Latency)

- 게임 스레드가 N번째 프레임을 만드는 동안 렌더 스레드는 N-1번째 프레임을 그린다.
- 즉, 화면에 보이는 건 항상 **한 프레임 전의 세상**이다. (약 16ms 지연 추가)
- 대부분의 게임에선 문제가 안 되지만, 격투/리듬 게임은 민감할 수 있다.
- **대책**: 입력 처리만은 파이프라인 맨 앞에서 최신 상태로 처리하고,
  지연이 체감되면 프레임 큐 길이를 1로 제한한다.

### 함정 5: 리소스 수명 문제 (Lifetime)

- 게임 스레드가 씬을 교체하며 텍스처를 delete했는데,
  렌더 스레드는 직전 프레임의 명령 목록에서 그 텍스처를 아직 쓰고 있다면? → 크래시.
- **대책**:
  1. 파괴는 즉시 하지 않고 "파괴 대기 목록"에 넣는다.
  2. 렌더 스레드가 해당 프레임을 다 그린 뒤(펜스 통과 후)에만 실제로 해제한다.
  3. 우리 엔진이라면 Director의 씬 교체 시점(프레임 경계)이 자연스러운 해제 타이밍이다.

## 2. 디버깅 도구와 방법

### 2-1. D3D11 디버그 레이어 (이미 엔진에 내장됨)

- `GraphicDevice::CreateDeviceAndSwapChain`은 디버그 빌드에서
  `D3D11_CREATE_DEVICE_DEBUG` 플래그로 디바이스를 만든다.
- 잘못된 API 사용(쓰기/읽기 동시 바인딩, 해제된 리소스 사용 등)을
  Visual Studio 출력 창에 빨간 글씨로 알려준다. **출력 창을 항상 켜두자.**
- 멀티스레드 관련 오류는 대부분 여기서 가장 먼저 잡힌다.

### 2-2. Visual Studio 병렬 스택 (Parallel Stacks)

- 디버깅 중 `디버그 > 창 > 병렬 스택` 메뉴.
- 모든 스레드가 지금 어느 함수에 멈춰 있는지 한눈에 보여준다.
- 교착 상태 디버깅의 필수 도구: 두 스레드가 서로의 Wait에 멈춰 있으면 교착이다.

### 2-3. 이름 붙이기 (스레드/리소스)

- 스레드에는 `SetThreadDescription(GetCurrentThread(), L"RenderThread")`로 이름을 붙인다.
- D3D 객체에는 `SetPrivateData(WKPDID_D3DDebugObjectName, ...)`으로 이름을 붙이면
  디버그 레이어 메시지에 "어떤 텍스처인지"가 이름으로 나온다.

### 2-4. 싱글스레드 스위치 만들기 (가장 중요!)

- 엔진에 `#define SGF_SINGLE_THREAD_RENDER 1` 같은 스위치를 만들어
  언제든 싱글스레드 모드로 되돌릴 수 있게 한다.
- 버그가 생겼을 때 스위치를 끄고 재현되면 → 게임 로직 버그,
  스위치를 끄면 사라지면 → 스레딩 버그로 범위를 좋혀나갈 수 있다.

### 2-5. 경쟁 상태 재현 요령

- 데이터 경쟁은 확률적이라 재현이 어렵다. 일부러 재현율을 높이려면:
  1. `Sleep(0)`/`YieldProcessor()`를 의심 구간에 임시로 넣어 타이밍을 흔들어본다.
  2. 디버그/릴리즈 빌드 모두에서 테스트한다. (최적화가 타이밍을 바꾼다)
  3. 의심되는 공유 변수에 쓰기 직전/직후 로그를 남겨 순서를 확인한다.

## 3. 체크리스트 (도입 전 반드시 확인)

- [ ] 즉시 컨텍스트를 만지는 스레드가 단 하나인가?
- [ ] 게임 스레드와 렌더 스레드가 같은 배열/객체를 동시에 만지는 곳이 없는가? (더블 버퍼링)
- [ ] 락 순서가 문서화되어 있고 모든 코드가 그 순서를 따르는가?
- [ ] 리소스 해제가 "렌더 스레드가 다 쓴 뒤"로 미뤄지는가?
- [ ] 싱글스레드 복귀 스위치가 있는가?
- [ ] 디버그 레이어 경고가 0개인가?

이 체크리스트를 모두 통과하면 `04_StepByStepMigrationPlan.md`의 단계별 이행을 시작해도 좋다.
