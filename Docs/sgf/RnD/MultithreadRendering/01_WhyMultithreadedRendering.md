# 01. 왜 멀티스레드 렌더링을 하는가?

> 결론부터: “그림 그리는 주문서 작성(CPU 일)”과 “게임 로직(CPU 일)”을 서로 다른 일꾼에게 나눠주면
> 한 프레임에 쓸 수 있는 CPU 시간이 사실상 두 배가 됩니다.

---

## 1. 음식점 비유로 이해하기

지금 우리 엔진(sgf v2)은 **1인 음식점**입니다.
사장님(메인 스레드) 혼자서 주문도 받고(입력), 재료 손질도 하고(게임 로직), 요리도 하고(드로우 콜 제출),
서빙까지(Present) 합니다. 손님이 적을 땐 괜찮지만 손님이 많아지면(그릴 게 많아지면) 주방이 밀립니다.

멀티스레드 렌더링 = **주방장을 따로 고용하는 것**입니다.
- 홀 담당(메인 스레드): 손님 응대(입력/윈도우 메시지) + 주문서 작성(게임 로직 → 렌더 큐에 기록)
- 주방장(렌더 스레드): 주문서를 보고 실제 요리(D3D 호출 → GPU 제출 → Present)

홀 담당이 프레임 N+1의 주문서를 쓰는 동안, 주방장은 프레임 N을 요리합니다. → 컸베이어(파이프라이닝)!

---

## 2. 숫자로 보는 이득

한 프레임에 16.6ms(60FPS)가 주어진다고 합시다.

### 싱글스레드 (지금)
```
[게임 로직 9ms][렌더링 9ms] = 18ms → 60FPS 실패! (55FPS로 떨어짐)
```

### 멀티스레드 (목표)
```
메인:  [로직 N+1: 9ms]        [로직 N+2: 9ms]
렌더:  [렌더 N:   9ms]        [렌더 N+1: 9ms]
→ 매 16.6ms마다 한 프레임씩 완성. 60FPS 유지!
```
각각 9ms씩 걸리던 두 일이 겹쳐서 진행되므로, 한 프레임의 체감 예산이 약 2배가 됩니다.

---

## 3. 공짜가 아닙니다 - 치륳 세 가지

1. **레이턴시 +1프레임**: 화면에 보이는 건 항상 “한 프레임 전” 결과입니다. (대부분의 상용 엔진이 이 비용을 지불하고 살아갑니다)
2. **복잡도**: 경쟁 상태/교착 같은 새로운 종류의 버그가 생깁니다. 재현이 어려워 디버깅이 힘듭니다.
3. **메모리**: 더블 버퍼링 때문에 “그릴 목록” 메모리가 2배로 듭니다.

**그래서 결론**: 지금 규모(튜토리얼 + sgcl 2D 게임)에서는 싱글스레드로 충분합니다.
하지만 엔진 구조를 “나중에 멀티스레드로 바꿀 수 **있는** 모양”으로 미리 정리해두는 게 이 연구의 목적입니다.
(v2에서 GraphicDevice를 SwapChain/DepthStencilSurface/RenderStates로 쪼갬 것도 그 준비입니다.)

---

## 4. 왜 “렌더링”을 분리하는가? (다른 후보들과 비교)

| 후보 | 설명 | 판정 |
|---|---|---|
| 로딩 스레드 | 텍스처/사운드 파일을 백그라운드에서 읽기 | 가장 쉽고 효과 확실. 1순위 추천 |
| 사운드 스레드 | XAudio2는 이미 내부 믹서 스레드를 사용 중 | **이미 되어 있음** (공짜 멀티스레드!) |
| 렌더 스레드 | 이 문서의 주제 | 효과 큼. 단, 구조 개편 필요 |
| 물리/AI 잡 시스템 | 일감 단위 병렬화 | 대형 엔진용. 우리에겐 과한 투자 |

참고로 우리 엔진은 이미 두 개의 “공짜 멀티스레드”를 쓰고 있습니다.
1. **XAudio2 믹서 스레드**: `SoundEngine::Play2d`는 제출만 하고, 실제 음양 합성은 XAudio2가 별도 스레드에서 합니다.
2. **GPU 자체**: GPU는 원래 CPU와 병렬로 도는 거대한 병렬 프로세서입니다. Draw 호출이 끝나도 GPU는 아직 그리는 중입니다.

즉, 이 연구의 질문은 정확히는 “CPU 쪽 주문서 작성 작업을 어떻게 병렬화할거냐”입니다.
