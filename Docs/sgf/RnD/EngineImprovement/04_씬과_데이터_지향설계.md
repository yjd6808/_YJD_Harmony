# 04. 씬과 데이터 지향 설계 — 파생 클래스 씬에서 컴포넌트/데이터 중심 씬으로

> 이 문서는 sgf의 씬 계층을 **"사용자가 코드로 직접 쓰는 파생 씬"**에서
> **"컴포넌트 기반 게임 오브젝트 + 직렬화 가능한 씬 데이터"**로 바꾸는 설계입니다.
> Unity의 GameObject/Component, Cocos2d-x의 Node/Sprite 계층과
> 비교하면서, 왜 데이터 지향(캐시·멀티스레드)이 필요한지까지 다룹니다.

## 1. 현재 상태 — "한 덩어리 씬"의 장점과 한계

### 1-1. 현재 씬의 모양 (Scene.h + Director.h)

```cpp
class MyScene : public sgf::Scene        // 사용자가 직접 작성하는 단 하나의 클래스
{
    Texture heroTexture_;                // OnEnter()에서 로드
    struct Box { vec2 pos; vec2 size; color c; } boxes_[16];
public:
    void OnUpdate(const jc::TimeSpan& _dt) override { /* 전부 직접 */ }
    void OnRender() override { g_cRenderer2D.DrawSprite(&heroTexture_, ...); }
};
// Application 파생: ApplicationDidFinishLaunching()에서 RunScene(new MyScene())
// Director: 윈도우별 SceneSlot이 씬 수명을 관리
```

- **장점**: 의존성이 없고, 코드가 단순하고, 움직임 자유도가 100%입니다.
- **한계 (01 문서의 문제 1~4와 연결)**:
  - 씬 상태가 "코드"이므로 저장/로드 불가 → 레벨 데이터, 세이브, 에디터 전부 불가
  - 오브젝트가 많아지면 같은 코드가 복붙으로 수천 줄 → 유지보수 불가
  - 로직과 그리기가 한 메서드 `OnRender()`에 섞임 → 렌더 큐(03 문서)와 연결이 어려움
  - 업데이트 코드가 오브젝트 간 순서에 따라 달라짐 → 멀티스레드 병렬화 불가

### 1-2. 왜 Cocos2d-x의 씬 그래프를 v2에서 버렸나

25 문서에 기록된 대로, v2는 Node/Sprite 씬 그래프를 **제거**했습니다.
"addChild해야 그려지는 구조"가 불필요한 복잡도를 만든다고 판단했기 때문입니다.
이 문서의 개선은 **그 결정을 뒤집는 것이 아니라**, "그리기 그래프"가 아니라
"**데이터(씬) 그래프**"를 다시 도입한다는 점이 다릅니다:

- v2가 버린 것: "그리기 단위 = Node" 라는 결합 (Node!=그리기), 편의용 Sprite
- 다시 가져올 것: "씬 데이터 = GameObject 트리" (그리기 컴포넌트는 그중 하나)

## 2. 개선 방향 1 — 게임 오브젝트 + 컴포넌트

### 2-1. 기본 골격

```
GameObject (오브젝트 한 개. id + 이름 + Transform 1개 + 컴포넌트 목록)
  ├── Transform          : 위치/회전/크기 + 부모 참조 (씬 트리를 이룸)
  ├── SpriteRenderer     : Texture 키 + 색 + 레이어 → 렌더 커맨드 생성
  ├── MeshRenderer       : Mesh 키 + Material 키 → 렌더 커맨드 생성
  ├── CameraComponent    : 프로젝션 설정 + ViewProjection 계산
  └── (사용자 컴포넌트)   : OnUpdate를 상속받는 작은 클래스
```

```cpp
class ComponentBase { public: virtual void OnUpdate(const TimeSpan& dt) {} };

struct Transform {
    GameObject* pParent_;
    vec3 position_, scale_;
    _f32 rotationZ_;          // 2D 우선, 3D는 quaternion으로 확장
};

class SpriteRenderer : public ComponentBase {
    _u64 textureKey_;         // ResourceMgr 키 (포인터 금지 — v3 방식 유지)
    color tint_;
    int layer_;
};
```

- **씬 = GameObject의 트리**. `Scene` 클래스는 트리 루트와 "씬 시스템"만 갖습니다.
- Component는 **"무엇을 하는가"로 분리**: 그리기(렌더 컴포넌트), 로직(사용자 컴포넌트),
  카메라(뷰 컴포넌트). 그래서 씬 파일로 저장하기 쉬운 "데이터"가 됩니다.

### 2-2. 트리와 월드 변환

- 10번 튜토리얼(WorldTransform)에서 배운 `world = parentWorld * local` 을
  **씬 트리대로** 적용합니다: 부모가 움직이면 자식도 같이 움직입니다.
- 매 프레임 전체를 다시 계산하지 않고 **dirty 플래그**로 필요한 것만 재계산합니다.

```
시스템: TransformSystem
  foreach (GameObject in 트리, 부모 우선 순회)
    if child.dirty: child.world = parent.world * child.local
    제출: 렌더가 쓰는 월드 행렬은 여기서 확정 (스냅샷)
```

### 2-3. 기존 씬과의 호환 전략

기존 `Scene` 파생 씬은 "레거시 화면"으로 계속 동작하게 두고(하위 호환 보존),
새 API로는 `GameObjectScene`(씬 파일을 로드하는 씬)을 제공합니다.
Director는 둘 다 같은 슬롯에서 돌릴 수 있어야 합니다 (SceneSlot 구조 유지).

## 3. 개선 방향 2 — 왜 ECS/데이터 지향이 필요한가

### 3-1. 컴포넌트 트리로도 부족한 이유 (하드웨어 관점)

객체 지향 컴포넌트는 관리하기 좋지만, **"같은 종류의 데이터가 메모리에 흩어진다"**
문제가 있습니다. 아래 두 배열을 비교해 봅시다.

```
[AoS] GameObject[]  : [pos][spd][sprite][hp][pos][spd][sprite][hp] ...
      1000마리 중 "위치만 갱신"하려면 메모리를 건너뛰며 읽어야 함 (캐시 라인 낭비)

[SoA] position[1000] float[3000]  ← 같은 종류가 연속
      velocity[1000]
      health  [1000]              ← "위치+속도 갱신"만 순차 접근 → 캐시 효율 최대
```

CPU는 64바이트 캐시 라인 단위로 메모리를 읽습니다. SoA(Structure of Arrays)로 두면
"한 시스템이 필요한 데이터"가 한 줄에 모여 있어, 캐시 미스가 크게 줄어듭니다.

### 3-2. ECS의 세 조각

| 조각 | 역할 | 예 |
|---|---|---|
| Entity | 그냥 id (숫자) | `0001` |
| Component | 순수 데이터 (메서드 없음) | Position, Velocity, Sprite |
| System | 데이터를 처리하는 로직 | MoveSystem: `foreach(e) e.pos += e.vel * dt` |

- sgf에서 **당장 풀 ECS를 만들 필요는 없습니다.** 컴포넌트 기반(2장) + SoA 배열로
  데이터만 정리하는 "**데이터 지향 컴포넌트**"에서 시작하면 충분합니다.
- 언제 풀 ECS로 가는가: 같은 시스템이 수만 개 엔티티를 돌 때, 워커 스레드로
  시스템별 병렬화를 하고 싶을 때.

### 3-3. 멀티스레드 관점

- 시스템 = "입력 → 읽음", "position → 씀" 처럼 **접근 데이터가 분리**되어 있으면
  시스템끼리 스레드를 나눠도 경쟁이 없습니다.
- 렌더 커맨드 생성(03 문서 S1)은 "GameObject → DrawCommand" 변환 시스템이고,
  이 변환은 엔티티마다 독립이라 **병렬 기록**이 쉽습니다.
- RnD 02 문서의 "Update 끝나면 Render 시작"의 순차 약속은, 커맨드가 스냅샷이므로
  그대로 지켜집니다.

## 4. 개선 방향 3 — 직렬화와 리로드 (씬을 파일로 저장/로드)

### 4-1. 왜 직렬화가 전부의 시작인가

씬을 데이터로 다룰 수 있으면 한 번에 세 가지가 얻어집니다:

1. **레벨 작업** — 디자이너가 텍스트/JSON을 편집 (후에 에디터 UI로 확장)
2. **세이브/로드** — 게임 진행 상태를 파일로 저장
3. **서버-클라이언트 동기화** — 씬 데이터가 곧 네트워크 페이로드

### 4-2. 포맷 예 (JSON 계열)

```json
{
  "objects": [
    {
      "id": 1, "name": "Hero", "parent": -1,
      "transform": { "x": 0, "y": 0, "rot": 0, "scale": 1 },
      "components": [
        { "type": "SpriteRenderer",
          "texturePath": "Resources/hero.png",
          "tint": [1, 1, 1, 1], "layer": 3 }
      ]
    },
    { "id": 2, "name": "CameraMain", "parent": -1,
      "components": [ { "type": "Camera", "orthographic": true, "width": 1280, "height": 720 } ] }
  ]
}
```

- 리소스는 **경로 문자열**로 참조: 로드 시 `ResourceMgr.LoadTextureFromFile("Resources/hero.png")`가
  중복 로딩을 자동 방지하므로, 서로 다른 오브젝트가 같은 텍스처를 공유해도 안전합니다.
- 저장은 현 상태(현재 위치 등)를 어떻게 반영할지 정해야 합니다:
  - **씬 시작 상태**만 저장: 시작 위치 기준 (레벨 파일)
  - **현재 상태**까지 저장: 세이브 파일 (런타임 값 마킹)

### 4-3. 리로드 (Hot Reload)

- 에디터/개발자 도구로 씬 파일을 바꿨을 때 **게임을 끄지 않고** 다시 로드:
  기존 씬 파괴 → 트리 재구성 → 리소스는 이미 로드되어 있어 즉시 표시.
- 지금 구조에서는 "씬을 살아있는 상태로 교체"가 `Director::ReplaceScene`의 프레임 경계
  교체로 이미 지원되므로, "파일 → 새 씬 생성 → ReplaceScene"만 해주면 됩니다.

## 5. 개선 방향 4 — 프리팹과 에셋 파이프라인 개념

### 5-1. 프리팹 (Prefab)

- "적 군집", "총알"처럼 **자주 만드는 오브젝트 묶음**을 템플릿 파일로 저장:
  `prefabs/enemy.json` (트리 + 컴포넌트).
- 씬 파일은 프리팹을 **참조**만 합니다: `{ "prefab": "prefabs/enemy.json", "pos": {...} }`.
- 이러면 같은 적을 100곳에 배치해도 중복 데이터가 없고, 프리팹 한 번 수정이 전부 반영됩니다.
- Unity의 Prefab, Cocos2d-x의 CCB(씬 에디터 파일)와 같은 위치의 개념입니다.

### 5-2. 에셋 파이프라인 (가벼운 버전)

| 단계 | 내용 | sgf 대응 |
|---|---|---|
| 원본 | png/svg/obj 등 원본 파일 | `Texture::LoadFromFile`(WIC), `LoadFromSvgFile`(nanosvg) |
| 가공 | 아틀라스 합치기, mip 생성, 포맷 변환 | 없는 상태 → S3(03문서)에서 아틀라스부터 |
| 카탈로그 | 경로 → 리소스 키 인덱스 | `pathIndex_` (이미 구현) |
| 스트리밍 | 필요할 때만 로드/해제 | `RemoveAll` → 참조 기반 언로드로 확장 |

- 핵심: 파이프라인 전체를 만들지 말고, **"경로 → 키" 카탈로그만 공고화**하면
  커스텀 임포터를 얹기 쉬워집니다.

## 6. 개선 방향 5 — 이벤트/발행-구독 시스템

### 6-1. 현재

- `jc::Event<T...>` 가 이미 있고, `Window::onActivated` (Application.h 의
  ACTIVATION_LISTENER_ID 구독), `InputManager::onKeyPressed/onMouseMoved` 등에서
  쓰입니다. 발행-구독 골격은 이미 존재합니다.

### 6-2. 확장: 엔진 전역 이벤트 버스

```cpp
g_cEventBus.Publish("SceneLoaded", sceneData);
g_cEventBus.Subscribe("SceneLoaded", [](const Variant& v) { ... });
```

| 이벤트 | 발행자 | 구독자 예 |
|---|---|---|
| `SceneLoaded` | Director::Update (교체 직후) | UI 메뉴 재구성, 사운드 BGM 시작 |
| `ResourceLoaded` | ResourceMgr::LoadTextureFromFile | 로딩 바 갱신 |
| `GamePaused/Resumed` | Application | 사운드 일시정지(기존 Background 처리 일원화) |
| `WindowClosed` | Application::DestroyClosedSubWindows | 세이브 트리거 |

- 주의: 이벤트는 **"언제 일어났는가"의 통지**로 쓰고, 씬 상태 전달은
  참조보다 복사(스냅샷)하는 것이 멀티스레드 대비에도 안전합니다.

## 7. Unity / Cocos2d-x 비교표 (관계 유지하며)

| 개념 | sgf (목표) | Unity | Cocos2d-x |
|---|---|---|---|
| 씬 단위 | `Scene` + GameObject 트리 | Scene | Scene (Node 트리) |
| 오브젝트 | GameObject | GameObject | Node |
| 부모-자식 | Transform 부모 참조 | Transform | Node::addChild |
| 그리기 | SpriteRenderer/MeshRenderer 컴포넌트 | SpriteRenderer/MeshRenderer | Sprite 노드 (그리기=노드) |
| 카메라 | CameraComponent | Camera | Camera 노드 |
| 로직 | 사용자 Component (OnUpdate) | MonoBehaviour | 클래스/함수 직접 |
| 저장 | 씬 JSON 파일 | .unity | - (개발자 자유) |
| 재사용 템플릿 | Prefab (JSON 참조) | Prefab | CCB 파일 |
| 이벤트 | jc::Event 버스 | C# events/Delegate | EventDispatcher |
| 업데이트 순서 | TransformSystem 등 시스템 | Update/MonoBehaviour 순서 | Node 순회 |

한 줄 정리: **Unity는 "컴포넌트+직렬화"의 완성형, Cocos2d-x는 "그리기 중심 노드"**.
sgf의 목표는 Unity 쪽에 가깝되, "그리기는 렌더 큐로 분리"(03문서)라는 독자 강점을 유지합니다.

## 8. 단계별 마이그레이션 계획

| 단계 | 이름 | 내용 | 기존 코드 영향 | 검증 |
|---|---|---|---|---|
| M1 | 데이터 구조 도입 | `GameObject`/`Transform`/`ComponentBase` 클래스만 추가 (렌더링 연결 없음) | 없음 | 유닛 테스트로 트리 world 계산 |
| M2 | 렌더 컴포넌트 | `SpriteRenderer`, `MeshRenderer`가 렌더 커맨드 생성 (03의 S1 커맨드 사용) | 새 API 추가 | 기존 씬과 새 씬 동시 표시 |
| M3 | 씬 파일 | JSON 파서(씬 로더) + 저장 함수 | 없음 | 저장→로드→화면 동일 |
| M4 | 프리팹 | prefab.json 참조 지원 | 없음 | 적 100마리 배치 한 줄 |
| M5 | 시스템화 | TransformSystem, RenderSubmitSystem 분리 (SoA 배열로 전환) | 씬 내부만 | 캐시 효율 벤치 (측정 도구로 확인) |
| M6 | 이벤트 버스 | EventBus 도입, 기존 jc::Event 정리 | 최소 | SceneLoaded로 UI 갱신 |
| M7 | 레거시 씬 이전 | 튜토리얼/게임 씬을 GameObject 씬으로 포팅 | 병행 유지 | 전 씬 통과 테스트 |

### 마이그레이션 원칙

1. **M1~M4는 "추가"만 한다** — 기존 `Scene` 파생 씬은 계속 동작. 안전.
2. **M5부터가 진짜 데이터 지향의 시작** — 성능이 목적이므로, 측정 도구
   (`GraphicContext::GetApiCallCount`, 프레임 시간)와 함께 진행.
3. **씬 전환은 기존 Director의 프레임 경계 교체(ReplaceScene)를 그대로 이용** — 
   다중 스레드 시대에도 유효한 패턴입니다 (RnD 02 문서의 암묵적 약속 2).

## 9. 결론

1. 씬을 "파생 클래스"에서 "데이터 트리"로 바꾸는 것이 직렬화·프리팹·에디터의 시작이다.
2. 컴포넌트 기반으로 시작하고, 규모가 커지면 SoA/시스템(데이터 지향)으로 진화한다.
3. 그리기는 컴포넌트가 렌더 커맨드를 만드는 것으로 03 문서의 렌더 큐와 연결된다.
4. 기존 Director/ResourceMgr의 좋은 설계(프레임 경계 교체, 키 참조)는 그대로 재사용한다.
5. 절대 "다 바꾸고" 하지 않는다 — 추가 → 병행 → 전환의 3단계를 고집한다.

이로써 4부작(01 진단 → 02 설계도 → 03 렌더 파이프 → 04 씬 데이터)이 완성됩니다.
이후 후속 작업으로 "에셋 파이프라인"(05), "멀티스레드 병렬화"(06) 문서가 이어질 수 있습니다.
