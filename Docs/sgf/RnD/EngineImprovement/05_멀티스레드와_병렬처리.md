## 1. 지금 sgf는 "1인 음식점"이다

`Application::Run()`은 여전히 **단일 스레드**로 돌아갑니다. 한 프레임은 정확히 이 순서입니다.

```
(1) window_.PumpMessage()     윈도우 메시지 펌프 (키/마우스 이벤트)
(2) timer_.Tick()             jc::TimeSpan 경과시간 측정
(3) g_cDirector.Update(dt)    현재 씬들의 OnUpdate()   ← 게임 로직
(4) OnUpdate(dt)              앱 훅
(5) device_.BeginFrame()      백버퍼/깊이버퍼 지우기    ← D3D 진입
(6) g_cDirector.Render(...)   Scene::OnRender → Renderer2D/3D 배치 → Flush
(7) OnRender()                앱 훅 (오버레이)
(8) device_.EndFrame(vsync)   Present (화면 표시)     ← D3D 종료
(9) input_.NextFrame()        입력 플래그 프레임 갱신
(10) g_cSound.Update()        끝난 사운드 슬롯 회수
```

그림으로 보면 이렇게 됩니다 (음식점 비유는 `MultithreadRendering/00_Glossary`를 참고):

```
 메인 스레드 한 명이 전부 수행
 ┌────────────────────────────────────────────────────────────┐
 │ [입력 받기]→[로직 계산]→[주문서 작성(Renderer2D 배치)]→[요리(D3D)]→[서빙(Present)] │
 └────────────────────────────────────────────────────────────┘
   게임 로직 8ms + 렌더 기록 7ms + Present 대기 5ms = 20ms → 60FPS 실패 (50FPS)
```

`Renderer2D`의 배치 버퍼(`jc::Vector<VertexPTC> vertices_`, 최대 2048쿼드)도,
`GraphicContext`의 스테이트 캐시도, `ResourceMgr`의 `resources_` HashMap도
**한 스레드만 접근한다는 전제 위에** 설계되어 있습니다. `GraphicDevice::Context()`가
즉시 컨텍스트 하나를 돌려주고, 모든 그리기가 그 창구 하나를 통과합니다.

### 한계는 어디인가?

- 16.6ms 예산을 로직과 그리기가 **더해져서** 소비한다. → 나누면 겹칠 수 있다.
- `EndFrame(vsync)`의 Present 대기 시간(최대 16.6ms)은 CPU가 `WaitForSingleObject`로 **놀면서** 기다린다.
- 대용량 텍스처 로딩(`Texture::LoadFromFile`의 WIC 디코딩)은 프레임을 통째로 멈춘다.

## 2. 왜 나눠야 하는가 — CPU 프레임 시간 분석

게임이 무거워지면 한 프레임 CPU 시간은 대략 이런 구성이 됩니다:

| 구성 요소 | 비용 | 병렬화 가능 |
|---|---|---|
| 게임 로직(OnUpdate, 물리, AI) | 높 | ⭕ (작업 단위로 분할) |
| 렌더 명령 기록(DrawXXX → 배치 → Flush) | 높 | ⭕ (렌더 스레드 분리) |
| D3D 호출/드라이버 검증 | 중~높 | ⭕ (렌더 스레드로 이전) |
| GPU 실행 자체 | 별도 (GPU가 병렬 실행) | — (CPU와 파이프라인) |
| VSync 대기 | 낮지만 손실 | ⭕ (렌더 스레드가 감당) |

60FPS(16.6ms) 유지에서 멀티스레드의 목표는 **더하기를 겹치기로 바꾸는 것**입니다.

```
[싱글]  로직 9ms → 렌더 9ms = 18ms  (낙제)
[멀티]  메인: [로직 9ms][로직 9ms]
        렌더: [렌더 9ms][렌더 9ms]  → 16ms 안에 프레임 1개 완성
```

Unity/Unreal급 게임이 무거워질 때 이 이득은 필수이며, 라이브러리 경쟁도 있습니다:
**GPU가 한 번에 처리하는 일이 늘어나는 것보다, CPU가 "주문서를 얼마나 빨리 써 내려가는지"가 병목이 되기 때문입니다.** (드로우 콜 = CPU 비용, 23번 문서의 실측 근거)

## 3. D3D11이 주는 병렬성 도구 — 현실과 한계

### 3-1. 두 종류의 스레드 안전성 (가장 중요한 한 줄)

| 객체 | 역할 | 스레드 안전 |
|---|---|---|
| `ID3D11Device` | 리소스 생성 "공장" (텍스처, 버퍼, 셰이더) | ⭕ 여러 스레드 동시 호출 가능 |
| `ID3D11DeviceContext`(즉시) | 명령 기록 "작업반" | ❌ 한 시점 한 스레드만 |

즉 "**만들기는 어디서나, 그리기 명령은 한 줄 서서**"입니다. sgf에 대입하면:
- `Texture::CreateFromMemory`, `Mesh` 생성, 버퍼 생성 → 워커 스레드 OK
- `Renderer2D::Flush` → `GraphicContext::Draw` → `Present` → **한 스레드 전담**

### 3-2. 지연 컨텍스트 (Deferred Context)와 커맨드 리스트

D3D11은 컨텍스트를 여러 개 만들 수 있는 방법을 제공합니다. 스레드마다 `.CreateDeferredContext()`로
"녹음기"를 만들고 명령을 기록하다가 `FinishCommandList()`로 `ID3D11CommandList`를 완성하고,
즉시 컨텍스트를 가진 렌더 스레드가 `ExecuteCommandList()`로 재생합니다.

```cpp
// 워커 스레드 (녹음만)
ID3D11DeviceContext* pDeferred = nullptr;
pDevice->CreateDeferredContext(0, &pDeferred);
pDeferred->PSSetShaderResources(0, 1, &srv);
pDeferred->DrawIndexed(...);

ID3D11CommandList* pCmdList = nullptr;
pDeferred->FinishCommandList(FALSE, &pCmdList);   // 녹음 완료

// 교환
pImmediate->ExecuteCommandList(pCmdList, FALSE);  // 렌더 스레드가 재생
pCmdList->Release();
```

**한계 1 — 백지 상태**: 지연 컨텍스트는 상태가 비어 있는 상태에서 시작합니다. 렌더타깃, 뷰포트,
모든 바인딩을 매번 다시 설정해야 합니다. 여기서 `GraphicContext` 스테이트 캐시가
"직전 값을 아는" 구조라 양식 그대로 쓰면 **잘못된 생략**(캐시는 한 컨텍스트를 전제로 기억하므로)
버그 위험이 있습니다. → 지연 컨텍스트와 스테이트 캐시는 **따로 관리**해야 합니다.

**한계 2 — 드라이버 복불복**(03 문서): `CheckFeatureSupport(D3D11_FEATURE_THREADING, ...)`로
`DriverConcurrentCreates`/`DriverCommandLists`가 진짜 병렬 처리를 하는지 확인할 수 있습니다.
드라이버가 에뮬레이션으로 처리하면 이득이 없습니다. (이것이 요즘 엔진이 D3D12/Vulkan으로 가는 이유)

**한계 3 — 데이터 소유**: 지연 컨텍스트는 그리기 명령 기록을 병렬화하는 도구이지
**게임 로직 병렬화** 도구가 아닙니다. 명령을 기록할 재료(씬 데이터)는 어차피 읽기 전용 스냅샷이어야 합니다.

## 4. 상용 엔진의 답 비교

| | Unity (Job System/Burst) | Unreal (스레드 계층) | 우리의 목표 |
|---|---|---|---|
| 일단위 | 컴포넌트 기반 Job(`IJobFor` 등) + Burst 컴파일러 | `FRunnable`/`AsyncTask` + `ENamedThreads::GameThread` 등 | 경량 `Job` 큐 |
| 데이터 | Entity Component System, `NativeArray` 캐시 친화 | `FGraphEvent`, 복사 스냅샷 | 프레임 단위 **소유권 이양** |
| 잠금 | 잠금은 커밋 단위 | 그래프 기반 의존성 잠금 | 잠금 최소화, 더블 버퍼링 |
| 렌더 스레드 | Render Thread + Graphics Jobs | Render Thread → RHI Thread → GPU | 1개의 Render Thread부터 |

Unreal의 "Game Thread → Render Thread → RHI Thread" 3단 넘김을 참고하면,
우리도 첫 단계는 **"Logic Thread ↔ Render Thread" 2단**으로 시작하는 것이 부담이 적습니다.
Unity의 Job System 정신(작은 잡 단위, 연속 메모리)은 나중에 물리/게임 로직 결과량이 커진 뒤 도입합니다
(현재 sgf 규모에서는 과잉 투자, 08 로드맵과 동일 판단).

## 5. sgf를 위한 설계: 잡(Job) 큐 + 렌더 커맨드 큐 + 프레임 소유권

멀티스레드를 할 때 "데이터를 어떻게 넘기는가"가 전부입니다. 제안하는 골격:

### 5-1. 잡큐 셈 (작업 시스템 - 1단계)

```cpp
// "작은 일" 한 조각.  함수 포인터 + 인자 + 우선순위
struct IJob
{
    enum class Priority { High, Normal, Low };
    virtual void Execute() = 0;    // 일꾼이 실행
    Priority priority_;
};

class JobSystem      // C++11 부터는 jc에 스레드 유틸이 없다면 Win32 래퍼로
{
    jc::Vector<std::function<void()>> pending_;  // 실제로는 제한 큐
    HANDLE workerSemaphore_;                      // 남은 일 알림
    // Push / Claim / Complete 인터페이스
};
```

`std`를 쓰지 않는 jc 관례를 지키려면 `jc::Delegate` + Win32 API 래퍼로 동일 기능을 만듭니다.
핵심 규칙: **잡은 다른 잡의 결과를 쿼리하지 않고, 오직 "준비된 일"만 수행한다.**

### 5-2. 렌더 커맨드 큐 — D3D 객체 없는 "주문서"

03 문서의 결론 그대로, D3D 객체가 담기지 않는 **값 타입 주문서 벡터**를 매 프레임 씬이 채웁니다.

```cpp
// Graphics/RenderCommand.h (신규) — 현재 Renderer2D::DrawXXX 인자를 그대로 구조체화
struct RenderCommand
{
    enum class Type { eSprite, eRect, eLine, eCircle, eFlush };
    Type        type_;
    _u64        textureKey_;      // Texture* 대신 ResourceMgr 키 (수명 안전)
    vec2        center_;  vec2 size_;
    color       tint_;    _f32 radian_;
    vec2        uvMin_;   vec2 uvMax_;
    int         segments_;        // circle용
    mat4        viewProjection_;  // 카메라 스냅샷 (Begin 시각)
};

// 프레임 단위 완성물
struct FrameRenderData
{
    jc::Vector<RenderCommand> commands_;   // 로직이 채우는 주문서
    color clearColor_;
};

FrameRenderData frames_[2];   // 더블 버퍼 (쓰는 것과 읽는 것)
```

왜 `Texture*` 대신 키인가? — `ResourceMgr`의 `Find<T>` 패턴(21번 문서)과 같은 이유입니다.
포인터는 수명을 보장하지 않지만, 키는 "매니저가 지우기 전까지 유효"라는 보증을 가집니다.
렌더 스레드는 그때그때 `ResourceMgr::Find(key)`로 해석하면 됩니다.

### 5-3. 프레임 데이터의 소유권

핵심 원칙 두 가지:

1. **읽는 쪽은 절대 쓰지 않는다.** 렌더 스레드는 `frames_[read]`를 읽기 전용으로만.
2. **"나중 이전"은 큐로.** 리소스 파괴, 씬 교체 등 렌더가 처리를 끝내야 하는 일은
   "파괴 대기 목록(FreeList)"에 넣고 렌더 스레드가 펜스 통과 후 처리합니다.
   (Director의 `pNextScene_` 교체 시점이 프레임 경계라는 기존 설계가 그대로 활용됩니다.)

```
메인 스레드 (프레임 N+1)       렌더 스레드 (프레임 N)
┌────────────────────────┐   ┌──────────────────────────┐
│ PumpMessage / Tick     │   │ (대기)                   │
│ Update / OnUpdate      │   │ [read]을 렌더러로 변환    │
│ Write frames_[w]       │   │ → g_cRenderer2D/3D Flush │
│ WaitForSingleObject    │───┼─► swap + 신호(CondVar)   │
└────────────────────────┘   └──────────────────────────┘
```

1차 목표는 **즉시 컨텍스트는 렌더 스레드가 전담**, 메인은 주문서 작성만 하는 2스레드 구성입니다.
지연 컨텍스트(3-2)는 그다음 한 단계 뒤의 선택지로 남겨둡니다.

## 6. 위험 요소와 함정 (들어가기 전에 읽기)

### 6-1. 데이터 경쟁 (Data Race)
두 스레드가 같은 배열을 동시에 만지면 값이 찢어집니다. 씬의 위치 변수(`m_PositionsX`)를
렌더가 읽는 동안 로직이 쓰면 "한 프레임 어긋난 위치"가 생깁니다. → 근본 대책은 더블 버퍼링.
**재현 불가 버그의 90%가 여기**입니다.

### 6-2. 스테이트 캐시와의 상호작용 (23번 문서와 연결)
`GraphicContext`의 캐시는 "한 즉시 컨텍스트를 한 스레드가 순서대로 만진다"를 전제로 합니다.
```
⚠ 지연 컨텍스트 + 스테이트 캐시 조합은 캐시가 "직전 값을 안다" 가정이 무너집니다.
   → 지연 컨텍스트를 도입할 때는 캐시를 컨텍스트 단위로 분할하거나
     "캐시 없음(전부 바인딩)" 모드로만 사용하는 두 가지 길만 있습니다.
```
이 문서 시리즈의 도입 단계에서는 1~3단계(주문서 큐 → 렌더 스레드 분리)가
지연 컨텍스트보다 우선입니다 — 스테이트 캐시를 그대로 살리고, 데이터 객체 자체를
나누는 쪽이 드라이버 복불복 없이 안전합니다.

### 6-3. CPU/GPU 밸런싱
렌더 스레드를 만들어도 "CPU와 GPU가 모두 바빠야" 이득입니다. 둘 중 하나가 놀면 파이프라인이 그냥 컨베이어 대기입니다.
목표: 메인 CPU 밀 비율, 렌더 CPU 밀, GPU busy 시간을 프로파일러로 보며 조절.
GPU가 병목이면 멀티스레드는 해결책이 아니고, 배칭(Phase A)이 먼저입니다.

### 6-4. 드라이버 버그
GPU 리소스 수명(해제 시점)을 **드라이버의 지연 삭제**(COM 참조 카운트 기반)와 혼동하지 마세요.
CPU에서 delete 하더라도 GPU가 명령을 실행하고 있을 수 있습니다(21장 6-1). 안전한 해제는
"렌더 스레드가 그 프레임의 펜스(Query 없음) 후"입니다.

### 6-5. 마이그레이션 체크리스트 (MultithreadRendering/05의 체크리스트 재인용)
- 즉시 컨텍스트를 만지는 스레드 단 하나?
- 데이터 경쟁 0, 락 순서 문서화, 타임아웃 있는 기다림?
- 리소스 파괴는 "다 쓴 뒤"로?
- #define SGF_SINGLE_THREAD_RENDER 1 복귀 스위치?
- 디버그 레이어의 경고 0개?

## 7. 도입 단계 (기존 코드에서 밟아 가기)

| 단계 | 내용 | 비고 | 검증 |
|---|---|---|---|
| 0 | 구조 정리(v2.1) — 이미 완료 | Device/Context/SwapChain 분리 | 튜토리얼 전체 동일 출력 |
| 1 | **로딩 스레드**: 텍스처/WAV 읽기만 워커로 | `Texture::LoadFromFile`는 디바이스(스레드 안전)만 쓰므로 OK | 10장 PNG 로딩 중 FPS 유지 |
| 2 | **프레임 데이터 더블 버퍼링**(단계 5-2 구조) | 아직 싱글 스레드로 구조만 | 모든 씬 동일 화면 |
| 3 | **렌더 스레드 분리** | `GraphicDevice`/`Renderer2D` 소유권 이전, 프레임 경계 동기 | 인위적 8ms 지연에서도 60FPS |
| 4 | (선택) 지연 컨텍스트로 커맨드 기록 병렬화 | 스테이트 캐시와의 궁합 해소 후에만 | 대규모 씬 대응 |
