## 1. 지금의 현실: 콘솔 목차가 최대 도구다

sgf를 실행해 만날 수 있는 "도구"는 `sgfr`의 콘솔 목차 런처(`Main.cpp` + `TutorialRegistry.cpp`) 전부입니다.
31개 튜토리얼이 하나의 앱에 등록되어 있고, 숫자를 입력하면 해당 튜토리얼이 창을 열고 실행됩니다.

```
┌─────────────────────────────────────────────────────────┐
│ [sgfr] 실행                                                │
│   01. 선형대수       15. PNG 텍스처       23. 스테이트 캐시   │
│   02. 윈도우 루프    16. SVG 텍스처       24. 셰이딩 모델      │
│   ...                ...                ...              │
│   31. 파이프라인 전체 여정   (q) 종료                       │
└─────────────────────────────────────────────────────────┘
```

이것은 "실행 확인" 도구입니다. 하지만 엔진이 커지면 필요한 것은 전혀 다른 종류가 됩니다:
- **게임 개발자**: 씬을 편집하고 싶다 (배치, 위치, 색)
- **아티스트**: 텍스처/타이틀이 어느 화면에서 어떻게 보이는지
- **프로그래머**: 지금 GPU가 얼마나 바쁜지, 어느 드로우 콜이 비싼지
- **QA**: 시나리오를 제대로 재생하고 싶다

## 2. 왜 도구가 필수인가 — 반복 주기의 비용

도구 없이 개발하는 것은, 요리사가 맛보기를 하다가 "재료를 다시 주방에 넣고 처음부터" 하는 것과 같습니다.
씬 하나를 수정하는 데 드는 시간은:

```
[수정] → [빌드] → [실행] → [창 조작으로 수동 확인] → [종료] → 반복
```

이 주기 한 바퀴가 1~2분이라도, 하루 50회 반복하면 1시간이 낭비됩니다. **콘솔 디버그 UI 하나만으로도
주기를 10분의 1로 줄일 수 있고**, 이게 도구 체계의 출발점입니다.

## 3. 단계별 로드맵 (0 → 3)

```
0단계         1단계                      2단계                    3단계
콘솔 디버그  →  외부 데스크톱 앱  →  임베디드 디버그 UI  →  본격 에디터
로그/프로파일   (독자 프로파일러/        (in-game overlay,        (씬 뷰포트 + 인스펙터
               DebugDraw 원격)          원격 명령 실행)          + 하이어라키)
```

| 단계 | 이름 | 내용 | 필요한 것 |
|---|---|---|---|
| 0 | 콘솔 디버그 | `jc::Console` + 프레임 평균/1프레임 시간 | `GraphicContext::GetApiCallCount` 정리, 타이머 |
| 1 | 외부 도구 앱 | WPF 클라이언트 ↔ 엔진(파이프/TCP) | 프로토콜 정의 (06와 연결) |
| 2 | 임베디드 UI | `Renderer2D`로 그리는 오버레이 폼, `InputManager` 이벤트 | `DrawRect/DrawText` 디버그 폰트 |
| 3 | 에디터 | 씬 뷰포트+인스펙터+하이어라키 | 렌더 커맨드(03), 컴포넌트/직렬화(04) |

이 순서를 지키는 이유: 0→1은 외부 UI가 내부 구조를 건드리지 않고 "프레임 통계 스냅샷"만
보내는 것이라 안전합니다. 2단계는 엔진 내부 UI를 만들어야 하지만, 3(본격 에디터)로 가기 전에
**데이터 직렬화와 렌더 큐가 준비**돼야 그 위가 가능합니다.

## 4. 0단계: 콘솔 디버그 출력과 통계 확장

`GraphicContext`는 이미 통계 카운터를 보고합니다 (23번 문서):
- `GetApiCallCount()` / `GetSkippedCallCount()` / `ResetStats()`

여기에 **프레임 평균**(`FrameTimer` + 경과 카운터)을 합치면:

```
[23. 스테이트 캐시]  api: 218, skip: 1570 | frame 16.2ms | draw 4,300 | 60FPS
```

### 0단계 구체 작업 리스트
1. `FrameTimer` 기반으로 1초 평균 FPS + 최저 프레임과 평균 프레임 표시
2. `GraphicContext` 카운터를 "프레임별 링버퍼"로 보강 (직전 120 프레임 기록, 9장의 GPU 쿼리와 결합)
3. `ResourceMgr::PrintStatus()`를 설정에서 확인하거나 F10 키에 매핑 (누수 조사 재개)

## 5. 1단계: 외부 데스크톱 앱 프로토콜 — WPF 클라이언트 + 엔진 상태 전송

sgf는 C++ 콘솔/윈도우 중심이라 UI 툴킷이 없지만, **이 저장소에는 이미 훌륭한 C# WPF 툴킷**이 있습니다:
`SteinsGate-Tools.UI` (게임 UI 편집/저작 도구, WPF+MVVM, AvalonDock), `SteinsGate-Tools.Research` (리서치 쉘),
`SteinsGate-Tools.Common` . 이들과 같은 패턴으로 **엔진과 떨어진 외부 앱** 을 만드는 것이
단계 1의 핵심입니다.

### 5-1. 프로토콜 설계

```
엔진 (C++, 실행 중)                      도구 (C#, WPF)
┌──────────────────────┐   socket/pipe   ┌──────────────────────┐
│ ProfilerServer       │◄────────────────►│ ProfilerClient       │
│  - 요청: GET_STATS   │──── counts,      │ - 실시간 프레임 표시   │
│  - 요청: GET_RESLIST  │      리소스 목록  │ - 리소스 목록/참조    │
│  - 요청: SET_DBG_DRAW │      디버그      │ - 디버그 드로우 체크박스 │
│  - 이벤트: GAME_LOG   │────────────────►│   로그 콘솔 시각화      │
└──────────────────────┘                   └──────────────────────┘
```

최소 프로토콜 아이디어:
```
[get] stats           →  {fps, frameMs, apiCall, skipCall, drawCalls, gpuMs}
[get] resources       →  [{key, type, name, byteEstimate}...]
[set] debug_enabled=1 →  엔진 내부 디버그 드로우 켜기 (Wireframe, 카메라 프레스텀)
[get] log?since=N     →  jc::Console에 쌓인 로그 플러시
```

### 5-2. 구현 포인트
- 전송: TCP 소켓(로컬) 또는 **명명 파이프**(`\\.\pipe\sgf_dbg`). 파이프가 구현이 간단합니다.
- 직렬화: JSON이면 C# 쪽이 자연스러운데, jc는 JSON 직렬화가 없다 → 06 문서의 이진 포맷을
  **통계 구조체에 재사용**하거나, 부담 없이 단순한 `key=value\n` 줄 프로토콜로 시작.

### 5-3. 이 단계의 독자 "도구"들
- **독자 프로파일러**: 프레임 타임라인 바 그래프 (로직/렌더/업로드/대기 4섹션) — 05의 CPU 분석과 그대로 연결
- **디버그 드로우 원격 제어**: 도형 제어를 엔진이 아니라 클라이언트 앱에서 켜고 끔
- **리소스 탐색기**: 현재 로드된 리소스와 메모리, 참조 카운트 — 06의 AddRef/Release 없이도 목록은 가능

## 6. 2단계: 임베디드 디버그 UI

외부 앱이 짜증나는 순간(게임 하면서 확인 못함)을 위해 엔진 안에 작은 UI를 넣습니다.

```
엔진 내부 오버레이 (Renderer2D로 그림, z 끝판왕)
┌──────────────────────────────────────┐
│ 23. StateCache [api:123 skip:1570]   │ ← 프레임 통계
│  FPS: 60  frame_ms: 16.2  tex: 12    │
│  [ ]와이어프레임  [x] AABB  [ ]네비   │ ← 토글식 체크박스
│  로그: ...                           │ ← jc::Console 스크롤
└──────────────────────────────────────┘
```

- 입력: `InputManager`의 키 이벤트로 토글 (예: **F2**)
- 그리기: `OnRender()` 맨 마지막에 `DrawRect`/`DrawText` (텍스트는 폰트 비트맵 필요 — 30번 응용)
- 표시 데이터: 0단계의 통계 링버퍼를 그래프로 표시 (최근 1000프레임)

이 단계에서 GPU 타임을 보여주는 방법은 8장(프로파일링)으로 넘깁니다.

## 7. 3단계: 본격 에디터 — 씬 뷰포트 + 인스펙터 + 하이어라키

에디터의 골격은 "모든 것을 조작하는 창"입니다.

```
┌────────────────────┬──────────────────────┐
│  씬 뷰포트           │  하이어라키           │
│  (실제 렌더링 화면)    │   Scene             │
│                    │    └ Camera        │
│                    │    └ Player        │
│                    │    └ MapLayer       │
├────────────────────┴──────────────────────┤
│  인스펙터                                  │
│   이름 : mySprite                        │
│   위치 : (x= 12.3, y= -4.2)  [드래그]    │
│   텍스처 : btn_start (key 47)            │
│   색조 : [■] r 1.0                      │
└───────────────────────────────────────────┘
```

필수 전제 조건 (이 시리즈 앞 문서들과의 연결):
- **03문서의 렌더 커맨드/배칭**: 인스펙터가 바꾼 값이 그리기에 그대로 반영되도록 (뷰포트 = 렌더 커맨드 큐 재생)
- **04문서의 컴포넌트 구조**: 하이어라키 트리가 실제 씬 데이터(컴포넌트 목록)를 보여주도록
- **04문서의 씬 직렬화 포맷**: 에디터 저장 파일이 곧 게임 로드 파일 (에셋 파이프라인 06과 연결)

에디터는 이 시리즈의 **최종 스테이지**입니다. 그 전까지 1단계(외부 도구)와 2단계(오버레이UI)의
기능이 에디터의 부속 기능으로 모두 들어가기 때문입니다.

## 8. Hot Reload — 개발 중인데 재시작 없이

Unity/Unreal의 에디터에서 자주 쓰는 "원본 파일을 바꾸면 바로 반영"입니다.
Vulkan/D3D12 환경에서는 파이프라인 상태 재생성이 필요해져 복잡하지만, D3D11에서는 방법이 간단합니다:

### 8-1. 셰이더 핫 리로드 (D3D11)
```
1. 파일 변경 감지 (FileSystem watcher — ReadDirectoryChangesW)
2. 오프라인 컴파일 (06의 임포트 단계) → 바이트코드
3. 새 ID3D11VertexShader/PixelShader 생성
4. Material에 새 셰이더 연결 (Material::SetVertexShaderKey / SetPixelShaderKey 재설정)
5. 같은 슬롯에 새 포인터가 들어가면 GraphicContext 캐시 비교가 자연히 무효
```

포인트: `GraphicContext`의 캐시는 **포인터로 비교** (23장 §6-2) 하므로,
셰이더 객체를 교체하면 자동으로 재바인딩됩니다. 캐시를 명시적으로
`InvalidateCache()` 를 호출하지 않아도 되는 점이 이 설계의 장점입니다.

### 8-2. 텍스처 핫 리로드
```
1. 파일 변경 → 재디코드 (WIC)
2. 새 ID3D11Texture2D + SRV 생성
3. 기존 리소스키는 보존 (ResourceMgr::Replace(키, 새리소스))
4. 렌더 스레드가 그 프레임의 사용이 끝나면 구 SRV 정리 (06의 삭제 큐)
```

주의: 이미 `Material`의 `textureKeys_[slot]`나 SceneRenderer의 lastKey 캐시가 있다면
**키를 유지**하는 것이 가장 안전한 경로입니다 (키 해석이 새 객체를 가리키게 됨).

### 8-3. 재시작이 필요한 것
D3D11에서는 swap chain 크기/형식 변경은 핸들은 자연 반영됩니다. **렌더러 구조 변경**
(정점 포맷, 프레임 계약)만 빌드를 요구합니다. 이것이 "구조와 플로우는 재빌드, 리소스는 핫" 이라는
한계를 문서로 남겨야 합니다.

## 9. 프로파일링 — 창을 뚫고 GPU/CPU를 본다

### 9-1. GPU 시간 측정 (D3D11 Query)

```
ID3D11Query (D3D11_QUERY_TIMESTAMP)
  Begin/End로 감싸고, End의 유효한 결과를 다음 프레임에 읽기
  CPU는 즉시 값을 못 받는다. (GPU와 CPU 파이프라인 격차) → 프레임 단위로 지연 판독
```

정확도 예: `D3D11_QUERY_TIMESTAMP_DISJOINT`로 단위 보정.

| 측정 대상 | 방법 | 손실 |
|---|---|---|
| 메인 스레드 구간 비용 | CPU 타이머 (QueryPerformanceCounter) | 없음 |
| 렌더 스레드 구간 비용 | CPU 타이머 (렌더 루프별) | 없음 |
| GPU 드로우 시간 | `ID3D11Query` | 1프레임 지연 |
| 드로우 카운터 | `GraphicContext::GetApiCallCount` 확장 | 없음 |

### 9-2. draw call 카운터 확장 (23번 확장)

`GetApiCallCount`는 "상태 바인딩 + 명령" 전체 호출 수입니다. 정확한 **그리기 명령만**의 개수도
따로 재보는 것: `GraphicContext::Draw/DrawIndexed` 안에서 별도의 원자 카운터를 올리고
(멀티스레드 대비 `InterlockedIncrement`, 05에서 사용), 프레임 끝에 로그로 기록:
```
drawCalls=980, stateCalls=4210, skipped=18700  (총 23,890)
```

### 9-3. 2D 엔진 특화
- 배치 메트릭: 배치 그룹 수, 배치 평균 정점 수 — 스프라이트 분산 상태 확인
- `ResourceMgr` 히트율: `Find` 성공 수 / 실패 수 (프레임 단위) — 낭비되는 로드 정책 조정

## 10. 마무리 — 도구 체계는 "타임어택"이 아니다

도구는 게임 기능이 아니어서 자꾸 미뤄집니다. 하지만 "조립 규모가 늘어날수록 도구가 없다면
**디버깅이 5배 느려지는**" 구조적 손실이 반드시 옵니다. 이 문서의 0→1→2→3단계를
각각 로드맵(08 문서) 타임라인에 배치하고, **0단계는 로드맵의 Phase 0에 끼워 넣는 것**을 권장합니다:
콘솔 통계(0단계)는 별도 예산이 없어도 프레임 루프에 카운터 두 개만 추가하면 됩니다.
