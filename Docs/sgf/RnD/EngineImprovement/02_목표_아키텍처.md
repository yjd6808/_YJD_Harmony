# 02. 목표 아키텍처 — Unity/Unreal이 보여주는 구조를 sgf 관점에서 그리기

> 01 문서에서 현재 구조를 진단했다면, 이 문서는 **"어디로 갈지"의 설계도**입니다.
> Unity/Unreal이 실제로 쓰는 구성 요소를 sgf 관점으로 정리하고, 이미 있는 것과
> 없는 것을 구분한 뒤, 진행 순서(로드맵)까지 제안합니다.
> 초보자도 따라올 수 있도록 비유와 용어 설명표를 넣었습니다.

## 1. 집 짓기 비유 — sgf는 "골조는 끝났고, 배선 공사 중"인 집

상용 엔진을 신축 아파트에, sgf의 개선 과정을 리모델링이라 비유합시다.

| 공사 단계 | 비유 내용 | sgf의 해당 부분 | 상태 |
|---|---|---|---|
| 1. 기초 공사 | 땅과 콘크리트. 무너지면 전부 무너짐 | 수학/메모리/컨테이너(`jc::Math`, `jc::Vector`) | **완성** |
| 2. 뼈대 공사 | 기둥/보/계단. 층이 서게 됨 | `Application`/`Window`/`GraphicDevice`/`Scene`/`Director` | **완성** |
| 3. 설비 배선 | 전기·수도를 방마다 배관 | 렌더 파이프 / 에셋 파이프 / 이벤트 파이프 | **이제 시작할 공사** |
| 4. 인테리어 | 가구·조명으로 실용화 | 에디터 | **아직 안 함** |

핵심 판단: **기초와 뼈대는 끝났다**. 남은 것은 (3) 배선 — "씬 데이터 → 렌더 → 화면"을
잇는 파이프라인을 제대로 놓는 일이고, 에디터는 (4)의 마지막에 얹는 옥상입니다.

## 2. 목표의 전체 그림 — 여섯 영역

상용 엔진의 부서 분리는 대략 아래와 같습니다. sgf 관점에서 바라보면:

```
┌──────────────────────────────────────────────────────────────┐
│  [Editor]      씬 뷰 / 인스펙터 / 프레임 디버거 / 에셋 브라우저 │
├──────────────────────────────────────────────────────────────┤
│  [Runtime]     GameObject+Component 트리 / 직렬화 / 프리팹   │
│  [Rendering]   렌더 큐·정렬·배칭 / PSO / 렌더 그래프 / 포스트 │
│  [Asset]       임포트 파이프 / 아틀라스 / 스트리밍            │
│  [Platform]    윈도우 · 입력 · 게임 루프 · 오디오             │
├──────────────────────────────────────────────────────────────┤
│  [Core]        수학 · 메모리 · 컨테이너 · 스레드 · 이벤트     │
└──────────────────────────────────────────────────────────────┘
   위쪽 레이어는 아래쪽에만 의존한다. Core는 아무것에도 의존하지 않는다.
```

### 2-1. 영역별 현재 vs 목표

| 영역 | sgf의 현재 대응 | 평가 | 부족한 것 |
|---|---|---|---|
| Core | `jc::` 라이브러리(Math/Vector/Time/Event) | 매우 견고 | ThreadPool, 프로파일링 카운터 |
| Platform | `Application::Run`, `Window`, `InputManager`, `SoundEngine` | 잘 갖춰짐 | 백그라운드 로딩, 전역 이벤트 버스 |
| Runtime | `Scene`(파생 클래스)+`Director`+`Camera` | **백지 수준** | GameObject/Component 트리, 직렬화, 프리팹 |
| Rendering | `Renderer2D/3D` 배치, `SceneRenderer`, `Material/Mesh/Shader`, `GraphicContext` 캐시 | 반쪽 | 렌더 정렬/배칭, PSO 관리, 렌더 그래프, 포스트/AA, 렌더 스레드 |
| Asset | `ResourceMgr`(키 발급+중복 방지) | 기반만 | 임포트 파이프라인, 메타데이터, 스트리밍 |
| Editor | 없음 | 없음 | 씬 뷰/인스펙터/디버그 뷰 |

핵심 관찰: Platform/Core는 "상용 수준의 밑그림"이고, 빈 곳은 Runtime·Rendering·Asset·Editor.
그래서 전략도 "가장 근간인 씬/렌더 파이프를 먼저, 에디터는 나중에"가 됩니다.

## 3. 지금 (단일 스레드·평면 구조) vs 목표 (계층·더블 버퍼)

### 3-1. 지금의 데이터 흐름 (Application.cpp / Director.cpp 기준)

```
입력(msg) → Director.Update(dt) → Scene::OnUpdate(dt)   // 로직
화면      → device_.BeginFrame(window, clearColor)
         → g_cRenderer3D.Begin(vp) / g_cRenderer2D.Begin(vp)
         → Scene::OnRender()  // 즉시 DrawSprite/DrawCube 호출
         → Renderer3D.End()   // 즉시 Flush → DrawIndexed
         → Renderer2D.End()   // 즉시 Flush
         → device_.EndFrame(window, vsync)               // Present
```

특징: 모든 일이 **메인 스레드 하나**에서, "그리려고 호출한 그 순간"에 일어납니다.

### 3-2. 목표의 구조 (렌더 스레드 분리까지)

```
메인 스레드 (씬 로직)                     렌더 스레드 (그리기)
 ── Update(dt) → 씬 세계 갱신               ── frames_[read]를 읽는다
 ── FrameRenderData[write]에                ├─ 컬링 → 정렬 → 배칭
     "그릴 목록"(메시+머티리얼+월드) 기록     ├─ 렌더 타깃 체인 (포스트 포함)
 ── 프레임 경계에서 공책 교환 + 신호          └─ Present (VSync 대기)
```

- **커맨드 기록 방식**이면 "무엇을, 어떻게, 어디에 그릴지"가 순수 데이터로 남으므로,
  렌더 쪽에서 자유롭게 정렬·배칭·멀티코어 워커를 쓸 수 있습니다.
- 카메라 행렬도 "기록하는 순간"에 스냅샷으로 남기므로, 로직이 그 사이에 바꿔도 안전합니다.
- 렌더 스레드가 VSync 대기에 걸리는 동안 메인 스레드는 다음 프레임을 진행할 수 있습니다.

## 4. 영역별 목표 상세

### 4-1. Rendering: 렌더 그래프 (프레임의 "시나리오")

지금은 `Application::Run`의 일정한 흐름(clear → 3D 배치 → 2D 배치 → Present)이
유일한 시나리오입니다. 목표는 렌더 파이프라인을 **클래스로 일반화**하는 것.

```
렌더 그래프 (한 프레임의 일정표)
  [Pass 1] 그림자 맵        → RenderTarget(깊이 전용)
  [Pass 2] 불투명 지오메트리 → RenderTarget(sceneColor + 깊이)
  [Pass 3] 반투명/오버레이   → RenderTarget(sceneColor)
  [Pass 4] 포스트 프로세스   → RenderTarget(화면 크기)
  [Pass 5] Present           → 백버퍼
```

- Unity의 **SRP(Scriptable Render Pipeline)**, Unreal의 **RenderGraph**와 같은 위치입니다.
- sgf는 이미 `RenderTarget`(Create/CreateDepthOnly)과 `GraphicDevice::SetRenderTarget`을
  갖고 있어서, 이 "일정표" 구조만 추가하면 후처리(Tutorial 26)와 그림자 맵(Tutorial 27)이
  엔진 기본 기능으로 승격합니다.

### 4-2. Asset: ResourceMgr → Asset 파이프

지금: `ResourceMgr`이 경로 중복 방지와 키 발급만 합니다.

```
파일("hero.png") → [같은 경로가 이미 로드됨? pathIndex_ 확인]
                 → Texture 생성(디바이스) → Add → 키(_u64) 반환
```

- 부족한 것: 파일 종속성 추적, 이후 로드/해제 집계(참조 계수), 임포트 변환.
- `RemoveAll()`이 "씬 전환 시 전부 방출"하는 방식 대신, "씬이 사라지는 참가자가 쓰던
  리소스만 방출"하는 방식으로 바꾸면 서버/클라 수명 오류가 줄어듭니다.

### 4-3. Runtime: Scene → 씬 그래프 (04 문서에서 상세)

```
Scene 파일(JSON 등으로 저장) → SceneLoader → 씬 트리
  [GameObject "Hero"]  Transform + MeshRenderer + PlayerController
  [GameObject "Eny"]   Transform + MeshRenderer + WanderScript
  [Camera]             Transform + Camera
씬 트리는 단순한 부모-자식 관계로 표현하고, 각 게임 오브젝트는 id(직렬화 키)만 소유.
```

- **직렬화**가 핵심 난제: 트리 구조, 컴포넌트 목록, 프리팹 참조를 텍스트(JSON)/이진으로
  저장하고 로드하는 함수 쌍이면 됩니다.

### 4-4. Cross-cutting: 이벤트/발행-구독

현재도 `jc::Event`가 있지만, `Window::onActivated` `InputManager::onKeyPressed` 등
특정 용도에만 쓰입니다. 목표는 **엔진 전역 이벤트 버스** 입니다.
"씬 로드 완료" "리소스 도착" "게임 일시정지" 같은 사실을 테마로 통지하는 것 (04 문서에서 상세).

## 5. 용어 설명표 (초보자용)

| 용어 | 뜻 | 비유 |
|---|---|---|
| 컴포넌트 (Component) | 오브젝트의 부품 | 자동차엔진·바퀴·좌석을 조립 |
| 씬 그래프 (SceneGraph) | 오브젝트의 부모-자식 나무 | 집안 가족 관계. 부모가 움직이면 자식도 따라가 |
| ECS | 오브젝트를 데이터+시스템으로 분리 | 여러 부서를 표로 관리 |
| 직렬화 (Serialization) | 상태를 파일로 변환/복원 | 체스판을 기록으로 저장 |
| 프리팹 (Prefab) | 오브젝트 재사용 템플릿 | 건축 도면. 한 장으로 여러 채 |
| 에셋 파이프라인 | 원본을 게임용으로 가공 | 밥 짓기 (쌀→밥) |
| PSO (Pipeline State) | 그리기 조건 묶음 | 요리 레시피 |
| 렌더 큐/렌더 그래프 | 그리기의 일정표 | 식당 주문표를 주방에 전달 |

## 6. 로드맵 — 무엇을 어떤 순서로 얹을 것인가

| 단계 | 이름 | 주요 작업 | 상세 문서 |
|---|---|---|---|
| P0 | 렌더 큐 도입 | "그릴 목록"을 만들고, 텍스처와 파이프라인 상태로 묶어 그리기 | `03_렌더링_아키텍처_개선.md` |
| P1 | 렌더 그래프 | RenderTarget 체인/포스트를 표준화 | `03` |
| P2 | 씬 그래프+직렬화 | 컴포넌트 도입, 씬 파일 저장/로드 | `04_씬과_데이터_지향설계.md` |
| P3 | 멀티 스레드 | 로딩 스레드 → 렌더 스레드 (더블 버퍼) | `03` + RnD/04 |
| P4 | 에셋 강화 | 메타 데이터·참조 집계·스트리밍 | 후속 문서 |
| P5 | 에디터 얹기 | 뷰포트·인스펙터·디버그 뷰 | 후속 문서 |

왜 이 순서인가:
1. **렌더 큐(P0)는 기존 코드를 뒤엎지 않는다.** 3D/2D 배치 호출 형태를 유지하면서
   "어떤 순서로 모아 그릴지"만 바뀌므로 리스크가 가장 작고, 이후 스레드화의 기반이 됩니다.
2. **씬 컴포넌트화(P2)는 렌더 큐와 독립적으로** 진행할 수 있습니다. 다만
   그 위에 그리기를 얹을 때 렌더 큐의 그리기 계약이 필요하므로 순서를 앞에 두었습니다.
3. P3의 스레드 분리는 RnD 문서의 5단계(로딩 → 더블 버퍼링 → 렌더 스레드)를 그대로
   구현하면 되며, P0의 렌더 큐 데이터 구조가 곧 프레임 데이터가 됩니다.
4. 에디터는 P2의 씬 파일과 P0의 렌더 디버그 데이터가 있어야만 쓸모가 있으므로 마지막입니다.

## 7. 결론 요약

1. Core/Platform은 이미 완성 — 재작성하지 않는다.
2. Rendering은 "통합"의 문제 — 기존 배칭을 살려 렌더 큐→그래프→스레드 순으로 층을 쌓는다.
3. Runtime은 "변형"의 문제 — 파생 클래스 씬에서 컴포넌트/데이터 중심 씬으로.
4. Asset은 "자동화"의 문제 — ResourceMgr을 유지하면서 참조와 파이프를 더한다.
5. Editor는 "보기"의 문제 — 마지막에 다른 계층 위에 얹는다.
