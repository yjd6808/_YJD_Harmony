# 03. 렌더링 아키텍처 개선 — 즉시 배치에서 렌더 큐와 렌더 그래프로

> 이 문서는 sgf의 렌더링을 "즉시 배치(Immediate-mode)"에서
> **렌더 큐(정렬·배칭) → 렌더 그래프(프레임 일정표) → 병렬 렌더링** 순서로
> 개선하는 방안을 다룹니다. Unity의 SRP, Unreal의 RenderGraph 개념이
> sgf에서 무엇에 대응하는지 표로 정리하고, 단계별 구현 계획을 제시합니다.

## 1. 현재 상태 — "즉시 배치 + 씬 렌더러"

### 1-1. 프레임 그리기 흐름 (Application.cpp → Director.cpp)

```
Application::Run()
  device_.BeginFrame(&window, clearColor)
  g_cDirector.Render(&window)
    ├─ g_cRenderer3D.Begin(scene->GetCamera().ViewProjection())
    ├─ g_cRenderer2D.Begin(viewProjection)
    ├─ scene->OnRender()          ← 씬 코드가 이 자리에서 즉시 그리기 호출
    ├─ g_cRenderer3D.End()        ← 배치 강제 Flush
    └─ g_cRenderer2D.End()        ← 배치 강제 Flush
  device_.EndFrame(&window, vsync)   // Present
```

- `Renderer2D`는 정점을 CPU 벡터에 쌓는 **즉시 배치**입니다. 호출 순서대로 쌓이고,
  텍스처가 바뀌거나 `MAX_QUADS`(2048)가 차면 그 자리에서 `Flush()`합니다.
- `Renderer3D`도 같은 원리로 삼각형/선 배치(각 4096)를 End 시점에 한 번에 Flush합니다.
- `SceneRenderer`(v3)는 `RenderObject{ meshKey_, materialKey_, world_, bVisible_ }`를
  받은 **순서 그대로** 하나씩 그립니다. `lastMeshKey_/lastMaterialKey_` 캐시로
  연속 동일 리소스의 `Find()`를 아끼지만, 정렬·배칭·컬링은 전무합니다.

### 1-2. 이 구조의 성능 특징 (하드웨어 관점)

| 항목 | 현재 sgf | 문제 |
|---|---|---|
| 드로우 콜 수 | 물체마다 1회, 텍스처 전환마다 1회 | 드로우 콜은 CPU가 명령 버퍼를 채우고 상태를 갱신하는 값비싼 작업 |
| CPU 캐시 | 렌더 대상이 포인터·객체 집합 | 그리는 순서가 임의라 캐시 라인 효율이 낮음 |
| GPU 효율 | 상태 변경이 섞이면 GPU가 헛돎 | 상태가 같으면 GPU는 파이프라인을 재사용해 빠름 |
| 확장성 | 새 효과(포스트 등)를 넣으려면 Run 루프를 수정 | 파이프라인 "일정표"가 코드에 고정 |

핵심 결론: **"무엇을 그릴지"와 "어떻게 그릴지"를 데이터로 분리하면** 정렬·배칭·병렬화가
모두 그 데이터 위에서 자유롭게 가능해집니다. 지금 `GraphicContext`의 바인딩 캐시
(GetApiCallCount/GetSkippedCallCount)는 그 데이터를 "소모"하는 쪽의 최적화일 뿐입니다.

## 2. 개선 방향 1 — 그리기 명령을 데이터(렌더 커맨드)로

### 2-1. 렌더 커맨드 (Render Command)

기존 `Scene::OnRender()`가 `g_cRenderer2D.DrawSprite(...)`를 호출하던 것을

```cpp
// 그리기 주문서. D3D 객체가 없다. 메시 + 머티리얼 + 월드 행렬 + 태그
struct DrawCommand
{
    _u64 meshKey_;        // ResourceMgr 발급 키
    _u64 materialKey_;    // ResourceMgr 발급 키
    mat4 world_;          // 월드 행렬 (기록 순간의 스냅샷)
    int  layer_;          // 그리기 순서 계층 (월드/오버레이/UI)
    _f32 distance_;       // 카메라 거리 (반투명 후방 정렬용)
    bool bVisible_;
};
```

씬은 이 구조체를 벡터에 **기록만** 합니다. 이 벡터가 곧 **렌더 큐**입니다.

### 2-2. 왜 "기록만" 하는가

1. **정렬이 자유로워진다.** 텍스처/머티리얼/거리 기준으로 한 번 정렬하면
   드로우 콜을 줄이는 최소 비용의 상태 변화 순서가 됩니다.
2. **배칭이 가능해진다.** 같은 메시+머티리얼이 연속하면 합치거나
   인스턴싱(Instancing)으로 드로우 콜을 1회로 줄입니다.
3. **멀티스레드의 기반이 된다.** 기록은 메인 스레드, 재생은 렌더 스레드가 하게 하면
   RnD 04 문서 단계 2의 `FrameRenderData`(더블 버퍼링)가 바로 들어맞습니다.
4. **디버깅이 쉬워진다.** "이번 프레임에 그린 커맨드 목록"을 그대로 덤프할 수
   있어 드로우 콜 카운터와 씬 그래프 검증에 그대로 씁니다.

### 2-3. 구현 규칙 (기존 API 보존)

현재 `SceneRenderer::Draw(const RenderObject&)`를 내부가 **커맨드 큐에 추가**하는
`SceneRenderer::Submit(const DrawCommand&)`로 바꾸고, `EndFrame` 직전에
`SceneRenderer::Execute(const FrameConstants&)`가 정렬 후 재생하게 합니다.
기존 `RenderObject` 필드가 그대로 쓰이므로 외부 호출 코드의 수정이 거의 없습니다.
`Renderer2D/3D`는 계속 즉시 배치로 두고, 큐 재생 시 "가능한 한" 배치로 흡수합니다.

## 3. 개선 방향 2 — 배칭과 드로우 콜 최소화

### 3-1. 정적/동적 지오메트리 구분

| 구분 | 예 | 버퍼 사용 | sgf 현재 | 목표 |
|---|---|---|---|---|
| 정적 지오메트리 | 땅, 벽, 건물 | DEFAULT (생성 후 불변) | `Mesh::Initialize`가 분류 없이 생성 | **STATIC/DYNAMIC 플래그 분리** |
| 동적 지오메트리 | 캐릭터, 몬스터 | DYNAMIC (매 프레임 갱신) | Renderer2D/3D만 동적 사용 | SceneRenderer도 동적 배치 블록 지원 |

지금 `Mesh::Initialize`는 항상 같은 방식으로 버퍼를 만들지만, "이 메시는 안 변한다"는
정보가 없어 정적 메시를 매 프레임 다시 올리는 낭비의 여지가 있습니다.
정적 메시는 별도 버퍼에 한 번만 올리고, 변하는 것만 갱신하면
**CPU→GPU 전송량(Map/Discard)이 줄고 캐시 친화적**입니다.

### 3-2. 스프라이트 배칭 — 텍스처 정렬 + 아틀라스

- `Renderer2D::PushQuad`의 "텍스처 전환 시 Flush"를 **텍스처 키로 정렬 후 Flush**로
  바꾸면, 같은 텍스처의 스프라이트가 전부 한 드로우 콜로 묶입니다.
- 더 나아가 자주 쓰는 스프라이트들을 **한 장의 아틀라스 텍스처**에 모으면
  "텍스처 전환 0회"가 되어 2D 드로우 콜이 거의 항상 1회가 됩니다.
- 코코스2d-x의 SpriteFrameAtlas와 같은 개념입니다. sgf의 `Texture`(WIC/SVG 로더) 위에
  `TextureAtlas` 클래스를 얹는 형태입니다.

### 3-3. GPU 인스턴싱 (선택 단계)

같은 메시를 수백 개 배치할 때(숲, 파티클) 1회 드로우 + `DrawIndexedInstanced` 하나로
끝냅니다. `VertexPNT`에 인스턴스 데이터(월드 행렬) 스트림을 더하는 작업이며,
b1 오브젝트 상수 버퍼 방식(현재 `ObjectConstants{world_}`)보다 훨씬 큽니다.
**단계적으로** 도입할 것을 권합니다.

## 4. 개선 방향 3 — 셰이더/패스 체계와 머티리얼

### 4-1. 현재: v3의 좋은 기반

- v3에서 셰이더는 `VertexShader`/`PixelShader`/`InputLayout`로 분리되고
  `Material`이 **키(_u64)**로 참조합니다. 상수 버퍼 슬롯 규약도 이미 있습니다:
  - `b0` 프레임 공통 (`FrameConstants`: view/projection/cameraPosition)
  - `b1` 오브젝트 (`ObjectConstants`: world)
  - `b2` 머티리얼 (`MaterialConstants`: baseColor)
- `Material`은 `SetRasterizer/SetBlend/SetDepth/SetSampler`로 파이프라인 상태를 조합하고,
  `Bind(GraphicContext&)`에서 `ResourceMgr`을 거쳐 셰이더/텍스처를 해석합니다.

### 4-2. 부족한 것: "패스(Pass)"와 "머티리얼 인스턴스"

1. **패스 개념이 없습니다.** Unity의 Shader는 여러 Pass(불투명/오버레이/포스트)를
   하나로 묶습니다. sgf는 머티리얼 1개 = VS+PS 1쌍입니다. 목표는
   `MaterialPass { vertexShaderKey, pixelShaderKey, blend, depth, rasterizer, sampler }` 를
   배열로 갖는 **멀티패스 머티리얼**입니다.
2. **인스턴스(복제) 개념이 없습니다.** 같은 머티리얼에 baseColor만 다르게 쓰려면
   머티리얼을 새로 만들어 ResourceMgr에 넣어야 합니다. 목표는
   `MaterialInstance`(base 머티리얼 키 + 오버라이드 값 묶음)로, b2 상수만 다르게 줍니다.
3. **파이프라인 확정을 매 Draw마다 하지 않습니다.** 정렬된 렌더 큐에서는
   "같은 파이프라인 상태가 연속되면 바인딩 생략"이 큰 이득입니다.
   `GraphicContext`의 바인딩 캐시가 이미 이 일을 하므로, 큐 정렬만 맞으면 됩니다.

### 4-3. 머티리얼 재사용 관점

머티리얼 키가 `GraphicContext` 캐시와 어울리도록, **큐 정렬 키 = materialKey** 로
잡으면 바인딩 생략률이 극대화됩니다. 지금 `lastMaterialKey_` 캐시가 이것의
작은 버전입니다.

## 5. 개선 방향 4 — GPU 스키닝과 Forward vs Deferred

### 5-1. GPU 스키닝

- 현재 `VertexPNT`는 위치/법선/UV만 있어 **애니메이션(본 트랜스폼)이 없습니다.**
- 목표: `VertexPNTSkinned`에 `blendIndices(4바이트)` + `blendWeights(4바이트)`를
  추가하고, **bone 상수 버퍼(b3)**에 역바인드 행렬×현재 본 행렬을 올린 뒤
  VS에서 `pos = sum(weight_i * mul(pos, boneMatrix[boneIndex_i]))`를 계산합니다.
- 물리·행렬 계산은 CPU, 정점 변환은 GPU → 정점 수가 많아도 CPU 부하는 거의 없습니다.
- 튜토리얼 30(SpriteAnimation)의 2D 시퀀스 이동이 3D 스키닝으로 확장되는 꼴입니다.

### 5-2. Forward vs Deferred

| 방식 | 원리 | 장점 | 단점 | sgf 판단 |
|---|---|---|---|---|
| Forward | 물체를 그릴 때마다 모든 빛 계산 | 빛 수가 적을 때 단순·빠름 | 빛 많아지면 드로우당 계산 폭증 | **현재 + 1차 목표** |
| Deferred | G-Buffer에 위치/법선/색 기록 후 빛 패스 | 빛 수십~수백 개 OK | G-Buffer 메모리 + 반투명 별도 처리 | 2차 목표 (조명 본격화 시) |

- 튜토리얼 14(Lighting)와 24(ShadingModel) 수준의 조명은 Forward로 충분합니다.
- Deferred는 `RenderTarget` 포맷(pfRgba32Float 등)과 다중 타깃(MRT)이 필요하므로,
  렌더 그래프(P1) 이후에 도입하는 것이 자연스럽습니다.

## 6. 개선 방향 5 — 렌더 타깃 체인과 포스트 프로세스 그래프

### 6-1. 현재 기반

- `RenderTarget`은 이미 색(+깊이) 타깃과 깊이 전용 타깃(`CreateDepthOnly`,
  그림자 맵용)을 지원하고, RTV/DSV/SRV 두 얼굴을 해석합니다.
- `GraphicDevice::SetRenderTarget(RenderTarget*)`으로 수동 전환,
  `Texture::Bind`으로 결과를 다시 샘플링할 수 있습니다.
- 튜토리얼 25(렌더 타깃), 26(포스트: 그레이/세피아/반전/비네트/물결),
  27(그림자 맵)이 이 기반을 보여줍니다.

### 6-2. 부족한 것: "체인/그래프"로 묶는 장치

지금은 누가 언제 어느 타깃에 그리는지를 호출자가 직접 맞춰야 합니다.
목표는 **RenderGraph(패스 목록)** 입니다:

```
[Pass 1] ShadowMap    : 그림자 렌더러 → depthTexture (해상도 1024~2048)
[Pass 2] Geometry     : SceneRenderer 큐 → sceneColor + sceneDepth
[Pass 3] Transparent  : 반투명 큐 (후방 정렬) → sceneColor
[Pass 4] PostProcess  : sceneColor → 화면 크기 타깃 (셰이더 체인)
[Pass 5] Present      : 최종 타깃 → 백버퍼 복사
```

- 각 패스는 "리소스(타깃) 선언 + 그릴 것(큐 일부) + 그릴 상태"의 묶음입니다.
- `RenderTarget` 생성/파괴를 매 프레임 하지 않도록 **풀(Pool)** 로 관리합니다.
- 구현 순서 제안: (1) `PostProcess` 패스 하나부터 수동 체인으로 (2) 패스 리스트로
  일반화 (3) 의존성(어느 타깃을 읽는지) 자동 스케줄 — 이 정도까지 가면 상용급.

### 6-3. 하드웨어 관점 정리

- 렌더 타깃 전환은 GPU 파이프라인 플러시를 유발하므로 **가능하면 한 패스에서
  많은 것을** 그리고, 포스트는 전체 화면 쿼드 한 장으로 처리합니다.
- 현재 `GraphicContext::InvalidateCache()`가 프레임 시작 시 캐시를 비우는 것처럼,
  타깃 전환 시점에도 일부 캐시(OM 단계)만 무효화하는 세분화가 이득입니다.

## 7. 개선 방향 6 — 안티앨리어싱 (AA)

| 방식 | 원리 | 비용 | 적용 대상 |
|---|---|---|---|
| MSAA (4x/8x) | 샘플을 여러 개 테스트 | 메모리/대역폭 증가 | 지오메트리 가장자리. D3D11 기본 지원 |
| FXAA | 후처리 필터로 계단 완화 | 저비용 | 모든 것을 일률적으로, 약간 흐릿 |
| TAA | 과거 프레임과 시간 축 평균 | 중간 | 상용 엔진 표준 (움직임 벡터 필요) |

- sgf의 `SwapChain` 백버퍼를 다중 샘플(예: DXGI_SAMPLE_DESC 4x)으로 만들면 MSAA가
  즉시 동작합니다. 깊이 버퍼도 같은 샘플 수로 맞춰야 합니다.
- 첫 단계로는 **MSAA 4x 옵션 + FXAA 후처리** 조합을 권합니다.
  (Unity의 Quality 설정, Unreal의 Anti-Aliasing Method와 동일한 스위치 위치입니다)

## 8. 개선 방향 7 — 병렬 렌더링 (RnD 도구 문서 통합)

RnD `MultithreadRendering` 문서들(특히 03, 04, 05)의 내용을 sgf 렌더 큐 위에
올리면 아래와 같은 단계가 됩니다.

### 8-1. 도구 요약 (03 문서)

- `ID3D11Device`(리소스 생성): 여러 스레드 동시 호출 **안전**
- `ID3D11DeviceContext`(즉시 컨텍스트): 한 스레드 전용
- **지연 컨텍스트(Deferred Context)**: 스레드마다 커맨드 리스트를 녹음 → 렌더 스레드가
  `ExecuteCommandList`로 재생
- 렌더 큐(우리가 만드는 커맨드)는 D3D 지식 없이도 병렬화의 기반이 됩니다

### 8-2. 렌더 스레드 분리 (04 문서 계획 반영)

```
메인 스레드                           렌더 스레드
FrameRenderData[write] 커맨드 기록      frames_[read] 재생
(씬 갱신, 입력)                        BeginFrame → Execute → Post → Present
프레임 경계: 교환 + 이벤트 신호
```

### 8-3. 함정 대비 (05 문서)

1. 데이터 경쟁 → 더블 버퍼링으로 원천 차단
2. 즉시 컨텍스트는 렌더 스레드 전용 (GraphicDevice::Context() 접근 규칙 문서화)
3. 교착 → 락은 항상 같은 순서, 기다림에 타임아웃
4. 텍스처 수명 → "파괴 대기 목록"으로 미룸 (Director의 씬 교체 시점 활용)
5. `SGF_SINGLE_THREAD_RENDER` 스위치 유지 → 싱글/멀티 즉시 전환 디버깅

## 10. 구현 단계 제안 (한 단계마다 "돌아가는 상태" 유지)

| 단계 | 작업 | 바뀌는 코드 | 검증 방법 |
|---|---|---|---|
| S1 | `SceneRenderer::Submit/Execute` 분리 (렌더 커맨드) | SceneRenderer.h/.cpp | 튜토리얼 22처럼 화면 동일 확인 |
| S2 | 커맨드 정렬 (materialKey → texture → layer) | Execute 내부 | `GetApiCallCount`가 줄어드는지 측정 |
| S3 | 2D 스프라이트 텍스처 정렬 + 아틀라스 | Renderer2D / 새 TextureAtlas | 2D 드로우 콜 수 확인 |
| S4 | 멀티패스 머티리얼 + MaterialInstance | Material.h/.cpp | 같은 머티리얼 다른 색을 인스턴스로 |
| S5 | PostProcess 패스 1개 (렌더 타깃 체인 시작) | RenderGraph 첫 버전 + 26장 코드 이식 | 세피아/비네트를 씬에 적용 |
| S6 | MSAA 4x + FXAA 옵션 | SwapChain 샘플 수 + 포스트 셰이더 | 계단 완화 육안 확인 |
| S7 | GPU 스키닝 (b3 bone) / Forward 확장 | VertexPNTSkinned / 셰이더 | 30장 애니메이션 3D화 |
| S8 | 더블 버퍼링 렌더 데이터 (FrameRenderData) | 새 FrameData 구조 | RnD 04 단계 2 검증법 |
| S9 | 렌더 스레드 분리 | Application::Run 분할 | RnD 04 단계 3 검증법 (Sleep 8ms 테스트) |
| S10 | (선택) 지연 컨텍스트 병렬 기록 | 워커 4개 분할 | 큰 씬에서 프레임 시간 측정 |

### 단계별 핵심 원칙

- **S1~S2**: 성능이 아니라 "구조"의 단계. 화면이 똑같으면 성공.
- **S5~S6**: 사용자가 눈으로 체감하는 단계. 완성도가 오르는 순간.
- **S8~S9**: RnD 문서의 계획을 그대로 이행하는 단계. `SGF_SINGLE_THREAD_RENDER`
  스위치를 걸고 언제든 되돌릴 수 있어야 합니다.

## 11. 결론

1. 지금의 배치 렌더러/스테이트 캐시는 버리지 않는다 — 그 위에 **렌더 커맨드 큐**를

4. 한 단계씩 "화면이 똑같이 나오는 상태"를 유지하며 전진하는 것이 안전하다.
