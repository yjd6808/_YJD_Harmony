## 1. 현재 sgf의 구조 요약

### 1-1. 클래스 규모

| 영역 | 클래스 | 라인 수 (대략) | 역할 |
|---|---|---|---|
| Core | `Application`, `Window`, `FrameTimer` | ~400 | 게임 루프, 윈도우/표면, 시간 |
| Input | `InputManager` | ~250 | 폴링+이벤트 입력 |
| Scene | `Scene`, `Director`, `Camera` | ~700+ | 씬 파생, 슬롯 관리, 행렬 계산 |
| Graphics | `GraphicDevice`, `GraphicContext`, `SwapChain`, `DepthStencilSurface`, `RenderStates`, `BatchRenderer`, `Renderer2D/3D`, `SceneRenderer`, `ResourceMgr`, `Material`, `Mesh`, `Shader/ShaderProgram`, `Texture`, `RenderTarget`, `Buffers` | ~2,600 | DX11 전면 래핑 |
| Audio | `SoundEngine` | ~630 | XAudio2 재생/캐시 |

총 약 30개 클래스, 소스 규모 약 4,300줄로 "작은 게임 하나"를 만들 수 있는 수준입니다.

### 1-2. 렌더링 방식: "즉시 배치 렌더링" (Immediate-mode Batch)

핵심 렌더 경로는 두 갈래입니다.

```
[A] 2D/3D 즉시 배치 (v2.1 이후 주력)
  Application::Run()
    ├─ g_cDirector.Render(Window*)         // Director.cpp
    │    ├─ g_cRenderer3D.Begin(viewProjection)   // BatchRenderer::Begin
    │    ├─ g_cRenderer2D.Begin(viewProjection)
    │    ├─ scene->OnRender()               // 씬 코드가 DrawSprite/DrawCube 호출
    │    ├─ g_cRenderer3D.End()             // 배치를 통째로 Flush (깊이 ON)
    │    └─ g_cRenderer2D.End()             // Flush (깊이 OFF + 알파)
    └─ device_.EndFrame(Window*, vsync)     // Present

[B] 씬 렌더러 (v3 신규, 정면 3D용)
  SceneRenderer::BeginScene(FrameConstants)  // b0: 뷰/프로젝션/카메라위치
  for (obj : objects)
    sceneRenderer.Draw(obj)                  // 키에서 머티리얼/메시 받아 b1 갱신 후 DrawIndexed
```

- **`Renderer2D`** (Renderer2D.h): `DrawSprite/DrawRect/DrawLine/DrawCircle` 호출 즉시
  `VertexPTC` 정점을 CPU 배열에 쌓고, **텍스처가 바뀌거나 배치가 꽉 차면** `PushQuad`
  내부에서 `Flush()`를 호출합니다. 최대 `MAX_QUADS = 2048`개, 즉 정점 최대 8192개.
- **`Renderer3D`**: `DrawTriangle/DrawCube/DrawLine3D/DrawGrid/DrawAxis`. 삼각형/선 배치를
  따로 모아 **가득 차거나 End() 시점에 한 번에** `FlushBatch`로 드로우.
- **`SceneRenderer`** (v3): 메시(무엇)+머티리얼(어떻게)+월드 행렬(어디에)의 묶음 `RenderObject`를
  **순서대로 하나씩 그리는** 루프입니다. `lastMeshKey_/lastMaterialKey_` 소형 캐시로
  연속 같은 리소스의 `Find()`를 생략하지만, **정렬(소팅)이나 드로우 콜 병합(batching)은 없습니다.**

### 1-3. 리소스: `ResourceMgr` 하나로 통합 (v3)

- `Add`는 소유권을 넘겨받고 키를 발급 (`Provider<AutoIncrementLinkedList<_u64>>`).
- `LoadTextureFromFile` 등은 `pathIndex_`(경로→키)로 **같은 경로를 두 번 로드하지 않음**.
- `Remove()`는 수동, `RemoveAll()`은 씬 전환 시 전체 해제용. 기본 리소스(디폴트 셰이더/머티리얼)는
  `defaultKeys_`로 보호.
- 재질은 `Material`이 셰이더/텍스처를 **키(_u64)**로 참조 — 포인터 수명 문제를 회피하는 좋은 설계.

### 1-4. 씬: `Application` 파생 + `Scene` 파생의 "틀"

- `class MyApp : public sgf::Application` → `g_cDirector.RunScene(new MyScene())`.
- `class MyScene : public sgf::Scene` → `OnEnter/OnUpdate/OnRender/OnExit`를 직접 구현.
- `Director`가 **윈도우 1개당 씬 1개(SceneSlot)**를 관리하고, 씬 교체는 프레임 경계에서 수행
  (Director.cpp의 `Update()`에서 예약 씬 pNext → pCurrent 교체).
- 씬은 자기 카메라(`Camera camera_`)를 갖고, `Director::Render`가 카메라의
  `ViewProjection()`으로 두 배치의 Begin/End를 감싸줍니다.

## 2. 실제 코드로 확인한 한계와 문제점

아래 여섯 가지는 "이론상 아쉽다"가 아니라 **코드에서 직접 확인되는 사실**입니다.

### 문제 1. 씬이 전부 수동 코딩. 직렬화가 없다

`Scene.h`의 씬은 순수 C++ 파생 클래스입니다. 타겟 배치, 적 위치, 점수 등은 모두
씬의 멤버 변수로 존재하며, **저장/로드라는 개념 자체가 없습니다.**

```cpp
class MyScene : public sgf::Scene {
    Enemy enemy_[32];     // 이 배열은 어떻게 파일로 저장하나요?
    int score_;
    void OnUpdate(...)
};
```

- Unity는 씬을 `.unity` 파일로, Unreal은 `.umap`으로 저장/로드합니다.
- sgf는 프로그램을 끄면 세상이 사라집니다. **레벨을 데이터로 다루는 팀 개발**과
  **에디터 없는 인게임 편집**이 둘 다 불가능합니다.
- 애셋도 `LoadTextureFromFile` 줄 때마다 경로 문자열로 즉시 로드 — 프리팹/번들/임포트 개념이 없습니다.

### 문제 2. 드로우 콜 일괄화(배칭)가 "텍스처 단위"에 머물러 있다

`Renderer2D::PushQuad`는 텍스처가 바뀔 때만 Flush합니다. 정렬 없이
DrawSprite(A) → DrawSprite(B) → DrawSprite(A) 순서로 호출하면 **Flush가 3번** 일어납니다:

```
DrawSprite(A)   ← 배치에 합류
DrawSprite(B)   ← 텍스처 바뀜 → Flush(A) 발행!    <-- 드로우 콜 1
DrawSprite(A)   ← 텍스처 바뀜 → Flush(B) 발행!    <-- 드로우 콜 2
End()                                             → Flush(A) <-- 드로우 콜 3
```

GPU 드로우 콜의 부하(명령 버퍼 전송, 상태 변경)는 CPU 쪽에서 꽤 비싸므로,
상용 엔진의 "텍스처별 정렬 후 한 번에 그리기"와 비교하면 손해가 많습니다.
`Renderer3D`도 도형 한 종류마다 동적 버퍼에 복사(MAP)해서 그리지만,
**불투명/반투명 정렬, 깊이 프리패스, 프러스텀 컬링이 전혀 없습니다.**

### 문제 3. ResourceMgr는 "중복 로드 방지만" — 수명 관리가 반 자동

- `Add()`/`Remove()`가 수동 호출이라, "그 리소스를 지금 누가 쓰는가"를 추적하지 않습니다.
- 참조 계수(Unity의 refcount, Unreal의 UObject 참조 정책)가 없으므로 씬 교체 시
  `RemoveAll()`로 몰아 방출하거나 `Find<>()`가 null을 반환하는 것을 감수해야 합니다.
- 임포트/종속성/경량화 파이프라인이 없어, 원본 파일(png, svg 등)이 곧 실행 리소스입니다.

### 문제 4. 에디터가 없다 → 검증 수준이 인디

Hierarchy/Inspector/Frame Debugger 같은 시각 도구가 전무합니다. 오브젝트 트리 조작,
프로퍼티 변경, 핫 리로드, 드로우 콜 디버깅을 전부 코드로만 해야 합니다.
`GraphicContext`의 `GetApiCallCount()/GetSkippedCallCount()` 훌륭한 "계기판"이지만
"셰이더 키, 메시, 머티리얼별 드로우 콜 목록" 같은 프로파일 뷰는 없습니다.

### 문제 5. 멀티스레딩이 전혀 없다 — 단일 코어 하나로 모든 것

`Application::Run()` (Application.cpp)에서 메시지 펌프·로직 갱신·렌더링·사운드 정리가
**하나의 스레드**로 직렬 실행됩니다. `ID3D11DeviceContext`(즉시 컨텍스트)는 스레드에
안전하지 않으므로 (MultithreadRendering 03 문서), 현재 구조에서는 CPU 코어가 남아도
렌더를 병렬로 넘길 수 없습니다. RnD 01 문서의 결론인
"CPU 예산 2배"를 얻기 위한 **프레임 데이터 더블 버퍼링**과 **렌더 스레드**(04 문서)는
아직 없습니다. 로딩조차 메인 스레드라 큰 PNG를 읽는 동안 화면이 멈칩니다.

### 문제 6. 2D/3D 파이프 확장 포인트가 없고, 렌더 그래프가 없다

- 튜토리얼(25~27장)에 렌더 타깃/후처리/그림자 맵 구현이 있지만 엔진의 기본 파이프라인 밖입니다.
  `RenderTarget`과 `GraphicDevice::SetRenderTarget`이 있어 수동으로는 가능하지만,
  "렌더 타깃 체인" "포스트 프로세스 그래프" 같은 **프레임 전반의 그래프 개념이 없습니다.**
- AA(멀티샘플), 톤매핑, SSAO 등 렌더링 파이프라인 스위치도 없습니다.

## 3. 해야 할 일의 방향

| 번호 | 지금 (사실) | 부족한 것 | 필요 구조 |
|---|---|---|---|
| 1 | 씬을 C++로 하나씩 작성 | 직렬화 | 씬/프리팹 파일, 리로드 |
| 2 | 그리기 즉시 호출 | 정렬/일괄 | 렌더 큐 + 정렬/배칭 |
| 3 | ResourceMgr 수동 해제 | 수명/참조 | 에셋 파이프라인 + 참조 계수 |
| 4 | 에디터 0 | 에디터 | 씬 뷰/프로파일 뷰 |
| 5 | 단일 스레드 | 로딩/렌더 병렬 | 커맨드 리스트, 워커 스레드 |
| 6 | 2D/3D 파이 확장 없음 | 통합 파이프 | 렌더 그래프 |

## 4. Unity/Unreal과의 격차 요약

| 항목 | sgf (현재) | Unity | Unreal |
|---|---|---|---|
| 씬 표현 | C++ 파생 클래스만 | GameObject+Component 트리 | AActor+UActorComponent 트리 |
| 씬 저장 | 없음 | `.unity` (YAML) | `.umap` |
| 아트 리소스 | Texture(PNG/SVG) 직접 로드 | 임포트 파이프라인+아틀라스 | FBX 등 임포트 파이프라인 |
| 렌더 큐 | 없음 (호출 순서) | RenderQueue + SpriteAtlas | RenderThread 정렬 |
| 드로우 배칭 | 텍스처 전환 시 자동 Flush | SRP Batcher / GPU Instancing | Nanite(3D) / 분할 배치 |
| 셰이더/패스 | VS+PS 1쌍 / Material 키 | Shader(Pass/SubShader) | Material param + shader permutation |
| 렌더 타깃 체인 | 수동 `SetRenderTarget` | Camera 스택 + 렌더 텍스처 | SceneColor / RenderGraph |
| 후처리/AA | 없음 | Post-process Volume/TAA | PostProcessVolume |
| 멀티 스레드 | 없음 | Job System + 렌더 스레드 | 렌더 병렬 + Nanite |
| 에디터 | 없음 | Hierarchy/Inspector/Frame Debugger | Outliner/Editor utility |
| 이벤트 | `jc::Event`(입력/창) | Delegates | Multicast delegates |

요약하자면, **기초(수학/코어)와 뼈대(플랫폼/루프)는 상용 수준의 밑그림을 갖췄지만,
그 위에 얹어야 할 "렌더 파이프 계층"과 "씬 데이터 계층"이 비어 있는 상태**입니다.
"어디를 순서대로 메워 가면 되는지"를 다음 문서 `02_목표_아키텍처.md`에서 그립니다.

## 5. 이 문서의 결론

1. 렌더링은 이미 배치 기반이므로 "파이프 통합"(렌더 큐/그래프)을 얹는 일이 남았다.
2. 씬은 데이터 없음이 가장 큰 한계 — 직렬화/컴포넌트화가 병목의 전부다.
3. 멀티스레드는 준비 상황(파트 분리 완료)이 갖춰져 있으므로 여건이 되면 바로 진행한다.
4. 에디터는 이 모든 것의 "결과물" — 마지막에 얹는다.
