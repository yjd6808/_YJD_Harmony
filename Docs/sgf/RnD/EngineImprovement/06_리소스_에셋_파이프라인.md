## 1. 현재 리소스 매니저가 하는 일과 못 하는 일

현재 `ResourceMgr`는 "도서관 관리자"(21번 문서)입니다. 요약:

| 기능 | 구현 | 한계 |
|---|---|---|
| 고유 키 발급/재사용 | `jc::Provider<AutoIncrementLinkedList<_u64>>` | 키의 대상은 `IResource*`뿐. 버전(세대) 정보 없음 |
| 경로 중복 로드 방지 | `pathIndex_` (경로 → 키 역색인) | 경로 문자열 동일성만 판정 |
| 타입 안전 검색 | `Find<T>(key)` 템플릿 | 타입 검증은 검색 시점, 포인터 수명은 "매니저 보유" |
| 텍스처 로더 | `LoadFromFile`(WIC), `LoadFromSvgFile`(nanosvg) | 항상 **동기** 디코딩 + GPU 업로드 |
| 소멸 | `Remove` / `RemoveAll` / `Finalize` (소유자 = 수명 결정자) | **참조 카운트 없음**. 씬 A가 `RemoveAll()`하면 씬 B가 쓰던 리소스도 사라짐 |
| 메타 정보 | 디폴트 7종 보호(`defaultKeys_`), 디버그 이름 | 파일 이름 외 아무것도 모름 |

현재 로딩 경로를 그림으로 보면:

```
파일(PNG) → jc::FileStream → WIC 디코드 → RGBA8 픽셀 배열
          → ID3D11Texture2D 생성 (초기 데이터, PCIe 업로드)
          → SRV 생성 → ResourceMgr::Add(key)
```

이 흐름이 전부 **프레임 루프 안에서 동기적으로** 일어납니다. 시작 로딩 화면에는 OK지만,
플레이 중에 새 씬 에셋을 로드하면 프레임이 통째로 멈춥니다 (05 문서의 도입 단계 1과 연결).

또한 런타임 텍스처는 항상 만들어진 그대로입니다 — 밉맵도, 압축 포맷도, SRGB 보정도 없습니다.
이게 "원본 파일을 그냥 읽어서 쓰는" 구조가 가진 한계 전부입니다.

## 2. 에셋 파이프라인이라는 개념

"에셋"은 아티스트/개발자가 만드는 **원본**(hero.png, model.fbx(개념), shader.hlsl)이고,
"파이프라인"은 원본을 **런타임이 빠르고 안전하게 읽는 바이너리**로 바꾸는 일련의 작업줄입니다.

```
┌──────────┐   ┌─────────┐   ┌───────────────┐   ┌────────────┐   ┌───────────────┐
│ 원본 소스  │ → │ DCC 도구 │ → │ 빌드 가공      │ → │ 이진 에셋   │ → │ 런타임 로드    │
│ (아트/코드)│   │ (PS 등) │   │ (임포터)      │   │ .sasset     │   │ 캐싱 → 스트림  │
└──────────┘   └─────────┘   └───────────────┘   └────────────┘   └───────────────┘
  hero.png      편집/저장     리사이즈+BC7+미맵   패킹/인덱스화     비동기 로드+GPU업
  ui.sprite       SpriteLayout 밀맵/아틀라스      GUID 색인        참조 카운트 유지
  shader.hlsl     IDE          오프라인 컴파일     프로젝트 정보    hot reload
```

핵심 통찰 하나: **원본 세계는 "사람이 반복해서 고치는 것", 이진 세계는 "게임이 반복해서 읽는 것"입니다.**
두 세계를 파일/형식으로 분리하면, ① 원본 수정 → 임포트만 다시 → 재시작 없는 핫 리로드,
② 원본 포맷(PNG/SVG/GLTF)은 건드리지 않고 바이너리 호환성만 지키는 것이 가능해집니다.

## 3. 종류별 가공 단계 — D3D11 관점

### 3-1. 텍스처

| 가공 단계 | 하는 일 | D3D11에서의 의미 |
|---|---|---|
| 포맷 변환 | RGBA8 → BC1/BC3/**BC7** 압축 | `DXGI_FORMAT_BC7_UNORM`(SRGB: `_SRGB` 변형). 픽셀당 8비트 수준까지 절약 → **VRAM 절감 + 텍스처 캐시 히트 향상**(캐시 라인 하나에 더 많은 텍셀) |
| 밉맵 생성 | 1/2/4… 배율 체인 | `MipLevels > 1` 텍스처 + 필터 샘플러 → 축소 시 원본 해상도를 그대로 샘플링하는 대신 미리 축소된 계층 선택 (**모아레/평각 제거**, 대역폭 저감) |
| sRGB 보정 | 색 공간 감마 인코딩 | `_UNORM_SRGB` 형식: 셰이더에서 선형 보간은 정규화되는 형태로 자동 처리. 2D 게임은 건너뛰어도 무방하지만 3D 라이팅 진입 시 필수 |
| 리사이즈 | 대상 크기로 사전 축/확대 | 런타임 기본 크기를 정적 유지 |
| 아틀라스화 | 여러 스프라이트를 한 텍스처에 태움 | Renderer2D가 **텍스처 스위치로 인한 Flush를 줄임** (배치 유지), 드로우콜 급감 — 아틀라스 한 장 = 드로우 콜 1회 |

현재 sgf는 밉맵/압축/아틀라스가 전부 없습니다. 30번 스프라이트 애니메이션처럼
스프라이트가 많은 게임(sgcl UI 화면 전환, 타이틀로고 등)에서 밉맵은 화질 문제보다
**메모리/대역폭** 문제로 먼저 느껴집니다. `Material::SetSampler(FilterMode)`로
선택하는 Linear 필터와 밉맵이 있으면 2단계 필터(선형 + 밉랩)로 자동 전환됩니다.

### 3-2. 메시 (3D 확장 시)

- 인덱스 포맷: 정점 수 < 65,536이면 `DXGI_FORMAT_R16_UINT` (인덱스 메모리 절반 절감)
- 정점 요소: `VertexPNT`(위치+노말+UV)를 용도별 분리 (VertexPN / VertexPC / VertexPT)
- 캐시 친화 재정렬: 삼각형 순서를 GPU 정점 캐시에 인접하도록 재배열 → 캐시 라인 히트율 증가
- LOD 체인: 거리별 메시 2~3단계 (이건 후반 Expansion 단계에서)

### 3-3. 셰이더

현재는 `DefaultShaders.h`에 HLSL 소스가 그대로 있고, 실행 시작 시 `D3DCompile`로 컴파일합니다.
가공 단계 목표:

```
shader.hlsl --(오프라인 컴파일: fxc.exe, SM5)--> .bin (바이트코드)
런타임:      D3DCompile 없이
            device->CreateVertexShader(bytecode) / CreatePixelShader(bytecode)
```

이렇게 하면 ① 실행 시작 컴파일 시간 제거, ② 빌드 실패가 "실행 중"이 아니라 "빌드 시점"에
잡히는, ③ 셰이더 파일 수정 감지 → 재컴파일 → 핫 스왑이 쉬워집니다 (07 문서와 연결).
레지스터 계약은 현재 규약을 그대로 **계약서로 승격**합니다:
`b0 = FrameConstants`(view/projection/cameraPosition), `b1 = ObjectConstants`(world), `b2 = MaterialConstants`(baseColor)
→ 이 계약을 어기는 셰이더는 임포터에서 즉시 오류로 거부.

## 4. 로딩 전략: 동기 → 비동기, 참조 카운트, 캐시 크기

### 4-1. 동기 vs 비동기

- 동기(현재): 프레임 안에 디코드+업로드 → 무겁고 뚝뚝 끊김(hiccup)
- 비동기(목표, 05 문서 단계 1과 같은 방향):
  1. 워커 스레드: 파일 읽기 + 디코드 (GPU X, 디바이스 X)
  2. **업로더 큐**에 픽셀 배열 전달
  3. 프레임 시작에 큐를 비우며 `CreateTexture2D` (디바이스는 스레드 안전이므로 OK)
  4. 아직 준비 안 된 텍스처는 `GetDefaultTexture()`(1x1 흰색)로 대체 → 완료 사건이 오면 교체

```cpp
// Assets/AsyncLoader.h (의사 코드 — 신규)
struct TextureUpload
{
    jc::Array<Color32> pixels_;   // 디코드 완료된 픽셀 데이터
    String            path_;      // pathIndex_ 등록용
};

class AsyncLoader
{
public:
    void Request(String path);                  // 워커 잡 등록 (파일 읽기+디코드)
    bool PollUploadQueue(TextureUpload* out);   // 메인이 매 프레임 한 번
};
```

### 4-2. 참조 카운트와 언로드 정책

현재 "키 = 유일 소유권" 모델은 씬 공유 리소스에 취약합니다. 도입안:

```
AddRef(_key)  : 참조 +1 (키는 살아 있음이 보장)
Release(_key) : 참조 -1, 0이 되면 [삭제 대기]에 보관
                → 렌더 스레드가 그 프레임을 다 그린 뒤 실제 Remove (05의 파괴 큐)
```

정책 후보:
| 정책 | 동작 | 용도 |
|---|---|---|
| 즉시 언로드 | 참조 0 = 삭제 | 전투 자원 (일시적) |
| LRU 캐시 | 참조 0이어도 최근 N개는 유지 | UI 스프라이트/캐릭터 재사용 |
| 고정 테이블 | 스트리밍 용량 한도 초과 시, 참조 0 중 가장 오래 안 쓴 것부터 제거 | 월드 렌더 |

가장 간단한 시작은: **"참조 카운트가 0인 것 중 가장 오래 안 쓴 것부터 정리"** 입니다.
캐시 크기 상한을 두면(`maxMemoryBytes_`), 초과 시 오래된 것부터 한꺼번에 제거합니다.

## 5. 에셋 메타데이터와 번들(패킹)

리소스를 식별하는 것은 **경로 문자열이 아니라 GUID+타입**이어야 합니다.

```
[Asset]
  id         : sgf-<type>-<8 bytes hex>   // 전역 고유 GUID
  type       : texture | sprite | shader | scene | ...
  name       : "ui/btn_start"
  importsFrom : "assets/ui/btn_start.png"  // 원본 경로 (디버그/임포트만)
  sha1       : ...                        // 원본 해시 → 변경 감지 → 재임포트
  deps       : [셰이더 키, 텍스처 키, ...] // 머티리얼 → 셰이더+텍스처 등
```

- **의존성(deps)**: 스프라이트 → 텍스처, 머티리얼 → 셰이더+텍스처. 의존성 그래프가 깨지면
  임포트 실패/경고. 언로드 시에도 편집 방향으로 역참조 관리.
- **번들/패킹**: 여러 컴포넌트를 하나의 `.sba`(바이너리 묶음)로 합치면:
  파일 열기 1회 + 연속 읽기 디스크 응답 시간(disk seek)과 IO 중복이 줄어듭니다.
  sgf는 현재 텍스처만 있지만, 포맷을 처음 만들 때부터 **"한 묶음 안에 여러 타입"**을
  전제로 두는 것이 좋습니다 (화면 단위 번들: UI_Screen.sba).

```
Unity        : Assets/ *.meta(GUID·종속) → [import] → Library/ 캐시
Unreal       : Content/ .uasset (자체 스토리지 + 필터를 통해 로드) + bulk data
대상 (sgf)   : Assets/원본 + .smeta → [AssetTool] → Assets/Built/*.s assets(번들)
```

## 6. 대상 형식 제안 — 간단한 바이너리 직렬화 스키마

"전용 이진 포맷"이라고 두려울 것 없습니다. 안전하게 하는 요령은
① 매직 헤더(버전), ② 오프셋 테이블(파싱 안전), ③ CRC(오염 검사) 3가지입니다.

```cpp
// SAssetFormat.h (신규 — 설명용 의사 코드)
namespace sgf
{
    struct SAssetHeader              // 파일 시작, 고정 크기
    {
        _u64  magic   = 0x53474546;  // "SG EF"
        _u32  version = 3;            // 포맷 버전
        char  type[8];                // "texture" | "shader" | ...
        _u64  assetGuid;              // GUID (전역)
_u64  sectionCount;            // 섹션(블록) 수
        _u64  totalBytes;              // 파일 전체 크기 (무결성 검사)
    };

    struct SAssetSection        // 오프셋 테이블의 한 줄
    {
        _u32 tag;                     // 'META' / 'DATA' / 'DEPN' ...
        _u64 offset;                  // 파일에서 시작 위치
        _u64 size;                    // 길이
    };

    // 텍스처 DATA 섹션 예: (밉맵이 있는 텍스처)
    struct TexturePayload
    {
        _u32 width, height;
        _u32 format8;                  // DXGI_FORMAT 값 그대로 (4byte)
        _u32 mipCount;
        // mipCount개 만큼 { offset, size } 가 뒤따른다
    };
}
```

판독 룰:
1. 헤더의 `magic`/`version`이 안 맞으면 즉시 실패 (파손/버전 검증)
2. `sectionSize`와 실제 파일 크기 불일치 시 실패
3. 섹션 오프셋은 **파일 끝초과 여부**를 검사 (아이테 다른 파일 포인터 조회 없음)

이 포맷의 장점: C++에서 `fwrite`/`fread` 한 번으로 쓰고, `jc::FileStream`과 크기가 안 맞아도
헤더만 보고 파서를 쉽게 테스트할 수 있습니다. JSON/YAML로 임포트 디버그 로그가 필요해지면
"이진 파일 + 별도 .meta(JSON)"처럼 메타를 밖으로 둡니다.

## 7. 도입 단계

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| 1 | AsyncLoader 도입 (05 단계 1과 시너지) | 큰 PNG 여러 장 로드 중 FPS 유지, 흰색 임시 교체 |
| 2 | 참조 카운트(AddRef/Release)와 삭제 큐 | 한 씬이 다른 씬과 텍스처를 공유해서 지워도 릭/크래시 0 |
| 3 | 오프라인 셰이더 컴파일 (레지스터 계약서) | 그림 변화 없음, 시작 시간 단축, 빌드 에러 조기 |
| 4 | 텍스처 가공기(밉맵/압축/DDS-like 포맷) | 디스크 크기 ↓, 아틀라스 배치 드로우콜 ↓ |
| 5 | GUID + 의존성 + 번들 | 파일 경로에 의존하지 않는 에셋 로드, 원본 변경 감지 → 재임포트 |

파이프라인을 한 번에 완성하려 하지 말고, **1단계 비동기 로딩은 05의 멀티스레드와,
3단계 셰이더는 07의 핫 리로드와** 차례로 이어붙이는 것이 자연스럽습니다.
