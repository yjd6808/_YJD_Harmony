# 01. 부팅과 메인 루프 — 전원 버튼부터 심장 박동까지

> **이 문서 하나로**: `g_cApp.Initialize()`가 어떤 순서로 무엇을 깨우는지, `Run()` 루프 한 바퀴에서 무슨 일이 일어나는지, 그리고 "왜 그 순서여야만 하는지"를 실제 코드와 함께 이해합니다.
>
> 관련 소스: `Core/Application.h/.cpp`, `Core/Window.h/.cpp`, `Core/FrameTimer.h/.cpp`

---

## 1. 큰 그림 — 게임은 결국 두 단계다

모든 게임 프로그램은 아무리 복잡해도 결국 이 두 단계입니다.

1. **부팅(Initialize)**: 창을 만들고, GPU와 연결하고, 부품들을 깨운다. (단 한 번)
2. **메인 루프(Run)**: "입력 받고 → 갱신하고 → 그리고 → 화면에 내보내고"를 초당 수십~수백 번 반복한다. (게임이 끝날 때까지)

sgf에서 이 둘을 총지휘하는 것이 `Application`(전역 `g_cApp`)입니다. 극장에 비유하면 **극장 지배인**입니다. 공연(씬)의 내용에는 관여하지 않지만, 극장 문을 열고(부팅), 매 회차 공연을 돌리고(루프), 문을 닫는(종료) 책임은 전부 지배인의 몫입니다.

```
[전원 ON]
   │
   ▼
Application::Initialize()   ← 2장: 부품을 깨우는 순서가 정해져 있다
   │
   ▼
Application::Run()          ← 3장: while 루프 = 심장 박동
   │  (매 프레임: 메시지 → 시간 → 갱신 → 그리기 → 표시)
   ▼
Application::Finalize()     ← 5장: 깨운 역순으로 재운다
```

## 2. 부팅 — 깨우는 순서에는 전부 이유가 있다

`Application::Initialize()`는 아래 순서로 부품을 깨웁니다. **순서가 곧 의존 관계**입니다. 앞 단계가 없으면 뒤 단계가 성립하지 않습니다.

| 순서 | 하는 일 | 왜 이 시점인가? |
|---|---|---|
| 1 | **윈도우 생성** (`window_.Create`) | 모든 것의 시작. 스왑체인을 만들려면 HWND가 필요하다 |
| 2 | **디바이스 생성** (`device_.CreateDeviceOnly`) | GPU와의 연결. 창과 무관하게 "디바이스만" 먼저 만든다 (멀티 윈도우 대비) |
| 3 | **리소스 매니저 초기화** (`g_cResourceMgr.Initialize`) | 디폴트 셰이더/흰색 텍스처/프리미티브 메시/기본 머티리얼을 미리 구워둔다. 디바이스가 있어야 GPU 리소스를 만들 수 있다 |
| 4 | **윈도우 표면 생성** (`window_.CreateSurface`) | 창 크기에 맞는 스왑체인 + 깊이버퍼. 디바이스가 있어야 만들 수 있다 |
| 5 | **Renderer2D 초기화** | 배치 버퍼/셰이더 준비. 디폴트 셰이더(3단계)가 필요하다 |
| 6 | **Renderer3D 초기화** | 상수버퍼 b0/b1 준비. 마찬가지 |
| 7 | **사운드 엔진 초기화** | 실패해도 게임은 계속된다(소리 없이). 그래서 마지막이고, 실패를 용인한다 |
| 8 | **onActivated 이벤트 + 타이머 Reset** | "이제 시작"을 알리고, 첫 프레임의 dt가 거대해지지 않게 시계를 0으로 맞춘다 |
| 9 | **`ApplicationDidFinishLaunching()` 훅** | 사용자가 첫 씬을 띄우는 곳 (Cocos2d-x와 같은 이름!) |

> **자주 하는 실수**: 첫 씬을 생성자에서 띄우려고 하면 안 됩니다. 생성자 시점에는 디바이스도 리소스도 없습니다. 반드시 `ApplicationDidFinishLaunching()` 훅에서 `g_cDirector.RunScene(...)`을 호출하세요.

### 2-1. 윈도우는 어떻게 만들어지나 — Window.h의 설명을 그대로

창 생성 절차와 메시지 루프의 개념은 `Window.h` 헤더 주석이 가장 잘 설명하고 있어서 그대로 옮깁니다.

```cpp
// Core/Window.h
/*
 * [윈도우가 만들어지는 과정]
 * 1. RegisterClassEx: "이런 종류의 창을 만들거야"라고 OS에 윈도우 클래스를 등록
 * 2. CreateWindowEx: 등록한 클래스로 실제 창을 생성 (HWND 핸들을 받음)
 * 3. ShowWindow: 창을 화면에 표시
 * 4. 메시지 루프: OS가 보내는 이벤트(키보드/마우스/종료 등)를 계속 꺼내서 처리
 *
 * [메시지 루프란?]
 * 윈도우 프로그램은 "이벤트 기반"으로 동작한다.
 * 마우스를 움직이면 OS가 WM_MOUSEMOVE 메시지를 프로그램의 메시지 큐에 넣어주고,
 * 프로그램은 PeekMessage/GetMessage로 이를 꺼내 WndProc에서 처리한다.
 * 게임은 메시지가 없을 때도 계속 그려야 하므로, 블로킹되는 GetMessage 대신
 * 비블로킹 PeekMessage를 사용하는 것이 핵심 차이점이다.
 */
```

마지막 문단이 핵심입니다. 일반 GUI 프로그램은 이벤트가 올 때까지 **잠들어도** 되지만(GetMessage), 게임은 아무 입력이 없어도 매 프레임 그려야 하므로 **잠들면 안 됩니다**(PeekMessage). 이 한 줄 차이가 "문서 편집기"와 "게임"의 구조적 차이입니다.

### 2-2. 창마다 그리기 표면이 하나씩 — 멀티 윈도우 구조

sgf는 서브 윈도우(미니맵, 디버그 뷰 등)를 지원합니다. 그래서 소유 구조가 중요합니다.

```cpp
// Core/Window.h
/*
 * [바뀐 점 - 윈도우가 그리기 표면을 소유]
 * 멀티 윈도우를 지원하려면 "백버퍼(그림이 그려지는 종이)"가 창마다 하나씩 필요하다.
 * 그래서 스왑체인(SwapChain)과 깊이버퍼(DepthStencilSurface)를
 * GraphicDevice가 아닌 각 Window가 소유하도록 바꿨다.
 * (디바이스/컨텍스트는 앱 전체에 1개, 표면은 창마다 1개씩 - 이게 자연스러운 소유 구조다)
 */
```

요약하면 **"화가(디바이스)는 한 명, 캔버스(스왑체인+깊이버퍼)는 창마다 하나"** 입니다. 이 구조 덕분에 메인 루프에서 창을 순회하며 같은 디바이스로 각 창의 캔버스에 그릴 수 있습니다.

## 3. 메인 루프 — Run() 한 바퀴 해부

엔진의 심장입니다. 실제 코드를 그대로 발췌했습니다. 주석 번호(1~8)를 따라가며 읽어보세요.

```cpp
// Core/Application.cpp — Run()
while (true)
{
	// 1. 윈도우 메시지 처리. WM_QUIT이면 루프 종료.
	// (PeekMessage가 스레드의 모든 창 메시지를 함께 처리하므로
	// 서브 윈도우는 따로 펌프할 필요가 없다)
	if (!window_.PumpMessage())
	{
		break;
	}

	// 2. 직전 프레임으로부터 경과 시간 측정 (jc::TimeSpan)
	timer_.Tick();
	const jc::TimeSpan& dt = timer_.Delta();

	// 3. 로직 갱신: 모든 윈도우의 씬 교체/갱신 -> 앱 훅
	g_cDirector.Update(dt);
	OnUpdate(dt);

	// 3.5. OnUpdate(ESC 종료 등)에서 메인 윈도우가 닫혔으면 즉시 루프 종료.
	// 이 체크가 없으면 파괴된 창(HasSurface=false)으로 BeginFrame을
	// 시도해 assert가 발생한다.
	if (window_.IsClosed())
	{
		break;
	}

	// 4. 사용자가 닫은 서브 윈도우 정리 (그리기 전에!)
	DestroyClosedSubWindows();

	// 5. 메인 윈도우 그리기: 화면 지우기 -> 씬 그리기 -> 앱 훅 -> 화면 표시
	device_.BeginFrame(window_.GetSwapChain(), &window_.GetDepthSurface(), clearColor_);
	g_cDirector.Render(&window_);
	OnRender();
	window_.GetSwapChain().Present(vsync_);

	// 6. 서브 윈도우들 그리기
	for (_s32 i = 0; i < subWindows_.Size(); ++i)
	{
		Window* pSub = subWindows_[i];
		if (pSub->IsClosed() || !pSub->HasSurface())
		{
			continue;
		}
		device_.BeginFrame(pSub->GetSwapChain(), &pSub->GetDepthSurface(), clearColor_);
		g_cDirector.Render(pSub);
		pSub->GetSwapChain().Present(vsync_);
	}

	// 7. 입력 상태를 다음 프레임으로 넘긴다.
	// (IsKeyPressed 같은 "막 눌림" 판정이 이 호출에 의존한다)
	input_.NextFrame();

	// 8. 사운드 엔진 정리 (재생이 끝난 소리의 재생기 회수)
	g_cSound.Update();
}
```

### 3-1. 읽는 포인트 셋

**첫째, 갱신과 그리기가 명확히 나뉩니다.** 3단계(Update)에서는 상태만 바꾸고, 5~6단계(Render)에서는 그리기만 합니다. 이 경계가 깨끗해야 나중에 멀티스레드 렌더링(갱신은 게임 스레드, 그리기는 렌더 스레드)으로 확장할 수 있습니다. `RnD/MultithreadRendering` 문서들이 바로 이 경계를 활용하는 연구입니다.

**둘째, 죽은 창 체크가 두 번 있습니다(3.5와 4).** ESC로 종료하거나 사용자가 X 버튼을 누르는 이벤트는 "갱신 중"에 일어납니다. 파괴된 창의 스왑체인에 BeginFrame을 하면 assert로 즉사하므로, **그리기 전에** 반드시 확인합니다. "이 체크가 없으면 assert가 발생한다"는 주석은 실제로 겪은 버그의 흔적입니다.

**셋째, 입력의 NextFrame이 루프의 거의 끝에 있습니다.** "이번 프레임에 막 눌렸는가?(IsKeyPressed)"는 이전 프레임과 현재 프레임의 상태 비교로 판정하는데, 그 "이전 상태 스냅숏"을 찍는 시점이 여기입니다. 그래서 Update/Render 어디에서 물어봐도 일관된 답을 받습니다. (자세한 원리는 08 문서)

## 4. 프레임 타이머 — 왜 float 초가 아니라 TimeSpan인가

매 프레임 `timer_.Tick()`이 측정하는 dt(DeltaTime)는 게임 프로그래밍의 기본 재료입니다.

```cpp
// Core/FrameTimer.h
/*
 * [왜 시간을 재야 하나?]
 * 컴퓨터마다 성능이 달라 1초에 그리는 프레임 수가 다르다.
 * 이동/회전 같은 값에 "프레임당 고정값"을 더하면 빠른 PC에서 더 빨리 움직인다.
 * 매 프레임 경과한 시간(DeltaTime)을 곱해줘야 한다.
 * 위치 += 속도 * DeltaTime;  <- 이 패턴이 게임 프로그래밍의 기본이다.
 *
 * [바뀐 점]
 * - 시간을 float 초가 아닌 jc::TimeSpan(마이크로초 단위 틱)으로 관리한다.
 *   float은 누적 시간이 커질수록 정밀도가 떨어지지만 정수 틱은 그렇지 않다.
 * - 디버거 중단 등으로 생긴 비정상적으로 큰 dt는 250ms로 잘라낸다.
 */
```

두 가지 설계 결정이 흥미롭습니다.

- **정수 틱 채택**: float으로 "게임 시작 후 총 시간"을 재면 몇 시간 뒤 정밀도가 무너집니다(큰 수 + 작은 수 덧셈에서 작은 수가 증발). 마이크로초 정수 틱은 이런 문제가 없습니다.
- **250ms 클램프**: 디버거로 5초 멈췄다 재개하면 dt=5초가 됩니다. `위치 += 속도 * 5초`면 캐릭터가 순간이동하죠. 그래서 비정상적으로 큰 dt는 250ms로 잘라 "세상이 잠깐 느려진 것처럼" 처리합니다. 물리가 폭발하는 것보다 훨씬 낫습니다.

측정 자체는 Windows의 고해상도 카운터 QueryPerformanceCounter(QPC)로 합니다.

## 5. 종료 — 깨운 역순으로 재운다

`Finalize()`는 Initialize의 정확한 역순입니다. 사운드 → Renderer3D → Renderer2D → 표면 → 리소스 → 디바이스 → 윈도우. **역순이어야 하는 이유**는 의존 관계 때문입니다. 예를 들어 리소스(텍스처/버퍼)는 디바이스로 만들어졌으므로, 디바이스보다 먼저 정리되어야 합니다. 디바이스를 먼저 죽이면 리소스 해제가 이미 죽은 디바이스를 참조하게 됩니다.

## 6. 자주 묻는 질문

**Q. OnUpdate와 씬의 OnUpdate는 뭐가 다른가요?**
`Application::OnUpdate`는 앱 전역 훅(모든 씬 공통 — ESC 전역 종료 처리 등), `Scene::OnUpdate`는 현재 씬의 로직입니다. 순서는 Director가 씬을 먼저 돌리고(3단계의 `g_cDirector.Update`), 그다음 앱 훅이 불립니다.

**Q. vsync는 어디서 켜고 끄나요?**
`Present(vsync_)`의 인자입니다. true면 모니터 주사율에 맞춰 대기(화면 찢어짐 방지, 60fps 고정), false면 최대 속도로 돌립니다.

**Q. 서브 윈도우가 닫히면 어떻게 되나요?**
루프 4단계 `DestroyClosedSubWindows()`가 그리기 전에 씬/표면/메모리를 회수합니다. "그리기 전에!"라는 주석이 강조하듯, 죽은 표면에 그리는 사고를 막는 위치가 중요합니다.

## 7. 요약 — 기억할 다섯 문장

1. `Application`은 극장 지배인이다 — 부팅(Initialize), 심장 박동(Run), 폐관(Finalize)을 책임진다.
2. 부팅 순서는 의존 관계다: **창 → 디바이스 → 리소스(디폴트 포함) → 표면 → 렌더러 → 사운드 → 첫 씬 훅**.
3. 게임의 메시지 루프는 잠들지 않는 **PeekMessage** 방식이다 — 입력이 없어도 매 프레임 그린다.
4. 한 프레임 = **메시지 → Tick(dt) → Update(씬→앱) → 창마다 BeginFrame→Render→Present → 입력 NextFrame → 사운드 정리**.
5. dt는 정수 틱(jc::TimeSpan)으로 재고 250ms로 클램프한다 — float 정밀도 붕괴와 디버거발 순간이동을 모두 막는다.
