## 1. 이 장에서 배우는 것

**법선(Normal)**이 무엇이고 왜 필요한지, 람버트 확산광 공식 `saturate(dot(N, -L))`이 내적 하나로 밝기를 계산하는 원리, 그리고 큐브 정점이 8개가 아니라 면별 **24개**가 되어야 하는 이유를 배웁니다. 상수버퍼는 b0(변환) / b1(조명)으로 분리됩니다.

## 2. 실행하면 보이는 것

콘솔에 람버트 법칙 설명(`PrintLambertExplanation`)이 출력된 후, 800×600 창에서 **주황색 큐브**가 회전하며 빛을 받습니다.

- 빛은 오른쪽 위 뒤에서 대각선으로 내리쬐므로, 빛을 정면으로 받는 면은 밝고 반대편 면은 어둡게 보입니다.
- 큐브가 회전하면서 **면마다 밝기가 계속 바뀝니다** (빛은 고정, 물체만 회전).
- **↑ / ↓ 화살표**: 주변광(Ambient) 세기 0~1 실시간 조절. 0으로 내리면 빛이 안 닿는 면이 거의 검게 보입니다.
- **ESC**: 종료

주목할 점: 13장의 무지개 큐브는 면에 그라데이션이 있었지만, 이번 큐브는 면 하나가 **단색**입니다. 같은 면에 속한 4정점의 법선이 모두 같아 람버트 계산 결과가 면 전체에서 동일하기 때문입니다. 면과 면의 경계에서 밝기가 확 달라지는 모습에서 "법선이 면 단위로 다르다"는 의미를 눈으로 확인할 수 있습니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 법선은 "면이 바라보는 방향"을 가리키는 화살표

종이를 들고 불빛 아래로 돌려 보세요. 종이를 빛에 정면으로 향하면 밝고, 빛과 평행하게 세우면 어두워집니다. 이 밝기 변화는 **면의 방향과 빛의 방향이 이루는 각도**로 정해집니다. 면이 바라보는 방향(수직 방향)을 나타내는 단위 벡터가 **법선(Normal)**입니다.

### 3-2. 람버트 법칙 — "내적 하나로 밝기 계산"

01장에서 배운 내적(dot)의 성질: 두 단위 벡터가 같은 방향이면 1, 수직이면 0, 반대면 -1. 법선 N과 **빛이 오는 방향 -L**의 내적이 곧 "빛을 얼마나 정면으로 받는지"입니다.

- 빛을 정면으로 받는 면: dot(N, -L) = 1 → 가장 밝음
- 비스듬한 면: dot = 0.5 → 반만 밝음
- 빛을 등지는 면: dot = 음수 → 0으로 잘라냄 (saturate)

표면이 받는 빛의 양은 코사인 법칙을 따르므로, 이 계산을 **람버트 확산광**이라고 부릅니다.

### 3-3. 주변광 — 완전한 암흑 방지용 최소 밝기

빛을 전혀 받지 못하는 면은 새까맣게 보여 물체 모양이 사라져 버립니다. 실제 세계에서는 빛이 벽에 반사되어 퍼지므로 완전한 암흑이 없습니다. 이 **간접광을 흉내 내는 최소 밝기**가 주변광(Ambient)입니다. `↑/↓`로 이 값을 실시간 조절해 보세요.

### 3-4. 왜 정점이 24개인가? — 법선은 "면"의 속성

13장의 큐브는 꼭짓점 8개면 충분했습니다. 색은 꼭짓점마다 하나면 되니까. 하지만 **법선은 면마다 다릅니다** (위를 바라보는 윗면의 법선과 앞을 바라보는 앞면의 법선은 다름). 한 꼭짓점은 3개 면에 동시에 속하므로, 면마다 다른 법선을 주려면 **같은 위치의 정점을 면별로 3개로 복제**해야 합니다. 면당 4정점 × 6면 = **24개**, 인덱스는 그대로 36개입니다.

### 3-5. 비균등 스케일과 역전치 — 주석이 경고하는 함정

"법선은 w=0으로 변환한다"는 규칙은 **균등 스케일(모든 방향 같은 배율)**일 때만 정확합니다. 상자 하나를 생각해 보세요. 상자를 x 방향으로만 2배 늘리면, 원래 위를 향하던 윗면이 **비스듬히 기울어져** 보입니다. 이때 w=0으로 변환된 법선도 함께 기울어져 방향이 틀어집니다. 면을 늘리는 변환과 법선을 돌리는 변환은 다른 규칙을 따르기 때문입니다.

이 문제를 정확히 푸는 행렬이 **월드 행렬의 역전치(inverse-transpose)**입니다. 월드 행렬의 역행렬을 구한 뒤 전치한 행렬을 법선에 곱하면, 비균등 스케일이 있어도 법선이 항상 면에 수직을 유지합니다. 이 튜토리얼의 셰이더 주석이 "비균등 스케일이 있으면 역전치 행렬이 필요하다"고 경고하는 이유이며, 실전 엔진(24장 셰이딩 모델)에서는 CPU가 매 프레임 이 행렬을 계산해 넘깁니다. 주석의 경고가 왜 존재하는지 이해하면, 나중에 스케일이 이상한 물체의 조명이 깨지는 버그를 금방 진단할 수 있습니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 법선(Normal) | 면이 바라보는 방향의 단위 벡터 | 종이의 앞면 방향 화살표 |
| 람버트 법칙 | 밝기 = max(0, dot(N, -L)) | 빛과 면의 각도로 밝기 결정 |
| 확산광(Diffuse) | 거친 표면에서 사방으로 퍼지는 반사광 | 광택 없는 벽에 비치는 빛 |
| 주변광(Ambient) | 빛이 닿지 않는 곳의 최소 밝기 | 실내 전체의 은은한 간접광 |
| 내적(dot) | 두 벡터의 방향 일치도를 나타내는 값 | 두 화살표가 얼마나 나란한가 |
| saturate | 0~1 범위로 잘라내기 (음수 → 0) | "어둡긴 어두워도 0 미만은 없다" |
| 단위 벡터 | 길이 1로 정규화된 벡터 | 방향만 있는 화살표 |
| 정규화(normalize) | 길이를 1로 만들어 방향만 남기기 | 화살표 길이를 한 뼘으로 통일 |
| VertexPNT | 위치+법선+UV 정점 구조체 | 3D 조명용 정점 양식 |
| 역전치(Inverse-Transpose) | 비균등 스케일에서 법선을 바로잡는 행렬 변환 | 뒤틀린 화살표를 다시 바로 세우기 |
| 광원 방향(LightDir) | 빛이 오는 반대 방향의 단위 벡터 | 태양광이 내려오는 방향 화살표 |
| CbTransform / CbLight | 변환용/조명용으로 분리한 상수버퍼 구조체 | 전용 메뉴판 두 장 |
| 보간(Interpolate) | 정점 값 사이를 픽셀마다 부드럽게 채우는 과정 | 두 점 사이의 연필 이어 그리기 |
| saturate(dot(N, -L)) | 내적 결과를 0~1로 잘라 조명값으로 쓰기 | 어두운 면은 0으로 눌러 앉기 |
| VertexPC | 위치+색 정점 구조체 (이전 2D 시절) | 2D용 정점 양식 |

표의 "CbTransform / CbLight 분리"가 이 장의 구조적 결실입니다. 조명 데이터는 물체가 무엇이든 동일하므로 b1 한 번 업로드로 모든 물체에 쓸 수 있고, 이 분리가 이후 장에서 오브젝트별/프레임별 업데이트 규약의 뼈대가 됩니다.

auto AddFace = [&](const vec3& _normal, const vec3& _right, const vec3& _up)
{

    _pOutVertices24[v + 2] = { center - (_up + _right) * 0.5f, _normal, vec2(0.0f, 1.0f) };

    // 삼각형 2개 (바깥에서 볼 때 시계 방향)

### 4단계: 람버트 셰이더 — 핵심 한 줄

```hlsl
cbuffer CbTransform : register(b0)
{
    row_major float4x4 gWorld;
    row_major float4x4 gWorldViewProj;
};

cbuffer CbLight : register(b1)
{
    float3 gLightDir;   // 빛이 나아가는 방향 (정규화됨)
    float  gAmbient;
    float4 gBaseColor;
};

VSOutput VSMain(VSInput _input)
{
    output.position = mul(float4(_input.position, 1.0f), gWorldViewProj);
    // 법선은 '방향'이므로 w = 0으로 변환한다. (이동 성분 무시)
    // 주의: 비균등 스케일이 있으면 역전치 행렬이 필요하지만,
    //       이 튜토리얼은 균등 스케일만 쓰므로 월드 행렬을 그대로 써도 된다.
    output.worldNormal = normalize(mul(float4(_input.normal, 0.0f), gWorld).xyz);
    return output;
}

float4 PSMain(VSOutput _input) : SV_TARGET
{
    float3 normal = normalize(_input.worldNormal);   // 보간으로 길이 왜곡 보정
    float diffuse = saturate(dot(normal, -gLightDir));  // ★ 람버트 핵심
    float lighting = saturate(gAmbient + diffuse * (1.0f - gAmbient));
    return float4(gBaseColor.rgb * lighting, gBaseColor.a);
}
```

- VS는 법선에 w=0을 넣어 **이동 성분을 제거**한 뒤 월드 행렬로 변환합니다.
- PS는 보간을 거쳐 길이가 틀어진 법선을 **다시 normalize**한 후 `dot(normal, -gLightDir)`로 밝기를 구합니다.

### 5~6단계: 렌더 루프 — 주변광 조절과 바인딩

```cpp
// ↑↓로 주변광 조절 (누르고 있는 동안 연속 변화)
if (input.IsKeyDown(VK_UP))   { ambient = Clamp(ambient + 0.5f * dt, 0.0f, 1.0f); }
if (input.IsKeyDown(VK_DOWN)) { ambient = Clamp(ambient - 0.5f * dt, 0.0f, 1.0f); }

const mat4 world = mat4::RotationY(elapsed * 0.8f) * mat4::RotationX(elapsed * 0.3f);

CbTransform cbT = {};
cbT.world_ = world;
cbT.worldViewProj_ = world * view * proj;
cbTransform.UpdateAndBind(&device, cbT, 0);   // register(b0)

CbLight cbL = {};
cbL.lightDir_ = vec3(-0.5f, -0.7f, 0.5f).Normalized();   // 오른쪽 위 뒤 → 왼쪽 아래 앞
cbL.ambient_ = ambient;
cbL.baseColor_ = color(0.9f, 0.6f, 0.2f, 1.0f);           // 주황색 큐브

```

빛 방향은 `Normalized()`로 정규화된 상수로, **큐브만 회전**하므로 면의 밝기가 계속 바뀝니다. 주변광 조절은 `IsKeyDown` 폴링이라 키를 누르고 있는 동안 초당 0.5씩 변하며, `Clamp`가 0~1 범위를 보장합니다. `0.5f * dt` 형태 덕분에 60FPS든 144FPS든 "1초에 반만큼 변하는" 속도가 유지되는데, 이는 11장에서 배운 프레임 독립 움직임의 또 다른 적용입니다.

루프에는 눈에 보이지 않는 상수 갱신이 두 번 있습니다. `cbTransform.UpdateAndBind`는 월드+WVP 행렬 2개(128바이트)를, `cbLight.UpdateAndBind`는 조명 데이터(32바이트)를 업로드합니다. 이 두 갱신이 "상수버퍼 슬롯 분리"의 실제 사례이며, 큐브가 하나뿐이라 효과가 잘 안 보이지만 물체가 수백 개가 되면 슬롯 분리 덕분에 조명 버퍼를 다시 업로드하지 않아도 되는 경우가 생깁니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. 람버트 연산의 하드웨어 단계

`dot(normal, -gLightDir)`은 픽셀 셰이더에서 **3번의 곱셈-덧셈(FMA)**입니다. GPU의 SM(셰이더 멀티프로세서)은 이를 스칼라/벡터 FMA 유닛에서 처리하며, 한 픽셀의 조명은 몇 사이클에 끝나기 때문에 조명 계산 자체는 거의 공짜입니다. 병목은 대부분 픽셀 수 × 메모리 접근입니다. 람버트 조명이 "가장 저렴한 조명 모델"이라 불리는 이유입니다.

### 6-2. 법선 변환의 수학적/하드웨어적 이유 — w=0 트릭

점(position)은 이동이 적용되어야 하므로 w=1로 변환하지만, 법선은 **방향이므로 이동에 면역**이어야 합니다. `mul(float4(normal, 0), gWorld)`에서 w=0이 이동 열의 기여를 정확히 소거합니다. 이것은 행렬 곱을 수행하는 벡터-행렬 곱 하드웨어의 4성분 연산 하나로 두 경우를 모두 커버하는 트릭입니다.

단, 이 트릭은 **균등 스케일(같은 배율)**일 때만 정확합니다. 비균등 스케일(예: x만 2배)로 면을 찌그러뜨리면 법선의 방향이 어긋나므로 **월드 행렬의 역전치(inverse-transpose)**가 필요합니다. 소스 주석이 이 사실을 경고합니다. 역전치는 4x4 역행렬 + 전치로 셰이더 상수로서 CPU에서 계산해 넘겨주며, 실전 엔진(24장 셰이딩 모델)에서는 이를 반영합니다.

이 w=0 트릭은 하드웨어 관점에서도 경제적입니다. VS는 위치와 법선을 각각 한 번의 벡터-행렬 곱으로 변환하는데, 두 변환 모두 같은 행렬(월드)을 사용하므로 상수 레지스터는 한 번만 로드해 재사용합니다. 위치용으로는 `gWorldViewProj`, 법선용으로는 `gWorld`를 따로 쓰지만, 셰이더가 멤버로 접근할 때 상수 캐시는 이미 두 행렬을 보유하고 있습니다. 128바이트(CbTransform)는 상수 캐시에 여유롭게 들어가는 크기입니다.

### 6-3. 보간된 법선의 재정규화 — 래스터라이저 보간의 부작용

VS가 만든 법선은 **정점 단위** 값이고, 삼각형 내부 픽셀은 래스터라이저가 세 정점 값을 **투영 보간(interpolation)**으로 섞어 받습니다. 래스터라이저의 보간 하드웨어는 픽셀 좌표 기반 가중치(바리센트릭)를 계산해 세 정점의 법선을 가중 평균하므로, 결과 벡터의 길이는 1이 아닐 수 있습니다. 그래서 PS가 `normalize()`로 한 번 더 길이를 맞춥니다. 이 재정규화는 3D 벡터의 제곱근-역수 연산 1회(RSQ)로 매우 저렴합니다.

### 6-4. 상수버퍼 슬롯 분리의 하드웨어 의미

b0(변환, 128B)와 b1(조명, 32B)을 나누면 매 프레임 **조명 값이 바뀌지 않아도 되는** 물체는 b1을 다시 업로드하지 않아도 됩니다. 하드웨어 관점에서 상수버퍼는 스테이지별 상수 레지스터 뱅크의 슬롯이고, 각 슬롯은 별도 메모리 매핑이므로 **한 슬롯만 갱신**하는 것은 상수 캐시의 일부 라인만 무효화합니다. 전부 한 버퍼에 구겨 넣었다면 전체 160B를 매번 다시 쓰고 캐시 라인 전체를 뒤흔들었을 것입니다. v3의 슬롯 규약은 이 하드웨어 캐시 동작과 정확히 맞물립니다.

### 6-5. 24정점 큐브와 정점 캐시 효율

면별로 복제된 24정점은 위치가 3번씩 중복되므로 IA 정점 캐시의 재사용률이 13장(8정점)보다 떨어지지만, 면 단위로 그리므로 캐시 손실은 작습니다. 실전에서는 정점이 공유되지 않는 스키닝 메시 등에서 이 문제가 커지며, 이를 줄이는 다양한 인덱스/캐시 최적화 기법이 있습니다. UV도 면마다 0~1로 배치되어 이후 텍스처 단계(15장)에서 바로 사용할 수 있습니다.

### 6-6. seturate와 비교 — 하드웨어 비교기

`saturate`는 0 미만은 0, 1 초과는 1로 자르는 클램프 연산으로, GPU의 산술 유닛에 내장된 **min/max 하드웨어**로 1 사이클에 처리됩니다. `gAmbient + diffuse * (1 - gAmbient)`로 주변광이 확산광을 밀어내는 비율을 보간한 뒤, 최종적으로 baseColor에 곱해 ROP로 보내집니다.

### 6-7. 픽셀당 연산량 — 람버트 셰이더는 왜 "싼" 셰이더인가

이 셰이더의 PS는 픽셀마다 대략 **RSQ(재정규화) 1회 + FMA(내적) 3회 + min/max 2회 + 곱셈 4회** 정도를 수행합니다. 1080p 화면이 약 200만 픽셀이고, 큐브가 20만 픽셀을 덮는다고 하면, 조명 연산은 SM의 산술 유닛(클럭당 수십~수백 개 연산)으로 1ms 안에 끝납니다. 이것이 "람버트는 가장 싼 조명"이라고 하는 하드웨어적 근거이며, 픽셀 수가 늘어나도 병목은 대부분 텍스처 캐시나 ROP 대역폭이지 조명 연산이 아닙니다.

주의할 점 하나: 셰이더 상수는 기본적으로 float32 정밀도지만, GPU가 중간 연산을 float16으로 처리하는 경우(일부 모바일/저전력 경로) 법선 내적의 정밀도가 떨어질 수 있습니다. 이 튜토리얼은 학습 환경(PC, float32)이므로 문제없지만, 나중에 고성능 모바일 최적화를 만나면 "중간 연산 정밀도"가 밴딩(banding) 현상의 원인이 되는 것을 기억해 두세요.

### 6-8. CbLight의 패킹 — vec3 + float가 16바이트가 되는 이유

`CbLight { vec3 lightDir_; _f32 ambient_; color baseColor_; }`는 12바이트(vec3) + 4바이트(float) = 16바이트가 먼저 채워지고, 그다음 color가 16바이트 칸을 차지해 총 32바이트입니다. HLSL 쪽도 `float3 gLightDir; float gAmbient;`가 정확히 같은 16바이트 칸을 공유합니다. 이 배열은 12장에서 배운 16바이트 정렬 규칙의 자연스러운 응용입니다 — `float3 + float` 조합이 한 칸을 정확히 채우는 lucky 패턴입니다. 만약 순서가 `vec3, vec3, float`였다면 여백이 생겨 셰이더와 어긋났을 것입니다. 상수버퍼를 만들 때는 "HLSL과 C++의 멤버 순서가 정확히 같은지"를 항상 확인하는 습관이 필요합니다.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| 람버트 공식 | `diffuse = saturate(dot(N, -L))` — 내적 하나가 밝기 |
| 법선 방향 | `-gLightDir` = 표면에서 빛을 향하는 방향으로 뒤집어 내적 |
| 정점 수 | 면마다 법선이 다르므로 4정점 × 6면 = 24개 (8개 아님) |
| 법선 변환 | w=0으로 이동 제거, 비균등 스케일이면 역전치 필요 |
| 재정규화 | PS에서 `normalize(worldNormal)` — 보간 길이 왜곡 보정 |
| 주변광 | `lighting = saturate(ambient + diffuse * (1 - ambient))` |
| 슬롯 분리 | b0 = 변환(월드+WVP), b1 = 조명(방향/주변광/색) |
| 조작 | ↑↓로 `Clamp(ambient ± 0.5*dt, 0, 1)` 실시간 조절 |
| UV 배치 | AddFace가 UV 0~1을 면마다 함께 배치 (15장 준비) |
| 가격 | PS당 RSQ 1 + FMA 수 개 — 가장 싼 조명 모델 |
| 패킹 | CbLight = vec3+float(16B) + color(16B) = 32B — 정렬 규칙 준수 |
| 역전치 | 비균등 스케일 시 법선 행렬 = world의 역전치 필요 |

표의 핵심 한 줄은 "람버트 = max(0, dot(N, -L))"입니다. 이 공식은 이후 셰이딩 모델(24장)에서 하이라이트·스펙큘러를 더하는 형태로 확장될 뿐, 뼈대는 그대로입니다. 조명값이 상수버퍼(빛 방향·주변광)와 정점(법선) 두 곳에서 온다는 사실도 함께 기억해 두세요. 셰이더가 "어디서 무엇을 읽는지"를 구분하는 습관이 곧 디버깅 실력입니다.

주변광 실험(↑↓ 키)도 의미 있게 되새길 만합니다. 주변광은 아무 방향도 아닌 "최소 밝기"이므로 람버트 공식의 계산 범위를 벗어나 있고, 그래서 별도의 상수로 존재합니다. 0으로 내리면 밤이 되고, 1로 올리면 모든 면이 균일해지는 것을 보면서 "확산광과 주변광은 더해지는 두 개의 독립된 항"이라는 인식이 정확히 박히게 됩니다. 또한 `Clamp` 덕분에 키를 계속 눌러도 범위를 벗어나지 않아, 상태가 안전하게 유지되는 것도 함께 관찰해 보세요. 빛 한 줄, 법선 24개, 상수 3개로 만들어 낸 이 조명이 이후 모든 조명 이론의 출발점이라는 점을 기억하며 장을 마칩니다. 다음 장에서는 텍스처가 등장해 표면에 색을 입힙니다. 조명과 텍스처가 만나면 표면이 훨씬 사실적으로 보입니다.
