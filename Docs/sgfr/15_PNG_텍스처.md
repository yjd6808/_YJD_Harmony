# 15. PNG 텍스처 — 파일에서 화면까지, UV 좌표계와 알파 블렌딩

> 관련 코드: `Projects/sgfr/Sources/sgfr/15_PngTextureDraw/15_PngTextureDraw_Main.cpp`, `15_PngTextureDraw_Function.cpp`
> (엔진: `Projects/sgf/Sources/sgf/Graphics/Texture.h` — WIC 로더, `Common/TutorialCommon.cpp` — TextureShaderSource)
> 실행: sgfr 실행 후 콘솔 메뉴에서 **15번** 선택
> 선행 학습: 07(정점/인덱스), 12(상수버퍼), 14(VertexPNT/UV 맛보기)

## 1. 이 장에서 배우는 것

PNG 파일이 화면에 나타나는 **전 과정** — 파일 → WIC 디코더 → RGBA 픽셀 배열 → GPU 텍스처 → UV 샘플링 — 을 배우고, UV 좌표계(0~1)와 알파 블렌딩(반투명)을 처음 도입합니다.

## 2. 실행하면 보이는 것

콘솔에 UV 좌표계 설명(`PrintUvExplanation`)이 출력된 후, 800×600 창의 정중앙에 이미지가 나타납니다.

- **`Resources\sample.png` 파일이 있으면**: 그 이미지가 그대로 표시됩니다.
- **파일이 없으면**: CPU로 직접 만든 **체커보드 텍스처**(256×256)가 대신 표시되며, 콘솔에 "sample.png가 없어 체커보드 텍스처로 대체합니다" 안내가 나옵니다.

ESC로 종료.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 이미지는 "물감을 칠할 벽지"다

지금까지 사각형은 정점 색(물감)으로 칠했습니다. 이제 **벽지(텍스처)**를 붙입니다. 삼각형을 그릴 때, 삼각형의 각 정점에 "벽지의 어느 지점을 붙일지"를 지정해 주고(UV), 래스터라이저가 그 사이를 보간해 **픽셀마다 벽지의 색을 뜯어 옮겨 붙입니다(샘플링)**.

### 3-2. UV — 해상도와 무관한 벽지 좌표

벽지의 왼쪽 위가 항상 (0,0), 오른쪽 아래가 항상 (1,1)이라고 약속하면, 벽지가 256×256이든 4000×3000이든 **같은 좌표로 위치를 지정**할 수 있습니다. 이것이 UV 좌표계입니다. 크기(픽셀 수)가 아니라 **비율**로 위치를 나타내는 좌표입니다.

**주의**: UV의 (0,0)은 왼쪽 **위**입니다. NDC(11장)에서 y가 위로 갈수록 커지는 것과 반대로, UV는 y가 아래로 갈수록 커집니다. 방향을 헷갈리면 이미지가 뒤집혀 보입니다.

구체적인 예를 보면: 이 튜토리얼의 왼쪽 위 정점은 `vec2(0.0f, 0.0f)`이고 오른쪽 아래 정점은 `vec2(1.0f, 1.0f)`입니다. 삼각형 내부의 픽셀은 래스터라이저가 이 두 값 사이를 비율로 보간하므로, 화면의 어느 픽셀을 그리든 "텍스처의 어느 지점을 떼어 붙일지"가 항상 정확히 정해집니다. UV가 (0.25, 0.5)라면 텍스처 왼쪽에서 4분의 1 지점, 위에서 절반 지점의 색이 그 픽셀의 색이 됩니다.

### 3-3. 알파 블렌딩 — 투명한 벽지

PNG는 알파(투명도) 채널을 갖습니다. 그냥 그리면 반투명 픽셀이 배경을 **덮어써 버리고**, 올바르게는 기존 색과 섞어야 합니다. 알파 블렌딩 공식:

```
최종색 = 새색 × 알파 + 배경색 × (1 - 알파)
```

알파 0이면 배경색이 그대로, 알파 1이면 새색이 그대로, 알파 0.5면 반반 섞입니다. 이 공식을 GPU에 켜 주는 것이 `device.SetAlphaBlending(true)`입니다.

### 3-4. 파일 → 화면까지의 파이프라인

```
PNG 파일 → [WIC 디코더] → RGBA 픽셀 배열 → [GPU 텍스처] → [UV로 샘플링] → 화면
```

WIC(Windows Imaging Component)는 윈도우 내장 이미지 디코더라 별도 라이브러리 없이 PNG/JPG/BMP를 읽을 수 있습니다.

### 3-5. 체커보드 만들기 — CPU가 픽셀을 찍는 법

이 튜토리얼은 PNG가 없어도 동작하도록 **CPU로 픽셀을 직접 그리는** 대체 경로를 갖고 있습니다. `((x / cell) + (y / cell)) % 2` 공식은 "픽셀의 칸 번호 합이 짝수면 밝은 칸, 홀수면 어두운 칸"이라고 판정합니다. `x / cell`은 x 좌표를 32픽셀 단위로 나눈 칸 번호이므로, 바둑판 무늬가 완성됩니다. 이렇게 **그냥 배열에 색을 채우는 것만으로 이미지를 만들 수 있다**는 사실은 나중에 16장의 대체 텍스처, 그리고 절차적 텍스처/노이즈 생성 등에서 다시 등장하는 아이디어입니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 텍스처(Texture) | 삼각형에 붙이는 이미지 데이터 | 벽지 |
| UV 좌표 | 텍스처 위의 0~1 비율 좌표, (0,0)=왼쪽 위 | 벽지의 구역 비율 |
| 샘플링(Sampling) | UV 위치의 텍스처 색을 읽어 오기 | 벽지에서 색 뜯어 오기 |
| WIC | 윈도우 내장 이미지 디코더 라이브러리 | 이미지 해석기 |
| 디코딩 | 압축된 이미지 파일을 픽셀 배열로 풀기 | 보물상자 열기 |
| RGBA | 빨강·초록·파랑·투명도 4채널 픽셀 포맷 | 4색 물감 세트 |
| 알파(Alpha) | 투명도 (0=완전 투명, 1=완전 불투명) | 유리창의 투명도 |
| 알파 블렌딩 | 새색×알파 + 배경색×(1-알파) 합성 공식 | 물감 섞기 |
| 틴트(Tint) | 텍스처 색에 곱하는 추가 색 | 색안경 끼우기 |
| SRV | 셰이더가 텍스처를 읽도록 하는 뷰 객체 | 벽지 열람권 |
| PSSetShaderResources | PS 스테이지 t0 슬롯에 텍스처를 장착하는 호출 | 벽지 설치 작업 |
| 프레임버퍼 | 화면에 그려질 최종 색을 담는 버퍼 | 최종 캔버스 |
| read-modify-write | 읽고→섞고→다시 쓰는 블렌딩의 메모리 접근 | 기존 그림 위에 덧칠 |
| 알파 채널 | 픽셀당 투명도 성분 (PNG가 가진 4번째 값) | 유리의 투명도 기록 |
| 틴트 색 | 정점 색으로 텍스처 색에 곱해지는 색 | 셀로판지 필터 |

표의 첫 줄(SRV)은 "텍스처 데이터와 셰이더를 연결하는 열람권"이라는 이미지로 기억하면, 이후 20장(머티리얼)에서 같은 패턴이 반복되는 것을 쉽게 알아볼 수 있습니다. 텍스처 하나마다 데이터(Texture2D)와 열람권(SRV)이 쌍을 이룬다는 것만 기억하세요.

## 5. 코드 워크스루

`PngTextureDraw_Main()`의 흐름입니다.

### 1~2단계: 텍스처 2단계 폴백

```cpp
Texture texture;
if (texture.LoadFromFile(&device, L"Resources\\sample.png"))
{
    printf("Resources\\sample.png 로드 성공! (%d x %d)\n", texture.Width(), texture.Height());
}
else if (CreateCheckerboardTexture(&device, &texture))
{
    printf("sample.png가 없어 체커보드 텍스처로 대체합니다. (%d x %d)\n", ...);
}
```

- `Texture::LoadFromFile(&device, 경로)`가 내부적으로 **WIC**로 파일을 디코딩합니다 (32bpp RGBA 포맷 변환 포함). 함수가 하는 일을 풀어 보면: WIC 팩토리 생성 → `CreateDecoderFromFilename`으로 PNG 열기 → `GetFrame(0)`으로 이미지 획득 → `CreateFormatConverter`로 32bpp RGBA로 변환 → `CopyPixels`로 픽셀 배열 복사 → `CreateTexture2D`로 GPU 텍스처 생성 → `CreateShaderResourceView`로 SRV 획득, 순서입니다. 파일 이름이 `wchar_t*`(유니코드)인 것도 Windows API 표준이라 눈여겨보세요.
- 없으면 `CreateCheckerboardTexture`가 CPU에서 체커보드 픽셀을 직접 만들어 `Texture::CreateFromMemory(&device, pixels, 256, 256)`로 GPU 텍스처를 만듭니다:

```cpp
// 체커보드 판정: 칸 좌표의 합이 짝수면 밝은 칸, 홀수면 어두운 칸
const bool bLight = (((x / cell) + (y / cell)) % 2) == 0;
const int idx = (y * size + x) * 4;
pixels[idx + 0] = bLight ? 235 : 60;    // R
pixels[idx + 1] = bLight ? 235 : 120;   // G
pixels[idx + 2] = bLight ? 235 : 200;   // B
pixels[idx + 3] = 255;                  // A (불투명)
```

256×256 = 65536 픽셀 × 4바이트 = 262144바이트의 RGBA 배열을 직접 만듭니다.

### 3단계: UV가 포함된 정점 — VertexPTC

```cpp
const _f32 aspect = window.AspectRatio();
const _f32 halfW = 0.5f;
const _f32 halfH = 0.5f * aspect;   // 화면 비율 보정으로 정사각형 유지

const VertexPTC vertices[] = {
    { vec3(-halfW, +halfH, 0.0f), vec2(0.0f, 0.0f), color::White() },  // 왼쪽위
    { vec3(+halfW, +halfH, 0.0f), vec2(1.0f, 0.0f), color::White() },  // 오른쪽위
    { vec3(-halfW, -halfH, 0.0f), vec2(0.0f, 1.0f), color::White() },  // 왼쪽아래
    { vec3(+halfW, -halfH, 0.0f), vec2(1.0f, 1.0f), color::White() },  // 오른쪽아래
};
const _u32 indices[] = { 0, 1, 2, 2, 1, 3 };
```

`VertexPTC`(위치+UV+색)에서 UV가 텍스처의 어느 부분을 붙일지를 결정합니다. 틴트는 `color::White()`라 곱해도 원본 그대로입니다.

### 4단계: 텍스처 셰이더 — TutorialCommon에서 재사용

```hlsl
Texture2D    gTexture : register(t0);   // 텍스처 (C++ Texture::Bind의 slot 0)
SamplerState gSampler : register(s0);   // 샘플러 (GraphicDevice가 자동 바인딩)

VSOutput VSMain(VSInput _input)
{
    output.position = float4(_input.position, 1.0f);   // NDC 그대로 통과
    output.uv = _input.uv;
    output.color = _input.color;
    return output;
}

float4 PSMain(VSOutput _input) : SV_TARGET
{
    return gTexture.Sample(gSampler, _input.uv) * _input.color;
}
```

`TextureShaderSource()`(TutorialCommon.cpp)는 NDC를 통과시키고 PS에서 `Sample`로 텍스처 색을 읽어 틴트와 곱합니다.

### 5단계: 알파 블렌딩 + 렌더 루프

```cpp
device.SetAlphaBlending(true);   // 반투명/투명 픽셀이 올바로 섞이도록

// 루프 안:
texture.Bind(&device, 0);        // PS의 t0 슬롯에 장착
vb.Bind(&device); ib.Bind(&device); shader.Bind(&device);
device.Context()->DrawIndexed(6, 0, 0);
```

`Texture::Bind(&device, 0)`은 내부적으로 SRV(ShaderResourceView)를 PS 스테이지 t0 슬롯에 바인딩합니다. 루프는 매우 단순합니다 — 텍스처 바인딩 → 정점/인덱스/셰이더 바인딩 → DrawIndexed(6) 4줄뿐입니다. 행렬을 전혀 쓰지 않는 이유는 이 장의 정점이 이미 NDC 좌표로 준비되어 있고(10장 이전의 방식), 셰이더도 NDC를 통과시키기만 하기 때문입니다. 텍스처가 화면 가운데 고정되어 그려지는 것을 확인하면, "행렬 없이도 그릴 수 있는" NDC 직결 방식과 "행렬로 배치하는" 이후 방식의 차이를 대비해 볼 수 있습니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. WIC 디코딩은 CPU 작업 — GPU는 픽셀만 받는다

`LoadFromFile` 내부에서 WIC는 `CreateDecoderFromFilename` → `GetFrame(0)` → `CreateFormatConverter` → 32bpp RGBA로 변환 → `CopyPixels` 순서로 **CPU에서** PNG를 픽셀 배열로 풉니다. PNG는 zlib 압축이라 CPU 디코딩은 수 밀리초가 걸릴 수 있습니다. 이후 `CreateTexture2D`로 **GPU 메모리(보통 VRAM)에 텍스처를 만들고** `CreateShaderResourceView`로 SRV를 얻습니다. 파일 읽기→디코딩→업로드는 CPU+메모리 버스를 거치는 무겁고 일회성인 작업이므로, 실전에서는 로딩 화면에서 미리 수행하고 캐시(21장 리소스 매니저)합니다.

### 6-2. 텍스처 저장 형식과 메모리

체커보드는 R8G8B8A8_UNORM(RGBA 8비트×4)으로 업로드되어 **픽셀당 4바이트**, 256×256 = 256KB입니다. 이 텍스처는 렌더 타깃이 아니라 샘플 전용이므로, GPU는 `D3D11_USAGE_IMMUTABLE` 계열로 CPU 재접근을 막고 **압축 텍스처 포맷(BC1~BC7)**으로 저장할 수도 있습니다(실제로는 CreateFromMemory가 픽셀 데이터를 그대로 넣습니다). 텍스처 메모리는 GPU의 전용 메모리(VRAM)에 상주하며, 샘플링 시 텍스처 캐시 계층(L1 텍스처 캐시 → L2)을 통해 읽힙니다.

### 6-3. 샘플링 하드웨어 — 텍스처 유닛(TMU)

`gTexture.Sample(gSampler, uv)`는 픽셀 셰이더가 직접 하는 연산이 아니라 **텍스처 유닛(TMU/Texture Mapping Unit)**이라는 GPU 전용 하드웨어가 담당합니다. TMU는:

1. 보간된 UV를 텍셀 주소로 변환 (mipp와 필터 설정 반영)
2. 주변 텍셀들을 읽고 (필터가 Linear면 4개, Point면 1개)
3. 비율대로 가중 평균해 색을 반환

이 과정은 셰이더 유닛과 병렬로 동작하며, 셰이더는 TMU가 결과를 가져다줄 때까지 다른 명령을 실행할 수 있습니다. UV는 정점 사이에서 **보간**되어 들어오므로, 삼각형이 크면 하나의 픽셀 셔드가 읽는 UV가 서로 달라 TMU 병렬 처리로 자연스럽게 해결됩니다. `color::White()` 틴트 곱셈(색×텍셀)은 별도의 곱셈 유닛에서 1사이클입니다.

### 6-4. 알파 블렌딩 — ROP의 혼합 연산

`SetAlphaBlending(true)`가 내부에서 바인딩하는 블렌드 상태는 `SrcBlend=SRC_ALPHA, DestBlend=INV_SRC_ALPHA`입니다. ROP(Output Merger)가 매 픽셀:

```
src.a = 0.5 → final = 0.5×src + 0.5×dst
```

을 계산합니다. 8비트 채널에서 반올림 오차가 생기므로, 반투명을 여러 번 겹칠수록 밝기 오차가 누적될 수 있습니다. 또한 블렌딩은 프레임버퍼의 기존 색을 **읽어야 하므로**(read-modify-write) 메모리 대역폭이 2배가 되고, ROP의 혼합 유닛이 추가 연산을 수행합니다. 이 비용이 "블렌딩은 가능하면 끄고 쓴다"는 관례의 이유입니다.

반투명을 올바로 그리려면 **뒤에 있는 것부터 그려야** 합니다. 블렌딩 공식이 "기존 색 위에 새 색을 얹는" 것이기 때문에, 순서가 뒤집히면 뒤쪽 물체가 앞쪽 물체를 투과해서 보이게 됩니다. 이 장은 이미지 한 장뿐이라 순서 문제가 없지만, 여러 반투명 물체가 등장하는 실전(예: 유리창 여러 개)에서는 **깊이 순 정렬 후 뒤부터 그리기**가 필수입니다. 13장에서 배운 깊이 테스트는 불투명 물체의 앞뒤만 해결할 뿐, 반투명은 별도 정렬이 필요하다는 것을 기억해 두세요. 18장에서 블렌드 상태를 세부 조절하며 이 주제를 다시 만납니다.

### 6-5. UV 방향과 텍스처 뒤집기

UV (0,0) = 왼쪽 위, v 증가 = 아래 방향인 것은 D3D 텍스처 좌표계의 관례입니다. 반면 NDC는 y 증가 = 위 방향이므로, 11장의 화면 좌표 계산과 UV를 그대로 연결하면 이미지가 상하로 뒤집힙니다. 이 튜토리얼은 정점의 y와 UV를 각각 독립적으로 지정해 UV의 위/아래를 정점 위치에 맞춰 적었습니다. 이 "텍스처 좌표계 뒤집힘" 문제는 엔진마다 로더/임포트 단계에서 처리하며, 실전에서 이미지가 뒤집혀 보이는 버그의 절반이 여기서 발생합니다.

### 6-6. 샘플러 — 필터링의 예고

셰이더의 `SamplerState gSampler : register(s0)`는 이 장에서 GraphicDevice가 기본 샘플러를 자동 바인딩해 줍니다. 샘플러는 "확대/축소할 때 픽셀 사이를 어떻게 메울지"(Linear/Point), "UV가 0~1을 벗어나면 어떻게 할지"(Clamp/Wrap/Mirror)를 결정하는 **텍스처 유닛 설정**입니다. 이 장의 체커보드는 해상도가 정확히 맞아 필터의 차이가 거의 안 보이지만, 17장에서 확대/축소하며 이 하드웨어 옵션을 직접 눈으로 비교합니다.

### 6-7. Mipmap과 밉 체인 — 축소 시 생기는 반짝임 문제

텍스처를 화면보다 작게 그리면(축소), 한 픽셀이 텍셀 여러 개를 덮게 됩니다. 이때 Linear 필터는 그중 4개만 골라 섞으므로, 먼 곳의 바닥이 반짝거리는 모아레(moire) 현상이 생길 수 있습니다. 이를 막는 하드웨어 장치가 **Mipmap(밉맵)**입니다 — 같은 텍스처를 1/2, 1/4, 1/8…로 미리 축소한 사본 체인을 만들어 두고, 픽셀이 덮는 영역 크기에 따라 적절한 단계를 골라 샘플링합니다. 이 튜토리얼은 화면 크기와 텍스처 크기가 비슷해 밉맵이 필요 없지만, 실전 텍스처는 대부분 밉맵을 함께 만들어 둡니다. GPU는 밉맵 체인을 텍스처 메모리(보통 원본의 3분의 1 추가)에 저장하고, 샘플링 시 텍셀의 밉 단계를 계산하는 전용 하드웨어를 갖습니다.

### 6-8. SRV — 텍스처 "보는 방법"도 객체다

GPU 텍스처 객체 그 자체는 "픽셀 덩어리"일 뿐입니다. 셰이더가 샘플링하려면 **ShaderResourceView(SRV)**라는 뷰 객체가 필요합니다. `Texture::Bind`가 묶는 것은 바로 이 SRV입니다. SRV는 "이 텍스처를 어떤 포맷으로, 어느 영역을, 어느 밉 단계까지 읽을 수 있는지"를 담는 일종의 열람권입니다. 같은 텍스처를 다른 포맷으로 해석하는 SRV를 여러 개 만들 수도 있어서(예: 하나는 RGBA, 하나는 각 채널별), 렌더 타깃(25장)과 그림자 맵(27장) 등에서 이 개념이 중요해집니다. 지금은 "텍스처 = 데이터, SRV = 열람권"이라는 두 층 구조만 기억해 두세요.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| 변환 체인 | PNG → WIC 디코딩 → RGBA → GPU 텍스처 → SRV → 샘플링 |
| 폴백 구조 | `LoadFromFile` 실패 시 `CreateCheckerboardTexture`로 대체 |
| UV 관례 | (0,0) = 왼쪽 위, y 증가 = 아래 (NDC와 반대!) |
| UV는 비율 | 해상도와 무관한 0~1 정규화 좌표 |
| 알파 블렌딩 | `final = 새색×알파 + 배경색×(1-알파)` |
| 틴트 | `Sample(uv) * color` — 흰색이면 원본 그대로 |
| 바인딩 | `texture.Bind(&device, 0)` = PS t0 슬롯 |
| 셰이더 재사용 | `TextureShaderSource()`는 TutorialCommon 공용 |
| 메모리 | RGBA 8비트 = 픽셀당 4바이트 (256×256 = 256KB) |
| 체커보드 공식 | `((x/cell) + (y/cell)) % 2` — 칸 번호 합의 홀짝으로 색 결정 |
| SRV | 텍스처의 "열람권" — 포맷/영역/밉 단계 정의 (25/27장에서 확장) |
| 밉맵 | 축소 시 반짝임 방지용 사전 축소 사본 체인 (17장에서 체험) |

표의 핵심 개념은 "텍스처 = 벽지, UV = 벽지 좌표"라는 이미지입니다. 샘플링이 어떻게 일어나는지는 17장에서 필터(Point/Linear)와 주소 모드(Wrap/Clamp/Mirror)를 직접 바꿔 보며 체감하게 됩니다. 그리고 알파 블렌딩의 공식은 18장에서 블렌드 스테이트 구조체를 직접 조절하며 심화됩니다. 이 장에서 만든 "알파 = 셰이더가 만든 최종 색의 일부"라는 관점을 유지하면 18장의 실험이 훨씬 명확해집니다.

또 하나, 이 장의 이미지 로딩 경로를 다시 따라가 보세요. `LoadFromPngFile` → WIC 디코더 → 픽셀 배열 → `CreateTexture2D` → SRV 생성 → PS t0 슬롯 바인딩까지, 파일 하나가 화면에 나타나기까지 다섯 단계를 거칩니다. 이 단계 중 어느 하나가 빠지거나 순서가 바뀌면 화면은 비어 있습니다. 21장(리소스 매니저)이 이 경로를 자원 관리 체계(경로→키→캐시)로 확장하므로, "로딩 경로"를 하나의 흐름으로 기억해 두면 그 장에서 시작 지점을 찾기 쉽습니다. 그리고 이 장에서 행렬을 쓰지 않았다는 사실 — 정점이 이미 NDC 좌표라는 점 — 을 10장의 행렬 방식과 대비해 보면, 이후 20장의 머티리얼이 두 세계를 합치는 방법도 예측할 수 있습니다.

체커보드의 구조도 다시 한 번 보세요. 8×8 격자에 검정과 흰색이 교대로 배치되어 있고, 어느 것이 "알파 255"인지 기억할 필요 없이 전부 불투명입니다. 그러나 파일에 반투명 영역이 있다면 그 값이 그대로 화면에 나타납니다. sample.png를 직접 편집해 반투명 영역을 만들어 보는 실험은, "텍스처의 알파 채널이 화면의 투명도를 결정한다"는 이 장의 핵심을 가장 빠르게 체감하는 방법입니다. 이렇게 파일 → 디코딩 → GPU 텍스처 → 화면까지의 전 과정을 한 장으로 정리하며 16장(SVG)으로 넘어갑니다. 그리고 샘플러 설정이 텍스처 품질을 결정하는 방법은 17장에서 직접 바꿔 보며 익힙니다.
