# 31. 파이프라인 여행 — 수도 코드 §1~§20 캡스톤, 전 과정 한 파일로

> 관련 코드: `Projects/sgfr/Sources/sgfr/31_PipelineJourney/31_PipelineJourney_Main.cpp` (단일 파일)
> 실행: sgfr 실행 후 콘솔 메뉴에서 31번 선택 (창이 뜨면 ESC로 종료)
> 선행 학습: 01~30 전 과정 (특히 `20_머티리얼.md`, `21_리소스매니저.md`, `22_렌더오브젝트.md`, `23_스테이트캐시.md`)

## 1. 이 장에서 배우는 것

1번(선형대수)부터 30번(스프라이트 애니메이션)까지 배운 모든 것을 **하나의 프로그램으로 연결**합니다. 설계 기준이 된 수도 코드 문서의 §1(윈도우)~§20(메인 루프)을 v3 API로 한 파일에 재현한 "파이프라인 여행"입니다. 리소스 매니저, 머티리얼, 메시, 렌더 오브젝트, 프레임 상수, SceneRenderer가 어떻게 한 줄씩 짜 맞춰지는지 전체 흐름을 복기합니다.

## 2. 실행하면 보이는 것

1280x720 창에 **체커보드 바닥 위에서 회전하는 큐브**가 보입니다. 바닥과 큐브가 함께 돌며(큐브는 제자리 회전, 바닥은 90도 눕힌 체커 판), ESC로 종료합니다.

콘솔에 출력되는 문장:

```
수도 코드 §1~§20이 이 파일 하나에 전부 들어있습니다. 주석의 [§N]을 따라가세요!
```

코드의 각 단계 앞에 `[§N]` 주석이 붙어 있어, 윈도우 → 디바이스 → 리소스 → 씬 렌더 → 루프의 순서를 **주석을 따라가며** 복기할 수 있습니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 파이프라인 여행 = 공장 견학 코스

이 튜토리얼은 "그래픽 공장" 견학 코스입니다. 공장의 각 부서(§)를 순서대로 지나갑니다.

1. **§1 건물(윈도우) 짓기**
2. **§2~6 기계(디바이스)와 컨베이어(컨텍스트) 설치** — 스왑체인, 백버퍼, 깊이 버퍼는 엔진이 내부에서 조립
3. **§7~9 자재 창고(리소스 매니저)** — 디폴트 셰이더/머티리얼, 체커 텍스처 등록
4. **§10~11 설계도(메시)** — 큐브와 바닥 쿼드의 정점/인덱스/레이아웃
5. **§12 주문서(렌더 오브젝트)** — "무엇을(메시), 어떻게(머티리얼), 어디에(월드 행렬)"
6. **§13~19 작업 지시(SceneRenderer)** — 프레임 상수 b0, 드로우
7. **§20 메인 루프** — ESC까지 반복

### 3-2. "무엇을"과 "어떻게"는 분리된 카탈로그

메시는 "무엇을 그릴지"의 형태 데이터, 머티리얼은 "어떻게 그릴지"의 상태 묶음입니다. 같은 큐브를 벽돌로도 금속으로도 그릴 수 있고, 같은 재질을 여러 물체에 쓸 수 있습니다. 렌더 오브젝트는 이 둘을 **키(key)**로 조합한 주문서입니다. (20번 머티리얼, 22번 렌더 오브젝트의 완성형)

### 3-3. 디바이스(공장)와 컨텍스트(작업반장)

- **GraphicDevice** = 리소스 생성 담당 "공장" (`ID3D11Device`)
- **GraphicContext** = 그리기 명령 담당 "작업반장" (`ID3D11DeviceContext`)

생성과 바인딩의 책임을 분리한 것이 v3의 핵심입니다. `device.GetContext()`로 작업반장을 받아 `InvalidateCache()` 같은 명령을 내립니다.

### 3-4. 리소스 매니저 = 자재 창고의 "수명 소유권"

`g_cResourceMgr.Add(리소스)`로 창고에 넣으면 **창고가 소유**합니다. 개별 `delete`는 하지 않고, 종료 시 `Finalize()`가 창고 안의 모든 자재를 일괄 소멸시킵니다. 주문서(머티리얼)는 포인터가 아닌 **키(_u64)**로 자재를 가리키므로, 자재가 사라져도 안전하게 감지됩니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 수도 코드 (Pseudo-code) | 실제 문법이 아닌 설계용 흐름 문서 (이 프로젝트의 §1~§20) | 공장 설계 도면 |
| v3 API | 이 시리즈의 최종 형태 엔진 API | 완성형 공장 설비 |
| 리소스 매니저 | 리소스 소유권과 수명을 관리하는 창고 | 자재 창고 |
| 키 (Key) | 리소스를 찾는 _u64 번호 (경로/자동 발급) | 창고 보관 번호 |
| 머티리얼 | 셰이더+상태+텍스처를 묶은 "그림 방법" | 도장 공정 설명서 |
| 메시 (Mesh) | VB/IB/입력 레이아웃/토폴로지 묶음 = 형태 | 부품 설계도 |
| 렌더 오브젝트 (RenderObject) | 메시키+머티리얼키+월드 행렬 = 그릴 것 하나 | 주문서 |
| 프레임 상수 (FrameConstants) | 뷰/투영/카메라 위치 (b0, 프레임당 1회) | 작업반 지시서 |
| SceneRenderer | 프레임 상수 + 오브젝트 상수(b1)를 소유하고 Draw | 작업반장 |
| InvalidateCache | 프레임 시작 시 바인딩 캐시 무효화 | 작업 전 공구함 정리 |
| memory:// URI | 파일이 아닌 메모리 데이터를 등록하는 경로 표기 | "이 물건은 창고 내부에서 만들어짐" 표시 |

## 5. 코드 워크스루

### 5-1. §1 윈도우 / §2~6 디바이스와 컨텍스트

```cpp
// [§1] 윈도우 초기화: window.init(1280, 720)
Window window;
if (!window.Create(L"31. 파이프라인 여행 (ESC 종료)", 1280, 720)) { ... }

InputManager input;
window.ConnectInput(&input);

// [§2~§6] 디바이스 + 컨텍스트 + 스왑체인 + 백버퍼 RTV + 깊이버퍼 DSV
//  - 수도 코드에서는 다섯 단계였지만, v3에서는 device.Initialize(hwnd, w, h) 한 번이다.
//  - 분리된 GraphicsContext는 device.GetContext()로 얻는다. (생성과 바인딩의 분리!)
GraphicDevice device;
if (!device.Initialize(window.Handle(), window.Width(), window.Height())) { ... }
GraphicContext& context = device.GetContext();
```

수도 코드에서 따로따로 하던 스왑체인 생성/백버퍼 RTV/깊이 DSV가 **엔진 내부**로 들어갔고, 사용자는 `device.Initialize` 한 번만 호출합니다. `device.GetContext()`로 작업반장(GraphicContext)을 얻습니다.

### 5-2. 리소스 매니저 — 디폴트 자재 준비

```cpp
// 리소스 매니저: 디폴트 셰이더/머티리얼이 여기서 준비된다. ([§8~§9]의 완성형)
if (!g_cResourceMgr.Initialize(&device)) { ... }
```

`Initialize`는 디폴트 2D/3D 셰이더, 흰색 텍스처, 디폴트 머티리얼까지 만들어 둡니다. `GetDefaultVertexShader2DKey()`, `GetDefaultMaterial3DKey()` 같은 접근자로 그 키를 꺼내 씁니다.

### 5-3. SceneRenderer

```cpp
// [§13] 프레임 상수버퍼 + [§16~§19] 바인딩/드로우 도우미 = SceneRenderer
SceneRenderer renderer;
if (!renderer.Initialize(&device)) { ... }
```

SceneRenderer는 **b0(프레임 상수: view/projection/카메라)와 b1(오브젝트 상수: world) 상수버퍼를 소유**하고, `BeginScene(frame)` → `Draw(object)` 흐름을 제공합니다. 22번(렌더 오브젝트 루프)에서 배운 SceneRenderer의 재사용입니다.

### 5-4. 체커 텍스처를 메모리에서 만들어 등록

```cpp
// [§9] 텍스처 생성 후 매니저 등록 (바닥 체커)
_u8 pixels[64 * 64 * 4];
FillChecker(pixels, 64, 64);

Texture* pChecker = dbg_new Texture();
if (!pChecker->CreateFromMemory(&device, pixels, 64, 64)) { ... }
pChecker->SetDebugName("JourneyChecker");
const _u64 checkerKey = g_cResourceMgr.Add(pChecker, "memory://journey_checker");
```

- `FillChecker`는 `((x/8 + y/8) % 2)`로 8픽셀 단위 체커보드 색(밝은 쪽 180,180,200 / 어두운 쪽 60,60,90)을 채웁니다.
- `Add(pChecker, "memory://journey_checker")` — **메모리 URI 경로**로 등록합니다. 파일에서 로드한 것이 아니므로 "memory://" 접두사로 구분합니다.
- `SetDebugName`은 디버그 출력용 이름표입니다.

### 5-5. 바닥 머티리얼 — 하이브리드 구성

```cpp
Material* pFloorMaterial = dbg_new Material();
if (!pFloorMaterial->Initialize(&device)) { ... }
pFloorMaterial->SetVertexShaderKey(g_cResourceMgr.GetDefaultVertexShader2DKey());
pFloorMaterial->SetPixelShaderKey(g_cResourceMgr.GetDefaultPixelShader2DKey());
pFloorMaterial->SetTextureKey(0, checkerKey);				// [§9] texture[8] 슬롯 중 t0
pFloorMaterial->SetRasterizer(CullMode::cmBack);			// [§7] 래스터라이저 상태
pFloorMaterial->SetBlend(BlendMode::bmNone);				// [§7] 블렌드 상태
pFloorMaterial->SetDepth(DepthMode::dmReadWrite);			// [§7] 깊이 상태
pFloorMaterial->SetSampler(FilterMode::fmLinear);			// [§7] 샘플러 상태
const _u64 floorMaterialKey = g_cResourceMgr.Add(pFloorMaterial);
```

**2D 셰이더 키를 쓰지만 3D 장면에 배치되는 하이브리드**가 포인트입니다. 바닥은 쿼드 메시(VertexPTC)라서 2D 셰이더를 쓰지만, `world_` 행렬(3D 변환)로 회전·평행 이동되어 공간에 눕혀집니다. `Material`은 셰이더 2종 + 텍스처 슬롯(t0) + 래스터라이저/블렌드/깊이/샘플러 상태 4종을 **하나의 값**으로 묶는 완성형입니다.

### 5-6. 메시 2종

```cpp
// [§10~§11] 메시: VB + IB + 입력 레이아웃 + 토폴로지를 한 덩어리로
Mesh* pCubeMesh = dbg_new Mesh();
Mesh* pQuadMesh = dbg_new Mesh();
if (!pCubeMesh->InitializeAsCube(&device, g_cResourceMgr.GetDefaultVertexShader3D()) ||
	!pQuadMesh->InitializeAsQuad2D(&device, g_cResourceMgr.GetDefaultVertexShader2D())) { ... }
```

- `InitializeAsCube`: 1x1x1 큐브 (VertexPNT, 면별 법선)
- `InitializeAsQuad2D`: XY 평면 1x1 쿼드 (VertexPTC, 중심 원점)

입력 레이아웃이 셰이더 서명과 일치하는지 검증됩니다.

### 5-7. 렌더 오브젝트 2개와 프레임 상수

```cpp
// [§12] 렌더 오브젝트: 무엇을/어떻게/어디에
RenderObject cube;
cube.meshKey_ = cubeMeshKey;
cube.materialKey_ = g_cResourceMgr.GetDefaultMaterial3DKey();

RenderObject floor;
floor.meshKey_ = quadMeshKey;
floor.materialKey_ = floorMaterialKey;

// [§13] 프레임 데이터: 뷰/투영/카메라 위치
FrameConstants frame;
frame.view_ = mat4::LookAtLH(vec3(0.0f, 2.0f, -4.0f), vec3::Zero(), vec3::Up());
frame.projection_ = mat4::PerspectiveFovLH(jc_math_deg2rad(60.0f), window.AspectRatio(), 0.1f, 100.0f);
frame.cameraPosition_ = vec4(0.0f, 2.0f, -4.0f, 1.0f);
```

큐브는 **디폴트 3D 머티리얼** 키를, 바닥은 우리가 만든 머티리얼 키를 씁니다. 뷰포트는 `device.Initialize`가 전체 화면으로 잡아둡니다 (필요하면 `context.SetViewport(...)`로 변경 가능).

### 5-8. §20 메인 루프

```cpp
while (window.PumpMessage())
{
	if (input.IsKeyPressed(VK_ESCAPE)) { break; }
	input.NextFrame();

	timer.Tick();
	elapsed += timer.DeltaTime();

	// 월드 행렬 갱신 (행벡터 규약: 회전 후 이동)
	cube.world_ = mat4::RotationY(elapsed) * mat4::Translation(0.0f, 0.5f, 0.0f);
	floor.world_ = mat4::Scale(6.0f) * mat4::RotationX(jc_math_deg2rad(90.0f)) * mat4::Translation(0.0f, -0.5f, 0.0f);

	// [§15] BeginFrame: 백버퍼/깊이버퍼 클리어 + 뷰포트/렌더타겟 장착
	device.BeginFrame(color(0.08f, 0.08f, 0.12f, 1.0f));
	context.InvalidateCache();	// BeginFrame이 원시 상태를 건드렸으므로 캐시를 비운다

	// [§16] UpdateFrameConstant: 프레임당 한 번 b0 갱신
	renderer.BeginScene(frame);

	// [§17~§19] BindMaterial + BindMesh + UpdateObjectConstant + Draw 가 한 줄씩
	renderer.Draw(floor);
	renderer.Draw(cube);

	device.EndFrame(true);
}
```

- 월드 행렬: 큐브는 y축 회전 후 (0,0.5,0)로 이동, 바닥은 6배 확대 후 x축 90도 회전으로 눕혀 이동. **행벡터 규약이므로 행렬 순서가 "회전 → 이동"**입니다.
- `BeginFrame`은 백버퍼/깊이버퍼를 지우고 원시 D3D 상태를 건드리므로, **`context.InvalidateCache()`로 바인딩 캐시를 비워** 23번(스테이트 캐시)의 캐시 정합성을 유지합니다.
- `renderer.BeginScene(frame)`이 b0(뷰/투영/카메라)를 프레임당 1회 갱신하고, `Draw(floor)`/`Draw(cube)`가 각각 머티리얼/메시를 키로 해석해 바인딩하고 b1(world)을 갱신한 뒤 그립니다.
- `EndFrame(true)` = Present (vsync 켬).

### 5-9. 정리 — 매니저가 일괄 소멸

```cpp
// 정리: 등록한 리소스(메시/머티리얼/텍스처)는 매니저 Finalize가 일괄 소멸시킨다.
renderer.Finalize();
g_cResourceMgr.Finalize();
device.Finalize();
window.Destroy();
```

`pChecker`/`pFloorMaterial`/`pCubeMesh`/`pQuadMesh`를 개별 delete하지 않습니다. **리소스 매니저가 소유권을 가진 채 Finalize에서 일괄 정리**합니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. 이 장의 드로우가 하드웨어에서 실행되는 전체 여행

`renderer.Draw(floor)` 한 줄이 실제로 GPU에서 수행하는 일을 따라가 봅시다.

1. **CPU (SceneRenderer::Draw)**: `meshKey_`와 `materialKey_`를 ResourceMgr에서 해석(작은 캐시로 Find 생략)해 `Mesh*`/`Material*`를 얻습니다.
2. **Material::Bind**: 셰이더/텍스처 키를 다시 해석해 **셰이더 바인딩**(VS/PS), **텍스처 바인딩**(t0), 그리고 래스터라이저/블렌드/깊이/샘플러 **상태 객체를 OM/RS 단계에 장착**합니다. D3D11 상태 객체는 불변(immutable)이라, 하드웨어가 상태 전환을 빠르게 처리할 수 있습니다. 스테이트 캐시(GraphicContext)가 같은 상태의 재바인딩을 걸러냅니다.
3. **오브젝트 상수**: `world_`가 Map(WRITE_DISCARD) → b1 상수버퍼로 업로드됩니다.
4. **Mesh::Bind**: VB/IB/입력 레이아웃/토폴로지를 IA에 장착합니다.
5. **Draw**: `DrawIndexed` 1회 → GPU 파이프라인 시작:
   - **IA**가 인덱스를 따라 정점을 조립, **VS**가 world(오브젝트 b1)·view/projection(프레임 b0)을 합성해 클립 좌표로 변환
   - **래스터라이저**가 삼각형을 픽셀로, **RS 상태**(백컬링)에 따라 뒤집힌 면은 거름
   - **PS**가 t0 체커 텍스처를 UV로 샘플링 (Linear 필터, Clamp)
   - **OM/ROP**가 깊이 테스트(dmReadWrite) 후 색을 백버퍼에 기록
6. **EndFrame(true)**: `Present`가 스왑체인을 플립해 완성된 프레임이 모니터로.

### 6-2. 상태 4종이 GPU 하드웨어에 의미하는 것

- **래스터라이저(cmBack)**: 컬링 유닛이 "면의 감김 방향"을 판정해 뒷면 삼각형을 폐기. 픽셀 셰이더 실행 전 단계라서 폐기된 픽셀은 ALU를 소모하지 않습니다.
- **블렌드(bmNone)**: ROP 블렌드 유닛이 단순 대체 쓰기 모드. 블렌드 유닛을 거치지 않는 것보다 상태가 "불투명"으로 고정되어 값싸게 처리됩니다.
- **깊이(dmReadWrite)**: 깊이 비교 유닛이 매 픽셀 z 비교 후 통과 시 새 깊이 기록. 바닥(먼저 그림)이 깊이를 차지하고, 큐브가 그 위에서 정확히 겹치게 하는 3D 장면의 기반입니다. 초기 깊이 테스트(Early-Z)가 대부분의 픽셀에서 PS 실행을 생략하게 만드는 경우도 있습니다.
- **샘플러(fmLinear, Clamp)**: 텍스처 필터 유닛이 2x2 텍셀 보간을 수행하고, UV가 0~1 밖이면 Clamp(가장자리 고정)로 처리합니다.

이 4종이 머티리얼로 묶여 바인딩되는 것은, GPU가 상태 전환을 "상태 블록 하나"로 인지해 내부 파이프라인 재구성을 최소화한다는 의미도 있습니다. 상태를 매 드로우마다 바꾸면 GPU는 파이프라인을 부분적으로 다시 설정해야 하지만, **같은 머티리얼로 연속 그리면 상태 전환 비용이 0에 가까워집니다.**

### 6-3. 키 기반 리소스 해석이 성능에 주는 영향

머티리얼이 포인터 대신 키(_u64)를 보관하는 이유는 **달링 포인터 방지**입니다. Bind 시점에 매번 ResourceMgr의 HashMap에서 키 → 리소스를 찾는데, SceneRenderer는 "직전 키와 같으면 Find를 생략하는 소형 캐시"를 둬서 연속 Draw의 해석 비용을 없앱니다. 실제 게임에서 수백 개 오브젝트를 그릴 때 이런 캐시가 프레임 비용을 결정합니다.

### 6-4. memory:// 텍스처와 VRAM

`CreateFromMemory` → `Add(pChecker, "memory://...")`의 경로에서:

1. CPU 픽셀 배열(64x64x4 = 16KB)이 `CreateTexture2D`로 VRAM 텍스처를 만들고 `UpdateSubresource`로 복사됩니다 (PCIe 전송).
2. 이후 CPU 메모리는 매니저가 소유권을 가진 상태로 유지되거나(리소스가 VRAM 사본을 소유) 해제됩니다 — 어느 쪽이든 셰이더는 VRAM 텍스처만 봅니다.
3. `memory://` URI는 `pathIndex_`(경로 → 키)에 등록되므로, 같은 URI로 다시 Add하면 중복 등록이 거부됩니다(INVALID_RESOURCE_KEY). "같은 파일을 두 번 로드하지 않는다"는 규칙이 메모리 리소스에도 적용되는 것입니다.

### 6-5. BeginFrame → InvalidateCache가 필요한 진짜 이유

`BeginFrame`은 내부적으로 뷰포트·렌더 타깃·클리어를 위해 **원시 D3D11 호출(OMSetRenderTargets, RSSetViewports, Clear...)**을 직접 사용합니다. GraphicContext의 바인딩 캐시는 "마지막으로 묶은 것"을 기억하므로, 이 원시 호출 이후에는 **캐시가 실제 GPU 상태와 다를 수 있습니다.** `InvalidateCache()`는 캐시를 비워 "다음 바인딩을 강제로 수행"하게 만듭니다. 스테이트 캐시(23번)의 정합성 규칙 — "외부에서 상태가 바뀌었으면 캐시를 무효화한다" — 를 지키는 표준 절차입니다.

### 6-6. D3D11 API 대응표

| sgf API | D3D11 API | 하드웨어 |
|---|---|---|
| `g_cResourceMgr.Add/Find` | 키 발급/조회 (내부 HashMap) | CPU측 리소스 테이블 |
| `Material::Bind` | `VSSetShader`/`PSSetShader`/`PSSetShaderResources`/`OMSetBlendState`/`OMSetDepthStencilState`/`RSSetState`/`PSSetSamplers` | 파이프라인 상태 장착 |
| `Mesh::Bind` | `IASetVertexBuffers`/`IASetIndexBuffer`/`IASetInputLayout`/`IASetPrimitiveTopology` | IA 정점 조립 |
| `renderer.BeginScene` | `VSSet/PSSetConstantBuffers(b0)` | 프레임 상수 캐시 |
| `renderer.Draw` | `VSSet/PSSetConstantBuffers(b1)` + `DrawIndexed` | 오브젝트 상수 + 드로우 |
| `device.EndFrame(true)` | `Present(1, 0)` | 스왑체인 플립 → 디스플레이 |

## 7. 핵심 규칙 요약

- 2D/3D 셰이더 동시 사용: 바닥은 2D 셰이더 키 + 3D 월드 행렬 (하이브리드), 큐브는 디폴트 3D 셰이더.
- Material = 셰이더 + 래스터라이저 + 블렌드 + 깊이 + 샘플러 + 텍스처 슬롯을 **한 값으로 묶는 완성형**.
- 리소스는 매니저가 **수명 소유** — 개별 delete 대신 `Finalize()` 일괄 정리.
- `BeginFrame` 후에는 반드시 `context.InvalidateCache()` (23번 스테이트 캐시 복습).
- `GetContext()`로 생성(디바이스)과 바인딩(컨텍스트) 분리.
- 상수 슬롯 규약: **b0 = 프레임 공통, b1 = 오브젝트(world), b2 = 머티리얼**.
- `memory://` URI로 메모리 텍스처 등록 (중복 등록 거부).
- 행벡터 규약: 월드 행렬은 "회전 → 이동" 순서.
- 뷰포트는 `device.Initialize`가 전체 화면으로 잡아둠.

## 9. 다음 단계로

이것으로 sgfr 튜토리얼 31개 전체가 끝납니다. 이제 여러분은 윈도우부터 셰이더, 렌더 타깃, 그림자, 씬, 애니메이션까지 **한 프레임이 GPU에서 완성되는 전체 경로**를 직접 만들고 설명할 수 있습니다.

앞으로 공부하면 좋은 것들:

- **PCF(Percentage-Closer Filtering)**: 27번의 Point 샘플러를 2x2/3x3으로 확장해 그림자 경계 부드럽게 하기
- **CSM(Cascaded Shadow Maps)**: 27번을 여러 깊이 구간으로 나눈 실무 그림자
- **GPU 파티클/스키닝 애니메이션**: 30번의 CPU 애니메이션을 정점 셰이더로 옮기기
- **지연 셰이딩(Deferred Shading)**: 24번 셰이딩 모델을 G-버퍼(렌더 타깃 여러 장)로 분리한 실무 라이팅

다시 처음부터 순환하며 수도 코드 문서와 대조해 보면, 같은 개념이 "이유"와 "최종 형태"로 연결되는 것을 발견할 수 있습니다.
