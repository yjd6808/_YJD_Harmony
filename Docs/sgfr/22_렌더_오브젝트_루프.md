# 22. 렌더 오브젝트 루프 — Renderer3D의 표준 그리기 패턴

> 관련 코드: `Projects/sgfr/Sources/sgfr/Tutorial/22_RenderObjectLoop/` (`22_RenderObjectLoop_Main.cpp`)
> 엔진 코드: `Projects/sgf/Sources/sgf/Graphics/Renderer3D.h/.cpp`, `Mesh.h/.cpp`, `DefaultShaders.h`
> 실행: sgfr 실행 후 콘솔 메뉴에서 **22번** 선택
> 선행 학습: 12번(셰이더 스테이지와 b0/b1), 20번(머티리얼), 21번(리소스 매니저)

## 1. 이 장에서 배우는 것

**RenderObject**(메시 키 + 머티리얼 키 + 월드 행렬 + visible)라는 "그리기의 최소 단위"를 정의하고, `Renderer3D::BeginScene(프레임 상수)` → `Draw(오브젝트)` 반복으로 이루어지는 **표준 렌더 루프**를 배웁니다. 12번에서 손수 하던 b0/b1 상수버퍼 갱신이 Renderer3D로 자동화되는 완성판이며, 모든 실전 렌더러가 쓰는 "프레임당 1회 갱신 + 오브젝트마다 갱신"의 갱신 주기 분리 설계를 익힙니다.

## 2. 실행하면 보이는 것

화면 가운데 **큰 큐브 1개**가 제자리에서 회전하고, 주변을 **작은 큐브 4개**가 90° 간격으로 공전하며 각자 제자리 회전(자전)합니다. 각 큐브는 면마다 색이 구분됩니다(디폴트 3D 셰이더의 고정 방향광 람버트 + 앰비언트 조명).

| 키 | 동작 |
|---|---|
| `1` | 가운데 큰 큐브 보이기/숨기기 토글 |
| `ESC` | 종료 |

`1`번 키를 누르면 `objects[0].visible_` 플래그만 false로 바뀌고, `renderer.Draw`가 그 오브젝트를 조용히 건너뜁니다. 나머지 4개 큐브는 계속 움직입니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. RenderObject = "촬영 대기 명단"

무대(씬)에 서는 배우를 생각해 봅시다. 배우를 부르려면 세 가지가 필요합니다.

- **누가**(메시 키): 어떤 몸(형태)을 가진 배우인가?
- **어떻게**(머티리얼 키): 무슨 의상과 조명 설정으로?
- **어디에**(월드 행렬): 무대 어느 위치에서 어떤 방향으로?

이 세 가지를 담은 명단 한 줄이 **RenderObject**입니다. 그리고 **Renderer3D**는 무대 감독입니다: "준비 시작!"(BeginScene)을 외치고 명단을 한 줄씩 읽어가며(BeginScene 후 Draw 반복) 배우들을 무대에 세웁니다.

### 3-2. 갱신 주기 분리: "세트장은 한 번, 배우는 매번"

b0(프레임 상수: 뷰/투영/카메라)는 **한 프레임 동안 모든 오브젝트가 공유**하는 값입니다. 카메라가 안 움직이면 100개 오브젝트를 그려도 뷰 행렬은 같습니다. b1(월드 행렬)은 **오브젝트마다 다릅니다.** 그래서 Renderer3D는

- `BeginScene(frame)`에서 b0를 **1회** 업데이트하고,
- `Draw(object)`마다 b1을 **그 오브젝트만큼** 업데이트합니다.

이렇게 "세트장은 한 번 설치하고, 배우 자세는 매번 조정"하는 갱신 주기 분리는 상수버퍼 업로드(Map/Unmap) 횟수를 최소화하는 핵심 최적화입니다.

### 3-3. 키 해석의 소형 캐시

`Draw`는 매번 `g_cResourceMgr.Find<Mesh>(meshKey)`를 호출할까요? 아닙니다. Renderer3D는 `lastMeshKey_`/`lastMaterialKey_`를 기억해, **직전과 같은 키면 Find를 생략**하고 기억해둔 포인터를 씁니다(Renderer3D.cpp:158~166). 100개 오브젝트가 같은 큐브 메시를 공유하는 실전 패턴에서 Find 호출 99개를 아끼는 장치입니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| RenderObject | 그릴 대상 한 개의 정의(메시+머티리얼+월드+visible) | 촬영 대기 명단 한 줄 |
| Renderer3D | BeginScene→Draw→EndScene 루프를 수행하는 렌더러 | 무대 감독 |
| 프레임 상수(b0) | 뷰/투영/카메라 등 프레임 공통 값 | 세트장 설치 |
| 오브젝트 상수(b1) | 오브젝트별 월드 행렬 | 배우 자세 |
| visible | 그릴지 말지 결정하는 플래그 | 대기 명단에서 빼기 |
| 공전 | 중심을 도는 운동 | 지구가 태양 주위를 돔 |
| 자전 | 제자리 회전 | 지구가 스스로 돎 |
| 키 해석 | 키를 매니저에 물어 포인터 얻기 | 청구번호로 책 찾기 |
| 행벡터 규약 | `v·M`으로 곱하는 행렬 관례 | 왼쪽부터 적용되는 결합 순서 |

## 5. 코드 워크스루

`RenderObjectLoop_Main()`의 흐름을 따라갑니다.

### 5-1. Renderer3D와 큐브 메시 등록

```cpp
if (!g_cResourceMgr.Initialize(&device)) { ... }

Renderer3D renderer;
renderer.Initialize(&device);   // b0/b1 상수버퍼를 내부에서 소유·생성

Mesh* pCube = dbg_new Mesh();
pCube->InitializeAsCube(&device, g_cResourceMgr.GetDefaultVertexShader3D());
pCube->SetDebugName("UnitCube");
const _u64 cubeMeshKey = g_cResourceMgr.Add(pCube);   // 소유권 이전
```

`BatchRenderer::Initialize`가 가상 훅 `CreateBatchResources`(Renderer3D.cpp:92~108)를 거쳐 `frameCb_`(b0)와 `objectCb_`(b1) 두 상수버퍼를 만듭니다(Renderer3D.cpp:104~105). `InitializeAsCube`는 VertexPNT(위치/법선/UV)용 1×1 큐브 메시로, 디폴트 3D 셰이더와 레이아웃이 맞습니다. 큐브는 면마다 법선이 달라 정점을 공유하지 않으므로 **정점 24개(면당 4개 × 6면)**와 인덱스 36개로 만들어집니다(Mesh.cpp:170~228). 앞면(+Z)의 정점 4개는 법선 (0,0,1)을, 뒷면(-Z)은 (0,0,-1)을 가집니다 — 이 면별 법선 덕분에 디폴트 3D 셰이더의 람버트 조명이 큐브의 각 면을 다른 밝기로 비춥니다. 19번에서 쓰던 `FillColorCube`(정점 8개 + 인덱스 36개, 정점 색 방식)와 대비되는 "면별 법선을 가진 재사용 가능한 메시"의 예입니다.

### 5-2. RenderObject 배열 구성

```cpp
RenderObject objects[1 + ORBIT_CUBE_COUNT];
for (int i = 0; i < 1 + ORBIT_CUBE_COUNT; ++i)
{
	objects[i].meshKey_ = cubeMeshKey;
	objects[i].materialKey_ = g_cResourceMgr.GetDefaultMaterial3DKey();
	objects[i].visible_ = true;
}
```

`RenderObject`(Renderer3D.h:75)는 `meshKey_`, `materialKey_`, `world_`, `visible_` 네 멤버뿐입니다. **월드 행렬은 매 프레임 갱신**되므로 여기서는 키와 가시성만 채웁니다. `GetDefaultMaterial3DKey()`는 리소스 매니저가 만든 디폴트 3D 머티리얼(불투명 + 깊이 읽기쓰기)을 가리킵니다.

### 5-3. 카메라와 월드 행렬 갱신

```cpp
FrameConstants frame;
frame.view_ = mat4::LookAtLH(vec3(0.0f, 2.5f, -5.0f), vec3::Zero(), vec3::Up());
frame.projection_ = mat4::PerspectiveFovLH(jc_math_deg2rad(60.0f), window.AspectRatio(), 0.1f, 100.0f);
frame.cameraPosition_ = vec4(0.0f, 2.5f, -5.0f, 1.0f);
```

```cpp
objects[0].world_ = mat4::RotationY(elapsed);   // 가운데: 제자리 회전

for (int i = 0; i < ORBIT_CUBE_COUNT; ++i)
{
	const _f32 angle = elapsed * 1.5f + jc_math_pi * 2.0f * (_f32)i / (_f32)ORBIT_CUBE_COUNT;
	objects[1 + i].world_ =
		mat4::Scale(0.3f) *                          // (1) 작게
		mat4::RotationY(elapsed * 3.0f) *            // (2) 제자리 회전 (자전)
		mat4::Translation(2.0f, 0.0f, 0.0f) *        // (3) 반지름만큼 밀고
		mat4::RotationY(angle);                      // (4) 중심 기준 공전
}
```

행벡터 규약에서는 **왼쪽부터 먼저 적용**됩니다. 궤도 큐브의 결합 순서는 ① 30% 크기로 축소 → ② 제자리 회전 → ③ x방향으로 2만큼 이동 → ④ 공전각 회전. 순서를 바꾸면 반지름이 변하거나 자전이 사라지는 것을 유추해 볼 수 있습니다.

### 5-4. 표준 렌더 루프

```cpp
device.BeginFrame(color(0x0F, 0x0F, 0x1A, 0xFF));
device.GetContext().InvalidateCache();   // BeginFrame이 원시 상태를 건드렸으므로 캐시 비움

renderer.BeginScene(frame);              // b0 1회 갱신
for (int i = 0; i < 1 + ORBIT_CUBE_COUNT; ++i)
{
	renderer.Draw(objects[i]);           // 오브젝트마다 b1 갱신 + 드로우
}
renderer.EndScene();                     // 배치 종료 (잔여 플러시)
device.EndFrame(true);
```

`Renderer3D::Draw(const RenderObject&)`(Renderer3D.cpp:150)의 내부 흐름:

1. `visible_ == false`면 즉시 return (숨김 처리).
2. `meshKey_`/`materialKey_`가 직전과 다를 때만 `Find<Mesh>`/`Find<Material>` (소형 캐시).
3. `Material::Bind(context)` — 셰이더/상태 4종/텍스처/b2 (20번에서 배운 것).
4. `Mesh::Bind(context)` — VB/IB/입력 레이아웃/토폴로지.
5. `ObjectConstants{ world_ }` 갱신 → `SetConstantBuffer(ssVertex, 1, ...)` (b1).
6. `Mesh::Draw(context)` — DrawIndexed/Draw.

정리 순서: `renderer.Finalize()` → `g_cResourceMgr.Finalize()`(큐브 메시는 매니저가 소멸) → `device.Finalize()` → `window.Destroy()`. 키 입력 처리는 `input.IsKeyPressed('1')`과 `input.NextFrame()` 사이클로, 이전 장들과 동일한 패턴입니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. BeginScene의 실제 D3D11 작업

`Renderer3D::BeginScene`(Renderer3D.cpp:116~124)은 `frameCb_.Update()`(Map WRITE_DISCARD → memcpy → Unmap) 후 `SetConstantBuffer(ssVertex, 0, ...)`와 `SetConstantBuffer(ssPixel, 0, ...)` 둘 다 수행합니다. b0를 VS/PS 양쪽에 꽂는 이유는 디폴트 셰이더에서 뷰/투영은 VS가, 카메라 위치는 PS가 사용할 수 있기 때문입니다(실제로 2D/3D 디폴트 셰이더의 `CbFrame`은 VS에서 mul에, PS에서는 `gCameraPosition`은 선언만 됨). Map은 CPU가 GPU 메모리 주소를 잠시 점유하는 **동기화 지점**입니다. 상수버퍼는 항상 DYNAMIC + WRITE_DISCARD로 만들어져 있으므로, GPU가 이전 프레임의 명령을 아직 실행 중이어도 Map이 블로킹되지 않습니다 — 드라이버가 버퍼의 다른 물리 페이지를 줄여 주기 때문입니다(18번 동적 버퍼와 같은 메커니즘). 그럼에도 Map/Unmap은 PCIe 왕복이 수반되므로 **프레임당 1회**로 줄이는 것이 좋고, 이것이 BeginScene이 b0를 1회만 갱신하는 이유입니다.

### 6-2. Draw마다 일어나는 일: 명령 버퍼와 드라이버 검증

`renderer.Draw()` 한 번은 GPU 관점에서 "현재 파이프라인 레지스터 상태로 DrawIndexed를 실행"입니다. 드라이버는 DrawIndexed 호출 시 현재 바인딩된 셰이더/상태/리소스/상수버퍼 조합을 검증해 내부 파이프라인 상태를 확정하고, 명령 버퍼(커맨드 리스트)에 기록합니다. 여기서 비용의 대부분은 **CPU 쪽 API 호출 처리**입니다:

- Material::Bind의 상태 설정 호출들이 **하나도 생략되지 않으면** 드로우마다 수십 개의 ID3D11DeviceContext 호출이 검증·기록됩니다.
- 이 비용은 23번 스테이트 캐시가 다루는 대상입니다: 같은 값 재바인딩을 건너뛰면 드로우당 호출 수가 급감합니다.
- 메시/머티리얼 키를 **Find로 다시 풀지 않는** 소형 캐시도 같은 목적(불필요한 CPU 작업 제거)입니다.

이 튜토리얼은 오브젝트가 5개라 미미하지만, 23번은 같은 구조로 100개를 그리며 차이를 수치로 보여줍니다.

### 6-3. 디폴트 3D 셰이더의 조명이 하드웨어에서 도는 방법

`DEFAULT_SHADER_SOURCE_3D`(DefaultShaders.h)의 PS는 `lighting = 0.25f + 0.75f * saturate(dot(normal, -lightDir))`를 계산합니다. 이는 셰이더 ALU에서 **FMA(Fused Multiply-Add) 한 두 개 + saturate** 정도로 실행되는 매우 가벼운 연산이며, 정점 단위가 아닌 **픽셀 단위**(보간된 법선)로 수행됩니다. 각 픽셀 셰이더 스레드는 SIMD 워프 안에서 병렬로 이 수식을 실행하므로, 조명이 켜진 큐브의 비용은 거의 "픽셀 개수 × 워프당 처리량"입니다. 법선은 `mul(input.normal, (float3x3)gWorld)`로 회전만 적용된 뒤 normalize되며, 이 보간·재정규화 과정은 24번 셰이딩 모델에서 정밀하게 다룰 내용의 복습판입니다.

### 6-3-2. 5개 오브젝트 루프의 명령 흐름

이 튜토리얼의 한 프레임은 CPU에서 대략 다음 순서로 명령 버퍼를 채웁니다: ① BeginFrame이 백버퍼를 지우고, ② BeginScene이 b0를 업로드(Map/Unmap + 2회 바인딩), ③ Draw 1회차가 머티리얼(셰이더/상태 4종/텍스처/b2)과 메시(VB/IB/레이아웃/토폴로지)를 바인딩하고 b1을 업로드한 뒤 DrawIndexed, ④ 나머지 4회차는 **같은 머티리얼/메시를 공유**하므로 상태 바인딩은 GraphicContext의 캐시가 생략하고 b1(월드) 갱신 + DrawIndexed만 반복, ⑤ EndScene이 배치를 종료, ⑥ EndFrame이 Present. 여기서 ④의 "같은 상태 생략"은 다음 장(23번)에서 창 제목 수치로 계량되는 바로 그 장치입니다. 또한 Present는 백버퍼와 프론트버퍼를 교체(DXGI 스왑)하고, vsync=true면 다음 수직 동기 신호까지 블로킹되어 프레임 속도를 60Hz로 고정합니다. 프레임 단위의 타이밍(경과 시간)은 `FrameTimer::Tick/DeltaTime`이 측정하며, 이 값이 회전 각도 `elapsed`로 사용됩니다.

### 6-4. 상수버퍼 슬롯 규약의 하드웨어 의미

b0(프레임)와 b1(오브젝트)을 나누는 것은 GPU 셰이더 코어의 **상수 레지스터 파일**과도 연결됩니다. HLSL cbuffer는 컴파일 시 상수 레지스터 뱅크로 펼쳐지고, cbuffer 단위로 슬롯(b0~b7)에 바인딩됩니다. b0 하나를 갱신하면 b0가 차지하는 레지스터들만 다시 로드되고 b1은 그대로입니다. 프레임 상수와 오브젝트 상수를 분리해 둔 덕분에, 100개 오브젝트를 그려도 뷰/투영이 담긴 b0 레지스터는 재로드되지 않고 b1(월드)만 오브젝트마다 갱신됩니다. 상수버퍼는 16바이트 워드 단위로 업로드되며 `FrameConstants`(144바이트 = 64+64+16)와 `ObjectConstants`(64바이트) 모두 이 정렬을 지킵니다. 이 "자주 바뀌는 것과 드문 것을 분리"하는 설계는 상수버퍼 갱신 대역폭을 최소화하는 표준 기법이며, 실전 엔진의 상수 분류(프레임/뷰/오브젝트/머티리얼)의 원형입니다.

## 7. 핵심 규칙 요약

- [ ] RenderObject = 메시 키 + 머티리얼 키 + 월드 행렬 + visible. 그리기의 최소 단위.
- [ ] 표준 루프: `BeginFrame → BeginScene(frame) → Draw(object) 반복 → EndScene → EndFrame`.
- [ ] **b0은 BeginScene에서 1회**, b1은 **Draw마다** 갱신한다 (갱신 주기 분리 설계).
- [ ] Draw 내부 순서: 키 해석(캐시 활용) → Material::Bind → Mesh::Bind → b1 갱신 → DrawIndexed.
- [ ] `visible_ == false`면 Draw가 즉시 건너뜀. (숨김 처리의 표준 방법)
- [ ] Renderer3D는 `lastMeshKey_`/`lastMaterialKey_` 소형 캐시로 연속 동일 키의 Find를 생략한다.
- [ ] 행벡터 규약: `Scale × RotationY × Translation × RotationY(공전)` — 왼쪽부터 적용. 회전 후 이동.
- [ ] 디폴트 3D 셰이더 = 고정 방향광 람버트 + 앰비언트 0.25 (VertexPNT용).
- [ ] 16바이트 배수: FrameConstants 144바이트(64+64+16), ObjectConstants 64바이트.
