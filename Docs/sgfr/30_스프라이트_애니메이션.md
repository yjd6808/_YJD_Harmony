# 30. 스프라이트 애니메이션 — 스프라이트 시트, FPS, 이징

> 관련 코드: `Projects/sgfr/Sources/sgfr/30_SpriteAnimation/30_SpriteAnimation_Main.cpp`, `30_SpriteAnimation_Function.cpp`
> 실행: sgfr 실행 후 콘솔 메뉴에서 30번 선택 (창이 뜨면 ESC로 종료)
> 선행 학습: `25_렌더_타깃.md`(UV 개념), `28_입력_처리.md`(동적 버퍼), `29_씬과_사운드.md`(스프라이트)

## 1. 이 장에서 배우는 것

한 텍스처에 여러 애니메이션 프레임을 바둑판처럼 모아둔 **스프라이트 시트**에서 **UV 오프셋/스케일로 원하는 프레임을 오려내는** 방법, 경과 시간을 프레임 번호로 바꾸는 **FPS 변환**, 그리고 이동 진행도를 곡선 함수에 통과시키는 **이징(Easing)**을 배웁니다.

## 2. 실행하면 보이는 것

같은 애니메이션 캐릭터(맥동하는 원 + 하이라이트 점)가 **두 줄로 동시에 왔다갔다** 합니다.

- **윗줄(Before)**: 항상 **선형(등속)** 이동 — 기준선입니다.
- **아랫줄(After)**: 선택한 이징 적용 — 속도 곡선이 달라집니다.
- `1`: 선형 / `2`: 부드럽게(양끝 느림, 중간 빠름) / `3`: 바운스(도착 지점에서 통통 튐)
- `↑`/`↓`: 애니메이션 FPS 증감 (4~60). **FPS를 낮추면 걸음 동작이 뚝뚝 끊기지만 이동 속도는 그대로**입니다 — 프레임 애니메이션과 위치 이동이 독립적인 시간 축이라는 증거입니다.
- `ESC`: 종료

콘솔 설명의 핵심:

```
[스프라이트 시트(Sprite Sheet)란?]
 애니메이션 프레임들을 한 장의 큰 텍스처에 바둑판처럼 모아둔 것.
 텍스처 교체 없이 UV 오프셋만 바꿔서 프레임을 넘기므로 매우 빠르다!
```

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 스프라이트 시트 = "컷 이미지"가 한 장에 있는 사진 필름

옛날 플립북(책의 구석에 손으로 빠르게 넘기는 그림)을 생각해보세요. 16장의 컷이 연속해서 보이면 캐릭터가 움직이는 것처럼 보입니다. **스프라이트 시트**는 그 16장을 한 장의 큰 그림에 4x4 바둑판으로 붙여놓은 것입니다. 프레임 전환은 "종이(텍스처)를 바꾸는" 것이 아니라 **UV라는 자로 사진의 한 칸을 오려내서** 표시하는 것입니다. 종이 교체 비용(드로우 콜, 텍스처 전환)이 없어 매우 빠릅니다.

### 3-2. UV = 사진 위의 자(눈금)

텍스처는 (0,0)~(1,1)의 UV 좌표로 읽습니다. 4x4 시트라면:

- 한 칸의 크기(스케일) = 1/4 = 0.25
- (열, 행) 번째 칸의 시작점(오프셋) = (열×0.25, 행×0.25)

이 두 값만 바꾸면 텍스처 교체 없이 16프레임을 모두 보여줄 수 있습니다. 사진을 재인화하지 않고 자(UV)를 움직여 칸을 보여주는 것입니다.

### 3-3. FPS = 초당 몇 컷을 보여줄까

`frame = (int)(경과시간 × FPS) % 16` — 경과 시간에 FPS를 곱하고 전체 프레임 수로 나머지를 구합니다. 예: 1.0초가 지났고 FPS가 16이면 `16 % 16 = 0`번째(첫 번째) 컷, 2.1초면 33번째이므로 `33 % 16 = 1`번째 컷. 자동으로 순환합니다.

**중요**: 프레임 애니메이션의 시간 축과 위치 이동의 시간 축은 **완전히 독립적**입니다. FPS를 4로 낮춰도 캐릭터의 이동 속도는 1초에 한 번씩 움직이는 것이 아니라, "걸음 동작만 뚝뚝 끊길" 뿐입니다.

### 3-4. 이징 = 진행도를 곡선 함수에 통과시키기

이동 진행도 t(0~1)를 그대로 쓰면 기계적인 등속 이동입니다. t를 곡선 함수에 넣으면:

- 스무스스텝 `t²(3-2t)`: 출발/도착이 부드러움 (양끝 느림)
- Penner easeOutBounce: 도착 직전에 튕기는 반동

진행도는 "어디쯤 왔나"일 뿐입니다. 곡선 함수는 그 "어디쯤"을 다른 값으로 재분배할 뿐입니다. 가속 페달을 밟는 타이밍을 바꾸는 것과 같지요 — 도착 지점은 같지만 도착하는 느낌이 완전히 달라집니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 스프라이트 (Sprite) | 화면 위를 움직이는 2D 이미지 조각 | 움직이는 캐릭터 스티커 |
| 스프라이트 시트 (Sheet) | 여러 프레임을 한 장에 모아둔 텍스처 | 한 장에 컷을 붙인 플립북 |
| UV 오프셋/스케일 | 오려낼 칸의 시작점/크기 | 사진 자의 이동/확대 |
| 프레임 (Frame) | 애니메이션의 컷 하나 | 플립북 한 장 |
| FPS (프레임 레이트) | 초당 보여주는 컷 수 | 초당 넘기는 장수 |
| 이징 (Easing) | 진행도를 곡선 함수로 바꿔 속도 곡선을 조절 | 가속 페달 타이밍 |
| 스무스스텝 (Smoothstep) | t²(3-2t). 부드러운 가속/감속 곡선 | S자 가속 |
| Penner easeOutBounce | 도착 지점에서 튕기는 고전 이징 공식 | 공이 땅에 닿아 튐 |
| 핑퐁 (Ping-pong) | 0→1→0 왕복 진행도 | 탁구공 왕복 |
| WRITE_DISCARD | 이전 내용을 버리고 새 공간을 주는 맵 | 칠판 전체를 지우고 새로 쓰기 |

## 5. 코드 워크스루

### 5-1. 시트 텍스처를 CPU에서 직접 생성

```cpp
const _s32 sheetSize = 256;
_u8* pPixels = new _u8[sheetSize * sheetSize * 4];
FillSpriteSheetPixels(pPixels);

Texture sheetTexture;
const bool bTextureOk = sheetTexture.CreateFromMemory(&device, pPixels, sheetSize, sheetSize);
JC_DELETE_SAFE(pPixels);	// GPU로 복사되었으므로 CPU 메모리는 바로 해제
```

`FillSpriteSheetPixels`는 256x256 RGBA 버퍼에 4x4 = 16프레임을 절차적으로 그립니다:

- 프레임마다 원 반지름이 사인파로 변함: `radius = 0.3 + 0.15 * sin(2π × progress)`
- 색상은 무지개처럼 순환: RGB 각각 위상이 120도씩 밀린 사인파
- 하이라이트 점이 원 가장자리를 한 바퀴 회전 (`dotAngle = 2π × progress`)
- 원 밖은 투명(continue), 가장자리는 음영, 하이라이트 근처는 흰색

`CreateFromMemory`가 CPU 픽셀을 GPU 텍스처로 복사하므로 **CPU 메모리는 바로 해제**할 수 있습니다 (`JC_DELETE_SAFE`).

### 5-3. 동적 쿼드 버퍼와 셰이더

```cpp
VertexBuffer quadVb;
IndexBuffer quadIb;
if (!quadVb.Create(&device, quadVertices, sizeof(VertexPTC), 4, true) ||	// 동적!
	!quadIb.Create(&device, quadIndices, 6))
```

셰이더는 공용 `TextureShaderSource()`(NDC 통과 + UV 샘플)를 재사용합니다. 상태 설정:

```cpp
// 알파 블렌드: 캐릭터 주변의 투명 픽셀이 배경과 자연스럽게 섞이도록
device.SetBlendMode(GraphicDevice::BlendMode::bmAlpha);
// 도트 느낌을 살리기 위해 Point 샘플러 (픽셀아트 게임의 핵심 세팅!)
device.SetSampler(GraphicDevice::SamplerFilter::fmPoint, GraphicDevice::SamplerAddress::amClamp, 0);
```

- **bmAlpha**: 시트의 투명 영역이 배경을 덮지 않게 블렌드합니다.
- **fmPoint**: Linear로 보간하면 픽셀아트가 번져 보이므로, **도트 그대로** 가장 가까운 텍셀을 읽습니다.

### 5-4. 매 프레임 공통 계산 — 프레임 번호와 진행도

```cpp
// (1) 경과 시간 -> 프레임 번호. 4x4 시트이므로 16으로 나눈 나머지로 순환
const _s32 frame = (_s32)(elapsed * animFps) % 16;
const _s32 col = frame % 4;
const _s32 row = frame / 4;
const vec2 uvOffset = vec2(col * 0.25f, row * 0.25f);
const vec2 uvScale = vec2(0.25f, 0.25f);

// (2) 2초 주기 핑퐁: 0~1초는 왼->오른, 1~2초는 오른->왼 (왕복 이동)
const _f32 cycle = fmodf(elapsed, 2.0f);
const _f32 pingPong = (cycle < 1.0f) ? cycle : 2.0f - cycle;

// (3) 이동 진행도(0~1)에 이징 적용. 윗줄은 항상 선형(=그대로), 아랫줄만 선택 모드!
const _f32 easedBefore = ApplyEasing(pingPong, 0);
const _f32 easedAfter  = ApplyEasing(pingPong, easingMode);

// (4) 진행도 -> 화면 x좌표 (NDC -0.6 ~ +0.6)
const _f32 posXBefore = Lerp(-0.6f, 0.6f, easedBefore);
const _f32 posXAfter  = Lerp(-0.6f, 0.6f, easedAfter);

// 종횡비 보정: NDC는 화면 비율과 무관하므로 x를 나누어 정사각형으로 보이게 한다
const vec2 halfSize = vec2(0.25f / window.AspectRatio(), 0.25f);
```

- 핑퐁: `fmodf(elapsed, 2)`로 0~2초 주기를 만들고, 1초를 넘으면 `2 - cycle`로 감소 구간을 만듭니다 (0→1→0 왕복).
- 두 줄은 **같은 frame과 같은 pingPong**을 공유하므로, 오직 이징만 다릅니다 — 순수한 Before/After 비교가 됩니다.
- aspect 보정: 25번과 달리 여기서는 **x 반폭을 aspect로 나누는** 방식을 씁니다 (결과는 같습니다).

### 5-5. 그리기 — 같은 동적 버퍼를 프레임당 2번

```cpp
// --- [Before] 윗줄 (y=+0.4): 항상 선형 이동 = 기준선 ---
FillSpriteQuad(quadVertices, vec2(posXBefore, +0.4f), halfSize, uvOffset, uvScale);
quadVb.Update(&device, quadVertices, 4);
quadVb.Bind(&device);
device.Context()->DrawIndexed(6, 0, 0);

// --- [After] 아랫줄 (y=-0.4): 선택한 이징 적용 ---
FillSpriteQuad(quadVertices, vec2(posXAfter, -0.4f), halfSize, uvOffset, uvScale);
quadVb.Update(&device, quadVertices, 4);
quadVb.Bind(&device);
device.Context()->DrawIndexed(6, 0, 0);
```

**같은 동적 버퍼를 한 프레임에 두 번 Update→Draw해도 되는 이유**는 `WRITE_DISCARD` 때문입니다. 맵 시점에 GPU가 아직 그리는 중인 이전 내용은 버려져도 상관없도록 **새 공간**을 할당받으므로, 첫 번째 Draw와 두 번째 Update 사이의 순서가 꼬이지 않습니다.

`FillSpriteQuad`는 UV를 `uvOffset ~ uvOffset + uvScale` 범위로 설정해 시트의 한 칸만 샘플링되게 합니다:

```cpp
_pOutVertices4[1] = { vec3(_center.x + _halfSize.x, _center.y + _halfSize.y, 0.0f),
	vec2(_uvOffset.x + _uvScale.x, _uvOffset.y), white };
// (4개 정점 모두 offset/offset+scale 조합)
```

### 5-6. 이징 함수 — ApplyEasing

```cpp
_f32 ApplyEasing(_f32 _t, _s32 _mode)
{
	const _f32 t = Clamp(_t, 0.0f, 1.0f);

	if (_mode == 1)
	{
		// [부드럽게] 스무스스텝: 천천히 출발 -> 중간에 빠르게 -> 천천히 도착
		return t * t * (3.0f - 2.0f * t);
	}

	if (_mode == 2)
	{
		// [바운스] 도착 지점에서 공처럼 몇 번 튀는 고전 공식 (Robert Penner의 easeOutBounce)
		_f32 tb = t;
		if (tb < 1.0f / 2.75f)      { return 7.5625f * tb * tb; }
		if (tb < 2.0f / 2.75f)      { tb -= 1.5f / 2.75f; return 7.5625f * tb * tb + 0.75f; }
		if (tb < 2.5f / 2.75f)      { tb -= 2.25f / 2.75f; return 7.5625f * tb * tb + 0.9375f; }
		tb -= 2.625f / 2.75f;
		return 7.5625f * tb * tb + 0.984375f;
	}

	// [선형] 그대로 반환. 등속 이동 (기계적인 느낌)
	return t;
}
```

Penner 바운스는 진행도를 4개의 구간(첫 도약, 두 번째, 세 번째, 마지막 튐)으로 나누어 포물선들을 이어붙인 것입니다. 상수 7.5625와 2.75는 최고점이 정확히 1에 도달하도록 정해진 값입니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. 텍스처 하나로 16프레임 — 메모리와 캐시 관점

시트 256x256 = 256KB의 VRAM 텍스처 하나로 16개의 애니메이션 프레임을 표현합니다. 텍스처를 16장 만들면 4MB가 필요하고, **텍스처 스위치(바인딩 변경)**가 프레임마다 일어나 드로우 콜이 흩어지지만, 시트 방식은:

1. **VRAM 절약**: 16장 대신 1장.
2. **텍스처 스위치 없음**: 셰이더의 t0 슬롯 바인딩이 프레임 전체에서 변하지 않음 → 배치(드로우 콜 합치기)가 그대로 유지됨.
3. **캐시 효율**: 애니메이션 프레임은 공간적으로 가깝기 때문에(64x64 칸), 연속 프레임을 넘길 때 텍스처 캐시의 인접 영역이 히트할 확률이 높습니다.

하드웨어에서 UV는 **텍셀 주소로 변환**됩니다: `texelX = u × 시트너비`. 예를 들어 UV 0.25는 256픽셀 중 64번째 텍셀에 해당합니다. 래스터라이저가 정점 UV를 삼각형 내부에서 **선형 보간**하고, 샘플러가 그 위치의 텍셀을 텍스처 캐시에서 읽습니다.

### 6-2. Point 필터와 "픽셀 아트"의 하드웨어 의미

Point(네어레스트) 필터는 보간 없이 **가장 가까운 텍셀 1개**를 선택합니다. 텍셀 위치의 소수부는 버려집니다(반올림). 하드웨어에서:

- Linear는 2x2 텍셀을 읽어 부동소수점 보간(4회 곱셈/덧셈)을 합니다.
- Point는 1텍셀만 읽어 보간이 없습니다 → **캐시 트래픽과 ALU가 더 적습니다.**

그래서 픽셀아트 게임은 Point를 쓰면 도트가 또렷하게 보이고(의도된 계단), Linear는 번져 보입니다. `amClamp`는 UV가 칸을 벗어나지 않게 하는 안전장치입니다.

### 6-3. 알파 블렌드가 원형 캐릭터를 만드는 과정

시트의 원 밖 픽셀은 알파=0(투명)입니다. `bmAlpha` 블렌드는 ROP(블렌드 유닛)에서 `결과 = 소스×srcAlpha + 목적지×(1-srcAlpha)`를 계산합니다.

- 원 안쪽 픽셀: 알파≈1 → 거의 불투명하게 덮음
- 원 경계 픽셀: 알파 중간 → 배경과 섞임
- 원 밖: 알파=0 → 배경이 그대로 유지됨

이 블렌드 연산은 **픽셀당 여러 번의 병렬 연산**이지만 ROP는 대역폭이 넉넉한 하드웨어 유닛이므로, 화면 크기에 비례하는 저비용 연산입니다. 800x600의 두 줄 캐릭터 정도는 전체 프레임 시간의 극히 일부를 차지합니다.

### 6-4. 이징 계산은 어디서 도는가

이징/핑퐁/프레임 번호 계산은 전부 **CPU의 ALU/FPU**에서 실행됩니다 (일반 사칙연산 + sin/cos은 28번에서 본 것처럼 부동소수점). GPU에는 **부동소수점 좌표가 담긴 버퍼가 매 프레임 업로드**되고, GPU의 VS가 NDC 통과만 수행합니다. 즉 이 장의 "성능 부담"은 사실상:

1. CPU: 사인파/이징 계산 (극히 가벼움)
2. PCIe: 정점 8개(두 줄) 업로드 (무시 가능)
3. GPU: 삼각형 4개 래스터화 + 2회 샘플링 (화면의 작은 영역)

애니메이션 로직을 CPU에서 계산하는 이유는 **게임 로직이 CPU에 있기 때문**입니다. 캐릭터 상태(체력, 위치)는 CPU가 결정하고, "이번 프레임의 모습"을 GPU에 넘기는 구조입니다. 고급 기법으로는 정점 셰이더가 전부 처리하는 GPU 애니메이션(스키닝 등)이 있습니다.

## 7. 핵심 규칙 요약

- 시트 UV: `offset = (열/N, 행/N)`, `scale = 1/N` — 텍스처 교체 없이 프레임 전환.
- 프레임 번호: `(int)(elapsed × fps) % 전체프레임수`.
- **프레임 애니메이션의 FPS와 위치 이동은 독립적인 시간 축** (FPS를 낮춰도 이동 속도 유지).
- 이징 = 진행도 t를 곡선 함수에 통과 (스무스스텝 `t²(3-2t)`, Penner easeOutBounce).
- 같은 동적 버퍼를 프레임당 2번 Update→Draw해도 됨 (WRITE_DISCARD가 순서 보호).
- 픽셀아트 = Point 샘플러 + 알파 블렌드(bmAlpha).
- CPU 픽셀 버퍼는 `CreateFromMemory` 후 즉시 해제 (`JC_DELETE_SAFE`).
- 전역 상태(블렌드 등)는 다음 장을 위해 복원 (`bmNone`).
