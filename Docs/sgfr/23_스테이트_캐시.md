# 23. 스테이트 캐시 — 같은 바인딩은 다시 하지 않는다

> 관련 코드: `Projects/sgfr/Sources/sgfr/23_StateCache/` (`23_StateCache_Main.cpp`)
> 엔진 코드: `Projects/sgf/Sources/sgf/Graphics/GraphicContext.h/.cpp` (바인딩 캐시 + 통계), `SceneRenderer.h/.cpp`
> 실행: sgfr 실행 후 콘솔 메뉴에서 **23번** 선택
> 선행 학습: 22번(렌더 오브젝트 루프), 20~21번(머티리얼/리소스 매니저)

## 1. 이 장에서 배우는 것

**GraphicContext**가 마지막으로 바인딩한 값을 기억해 **같은 값이면 D3D11 호출을 생략**하는 스테이트 캐시의 동작을 배웁니다. 10×10=100개 큐브를 그리며 "API 호출: n, 생략: m" 통계를 창 제목으로 직접 확인하고, 1번 키로 캐시를 끄면(v2 방식 흉내) 수치가 어떻게 변하는지 비교합니다. 실전 렌더러에 스테이트 캐시가 필수인 이유를 수치로 체감하는 장입니다.

## 2. 실행하면 보이는 것

위에서 내려다보는 카메라 시점에 **10×10 = 100개의 큐브**가 격자로 배치되어 회전합니다. 창 제목이 매 프레임 갱신됩니다:

```
23. 스테이트 캐시 [캐시 켜짐] - API 호출: 218, 생략: 1570 (1 토글, ESC 종료)
```

| 키 | 동작 |
|---|---|
| `1` | 캐시 무력화 토글 (매 Draw 앞 InvalidateCache = v2 방식 흉내) |
| `ESC` | 종료 |

캐시가 켜져 있을 때는 모든 큐브가 같은 메시/머티리얼을 공유하므로 "생략" 수가 "호출" 수보다 몇 배 많습니다. `1`번을 누르면 `[캐시 꺼짐]`으로 바뀌고, 생략이 0으로 떨어지며 호출 수가 급증합니다. 같은 화면인데 수치가 확 바뀌는 모습이 이 장의 하이라이트입니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 스테이트 캐시 = "손이 기억하는 스위치"

식당 주방에서 "가스 불 세기"를 생각해 봅시다. 요리할 때마다 **현재 불이 어느 세기인지 확인하고, 이미 맞으면 그대로 두는** 것이 현명합니다. 매번 손잡이를 꺾었다 놓으면 불필요한 동작이고, 가스 밸브처럼 "꺾는 동작" 자체에 비용이 들면 더 심각합니다. GraphicContext는 바로 이 "손의 기억"입니다:

- `SetXxx(값)` 호출이 오면 **직전에 바인딩한 값과 비교**하고,
- 같으면 `skippedCallCount_ += 1` 후 **즉시 반환** (D3D 호출 생략),
- 다르면 실제 `ID3D11DeviceContext` 호출을 하고 `apiCallCount_ += 1`.

### 3-2. 캐시를 비워야 하는 순간: "밖에서 손이 갔을 때"

`BeginFrame`은 GraphicContext를 거치지 않고 **원시 `ID3D11DeviceContext`로 직접** 배경 지우기·뷰포트 설정을 수행합니다. 주방에 비유하면, 손님(외부 코드)이 직접 주방에 들어와 밸브를 조작한 뒤 "그대로예요"라고 말하는 상황입니다. 그래서 매 프레임 `BeginFrame` 직후 `context.InvalidateCache()`를 호출해 **손의 기억을 지웁니다.** 기억을 지우면 다음 바인딩은 전부 "다른 값"으로 판정되어 실제 호출이 갑니다 — 틀린 기억보다 안전한 재확인이 낫기 때문입니다.

### 3-3. "캐시 끄기" = v2 방식의 재현

`1`번 키를 누르면 Draw **앞마다** `InvalidateCache()`를 호출합니다. 그러면 모든 Draw가 "처음 그리는 것처럼" 전부 실제 바인딩을 수행합니다. 이것이 스테이트 캐시가 없던 v2 렌더러의 동작입니다. 같은 씬을 그리는데 D3D 호출이 몇 배로 늘어나는 것을 보고, 캐시가 CPU 오버헤드를 줄여주는 장치임을 실감합니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 스테이트 캐시 | 직전 바인딩을 기억해 중복 호출을 생략 | 손이 기억하는 스위치 |
| API 호출 수 | 실제로 D3D에 내려간 호출 횟수 | 밸브를 실제로 꺾은 횟수 |
| 생략 수 | 캐시 덕에 건너뛴 호출 횟수 | "이미 맞네" 하고 넘긴 횟수 |
| InvalidateCache | 캐시를 비워 전부 재바인딩하게 만들기 | 손의 기억 지우기 |
| 프레임 통계 | ResetStats로 매 프레임 새로 재는 수치 | 일일 매출 장부 |
| 즉시 컨텍스트 | D3D11의 CPU→GPU 명령 창구 | 주방의 단일 작업대 |
| 오버헤드 | 본연의 작업에 붙는 부가 비용 | 포장지와 스티커 |

## 5. 코드 워크스루

`StateCache_Main()`의 흐름을 따라갑니다. 초기화(윈도우/입력/디바이스/리소스 매니저/SceneRenderer)는 22번과 거의 동일하므로 차이점 중심으로 봅니다.

### 5-1. 100개가 공유하는 메시 하나

```cpp
Mesh* pCube = dbg_new Mesh();
pCube->InitializeAsCube(&device, g_cResourceMgr.GetDefaultVertexShader3D());
pCube->SetDebugName("CacheDemoCube");
const _u64 cubeMeshKey = g_cResourceMgr.Add(pCube);

RenderObject object;                                  // 하나만 만든다!
object.meshKey_ = cubeMeshKey;
object.materialKey_ = g_cResourceMgr.GetDefaultMaterial3DKey();
```

**의도적인 설계**: 큐브 메시 하나와 머티리얼 하나를 100개 오브젝트가 공유합니다. 그래야 바인딩이 반복적으로 "같은 값"이 되고 캐시 적중률이 극대화됩니다. 만약 100개가 각자 다른 머티리얼을 가졌다면 캐시가 할 일이 없었을 것입니다.

### 5-3. 렌더 루프와 통계 출력

```cpp
device.BeginFrame(color(0.06f, 0.06f, 0.1f, 1.0f));
context.InvalidateCache();   // BeginFrame이 원시 상태를 건드렸으므로 캐시를 비운다
context.ResetStats();        // 이번 프레임 통계만 재다

renderer.BeginScene(frame);

for (int z = 0; z < CUBE_GRID_SIZE; ++z)
{
	for (int x = 0; x < CUBE_GRID_SIZE; ++x)
	{
		if (bCacheDisabled)
		{
			context.InvalidateCache();   // v2 흉내: 매번 "처음 그리는 척"
		}
		RenderObject& drawn = object;
		drawn.world_ =
			mat4::Scale(0.35f) *
			mat4::RotationY(elapsed + (_f32)(x + z) * 0.2f) *
			mat4::Translation((_f32)(x - CUBE_GRID_SIZE / 2) * 1.5f, 0.0f, (_f32)(z - CUBE_GRID_SIZE / 2) * 1.5f);
		renderer.Draw(drawn);
	}
}

wchar_t szTitle[256];
swprintf_s(szTitle, L"23. 스테이트 캐시 [%s] - API 호출: %llu, 생략: %llu (1 토글, ESC 종료)",
	bCacheDisabled ? L"캐시 꺼짐" : L"캐시 켜짐",
	context.GetApiCallCount(),
	context.GetSkippedCallCount());
window.SetTitle(szTitle);
device.EndFrame(true);
```

- 각 큐브는 `Scale(0.35) × RotationY(시간+격자마다 다른 위상) × Translation(격자 위치)`로 그려지고, **월드 행렬만 다릅니다.** 월드 행렬은 b1 상수버퍼이므로 매 Draw마다 실제로 갱신됩니다 — 이것은 캐시가 생략할 수 없는 "오브젝트별 필수 작업"입니다.
- 캐시가 생략하는 것은 **메시 VB/IB/레이아웃/토폴로지, 셰이더, 상태 4종, 텍스처, b2** 같은 "같은 값 반복 바인딩"입니다.
- `ResetStats()`는 프레임 시작에서 카운터를 0으로 되돌려 "이번 프레임"의 수치만 재게 합니다.
- 통계는 매 프레임 `swprintf_s` + `window.SetTitle`로 창 제목에 반영됩니다.

### 5-4. 캐시 무력화 토글

```cpp
if (input.IsKeyPressed('1'))
{
	bCacheDisabled = !bCacheDisabled;
}
```

Draw 100회 **각각 앞에서** `InvalidateCache()`가 호출되면, 22번에서 배운 SceneRenderer의 키 해석 캐시(Find 생략)는 그대로 동작하지만 GraphicContext의 바인딩 캐시는 매번 비워져 모든 상태가 "처음"으로 인식됩니다. 그래서 D3D 호출이 전부 실제로 내려갑니다.

정리 순서: `renderer.Finalize()` → `g_cResourceMgr.Finalize()` → `device.Finalize()` → `window.Destroy()`.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. D3D11 즉시 컨텍스트 호출의 실제 비용

`ID3D11DeviceContext`의 메서드(VSSetShader, PSSetShaderResources, RSSetState, OMSetBlendState 등)는 GPU로 직접 가는 것이 아니라 **드라이버 런타임이 수행하는 함수 호출**입니다. 각 호출은 내부적으로 ① 인자 검증(유효성/범위 체크), ② 디바이스 상태와의 일관성 검사, ③ 명령 버퍼(커맨드 버퍼)에 기록, ④ 상태 추적 갱신을 거칩니다. 커맨드 버퍼는 CPU 메모리에 쌓였다가 GPU가 실행할 때 DMA로 전송되는 일급 구조입니다. 따라서 "바인딩 호출 1회"는 GPU 연산이 아니라 **CPU 사이클과 메모리**를 소모하는 작업이고, 100개 오브젝트 × 수십 개 호출이면 CPU가 파이프라인을 채우는 속도(드로우를 기록하는 속도)가 병목이 될 수 있습니다. 이것이 "드로우 콜 줄이기"와 "중복 상태 설정 줄이기"가 실전 엔진의 최우선 과제인 하드웨어적 이유입니다.

### 6-2. 캐시가 덮는 레지스터 공간

GraphicContext의 캐시 배열은 실제로 D3D11의 **각 스테이지 레지스터 슬롯**을 그대로 미러링합니다(GraphicContext.h:102):

| 캐시 배열 | 대응 D3D11 레지스터 | 상태 |
|---|---|---|
| `pCachedVs_/pCachedPs_` | VS/PS 셰이더 스테이지 | 1개씩 |
| `pCachedRasterizer_/pCachedBlend_/pCachedDepth_` | RS/OM 단계 상태 | 1개씩 |
| `pCachedSrvs_[stage][8]` | t0~t7 텍스처 레지스터 | 스테이지×슬롯 |
| `pCachedSamplers_[stage][8]` | s0~s7 샘플러 레지스터 | 스테이지×슬롯 |
| `pCachedCbuffers_[stage][8]` | b0~b7 상수버퍼 레지스터 | 스테이지×슬롯 |

"같은 값"의 판정 기준은 **D3D11 객체의 포인터(ID3D11Xxx\*)**입니다. 같은 객체를 다시 바인딩하면 생략하고, 다른 객체(같은 설정이라도 다른 인스턴스)면 다시 호출합니다. 그래서 엔진의 `RenderStates`가 상태 객체를 **캐싱·재사용**하는 것이 이 캐시의 적중률을 높이는 전제 조건입니다 — 매번 새 `ID3D11RasterizerState`를 만들었다면 포인터가 항상 달라져 캐시가 무력화되기 때문입니다.

참고로 캐시가 생략하지 못하는 호출도 있습니다. `SetViewport`는 값이 작아 포인터 비교가 오히려 비싸다고 판단해 캐시 없이 **항상 적용**합니다(GraphicContext.cpp:251). 즉 스테이트 캐시도 "모든 것을 기억하는" 만능이 아니라, **포인터 하나로 비교 가능한 객체 바인딩만** 다루는 절충 설계라는 점이 중요합니다. 이 원칙은 상수버퍼의 내용(월드 행렬)처럼 매번 달라지는 데이터에는 적용할 수 없고, "어떤 객체를 꽂는가"에만 해당합니다.

### 6-3. 왜 BeginFrame 후에는 캐시를 비워야 하는가

`GraphicDevice::BeginFrame`은 GraphicContext를 거치지 않고 `swapChain_.RTV()`·`depthSurface_.DSV()`를 직접 `OMSetRenderTargets`로 바인딩하고 `ClearRenderTargetView`·`ClearDepthStencilView`를 호출합니다(GraphicDevice.cpp:300). GraphicContext의 캐시는 이 호출들을 **보지 못합니다.** 만약 캐시를 비우지 않으면, 프레임이 바뀐 뒤에도 "지난 프레임과 같은 값"이라는 잘못된 판단으로 실제 바인딩을 생략할 수 있습니다(특히 다른 렌더 타깃으로 바꿨다 돌아온 경우 25번 이후). `InvalidateCache()`는 캐시의 모든 원소를 nullptr로 초기화해 다음 호출을 전부 "변경"으로 만들고, 이것은 잘못된 생략보다 비용이 저렴하므로 **매 프레임** 수행하는 안전 규칙입니다. D3D12로 옮겨가면 이 규칙이 "디스크립터 힐 재설정"으로 진화합니다.

### 6-4. 통계가 알려주는 성능 지표

`GetApiCallCount()`/`GetSkippedCallCount()`는 프레임 단위로 GPU가 아니라 **CPU가 수행한 작업량**을 측정합니다. 이 장의 실험에서 "생략 수 = 호출 수 × 몇 배"라는 비율은 바인딩의 중복도, 즉 "오브젝트 수가 늘어도 상태 설정은 한 번만 하면 되는 구조"를 증명합니다. 실제 게임 엔진은 같은 이유로 **재질별 정렬**(같은 머티리얼 오브젝트를 모아 그리기)을 수행합니다 — 같은 상태를 한 번만 바인딩하고 world 행렬만 바꿔가며 그리는 것이 이 장의 100개 큐브 실험 그 자체입니다. 이 정렬 기법은 30번 스프라이트 애니메이션의 배칭과도 이어집니다.

주의할 점: 이 통계는 어디까지나 **CPU 측 호출 수**이지 프레임 시간(GPU 비용)이 아닙니다. 캐시를 꺼도 GPU는 같은 픽셀을 같은 횟수로 그리므로 화면은 동일합니다. 변하는 것은 CPU가 상태 검증·명령 기록에 소비하는 시간입니다. 100개 큐브에서는 수치가 크게 보이지만 실제 성능 영향은 드로우 수가 수만 개가 되고 셰이더/상태 전환이 잦아질 때 드러납니다 — 그때가 되면 이 장의 실험이 "미리 배운 예습"이 되는 셈입니다. 통계를 프레임 단위로 리셋하는 `ResetStats()`는 카운터 두 개를 0으로 되돌릴 뿐이며, 캐시 내용에는 영향을 주지 않아 `InvalidateCache()`와는 별개의 작업임도 기억해 두세요.

## 7. 핵심 규칙 요약

- [ ] GraphicContext는 **같은 값을 다시 바인딩하면 D3D 호출을 생략**한다 (포인터 비교).
- [ ] `GetApiCallCount()` = 실제 호출 수, `GetSkippedCallCount()` = 생략 수. `ResetStats()`로 프레임 단위 리셋.
- [ ] `BeginFrame`은 원시 컨텍스트를 직접 건드리므로 **매 프레임 직후 `InvalidateCache()`가 필수**.
- [ ] 캐시 무력화(1번 키) = 매 Draw 앞 InvalidateCache = v2 방식. 호출 수가 급증한다.
- [ ] **같은 메시/머티리얼을 최대한 공유**하는 것이 캐시 적중률을 극대화한다 (재질별 정렬의 근거).
- [ ] 월드 행렬(b1)은 오브젝트마다 다르므로 캐시와 무관하게 매 Draw 갱신된다 — 캐시가 아끼는 것은 "같은 상태"의 반복 바인딩이다.
