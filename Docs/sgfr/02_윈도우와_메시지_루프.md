# 02. 윈도우와 메시지 루프 — 그림을 그릴 '종이' 만들기

> 관련 코드: `Projects/sgfr/Sources/sgfr/02_WindowAndMessageLoop/` (`02_WindowAndMessageLoop_Main.cpp`, `02_WindowAndMessageLoop_Function.cpp`)
> 실행: sgfr 실행 후 콘솔 메뉴에서 **2번** 선택
> 선행 학습: 01. 선형대수 (선택 — 이번 장은 수학이 거의 필요 없음)

## 1. 이 장에서 배우는 것

GPU에게 "그려라"라고 명령하기 전에, 그림이 그려질 **창(윈도우)**이 있어야 합니다. 이 장은 Windows 운영체제에서 창이 어떤 절차로 만들어지는지(RegisterClassEx → AdjustWindowRect → CreateWindowEx), 그리고 운영체제가 보내는 이벤트를 게임이 매 프레임 꺼내 처리하는 **메시지 루프**가 무엇인지 배웁니다. 또한 키 입력을 받는 두 가지 방식인 **이벤트 방식**과 **폴링 방식**을 직접 실험합니다.

## 2. 실행하면 보이는 것

800×600 크기의 창이 하나 뜹니다. 콘솔에는 "윈도우가 생성되었습니다. 아무 키나 마우스를 눌러보세요"라는 안내가 출력됩니다. 이제:

- 아무 키나 누르면 콘솔에 `[이벤트] 키 누름: A (코드: 0x41)`처럼 키 이름과 코드가 출력됩니다.
- 마우스 버튼을 누르면 `[이벤트] 마우스 왼쪽 버튼 클릭: (400, 300)`처럼 좌표가 출력됩니다.
- **ESC**를 누르거나 창의 X 버튼을 누르면 "ESC 입력 -> 종료"가 출력되며 프로그램이 목차로 돌아갑니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 윈도우는 "예약 신청" 후에야 만들어집니다

식당에 가면 손님은 "테이블 종류"를 정해 신청해야 자리가 배정됩니다. Windows도 마찬가지입니다. 먼저 `RegisterClassEx`로 "이런 모양·동작의 창을 만들겠다"고 신청서를 제출하고, 그다음 `CreateWindowEx`로 실제 창을 받습니다. 이때 창의 **식별번호(HWND)**가 발급되는데, 이것이 이후 모든 그래픽 명령이 "이 창에 그려라"라고 가리키는 주소입니다.

### 3-2. 메시지 큐 = 은행 창구의 대기 번호표

운영체제는 키 입력, 마우스 클릭, 창 크기 변경 같은 모든 사건을 프로그램의 **메시지 큐**라는 대기줄에 번호표로 쌓아둡니다. 프로그램이 이 대기줄을 치우지 않으면 OS는 더 이상 일을 줄 수 없고, 결국 창은 "응답 없음" 상태가 됩니다. 게임은 `PumpMessage()`로 매 프레임 이 대기줄을 비우며, 큐가 비면 (GetMessage 대신 PeekMessage를 쓰므로) 블로킹 없이 바로 게임 로직으로 넘어갑니다.

### 3-3. 이벤트 방식 vs 폴링 방식 = 우체국 vs 벽 시계

키 입력을 받는 방법은 두 가지입니다. **이벤트 방식**은 "키가 눌린 그 순간"에만 알림이 오는 것으로, 우체국이 소포가 도착할 때마다 전화하는 것과 같습니다. **폴링 방식**은 "지금 이 순간 키가 눌려 있나?"를 매 프레임 직접 묻는 것으로, 벽에 걸린 시계를 볼 때마다 시간을 확인하는 것과 같습니다. 게임은 대부분 폴링을 쓰는데, 이유는 키를 **누르고 있는 상태**를 유지해야 하기 때문입니다. 이 장에서는 두 방식 모두를 사용해 비교합니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| HWND | 창의 식별 번호 (핸들) | 창의 주민등록번호 |
| RegisterClassEx | 창의 종류를 OS에 등록 | 식당 예약 신청서 |
| CreateWindowEx | 실제 창 생성 | 자리 배정 받기 |
| 메시지 큐 | OS가 보낸 사건들의 대기줄 | 은행 대기 번호표 |
| PumpMessage | 대기줄의 메시지를 꺼내 처리 | 매 프레임 번호표 뽑기 |
| WM_QUIT | "창 닫혔음, 종료해라" 메시지 | 영업 종료 종 |
| WndProc | 메시지를 처리하는 콜백 함수 | 각 사건별 응대 매뉴얼 |
| 폴링 (Polling) | 매 프레임 상태를 직접 물어봄 | 벽시계 보기 |
| 이벤트 (Event) | 사건 발생 순간의 알림 | 도착 전화 |
| 가상 키코드 (VK_*) | 키보드 종류와 무관한 키 번호 | 키의 표준 이름표 |

## 5. 코드 워크스루

`02_WindowAndMessageLoop_Main.cpp`의 `WindowAndMessageLoop_Main()`을 따라갑니다.

### 5-1. 윈도우 생성 (코드 36~41행)

```cpp
Window window;
if (!window.Create(L"02. 윈도우와 메시지 루프 (ESC로 종료)", 800, 600))
{
	printf("윈도우 생성 실패!\n");
	return;
}
```

`Window::Create` 내부(`Projects/sgf/Sources/sgf/Core/Window.cpp`)에서는 세 단계가 진행됩니다.

1. `RegisterClassEx` — 창 클래스 등록
2. `AdjustWindowRect` — 요청한 800×600이 **그림 영역(클라이언트 영역)**이 되도록 테두리까지 포함한 전체 크기를 계산
3. `CreateWindowEx` — 실제 창 생성 및 HWND 발급

### 5-2. 입력 관리자 연결과 이벤트 등록 (코드 44~60행)

```cpp
InputManager input;
window.ConnectInput(&input);

input.onKeyPressed.Register(1, [](int _vkCode)
{
	printf("[이벤트] 키 누름: %s (코드: 0x%02X)\n", VkCodeToName(_vkCode), _vkCode);
});
```

`ConnectInput`은 윈도우의 WndProc가 받은 키/마우스 메시지를 `InputManager::HandleMessage`로 흘려보내도록 연결합니다. `onKeyPressed.Register(1, ...)`의 `1`은 구독 ID로, 나중에 `Unregister(1)`로 해제할 수 있습니다. `VkCodeToName`(Function.cpp)은 가상 키코드를 이름으로 바꿔주며, 특이점으로 알파벳/숫자 키는 ASCII 코드와 값이 같아서 `'A' == 0x41 == VK_A`입니다.

### 5-3. 메시지 루프 (코드 66~82행) — 게임 루프의 뼈대

```cpp
while (window.PumpMessage())
{
	if (input.IsKeyPressed(VK_ESCAPE))
	{
		printf("ESC 입력 -> 종료\n");
		break;
	}
	input.NextFrame();
	Sleep(1);
}
```

- `PumpMessage()`가 `true`를 반환하는 동안 계속 돕니다. **false를 반환하면 WM_QUIT(창 닫힘)이 도착한 것**이라 루프를 빠져나갑니다.
- 루프 안에서 `IsKeyPressed(VK_ESCAPE)`로 매 프레임 ESC 상태를 폴링합니다.
- `input.NextFrame()`은 현재 키 상태를 "이전 프레임 상태"로 복사해, 다음 프레임의 `IsKeyPressed`가 "막 눌린 첫 프레임"을 정확히 구분할 수 있게 합니다. (이것이 없으면 키가 눌린 상태가 계속 눌린 것으로 처리됩니다.)
- `Sleep(1)`은 아직 그리기가 없어 빈 루프가 CPU 한 코어를 100% 점유하지 않도록 1ms씩 양보하는 것입니다.

### 5-4. 정리 (코드 85~89행)

`window.Destroy()`로 창을 파괴하고, `input.onKeyPressed.Unregister(1)`로 이벤트 구독을 해제합니다.

### 사용된 sgf API 정리

| API | 역할 |
|---|---|
| `Window::Create(title, w, h)` | 윈도우 생성 (내부: RegisterClassEx → AdjustWindowRect → CreateWindowEx) |
| `Window::PumpMessage()` | 메시지 큐 처리, false = WM_QUIT |
| `Window::Destroy()` | 창 파괴 |
| `Window::ConnectInput(&input)` | 입력 메시지를 InputManager로 전달 |
| `InputManager::IsKeyPressed(VK_ESCAPE)` | 폴링: 방금 눌렸는지 |
| `InputManager::NextFrame()` | 현재 상태를 이전 프레임 상태로 갱신 |
| `input.onKeyPressed.Register(id, lambda)` | 이벤트: 키가 눌린 순간 호출 |
| `input.onMousePressed.Register(id, lambda)` | 이벤트: 마우스 버튼 눌린 순간 (버튼, x, y 인자) |
| `VkCodeToName(vkCode)` | 가상 키코드 → 이름 문자열 |

## 6. GPU와 DX11, 하드웨어 깊이 보기

이 장의 내용은 CPU와 OS 레벨이지만, 이 장이 만드는 "메시지 루프 + 창" 구조가 GPU 렌더링과 어떻게 맞물리는지 이해하면 이후 장이 훨씬 쉽습니다.

### 6-1. Win32 메시지 루프가 GPU와 만나는 순간: 프레임 타이밍

게임의 렌더 루프는 본질적으로 "메시지 처리 → 입력 → 업데이트 → 그리기 → Present"의 반복입니다. 이 장은 그리기가 없어 `Sleep(1)`로 CPU를 놀게 했지만, 실제 게임은 `Sleep` 대신 **GPU의 수직동기화(VSync) 대기**를 사용합니다. `EndFrame(true)`(04번)가 Present를 호출할 때, GPU는 모니터의 주사선 갱신(보통 60~144Hz)에 맞춰 블로킹합니다. 이때 CPU가 놀고 있는 시간이 바로 "메시지 루프가 GPU의 페이스에 맞춰지는" 현상입니다.

### 6-2. PeekMessage vs GetMessage — 왜 게임은 GetMessage를 안 쓸까

Windows 프로그래밍 입문서에는 `GetMessage`가 나오지만, 게임 루프는 **PeekMessage**를 씁니다. `GetMessage`는 큐가 비면 프로그램을 잠들게 하는 블로킹 함수라서, 메시지가 없는 동안 게임 로직과 렌더링을 진행할 수 없습니다. 반면 `PeekMessage`는 큐가 비면 즉시 "메시지 없음"을 반환하므로, 게임은 남는 시간에 프레임을 계속 그릴 수 있습니다. `Window::PumpMessage`가 바로 PeekMessage를 사용합니다. 이 "큐가 비면 곧바로 다음 프레임" 구조 덕분에 게임은 1초에 수십~수백 프레임을 그릴 수 있습니다.

### 6-3. 메시지 스레드와 DirectX 디바이스의 스레드 제약

중요한 하드웨어/API 지식이 하나 있습니다: **D3D11 디바이스는 생성한 스레드에서 사용해야 하며(스레드 선호성), 메시지 루프는 메인 스레드에서 실행됩니다.** 따라서 이 장의 메시지 루프 스레드에서 다음 장의 `GraphicDevice`를 만들고 그리는 것이 자연스럽고 안전합니다. (멀티스레드 렌더링을 하려면 D3D11의 Deferred Context를 별도로 만들거나 렌더링 자체를 메인 스레드에 집중시키는 구조를 씁니다.) sgf 엔진이 v3에서 GraphicDevice와 GraphicContext를 분리한 이유 중 하나가 바로 이 멀티스레드 확장 대비입니다.

### 6-4. 하드웨어 입력: 키보드/마우스 → OS → 응용 프로그램의 경로

키를 누르면 키보드 컨트롤러(USB HID)가 인터럽트로 신호를 보내고, OS 드라이버가 **가상 키코드(VK_*)로 번역**한 뒤 포커스된 창의 메시지 큐에 WM_KEYDOWN으로 넣습니다. 여기서 "가상 키코드"의 의미가 드러납니다: 물리적 키보드의 배치(쿼티/드보락)와 무관하게 OS가 약속한 논리적 키 번호이므로, 게임은 키보드 종류를 신경 쓰지 않고 VK_A, VK_ESCAPE 같은 번호만 검사하면 됩니다. sgf의 `InputManager::HandleMessage`는 이 메시지를 해석해 폴링용 상태 배열(키가 눌려있는가)과 이벤트용 콜백(눌린 순간)을 각각 갱신합니다.

### 6-5. 왜 800×600일까 — 백버퍼 크기와의 관계

창 크기 800×600은 곧 04번에서 만들어질 **백버퍼(back buffer)의 픽셀 개수**가 됩니다. 800×600 = 480,000 픽셀, 각 픽셀이 RGBA 8비트 4채널이면 약 1.83MB입니다. 프론트버퍼와 백버퍼(더블 버퍼링)를 합치면 약 3.7MB가 GPU 메모리에서 이 창 하나를 위해 사용됩니다. `AdjustWindowRect`가 계산하는 것은 바로 이 픽셀 영역이 아니라, 창 전체(테두리+제목줄 포함)의 크기입니다 — "클라이언트 영역이 정확히 800×600이 되도록" 말입니다. 나중에 25번 렌더 타깃에서 화면 크기와 버퍼 크기의 불일치 문제를 만나게 되는데, 그 근본은 이 장의 창 크기 결정에서 시작됩니다.

### 6-6. Sleep(1)의 정밀도와 게임 루프의 진짜 대기 수단

`Sleep(1)`이 CPU 점유율을 낮추는 이유는 스레드가 최소 1ms(실제로는 OS 타이머 해상도상 1~2ms) 동안 실행 큐에서 빠져나가기 때문입니다. 하지만 Sleep은 절대 정확한 프레임 타이밍을 제공하지 못합니다 — OS가 스레드 스케줄링을 마음대로 하기 때문입니다. 실전 게임이 프레임율을 정확히 맞추는 방법은 두 가지입니다: 04번에서 배울 **VSync 대기**(GPU가 모니터 주사율에 맞춰 블로킹)와, 정밀 루프(Spin Wait)입니다. `FrameTimer`가 `QueryPerformanceCounter`(하드웨어 고해상도 타이머)를 쓰는 것도 이와 같은 이유입니다. 즉 이 장의 Sleep(1)은 "그릴 것이 없을 때 CPU를 놀려주는 임시방편"이고, 그리기가 생기면 VSync가 그 자리를 차지합니다.

### 6-7. 창 프로시저(WndProc)와 하드웨어 메시지 경로

키를 누르는 순간부터 콜백이 실행되기까지의 경로를 정리하면: 키보드 컨트롤러 → OS 드라이버 → 커널 메시지 큐 → 응용 프로그램 메시지 큐 → `PumpMessage`의 PeekMessage → `DispatchMessage` → `WndProcStatic` → `WndProc` → `InputManager::HandleMessage` → 이벤트 콜백 호출. 이 경로는 전부 CPU와 OS 커널을 거치므로, 입력 처리 자체가 GPU와 무관한 CPU 작업입니다. 따라서 게임 루프에서 "입력 → 갱신 → 그리기" 순서가 중요한 이유가 분명해집니다 — 입력은 이번 프레임의 결정(캐릭터 움직임)에, 그리기는 그 결정의 결과물에 쓰여야 한 프레임의 지연만 생기기 때문입니다. 이 한 프레임 지연을 줄이는 고급 기법(입력 지연 완화)은 실전 게임의 반응성 튜닝 주제로 이어집니다.

## 7. 핵심 규칙 요약

- [ ] 윈도우 생성 3단계: RegisterClassEx → AdjustWindowRect → CreateWindowEx.
- [ ] `PumpMessage()`가 false = WM_QUIT 도착 = 루프 종료.
- [ ] 게임 루프는 GetMessage가 아닌 PeekMessage(비블로킹) 기반.
- [ ] 이벤트 방식(누른 순간 콜백) vs 폴링 방식(매 프레임 상태 질문) — 게임은 폴링을 주로 사용.
- [ ] `input.NextFrame()`을 호출해야 IsKeyPressed가 "막 눌린 프레임"을 구분한다.
- [ ] `Sleep(1)`은 빈 루프의 CPU 100% 점유 방지용. 실전은 VSync 대기로 대체.
- [ ] 알파벳/숫자 키: ASCII 코드 == VK_ 코드 (`'A' == 0x41 == VK_A`).
- [ ] 이벤트 구독 후에는 `Unregister(id)`로 해제 (생명주기 관리).
