# 10. 월드 변환 — 행렬로 물체 움직이기, 태양-지구-달 계층 구조

> 관련 코드: `Projects/sgfr/Sources/sgfr/10_WorldTransform/10_WorldTransform_Main.cpp`, `10_WorldTransform_Function.cpp`
> (엔진: `Projects/sgf/Sources/sgf/Graphics/Buffers.h` — ConstantBuffer, `jc/Math.h` — mat4)
> 실행: sgfr 실행 후 콘솔 메뉴에서 **10번** 선택
> 선행 학습: 01(선형대수 — 행렬 곱셈), 09(상태 객체)

## 1. 이 장에서 배우는 것

정점 좌표를 건드리지 않고 **행렬 하나로** 물체의 크기·회전·위치를 바꾸는 월드 변환, SRT 곱셈 순서의 의미, 그리고 행렬 곱으로 부모-자식 계층 구조(태양-지구-달)를 구현하는 방법을 배웁니다.

## 2. 실행하면 보이는 것

콘솔에 계층 변환의 핵심 원리(`PrintHierarchyExplanation`)가 먼저 출력됩니다. 800×600 창에는:

- 중앙에서 노란 태양이 **제자리에서 천천히 자전**
- 파란 지구가 태양 주위를 **공전하면서 스스로도 자전**
- 회색 달이 지구 주위를 **공전** (달은 지구를 따라 함께 태양 주위를 돕니다)

세 천체는 전부 **같은 모양의 사각형 버퍼**로 그려집니다. 행렬만 바꿔 3회 재사용하는 것입니다. ESC로 종료.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 행렬은 "물체를 옮기는 지시서"

종이에 네모를 그리고 싶은데, 매번 새 네모를 그리는 게 아니라 **투명 필름 하나에 네모를 그려 두고**, 그 필름을 "2배로 늘리고, 45도 돌리고, 오른쪽으로 3칸 옮기는" 프레임(행렬)에 끼워 화면에 비춘다고 상상해 보세요. 월드 행렬은 바로 이 **프레임의 변환 지시서**입니다. 정점 데이터는 하나뿐이고, 매 프레임 지시서(행렬)만 갈아끼우면 네모가 움직입니다.

### 3-2. 지시서를 읽는 순서 (SRT)

행렬은 "왼쪽에 쓴 지시가 먼저 실행됩니다"(행 벡터 규약). 크기→회전→이동 순서인 `S * R * T`가 정답인 이유:

- 먼저 **S**: 제자리에서 2배로 키운다
- 그다음 **R**: 제자리에서 회전한다 (크기가 적용된 상태로 돌기 때문에 찌그러지지 않음)
- 마지막 **T**: 옮긴다

만약 순서가 반대(`T * R * S`)면 "먼저 옮겨버린 뒤" 회전하게 되어, 물체가 자기 중심으로 도는 것이 아니라 **원점 주위를 도는 공전**이 되어 버립니다.

### 3-3. 공전과 자전, 그리고 부모-자식

공전은 "**먼저 밖으로 이동(T)한 뒤 원점 기준으로 회전(R)**"입니다. 그리고 계층 구조는 **자식의 변환 뒤에 부모의 변환을 곱해 붙이는** 것입니다. 달이 지구를 따라가는 이유는, 달의 월드 행렬 안에 지구의 공전 행렬이 함께 곱해져 있기 때문입니다. "아빠가 이동하면 아빠 어깨에 앉은 아이도 같이 움직이는" 원리와 같습니다.

### 3-4. 왜 전부 "중심이 원점인 사각형"인가?

이 튜토리얼의 사각형은 모두 한 변 길이 1짜리, **중심이 원점(0,0)**인 정사각형입니다. 중심이 원점이어야 "제자리에서 회전"이 의미를 갖기 때문입니다. 만약 사각형이 원점에서 멀리 떨어져 있다면, 크기 변환과 회전 변환이 그 떨어진 위치를 기준으로 작용해 이상한 결과가 나옵니다. 게임 모델들도 전부 "모델링 단계에서 중심이 원점에 오도록" 만들어 두고, 행렬로 배치합니다. 이렇게 정점 데이터를 표준 크기로 만들어 두면, **크기 0.2의 지구도 0.08의 달도 같은 사각형 버퍼 하나로** 그릴 수 있습니다. 이것이 "정점은 그대로, 행렬로 움직이는" 설계의 핵심 전제입니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 로컬 좌표 | 물체 자신을 기준으로 한 좌표 | "내 코는 내 얼굴 중심에 있다" |
| 월드 좌표 | 세상을 기준으로 한 좌표 | "서울은 지구 위 어디에 있다" |
| 월드 행렬 | 로컬 좌표를 월드 좌표로 옮기는 행렬 | 투명 필름의 프레임 지시서 |
| SRT | 크기(Scale)→회전(Rotate)→이동(Translate) 순서 | "키우고→돌리고→갖다 놓기" |
| 자전 | 제자리에서 도는 회전 | 팽이 |
| 공전 | 다른 물체 주위를 도는 회전 | 지구가 태양을 돎 |
| 행 벡터 규약 | v' = v × M, 왼쪽 행렬이 먼저 적용 | 지시서를 왼쪽부터 읽기 |
| 직교 투영 | 거리와 무관하게 같은 크기로 보는 투영 | 설계도면 |
| 화면 비율(Aspect) | 가로 ÷ 세로 (800/600 = 1.33) | TV 화면의 폭 비율 |
| NDC | -1~+1로 정규화된 화면 좌표 | 화면을 정수 눈금으로 본 눈금판 |
| 누적 시간(elapsed) | 프레임마다 deltaTime을 더해 만든 흐른 총 시간 | 스톱워치의 누적 초 |
| UpdateAndBind | 버퍼 내용 갱신 + 셰이더 슬롯 장착을 한 번에 하는 헬퍼 | 메뉴판 갱신 후 부착 |
| D3D11_MAP_WRITE_DISCARD | "기존 내용 버리고 새로 씀"을 알리는 맵 옵션 | 지난 메뉴판은 버리고 새로 쓰기 |
| 상수 레지스터 | 셰이더가 상수값을 담아 두는 GPU 내부 메모리 | 계산대의 물가표 |
| 멱등(idempotent) 결합 | 같은 행렬 결합이 반복돼도 결과가 같은 성질 | 지시서를 여러 번 읽어도 같음 |

용어 사전의 마지막 줄을 보충하면, "같은 지시서를 여러 번 읽는다"는 비유가 행렬 결합의 안정성을 잘 나타냅니다. 행렬 곱은 실수 반올림이 있지만 결합 순서만 유지하면 결과가 거의 동일하므로, 매 프레임 같은 WVP를 다시 계산해도 화면이 흔들리지 않습니다.

## 5. 코드 워크스루

`WorldTransform_Main()`의 흐름입니다.

### 1단계: 콘솔 설명 + 기본 장치

`PrintHierarchyExplanation()`가 계층 원리를 출력한 뒤, `window.Create` → `device.Initialize` 순서로 창과 디바이스를 준비합니다.

### 2단계: 사각형 하나를 3번 재사용

`MakeQuad` 람다가 한 변 길이 1짜리 정사각형(중심 원점)을 색만 다르게 채웁니다. `VertexPC`에는 틴트 기능이 없어 천체별로 정점 버퍼 3개를 만듭니다.

```cpp
auto MakeQuad = [](const color& _color, VertexPC* _pOut)
{
    _pOut[0] = { vec3(-0.5f, +0.5f, 0.0f), _color };
    _pOut[1] = { vec3(+0.5f, +0.5f, 0.0f), _color };
    _pOut[2] = { vec3(-0.5f, -0.5f, 0.0f), _color };
    _pOut[3] = { vec3(+0.5f, -0.5f, 0.0f), _color };
};

VertexPC sunVertices[4], earthVertices[4], moonVertices[4];
MakeQuad(color(1.0f, 0.8f, 0.1f, 1.0f), sunVertices);   // 태양 (노랑)
MakeQuad(color(0.2f, 0.4f, 1.0f, 1.0f), earthVertices); // 지구 (파랑)
MakeQuad(color(0.7f, 0.7f, 0.7f, 1.0f), moonVertices);  // 달 (회색)
```

인덱스는 `{0,1,2},{2,1,3}` 6개 하나를 공유합니다. `VertexBuffer::Create(&device, vertices, sizeof(VertexPC), 4)`가 GPU 메모리에 정점을 복사해 넣고, `IndexBuffer::Create(&device, indices, 6)`이 인덱스를 넣습니다. 정점 4개는 각각 왼위/오른위/왼아래/오른아래라서, 이후 행렬로 회전시키면 사각형이 통째로 회전합니다. 지구가 노란 태양과 겹칠 때는 지구가 더 나중에 그려지므로(드로우 순서) 지구가 태양 위에 덮여 보입니다. 깊이 테스트를 쓰지 않는 2D라서 "나중에 그린 것이 위에 보인다"는 규칙이 그대로 적용됩니다.

### 3단계: 셰이더 + 상수 버퍼

`TransformShaderSource()`(Function.cpp)는 `register(b0)`에 `row_major float4x4 gWorldViewProj` 하나만 받는 단순 셰이더입니다. VS에서 `mul(float4(_input.position, 1.0f), gWorldViewProj)`로 변환합니다.

`CbTransform`은 `mat4 worldViewProj_` 하나 = **64바이트 = 16의 배수**라 상수 버퍼 규칙을 만족합니다.

### 4단계: 직교 투영 + 화면비 보정

```cpp
const _f32 aspect = window.AspectRatio();
const mat4 proj = mat4::OrthographicOffCenterLH(-aspect, +aspect, -1.0f, +1.0f, 0.0f, 1.0f);
```

NDC는 가로세로 모두 -1~1이라, 800×600 창에서는 가로로 늘어나 보입니다. 가로 범위를 화면 비율만큼 넓게(-1.33~+1.33) 잡으면 정사각형이 정사각형으로 보입니다.

### 5단계: DrawQuad 람다

```cpp
auto DrawQuad = [&](VertexBuffer& _vb, const mat4& _world)
{
    CbTransform cb = {};
    cb.worldViewProj_ = _world * proj;    // 월드 다음 투영 (왼쪽이 먼저 적용)
    cbTransform.UpdateAndBind(&device, cb, 0);
    _vb.Bind(&device);
    ib.Bind(&device);
    shader.Bind(&device);
    device.Context()->IASetPrimitiveTopology(D3D11_PRIMITIVE_TOPOLOGY_TRIANGLELIST);
    device.Context()->DrawIndexed(6, 0, 0);
};
```

`ConstantBuffer<CbTransform>::UpdateAndBind(&device, cb, 0)`은 **Map(D3D11_MAP_WRITE_DISCARD) → memcpy → Unmap** 후 VS/PS 양쪽 슬롯 0에 바인딩합니다. `DrawIndexed(6,0,0)`은 정점 버퍼와 인덱스 버퍼를 이미 묶었으므로 "인덱스 0부터 6개를 삼각형 리스트로 그려라"는 뜻입니다.

### 6단계: 렌더 루프 — 세 천체의 월드 행렬

```cpp
// 태양: 제자리 자전. SRT2D(크기, 회전각, 이동) 헬퍼
const mat4 sunWorld = mat4::SRT2D(vec2(0.5f, 0.5f), elapsed * 0.5f, vec2(0.0f, 0.0f));

// 지구: 공전 = 먼저 이동(T) 후 원점 기준 회전(R)
const mat4 earthOrbit = mat4::Translation(0.7f, 0.0f, 0.0f) * mat4::RotationZ(elapsed * 1.0f);
const mat4 earthWorld = mat4::Scale(0.2f, 0.2f, 1.0f) * mat4::RotationZ(elapsed * 3.0f) * earthOrbit;

// 달: 부모(지구)의 공전 행렬을 통째로 곱한다
const mat4 moonOrbit = mat4::Translation(0.2f, 0.0f, 0.0f) * mat4::RotationZ(elapsed * 4.0f);
const mat4 moonWorld = mat4::Scale(0.08f, 0.08f, 1.0f) * moonOrbit * earthOrbit;
```

- `earthOrbit` = `T(0.7,0,0) * Rz(t)`: 먼저 반지름 0.7 위치로 이동, 그다음 회전 → **원점(태양) 주위 공전**
- `earthWorld` = `S(0.2) * Rz(3t) * earthOrbit`: 지구 자체 자전(3배 빠름) + 공전
- `moonWorld` = `S(0.08) * moonOrbit * earthOrbit`: 달 로컬 공전 뒤에 **지구의 공전 행렬**을 곱해 지구를 따라다니게 함. 지구의 자전/크기는 달에게 물려주지 않기 위해 `earthWorld`가 아니라 `earthOrbit`만 사용합니다.

`elapsed`는 `FrameTimer::Tick()` + `DeltaTime()` 누적으로, 프레임 속도와 무관하게 부드럽게 움직입니다. `DeltaTime()`이 크면(프레임 드롭) 각도도 그만큼 커져, 화면이 멈추지 않고 이어집니다.

### 곱셈 순서를 머릿속에 그리는 법

`moonWorld = S(0.08) * moonOrbit * earthOrbit`를 읽을 때는 **오른쪽부터 왼쪽으로** "달의 부모인 지구의 공전 먼저, 그다음 달의 공전, 마지막에 달 크기" 순서로 해석하면 됩니다. 왼쪽 행렬이 먼저 적용되므로, 세상에 실제로 일어나는 순서는 오른쪽 행렬부터입니다. 이것이 행 벡터 규약에서 행렬 결합을 읽는 정석적인 요령이며, 이후 11장(카메라), 13장(큐브)에서도 똑같이 적용됩니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. 변환은 VS의 시뮬레이션 하드웨어에서

행렬 곱은 픽셀 단위가 아니라 **정점 단위** 연산입니다. GPU의 버텍스 셰이더는 정점들을 처리하는 **SIMD 스레드 풀**(예: 128~1024 ALU 코어)에서 실행됩니다. `mul(float4(position, 1), gWorldViewProj)`는 4x4 행렬과 4성분 벡터의 곱으로, 하드웨어적으로는 **16회 곱셈 + 12회 덧셈**(FMA)에 해당합니다. GPU 코어는 이 FMA를 1~2 사이클에 끝내며, 6개 인덱스가 만드는 4개 정점은 4개의 병렬 스레드로 동시에 처리됩니다. 여기서 중요한 것은 월드 행렬이 바뀌면 **정점 버퍼 내용은 그대로 두고 상수 버퍼만 갱신**한다는 점 — GPU 메모리 대역폭이 아닌, 셰이더 유닛의 레지스터/상수 메모리만 소비합니다.

### 6-2. 상수 버퍼: D3D11 상수 메모리와 레지스터 파일

`ConstantBuffer<CbTransform>::UpdateAndBind`는 내부적으로:

1. `ID3D11DeviceContext::Map(buffer, 0, D3D11_MAP_WRITE_DISCARD, ...)` — GPU 버퍼의 메모리를 **CPU 주소 공간에 임시 매핑**. 이 버퍼는 `D3D11_USAGE_DYNAMIC + D3D11_CPU_ACCESS_WRITE`로 만들어져 있어, 일반 GPU 전용 메모리(DEFAULT)와 달리 CPU 쓰기 접근이 가능합니다. `DISCARD`는 "이전 내용은 버려도 된다"는 뜻으로, GPU가 아직 이전 프레임의 상수를 읽고 있어도 드라이버가 **새 메모리 조각**을 할당해 충돌 없이 즉시 진행시킵니다(미래의 메모리링). 이 때문에 CPU는 GPU가 그리기를 끝내기를 기다리지 않습니다.
2. `VSSetConstantBuffers(0, 1, ...)` / `PSSetConstantBuffers(0, 1, ...)` — 버퍼를 **셰이더 스테이지의 상수 슬롯**에 묶습니다.
3. 실제 읽을 때 드라이버는 상수 버퍼 데이터를 GPU가 상수값을 담아두는 **상수 레지스터 파일/상수 캐시**에 반영합니다. 셰이더가 `gWorldViewProj`를 참조하면 이는 이 레지스터 메모리에서 값을 읽는 것이며, 상수 메모리 읽기는 일반 메모리 접근보다 훨씬 빠릅니다(명령당 부가 사이클 없음).

64바이트(16 플로트) 상수는 캐시 라인 하나(보통 128B) 안에 들어가는 크기로, 하나의 셰이더 스레드가 상수 캐시에서 2사이클 안에 전부 읽습니다.

한 가지 주의할 점은 `UpdateAndBind`가 매 호출마다 Map/Unmap을 수행한다는 것입니다. 이 튜토리얼은 드로우콜이 3개뿐이라 부담이 없지만, 물체가 수천 개면 매번 Map/Unmap 하는 방식은 CPU 부하가 커집니다. 실전 엔진은 "프레임당 한 번 업로드 후 재사용"(22장 배치 렌더러)하거나 갱신이 잦은 데이터를 분리(12장 b0/b1 규약)합니다. 지금은 "Map = CPU가 GPU 메모리에 쓰는 일"이라는 사실만 기억해 두면 됩니다.

### 6-3. 직교 투영과 NDC, 클리핑

`OrthographicOffCenterLH`는 시야를 상자로 만들어 **w가 1로 유지**되는 투영입니다(원근과 달리 거리로 나누지 않음). 투영된 좌표는 **클립 공간(clip space)**에 들어가고, GPU의 **클리퍼(고정기능)**가 x,y,z가 -w~+w 밖인 정점을 잘라냅니다. 이후 하드웨어 뷰포트 변환이 NDC(-1~1)를 픽셀 좌표로 옮기고, 래스터라이저가 삼각형을 픽셀로 깁니다.

### 6-4. 왜 "행렬만 바꾸고 버퍼 재사용"이 빠른가

드로우콜마다 GPU는 정점 버퍼의 데이터를 꼭 다시 읽어야 하지만, **같은 버퍼를 다시 바인딩하면 버퍼 객체는 그대로**라 드라이버 검증 비용이 줄고, GPU의 정점 캐시(지난 정점 재사용 캐시)와 L2 캐시가 이미 따뜻해져 있습니다. 세 드로우콜이 전부 같은 IB/VB를 쓰고 상수 버퍼만 갱신하므로, GPU는 인덱스·정점 데이터를 캐시에서 재사용합니다. 이것이 나중에 배울 **배치 렌더러(드로우콜 최적화)의 밑바탕**이 됩니다.

### 6-5. row_major와 전치 비용

jc::Mat4는 행 우선(row-major) 저장이므로, HLSL에서 `row_major float4x4`로 선언하면 **전치 없이 그대로 복사**됩니다. 만약 column-major 기본값이었다면 드라이버/셰이더 컴파일러가 매 프레임 전치(transpose)를 수행해야 하고, 셰이더 스레드마다 상수 로드 패턴이 달라져 성능 손실이 있었을 것입니다. `mul(v, M)` 행 벡터 규약과 row-major 저장의 조합은 GPU의 벡터-행렬 곱 배선(dot product 유닛)과 정확히 한 번에 맞아떨어지는 조합입니다.

### 6-6. 시간은 어디에서 오는가 — CPU 클록과 GPU

이 튜토리얼의 `elapsed += timer.DeltaTime()`은 GPU가 아니라 **CPU**에서 흐르는 시간입니다. GPU는 자체 클록을 갖지 않아 "지금이 몇 초인지" 모릅니다. 그래서 게임의 시간은 항상 CPU가 재고(QueryPerformanceCounter 계열), 결과를 상수버퍼나 정점 갱신으로 GPU에 보냅니다. `FrameTimer::Tick()`은 직전 Tick 이후의 경과 시간을 측정하고, `DeltaTime()`이 그 값을 초 단위로 돌려줍니다.

드로우콜 파이프라인 관점에서 중요한 점은, CPU가 매 프레임 **GPU가 지난 프레임을 아직 그리는 동안** 벌써 다음 프레임의 행렬을 계산할 수 있다는 것입니다. 60FPS라면 한 프레임이 16.7ms인데, GPU가 10ms를 쓰고 있으면 CPU는 그 사이에 다음 프레임 준비를 끝냅니다. 이 병렬 실행은 드라이버가 명령을 큐잉하는 방식 덕분에 가능하며, 상수버퍼 `UpdateAndBind`의 `D3D11_MAP_WRITE_DISCARD`가 이 병렬성을 안전하게 지켜 줍니다. `elapsed`가 매 프레임 증가해 행렬 각도가 계속 커지는 것도 전부 이 CPU 시간 흐름의 결과입니다.

### 6-7. 월드 행렬은 어느 스테이지에 사는가

월드 변환은 VS(버텍스 셰이더) 단계에서 일어납니다. `mul(float4(position,1), gWorldViewProj)`는 정점마다 실행되고, 결과 클립 공간 좌표가 래스터라이저로 전달됩니다. 여기서 유의할 것은 **월드 행렬은 GPU의 상수 메모리에서 읽히는 데이터**라는 점입니다. VS가 실행되는 셰이더 유닛마다 이 상수들이 레지스터 파일/상수 캐시에 올라와 있고, 행렬 요소 16개는 4개의 벡터 상수 레지스터(4×float4)로 읽힙니다. 그래서 "행렬을 바꾼다"는 것은 GPU 코어의 연산 회로를 바꾸는 것이 아니라, 단지 상수 레지스터의 내용이 바뀌는 것뿐입니다. 이것이 월드 변환이 이토록 값싸고 유연한 이유입니다.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| SRT 순서 | 크기 → 회전 → 이동 (`S * R * T`), 행 벡터 규약은 왼쪽부터 적용 |
| 공전 | `T(반지름) * Rz(각도)` — 먼저 이동 후 회전 |
| 계층 구조 | 자식 월드 = 자식 로컬 × 부모 월드 행렬 |
| 상수 버퍼 | 구조체는 16바이트 배수 (mat4 64바이트 OK) |
| 결합 행렬 | `wvp = world * view * proj` — 왼쪽이 먼저 적용 |
| 직교 투영 | `OrthographicOffCenterLH(-aspect, +aspect, -1, +1, 0, 1)` — 비율 보정 |
| HLSL 규약 | `row_major float4x4` + `mul(v, M)` — 전치 불필요 |
| 재사용 | 같은 VB/IB를 행렬만 바꿔 여러 번 DrawIndexed |
| 프레임 독립 | `elapsed += timer.DeltaTime()` 누적 각도 사용 |
| 헬퍼 | `mat4::SRT2D(크기, 각도, 이동)` = S·R·T 한 번에 |
| 중심 원점 | 표준 크기 정점(중심 원점) → 하나의 버퍼로 모든 천체 표현 |
| 상수 슬롯 | `UpdateAndBind(&device, cb, 0)` → b0에 WVP |

표를 되새길 때는 "행렬 결합은 왼쪽부터 적용되고, 순서가 곧 결과"라는 한 줄만 중심에 두세요. 공전·계층 구조·WVP 결합이 전부 이 규칙에서 파생됩니다. 또 하나 기억할 것은 월드 변환이 "물체를 움직이는" 것이 아니라 "물체를 그릴 좌표계를 바꾸는" 것이라는 관점입니다. 이 관점이 다음 장에서 카메라를 이해하는 열쇠가 됩니다.

더 나아가, 이 장에서 본 세 드로우콜이 공유하는 것(같은 셰이더, 같은 VB/IB, 같은 토폴로지)과 바뀌는 것(상수버퍼의 WVP만)을 구분해 보세요. "공유되는 것과 바뀌는 것의 분리"는 이후 배치 렌더러(22장)와 리소스 매니저(21장)의 설계 원리이기도 합니다. 매 프레임 갱신해야 하는 것은 오직 상수버퍼뿐이라는 점이 이 튜토리얼이 말하는 핵심 효율입니다. 사각형 하나의 정점 4개와 인덱스 6개는 프로그램 시작 시 한 번만 업로드되면 그 후로는 절대 바뀌지 않는다는 점, 그리고 회전이 "정점을 다시 계산하는 것"이 아니라 "행렬 각도만 바뀔 뿐"이라는 점을 확인하며 표를 닫습니다. 결과적으로 이 장의 실험은 "하드웨어는 정점을 그대로 두고, 우리가 행렬로 세상을 바꾼다"는 원칙의 첫 실습이었습니다. 이 원칙은 앞으로 모든 장에서 반복되므로, "정점은 변하지 않는다"는 사실이 가장 확실한 앵커가 됩니다. 행렬을 다루는 연습이 쌓이면 3D에서도 같은 코드가 그대로 통합니다.
