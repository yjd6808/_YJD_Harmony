# 04. 디바이스와 스왑체인 — 화면을 부드럽게 지우고 보여주기

> *   **두 번째 읽을 때**: 7 심화를 정독 — 5에서 배운 "왜 2장인가"가 하드웨어에서 어떻게 구현되는지 연결됩니다.

> **이 문서의 더블 버퍼링 그림에 대하여**
> 3·5장에서 쓰는 "프론트 1 + 백 1, Present로 맞바꾼다"는 **전통적인 더블 버퍼링의 개념적 모델**입니다. 실제 DXGI의 동작은 `SwapEffect`와 창/전체화면 여부에 따라 다르며, 본 엔진의 `DXGI_SWAP_EFFECT_DISCARD` 구성에서는 BitBlt presentation model로 동작합니다. 개념으로 먼저 이해하고, 5-3·7-1에서 실제 DXGI 동작을 정확히 구분합니다.

## 1. 이 장에서 배우는 것

창에 이제 본격적인 그래픽 장치를 연결합니다. `GraphicDevice::Initialize(HWND, w, h)`가 내부적으로 수행하는 전체 초기화 절차(D3D11CreateDeviceAndSwapChain → RTV → 깊이 버퍼/DSV → 상태 객체 → 뷰포트)를 파악하고, **스왑체인(더블 버퍼링)**이 왜 화면을 깜박임 없이 보여주는지, 왜 매 프레임 **화면을 지워야(Clear)** 하는지, 그리고 **BeginFrame/EndFrame 프레임 루프**의 완성형을 배웁니다. 실행 결과로 화면 배경색이 무지개처럼 부드럽게 순환합니다.

## 2. 실행하면 보이는 것

800×600 창이 뜨고, 배경색이 파동처럼 **무지개 색으로 부드럽게 순환**합니다. 시간이 지남에 따라 빨강→초록→파랑이 자연스럽게 섞이면서 변합니다. 이는 "지우는 색(Clear color)"이 매 프레임 조금씩 바뀌기 때문이며, 아직 아무것도 그리지 않아 "화면 지우기 그 자체"가 주제인 튜토리얼입니다. ESC 또는 창 닫기로 종료합니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 스왑체인 = 무대 뒤의 무대 (개념적 모델)

연극 무대에서 관객에게 보이는 **프론트 무대**와, 다음 장면을 준비하는 **백스테이지(백버퍼)**가 분리되어 있다고 상상해 봅시다. 배우들이 백스테이지에서 미리 준비를 마치면, 무대 전체를 순식간에 통째로 바꿉니다. 만약 관객이 보는 무대에서 바로 그림을 바꾸면, 바꾸는 과정이 그대로 노출되어 깜박임이 보일 것입니다.

개념적으로 D3D11도 같습니다. 애플리케이션이 **백버퍼**에 그리고, `Present()`로 그 결과를 표시 시스템에 전달하면, 모니터는 완성된 그림만 봅니다. 이것이 더블 버퍼링의 직관이며, 깜박임과 화면 찢어짐(tearing)이 사라지는 이유입니다. sgf의 `EndFrame(true)`가 바로 이 Present 호출입니다.

> **정확히 구분하기**: 위 "두 장을 맞바꾼다"는 이해를 돕는 전통적 모델입니다. 본 엔진이 쓰는 `DXGI_SWAP_EFFECT_DISCARD`는 Microsoft가 **BitBlt presentation model**이라 부르는 방식으로, `Present` 시 백버퍼 내용이 Windows 표시/합성 시스템(DWM)으로 전달(복사)되는 경로입니다. "VRAM의 두 장 주소를 0.01ms에 원자적으로 교환한다"는 식의 구현 단정은 하지 않습니다. 자세한 분기는 5-3에서 다룹니다.

### 3-2. 매 프레임 화면을 지우는 이유 = 칠판 지우기

교실 칠판에 매일 새로운 그림을 그리려면 전날 그린 그림을 먼저 지워야 합니다. GPU 백버퍼도 마찬가지입니다 — **지난 프레임에 그린 그림이 백버퍼에 그대로 남아 있습니다.** 렌더 타깃은 자동으로 매 프레임 초기화되지 않으므로, 지우지 않고 그리면 이전 그림 위에 새 그림이 겹쳐 그려집니다. 게다가 화면의 일부만 그리는 게임은 지우지 않으면 이전 프레임 잔상이 영원히 남게 됩니다. 그래서 매 프레임 시작 시 `ClearRenderTargetView`로 단색을 채워 밀어내는 것이고, sgf의 `BeginFrame(color)`이 이 일을 합니다. 단, 모든 패스에서 반드시 Clear해야 하는 것은 아니며 의도적으로 이전 내용을 유지하는 경우도 있습니다.

### 3-3. DeltaTime = 프레임 독립 애니메이션

빠른 컴퓨터는 초당 300프레임, 느린 컴퓨터는 30프레임일 수 있습니다. 만약 애니메이션이 "프레임마다 0.01 증가"한다면 빠른 컴퓨터에서 10배 빠르게 도는 버그가 생깁니다. 올바른 방법은 "지난 프레임에서 **몇 초**가 지났는지(DeltaTime)를 재서 곱해주는" 것입니다. 위치 += 속도 × DeltaTime 패턴이 바로 그것이고, `FrameTimer::Tick()` + `DeltaTime()`이 이 장에서 소개됩니다.

*   **비유**: 자동차 속도가 시속 60km라면, 1초 갔을 때 60km, 0.5초 갔을 때 30km 가야 합니다. "프레임마다 1km"로 하면 빠른 차(300fps)는 1초에 300km, 느린 차(30fps)는 30km가 되어 버립니다. DeltaTime이 바로 "이번 프레임에 몇 초를 달렸는가"를 재는 계기판입니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 스왑체인 (SwapChain) | 백버퍼 등 표시용 버퍼를 관리하고 Present로 표시를 요청하는 장치 | 무대 전환 장치 |
| 백버퍼 (Back Buffer) | 애플리케이션이 지금 그리고 있는 버퍼 | 백스테이지 |
| Present | 백버퍼 내용을 표시 시스템에 전달하는 요청 | 무대 전환 요청 |
| 더블 버퍼링 | 개념적으로 두 벌의 그림으로 깜박임 제거 (실제 DXGI 동작은 SwapEffect에 따라 다름) | 무대+대기실 구조 |
| Clear | 매 프레임 시작에 화면을 단색으로 밀기 | 칠판 지우기 |
| RTV (RenderTargetView) | "여기에 그려라" 표시 (그리기 대상 뷰) | 화가가 바라보는 캔버스 |
| DSV (DepthStencilView) | 깊이(앞뒤) 판정용 버퍼의 뷰 | 거리 측정 자 |
| VSync (수직동기) | 프레젠테이션을 모니터 주사율에 동기화하는 요청 | 관객 타이밍 맞추기 |
| HBlank (수평 블랭킹) | 한 줄을 다 읽은 뒤 다음 줄로 넘어가는 짧은 쉬는 구간 | 타자기 줄바꿈 |
| VBlank (수직 블랭킹) | 한 장을 다 읽은 뒤 다음 장으로 넘어가는 긴 쉬는 구간 | 책장 넘기기 |
| DWM | 바탕 화면 창 관리자 — 여러 창의 그림을 한 장으로 합성해 모니터로 내보냄 | 식당 서빙 카운터 |
| DeltaTime | 지난 프레임에서 흐른 시간(초) | 스톱워치 초계 |
| 뷰포트 (Viewport) | 클립 공간을 픽셀/윈도우 좌표로 매핑할 화면 영역 | 캔버스에서 그릴 구역 |

## 5. 왜 프론트 한 장으론 안 되는가 — 모니터가 그림을 꺼내는 원리 (초보자 필수)

> 3장의 비유가 "무대가 2개 필요하다"였다면, 이 장은 "**왜 1개로는 찢기는가**"를 모니터의 동작으로 증명합니다. 이 장을 이해하면 다음 장(코드 워크스루)의 `BeginFrame`/`EndFrame`이 왜 그렇게 생겼는지 바로 이해됩니다.
> *   **5-1·5-2는 초보자 필수** — 복사기·칠판 비유만으로 "왜 2장이 필요한지"가 끝납니다.
> *   **5-3·5-4·5-5는 "개념 한 줄 + 비유"만 먼저 읽고, 도식·코드는 6장 뒤에 다시 봐도 됩니다.** 처음엔 굵은 글씨와 비유만으로 충분합니다.

### 5-1. 모니터는 "한 줄씩 읽는 복사기"다 — 스캔아웃(Scanout)

모니터를 800×600개의 작은 전구(픽셀)가 격자판처럼 박힌 판이라고 상상해 봅시다. 각 전구는 R/G/B 3색을 0~255로 켭니다. 모니터는 이 판을 **왼쪽 위 → 오른쪽, 한 줄 끝나면 다음 줄**로 1초에 60번 처음부터 끝까지 읽어 전구를 갱신합니다. 이를 **스캔아웃**이라 합니다.

```
프레임 1장의 스캔 순서 (800×600 예시)

(0,0) ──────────────────► (799,0)   ← 0번 줄 (Active: 실제 픽셀이 보이는 구간)
  │  ◄─── HBlank(수평 블랭킹) ── 다음 줄로 넘어가는 숨 고르기
(0,1) ──────────────────► (799,1)   ← 1번 줄
  ...
(0,599) ───────────────► (799,599) ← 마지막 줄
  ▼
 VBlank(수직 블랭킹) ← 한 장(refresh)의 끝과 다음 장 사이 숨 고르기
  ▼
 다시 (0,0)으로 돌아가 다음 프레임 스캔 시작
```

*   **단어 뜯어보기**
    *   **Scanout** = Scan(쓸어 읽다) + Out(내보내다). GPU 메모리에 있는 그림을 픽셀 단위로 쓸어 읽어 모니터로 내보내는 동작입니다.
    *   **HBlank** = Horizontal Blank(수평 블랭킹). Blank는 "비어 있음, 쉬는 구간"이라는 뜻입니다. 한 줄을 다 읽은 뒤 다음 줄 첫 칸으로 펜을 옮기는 동안 화면에 아무 픽셀도 보내지 않는 짧은 쉬는 시간입니다.
    *   **VBlank** = Vertical Blank(수직 블랭킹). 한 장(프레임)을 다 읽은 뒤 다음 장의 첫 줄로 돌아가는 더 긴 쉬는 시간입니다. `VBlank`는 한 refresh의 끝과 다음 refresh의 시작 사이 구간 전체를 말합니다.
    *   **Active** = 실제로 픽셀이 보이는 구간(HBlank/VBlank를 제외한 나머지). 800×600이면 Active가 800×600, Blanking은 그 바깥의 여백입니다.

*   **비유 1 — 타자기로 글 읽기**: 타자기로 글을 읽는다고 상상해 봅시다. 글자를 왼쪽에서 오른쪽으로 한 글자씩 읽고(HActive), 줄 끝에 도달하면 종이를 딸깍 올려 다음 줄로 이동합니다(HBlank). 페이지를 다 읽으면 다음 페이지 첫 줄로 손을 옮깁니다(VBlank). 모니터도 글자 대신 픽셀을 같은 순서로 읽습니다. 타자기가 줄을 읽는 도중에 누군가 종이에 글씨를 덧쓰면(프론트에 직접 그리기), 읽는 사람은 윗줄은 새 글씨, 아랫줄은 옛 글씨를 보게 됩니다 — 이게 찢김입니다.

*   **비유 2 — 숨 고르기**: 달리기를 할 때 한 발짝(HActive)마다 짧게 숨을 쉬고(HBlank), 한 바퀴를 다 돌면 길게 숨을 쉽니다(VBlank). 이 숨 고르는 시간에 아무도 트랙(화면)을 밟지 않으므로, 이때 그림을 갈아끼우면 발에 밟히지 않습니다. 그래서 전통적으로 "VBlank 때 버퍼를 바꾸면 찢김이 없다"고 말합니다. 단, 현대 DXGI에서는 이 VBlank 자체가 아니라 `Present`가 presentation queue에 요청을 넣고 타이밍에 맞춰 표시할 프레임이 결정되는 구조이므로, "VBlank 0.5ms 동안에만 교환한다"는 단순화는 정확하지 않습니다(5-5 참조).

*   **왜 Blanking이 존재하는가**: 옛 CRT 모니터에서는 전자빔이 형광면을 왼쪽→오른쪽, 위→아래로 쏘며 그렸습니다. 줄 끝에서 다음 줄로, 화면 끝에서 첫 줄로 빔을 되돌리는 동안은 화면을 끄(blank)야 궤적이 보이지 않았습니다. LCD/OLED는 전자빔이 없지만, 디스플레이 인터페이스(HDMI/DP)의 타이밍 신호는 이 Active/Blank 구조를 그대로 유지합니다. 단순히 "CRT 호환 때문에 남았다"가 아니라, 디지털 신호가 한 줄·한 프레임의 경계를 구분하기 위해 필요한 타이밍 여백입니다. 이 여백 안에 Front Porch / Sync / Back Porch 같은 세부 신호가 들어갑니다 — 초보자는 "줄·장 사이의 구분용 쉬는 시간"으로만 기억하면 충분합니다.

*   **뷰포트가 하는 일**: 클립 공간을 픽셀/윈도우 좌표로 매핑하는 변환. 개념적으로 `pixelX = (ndcX*0.5+0.5)*width`로 이해하면 되며, `GraphicDevice.cpp:81` `swapChain_.ApplyFullViewport`, `SwapChain.cpp:79` `RSSetViewports`가 이 구간을 지정합니다. Active 영역(800×600) 중 어디를 캔버스로 쓸지를 정하는 것이 뷰포트이며, 정확히는 클립 공간 → perspective divide → NDC → viewport transform → 윈도우 좌표 과정입니다. Blanking은 뷰포트가 건드릴 수 없는 신호 레벨의 여백입니다.

> **엔지니어 포인트**: 모니터는 표시용 메모리를 "파일처럼 한 번에" 읽지 않습니다. **매 프레임 같은 주기로 같은 순서로**(왼쪽→오른쪽, 위→아래, Active→HBlank→VBlank) 읽습니다. 그래서 GPU가 쓰는 타이밍과 모니터가 읽는 타이밍이 겹치면 찢김이 납니다.

> **초보자 한 줄 요약**: 모니터는 위에서 아래로 한 줄씩 60번/초 읽는 복사기. 줄 사이(HBlank)·장 사이(VBlank)엔 짧은 숨 고르기가 있고, 이 복사가 진행 중일 때 GPU가 같은 종이에 그림을 덧칠하면 찢김이 난다. VBlank는 "장 사이의 숨 고르기"다.

### 5-2. 프론트에 직접 그리면 찢기는 이유 — "칠판에 글 쓰는 도중 사진 찍기"

표시 중인 표면에 GPU가 직접 그리면 찢김이 납니다.

| 시간 | GPU (쓰기) | 모니터 (읽기) | 화면에 보이는 것 |
|---|---|---|---|
| 0ms | `Clear(빨강)` 시작 — 위 100줄을 빨강으로 칠함 | 0~150줄을 읽어 표시 | 위는 빨강, 중간부터는 지난 프레임 파랑 |
| 2ms | 삼각형 500개를 2ms에 걸쳐 그림 | 300줄째 읽는 중 | **위 300줄=새 그림, 아래 300줄=옛 그림**이 한 화면에 공존 |
| 16ms | 다음 프레임 Clear 시작 | 다시 0줄부터 읽음 | 1초에 60번 반그린 장면이 번쩍임 |

이게 **tearing(찢김)**. 비유하면 칠판에 글씨를 쓰는 도중에 사진을 찍으면 "쓰다 만 글씨"가 찍히는 것과 같습니다.

D11 코드로 보면 `GraphicDevice.cpp:320` `ClearRenderTargetView(swapChain_.RTV(), ...)`의 `RTV()`가 표시 중인 표면이었다면, Clear 순간부터 섬광이 그대로 노출됩니다. 백버퍼 RTV라서 보이지 않는 것입니다.

```cpp
// SwapChain.cpp:39 — RTV는 애플리케이션이 렌더링하는 백버퍼에서 만든다.
pSwapChain_->GetBuffer(0, __uuidof(ID3D11Texture2D), (void**)pBackBuffer.GetAddressOf());
_pDevice->CreateRenderTargetView(pBackBuffer.Get(), nullptr, pRenderTargetView_.GetAddressOf());
// 이 설정(DISCARD, BufferCount=1)에서 애플리케이션이 접근하는 백버퍼는 1개이며,
// GetBuffer(0)으로 얻는다. GetBuffer(1)을 호출할 수 없다는 설명은 맞다.
```

### 5-3. Present는 "두 장의 주소를 교환"이 아니다 — "복사해 전달" vs "원본을 공유"

초보자 설명에서 흔히 "Present로 두 버퍼의 주소를 맞바꾼다, 0.01ms 원자적 교환, VRAM 대역폭 0"이라고 하지만, 현대 DXGI의 일반적인 `Present()` 동작으로는 부정확합니다. 특히 현재 엔진은 `DXGI_SWAP_EFFECT_DISCARD`이며, Microsoft는 이를 **BitBlt presentation model**이라 명시합니다.

*   **비유**: BitBlt는 "그림을 복사기로 복사해 제출" — 원본 백버퍼는 그대로 두고 복사본을 Windows에 건넨다. Flip은 "원본 서류를 직접 공유" — Windows가 내 원본을 직접 들고가 화면에 쓴다. 둘 다 "표시해 달라"는 요청이지만 가는 길이 다르다.

*   **현재 엔진(DISCARD) — BitBlt 모델**:
    ```
    GPU
     │
     │ 렌더링
     ▼
    Swap Chain Back Buffer (애플리케이션이 GetBuffer(0)으로 얻는 1개)
     │
     │ Present()
     ▼
    DXGI / Windows 표시 시스템
     │
     │ BitBlt model: back buffer 내용이 DWM redirection surface로 전달(복사)될 수 있음
     ▼
    DWM / Desktop 합성
     │
     ▼
    Display → Monitor
    ```
    `Present` 시 백버퍼 내용이 DWM의 redirection surface로 복사되는 경로가 될 수 있습니다. "주소만 교환, VRAM 대역폭 0, 0.01ms"라는 단정은 삭제합니다.

*   **현대 권장(Flip Model)**:
    ```
    GPU
     │
     │ 렌더링
     ▼
    Swap Chain Buffer
     │
     │ Present()
     ▼
    Presentation Queue
     │
     ▼
    DWM이 공유된 Swap Chain Buffer를 직접 합성 (불필요한 복사 감소)
     │
     ▼
    Display → Monitor
    ```
    `DXGI_SWAP_EFFECT_FLIP_DISCARD` / `FLIP_SEQUENTIAL`은 Flip model이며, DWM이 swap-chain buffer를 직접 합성할 수 있어 일반적으로 더 효율적입니다. Microsoft도 새 애플리케이션에는 Flip Model 사용을 권장합니다. Win10부터 창모드에서 Flip 모델이 DWM과 궁합이 좋아 지연이 줄어듭니다.

*   **소스**: `SwapChain.cpp:68` / `GraphicDevice.cpp:119,238`
    ```cpp
    void SwapChain::Present(bool _vsync) {
        if (pSwapChain_) pSwapChain_->Present(_vsync ? 1 : 0, 0);
        // SyncInterval: 프레젠테이션을 수직 블랭킹에 동기화하는 간격 (무조건 VBlank 대기와 다름, 5-4 참조)
    }
    // 현재 엔진의 스왑체인 설정 — 개념적 더블 버퍼링을 가장 단순한 DISCARD로 구현한 예시
    DXGI_SWAP_CHAIN_DESC scd = {};
    scd.BufferCount = 1; // 이 DISCARD 구성에서 애플리케이션이 렌더링하는 백버퍼 1개 (Microsoft 문서에서 BufferCount 의미는 SwapEffect와 창/전체화면에 따라 해석이 달라 단순히 "백 개수"로 외우지 말 것)
    scd.BufferDesc.Format = DXGI_FORMAT_R8G8B8A8_UNORM;
    scd.SwapEffect = DXGI_SWAP_EFFECT_DISCARD; // BitBlt model. 교체 후 백버퍼 내용은 버려질 수 있음(DISCARD)
    D3D11CreateDeviceAndSwapChain(nullptr, D3D_DRIVER_TYPE_HARDWARE, nullptr, flags,
        featureLevels, 1, D3D11_SDK_VERSION, &scd, &pRawSwapChain, &pDevice_, ...);
    // 참고: Flip Model의 전형은 BufferCount=2, FLIP_DISCARD이며 Microsoft 샘플도 이를 double-buffering으로 설명한다.
    ```

> **정리**: "프론트 1 + 백 1 주소를 맞바꾼다"는 전통적 개념 모델로만 이해하고, 실제 DXGI 구현은 SwapEffect에 따라 BitBlt(복사 경로) / Flip(공유 경로)로 나뉜다고 기억합니다. 본 튜토리얼은 DISCARD로 개념을 가르치지만, 현대 Windows 게임은 Flip을 권장합니다. **초보자 한 줄 요약**: Present는 "이 그림을 화면에 내달라"는 요청. DISCARD는 복사본을 건네는 옛날 방식, Flip은 원본을 공유하는 요즘 방식.

### 5-4. VSync는 "VBlank까지 무조건 대기"가 아니다

`Present(1,0)`과 `Present(0,0)`의 차이 — **비유**: 지하철 문이 닫힌(VBlank) 순간에만 객차를 갈아타면 승객(픽셀)이 넘어지지 않습니다. 문이 열린 채 갈아타면(즉시 Present) 승객이 반은 옛 객차, 반은 새 객차에 걸칩니다:

*   `SyncInterval=1` (`EndFrame(true)`): 프레젠테이션을 **수직 동기화에 맞추도록 요청**합니다. 이 과정에서 `Present`가 대기할 수 있지만, 실제 언제 반환되고 얼마나 블로킹되는지는 CPU/GPU 작업 상태, swap-chain 버퍼 상태, DWM, presentation queue, frame latency, 시스템 합성 상태 등에 따라 달라집니다. "GPU가 VBlank까지 무조건 CPU를 멈춘다"로 이해하면 안 됩니다.
*   `SyncInterval=0` (`EndFrame(false)`): 프레젠테이션을 동기화 없이 가능한 빨리 표시하도록 요청합니다. FPS는 올라갈 수 있지만, 표시는 찢길 수 있습니다.

*   **파이프라이닝**: CPU와 GPU는 동시에 움직입니다. `Present()`가 CPU-side `WaitForGpuIdle()`처럼 모든 GPU 명령 완료를 먼저 기다리는 함수라고 이해하면 안 됩니다. `Present`는 presentation queue에 요청을 넣고, GPU 작업 완료·프레임 페이싱·swap-chain 상태 등이 얽혀 처리됩니다.
    ```
    CPU ── Draw N ── Draw N ── Present ── Draw N+1 ── ...
    GPU ── Draw N ── Draw N ── ... (병렬 실행)
    ```

*   **전통적 VSync 현상에 대한 조건**: 흔히 "60Hz VSync에서 60fps를 못 맞추면 30fps로 떨어진다"거나 "입력 지연 +16ms"라고 하지만, 이는 전통적인 VSync + 특정 버퍼링/페이싱 조건에서 나타날 수 있는 현상이며 절대 법칙이 아닙니다. 현대 Windows의 DWM/Flip Model/presentation 경로에서는 버퍼 수와 모델에 따라 동작이 달라집니다. 전통적 방식에서는 한 프레임을 다음 VBlank까지 제출하지 못하면 다음 표시 주기를 놓쳐 30fps 수준으로 떨어지는 현상이 *나타날 수 있다* 정도로 이해합니다. VSync는 일반적으로 표시 대기를 추가해 latency를 증가시킬 수 있지만, 60Hz에서 `+16ms`가 고정으로 추가되는 것은 아니며 한 refresh(≈16.67ms)만큼 추가될 수 있는 정도로 이해합니다.

*   **초보자 한 줄 요약**: `Present(1,0)`은 "VSync에 맞춰 표시해 달라"는 요청. 진짜 얼마나 기다리는지는 CPU/GPU/DWM 상태에 따라 달라진다. "무조건 16ms 대기"가 아니다.

*   **소스 — 프레임 루프의 완성형** (`04_DeviceAndSwapChain_Main.cpp:91` 패턴 + `GraphicDevice.cpp:309`)
    ```cpp
    // 매 프레임
    timer.Tick(); elapsed += timer.DeltaTime();
    device.BeginFrame(color); // 백버퍼 Clear + RTV/DSV 바인딩
    // ... 여기에 05번부터 그리기 코드가 들어간다 ...
    device.EndFrame(true);    // Present(1,0) — 프레젠테이션을 VSync에 동기화하도록 요청
    ```

### 5-5. 신호가 모니터까지 가는 전체 길 — 주방부터 손님까지 (처음엔 그림만 보기)

> 처음 읽을 때는 아래 그림의 화살표만 따라가면 됩니다. 글은 7장에서 다시 읽어도 됩니다.

```
[CPU] 앱 → DX11 명령 → [커맨드 큐] (Immediate Context는 명령을 GPU 명령 스트림에 기록)
         ↓
[GPU] 셰이더/래스터라이저 실행 → GPU가 사용할 수 있는 메모리의 Swap Chain Back Buffer에 픽셀 기록
         ↓ Present (표시 요청)
[DXGI / Presentation Queue] 프레젠테이션 요청 큐잉, 디스플레이 타이밍에 맞춰 표시할 프레임 결정
         ↓
[DWM 합성 또는 Independent Flip/DirectFlip/MPO 등 — 조건에 따라 경로가 다름]
         ↓
[Display Engine] 표시할 surface/프레임버퍼를 읽어 HDMI(TMDS)/DP 패킷 등으로 직렬화
         ↓
[케이블]
         ↓
[모니터 TCON] 신호를 패널 타이밍으로 변환
         ↓
[패널] 액정/OLED가 빛을 내 화면에 표시
```

*   **Display Engine**: GPU 안의 블록으로, 표시할 surface/프레임버퍼를 읽어 픽셀 클록에 맞춰 신호로 내보냅니다. 셰이더와 별개로 동작하며, 전통적 모델의 "VRAM 프론트버퍼를 DMA로 읽는다"보다 "표시할 surface를 읽는다"가 Flip Model까지 포괄하는 정확한 표현입니다. Active/Blank 타이밍 신호도 이 엔진이 만듭니다.
*   **VBlank vs Present**: `VBlank`는 디스플레이의 한 refresh가 끝나고 다음 refresh가 시작되기 전의 구간(디스플레이 타이밍, 5-1)입니다. `Present(1)`은 프레젠테이션을 VSync에 맞추도록 요청하는 API 호출이며, 둘은 같은 개념이 아닙니다. "VBlank 0.5~1ms 동안에만 버퍼를 바꾼다"는 전통적 직관으로는 괜찮지만, 현대 DXGI에서는 Present가 presentation queue에 들어가 타이밍에 맞춰 표시될 프레임이 결정되는 구조로 이해해야 합니다.
*   **DWM — 단어 뜯어보기**: **DWM** = Desktop Window Manager(바탕 화면 창 관리자). Windows Vista부터 도입된 합성 관리자입니다. DWM이 하는 일은 "여러 창을 한 장으로 합성해 모니터에 내보내기"입니다.
    *   **비유 — 식당 주방과 서빙 카운터**: 게임·브라우저·메모장은 각자 주방(백버퍼)에서 요리(그림)를 합니다. DWM은 서빙 카운터(합성)입니다. 손님(모니터)은 주방을 직접 보지 않고, 서빙 카운터가 모든 요리를 한 쟁반(최종 화면)에 예쁘게 담아 내오는 것만 봅니다. 이 덕분에 창에 투명 효과·그림자·Alt+Tab 미리보기가 가능해졌습니다. DWM이 없던 XP 시절엔 창을 드래그하면 잔상이 남았습니다.
    *   **왜 필요한가**: DWM이 합성을 맡으므로, 앱이 `Present`를 호출해도 곧바로 모니터가 아니라 DWM의 쟁반으로 갑니다. DWM이 60Hz(또는 모니터 주사율)에 맞춰 쟁반을 모니터에 내보냅니다. 창모드 앱은 이 쟁반을 거치므로, VSync를 꺼도 DWM이 대신 VSync를 맞춰 찢김이 덜합니다.
    *   **DISCARD(BitBlt) vs Flip — DWM 경로 비교**:
        ```
        [현재 엔진: DISCARD — BitBlt model]
        Game Back Buffer (GetBuffer(0) 1개)
          │ Present()
          ▼
        DWM Redirection Surface로 복사(복사본 전달)
          │ Composition(여러 창 합성)
          ▼
        Display → Monitor

        [현대 권장: FLIP model]
        Game Swap Chain Buffer (Flip은 BufferCount=2 전형)
          │ Present()
          ▼
        Presentation Queue
          │ DWM이 원본 Buffer를 직접 공유·합성 (복사 감소)
          ▼
        Display → Monitor
        ```
        Microsoft 설명 그대로, DISCARD(BitBlt)에서는 Present 시 back buffer 내용이 DWM redirection surface로 복사될 수 있고, Flip에서는 DWM이 swap-chain buffer를 공유해 합성하므로 불필요한 복사를 줄입니다. "창모드는 항상 한 번 더 복사한다"로 일반화하면 틀립니다 — Flip 창모드는 공유합니다.
    *   **Redirection Surface란**: DWM이 각 창마다 따로 두는 "창 전용 임시 쟁반"입니다. BitBlt 모델에서 게임이 Present한 그림은 먼저 이 임시 쟁반에 복사된 뒤, DWM이 모든 창의 임시 쟁반을 모아 최종 쟁반으로 합성합니다.
    *   **전체화면과 DWM 우회**: "전체화면 독점이면 무조건 DWM을 우회해 직접 스캔아웃"은 현대 Windows에서 단정할 수 없습니다. 실제로는 Independent Flip, DirectFlip, MPO(Multi-Plane Overlay) 등 여러 presentation path가 있으며, 창이 화면을 완전히 덮고 포맷·스케일 등 조건이 맞으면 DWM 합성을 거치지 않고 Display Engine이 게임 버퍼를 직접 읽는 경로로 전환될 수 있다 정도로 이해합니다. 조건이 안 맞으면 전체화면 창모드라도 DWM 합성을 거칩니다.
    *   **초보자 한 줄 요약**: DWM은 Windows의 서빙 카운터. 창모드에선 내 그림이 DWM 쟁반을 거쳐 모니터로 간다. DISCARD는 복사본을 쟁반에 올리고, Flip은 원본을 쟁반에 직접 공유해 더 빠르다.

> 이 5장을 이해했다면 스왑체인을 "마법 상자"가 아니라 **"백버퍼에 그리고 Present로 표시를 요청하는 장치이며, 실제 경로는 SwapEffect에 따라 BitBlt/Flip으로 나뉜다"**는 구체적 메커니즘으로 설명할 수 있어야 합니다. 이제 이 지식을 들고 코드를 보면 모든 줄이 연결됩니다.

`Initialize(HWND, w, h)` 내부(`GraphicDevice.cpp`의 `CreateDeviceAndSwapChain`)에서 일어나는 일:

1. `D3D11CreateDeviceAndSwapChain` — **Device + Context + SwapChain**을 한 번에 생성 (백버퍼를 포함한 swap chain 생성 + 포맷 협상. 본 엔진은 DISCARD, BufferCount=1 구성)
2. 백버퍼에 대한 **RenderTargetView(RTV)** 생성 — "이 그림에 그려라" 표시 (`SwapChain.cpp:42` `GetBuffer(0)` — 이 구성에서 애플리케이션이 사용하는 백버퍼 1개를 얻음)
3. **깊이 버퍼와 DepthStencilView(DSV)** 생성 — 3D에서 앞/뒤 판정용 (13번 큐브에서 본격 사용)
4. 블렌드/깊이/래스터라이저/샘플러 **상태 객체** 생성
5. **뷰포트** 설정 — NDC 좌표(-1~+1)를 픽셀 좌표로 매핑하는 영역 (`SwapChain.cpp:79` `RSSetViewports`)

이 5단계가 "GPU에 그림 그릴 준비 전체"입니다. 5장에서 본 DISCARD/BitBlt 구성이 바로 1번에서 체결되는 계약입니다.

### 6-3. 타이머 (코드 65~68행)

```cpp
FrameTimer timer;
timer.Reset();
_f32 elapsed = 0.0f;	// 누적 시간(초)
```

`FrameTimer::Reset()`은 고해상도 카운터(QueryPerformanceCounter) 기반 타이머를 초기화합니다.

### 6-4. 렌더 루프 (코드 71~91행) — 이제부터의 표준 골격

```cpp
while (window.PumpMessage())
{
	if (input.IsKeyPressed(VK_ESCAPE))
	{
		break;
	}
	input.NextFrame();

	timer.Tick();
	elapsed += timer.DeltaTime();

	device.BeginFrame(RainbowColor(elapsed));	// 지우기 + 그리기 대상 묶기
	device.EndFrame(true);						// Present + VSync 동기화 요청
}
```

- `timer.Tick()` — 직전 호출로부터 경과 시간 계산, `DeltaTime()`이 초 단위로 반환
- `elapsed += timer.DeltaTime()` — 프레임마다 누적 → 이 값이 무지개 색 계산의 입력
- `BeginFrame(color)` — 백버퍼를 지정 색으로 지우고 RTV/DSV를 묶고 뷰포트 설정 (`GraphicDevice.cpp:309`). Clear는 Immediate Context에서 GPU 명령 스트림에 기록되는 방식으로 동작하며, CPU 호출 즉시 GPU가 수행한다는 의미가 아닙니다.
- `EndFrame(true)` — 프레젠테이션을 VSync에 동기화하도록 요청하는 Present (`SwapChain.cpp:68` `Present(1,0)`). 실제 블로킹 여부는 queue/DWM 등에 따라 다릅니다.

### 6-5. 무지개 색 함수 (Function.cpp)

```cpp
color RainbowColor(_f32 _timeSec)
{
	const _f32 r = std::sin(_timeSec) * 0.5f + 0.5f;
	const _f32 g = std::sin(_timeSec + jc_math_deg2rad(120.0f)) * 0.5f + 0.5f;
	const _f32 b = std::sin(_timeSec + jc_math_deg2rad(240.0f)) * 0.5f + 0.5f;
	return color::FromFloat(r, g, b, 1.0f);
}
```

sin은 -1~+1을 부드럽게 오가므로 `* 0.5 + 0.5`로 0~1 범위로 만듭니다. R/G/B에 각각 0°/120°/240° **위상 차**를 주면 색상이 무지개처럼 도는 효과가 나옵니다. `jc::color`는 float 생성자가 없으므로(정수 0~255 생성자만 존재) 0~1 실수를 넘기려면 `color::FromFloat` 변환을 사용합니다.

## 7. GPU와 DX11, 하드웨어 깊이 보기 (심화 — 처음엔 굵은 글씨와 비유만)

> 이 장은 **두 번째 읽을 때** 정독하면 좋습니다. 5장에서 직관을 잡았다면, 여기서는 그 직관이 하드웨어에서 어떻게 구현되는지 수치와 함께 확인합니다. 처음 읽을 때는 각 절의 **비유와 굵은 글씨만** 보고 넘어가도 됩니다. 7-8(DeltaTime), 7-9(오해 5가지)는 초보자도 꼭 읽는 것을 권장합니다.

### 7-1. D3D11CreateDeviceAndSwapChain의 하드웨어 협상 과정

이 함수는 한 번의 호출로 여러 계층의 초기화를 수행합니다. 먼저 DXGI(DirectX Graphics Infrastructure) 팩토리가 GPU 어댑터를 선택하고, **백버퍼 포맷(R8G8B8A8_UNORM)**을 협상합니다. 스왑체인 생성 시 지정하는 버퍼 수와 `SwapEffect`는 함께 해석해야 하며, Microsoft 문서도 전체화면/창 모드와 Flip Model 여부에 따라 의미를 구분합니다. 본 엔진처럼 `BufferCount = 1` + `DXGI_SWAP_EFFECT_DISCARD` 구성에서는 애플리케이션이 `GetBuffer(0)`으로 접근하는 백버퍼가 1개이며, Flip Model의 전형인 `BufferCount = 2` + `FLIP_DISCARD`를 double-buffering으로 설명하는 Microsoft 샘플도 있습니다. 따라서 "BufferCount를 단순히 백버퍼 개수라고 외우지 말 것"이 안전합니다. 화면 주사율 관련 설정 등이 모두 이 단계에서 GPU 디스플레이 하드웨어와의 계약으로 체결됩니다. 백버퍼 리소스는 GPU가 사용할 수 있는 메모리에 생성되며(WDDM 메모리 관리 하에 물리 VRAM 위치를 단정하지 않음), 논리적인 픽셀 데이터 크기는 800×600×4바이트 ≈ 1.83 MiB입니다. 실제 GPU 리소스의 물리적 메모리 사용량은 alignment/padding 등에 의해 달라질 수 있습니다.

### 7-2. Clear의 하드웨어 경로: 일반적인 Draw와 다른 지우기

`ClearRenderTargetView`는 일반적인 Draw 호출처럼 VS/PS를 실행해 픽셀을 만드는 방식이 아닙니다. **비유**: 넓은 벽을 붓으로 한 줄씩 칠하는(Draw) 게 아니라, 페인트 롤러로 한 번에 밀어버리는(Clear) 것과 같습니다. GPU 메모리 대역폭이 넓기 때문에 풀HD(1920×1080) 기준 논리적으로 약 8MB에 해당하는 영역을 빠르게 지울 수 있습니다. GPU 내부 구현이 고정기능 유닛인지 여부는 제조사별로 다를 수 있어 API 수준에서 단정하지 않습니다. D3D11 Immediate Context에서 `context->ClearRenderTargetView(...)`를 호출하면 GPU 명령 스트림에 해당 작업이 기록/제출되는 방식으로 동작합니다. "즉시 실행되어 커맨드 큐에 쌓이지 않는다"는 설명은 잘못되었으며, CPU에서 호출했다고 GPU가 즉시 수행한다는 의미가 아닙니다. 04번 튜토리얼이 "지우는 것"을 주제로 삼는 이유는, 이 명령이 프레임 루프의 첫 단계로 모든 렌더링의 전제 조건이기 때문입니다.

### 7-3. Present와 VSync: GPU 파이프라인과 모니터의 만남

`EndFrame(true)`의 Present는 프레젠테이션을 VSync에 동기화하도록 요청하는 역할을 하며, 실제 Present의 블로킹 여부는 앞서 5-4에서 본 것처럼 queue/버퍼 상태/DWM 등에 따라 달라집니다. CPU/GPU는 파이프라이닝으로 동시에 움직이므로 Present가 모든 GPU 작업을 먼저 기다리는 함수라고 이해하면 안 됩니다. VSync 없이 아무 때나 표시를 요청하면 찢김이 보일 수 있습니다. VSync를 켜면 프레젠테이션이 디스플레이 타이밍에 맞춰지도록 요청되므로, 전통적으로는 CPU 프레임이 주사율에 맞춰지는 효과가 나타납니다. 이것이 02번에서 본 `Sleep(1)`이 실전에서 사라지는 이유 중 하나로 설명되지만, 현대 Windows의 실제 프레임 페이싱은 더 복잡합니다.

### 7-4. 깊이 버퍼와 DSV: 백버퍼와 쌍을 이루는 두 번째 표면

Initialize 내부의 3번째 단계인 깊이 버퍼는 백버퍼와 크기가 같은 별도의 GPU 메모리 표면입니다. 흔히 `DXGI_FORMAT_D24_UNORM_S8_UINT`(24비트 깊이 + 8비트 스텐실) 구성을 사용하지만 반드시 그런 것은 아니며, 이 엔진이 해당 포맷을 사용한다면 그 포맷으로 명시하는 것이 가장 정확합니다. **비유**: 책을 쌓을 때 아래 책이 위 책에 가려지듯, GPU도 픽셀마다 "깊이(앞뒤 거리)"를 적어두고 더 가까운 것만 남깁니다. 이 튜토리얼은 2D만 다뤄 깊이 판정을 쓰지 않지만, 하드웨어적으로 OM(Output Merger) 단계는 매 픽셀마다 깊이 비교 연산을 수행할 준비가 되어 있습니다. 13번 3D 큐브 튜토리얼에서 이 버퍼가 켜지는 순간을 만나게 됩니다. 깊이 버퍼도 프레임마다 Clear해야 하는데, `BeginFrame`이 RTV와 DSV를 **동시에** 지정 색과 깊이 1.0으로 지우는 이유입니다.

### 7-5. 뷰포트: NDC를 픽셀로 매핑하는 변환

파이프라인에서 래스터라이저는 클립 공간 좌표를 뷰포트 변환으로 픽셀 좌표로 바꿉니다. **비유**: 지도(NDC -1~+1)를 액자(800×600 픽셀)에 맞춰 늘려 붙이는 것. 개념적으로 `pixelX = (ndcX * 0.5 + 0.5) * width`로 이해하면 되며, 나중에 25번 렌더 타깃에서 "백버퍼가 아닌 다른 표면"으로 뷰포트를 바꾸는 응용으로 이어집니다. 정확히는 클립 공간 → perspective divide → NDC → viewport transform → 윈도우 좌표 과정입니다. Initialize에서 뷰포트를 창 크기로 채워두는 것은 "백버퍼 전체를 캔버스로 쓰겠다"는 선언입니다.

### 7-6. 프레임 루프의 CPU-GPU 파이프라이닝

매 프레임 `BeginFrame → (그리기) → EndFrame`의 구조는 CPU와 GPU가 **파이프라이닝(동시 작업)**을 하게 합니다. CPU는 프레임 N+1의 명령을 준비하고, GPU는 프레임 N의 렌더링을 실행합니다. 프레젠테이션이 VSync에 동기화되면 전통적으로는 파이프라인 깊이가 제한되어 CPU가 너무 앞서가지 못하게 막는 효과가 있었습니다. 현대 Windows의 실제 동작은 Flip Model/DWM 등에 따라 더 복잡합니다. 이 장의 무지개 애니메이션이 프레임 수와 무관하게 일정한 속도로 도는 것은 `elapsed += DeltaTime` 누적 덕분입니다 — 300fps 컴퓨터든 60fps 컴퓨터든 같은 속도로 순환합니다.

### 7-7. 트리플 버퍼링과 스왑 체인 모드: 더블 버퍼링의 확장

이 장의 더블 버퍼링은 가장 기본 형태입니다. 더 많은 버퍼를 쓰는 **트리플 버퍼링** 등은 VSync가 켜진 상태에서 GPU가 프레임을 만드는 동안 표시 버퍼를 추가로 확보하는 등의 목적으로 사용되는 경우가 있지만, 게임마다 latency/performance trade-off가 다릅니다. "VSync OFF + Triple Buffering이 경쟁 FPS의 표준"이라는 설명은 삭제합니다. 경쟁 게임은 보통 VSync OFF + FPS 제한 / Reflex / low latency 설정 + 적절한 swap chain / present mode 등 다양한 구성을 사용합니다. (본 엔진은 `BufferCount = 1` + `DXGI_SWAP_EFFECT_DISCARD`로 가장 단순한 구성을 쓰며, `EndFrame(true)`는 이 트레이드오프의 가장 단순한 한 점일 뿐입니다.) 이후 31번 파이프라인 여행에서 성능 튜닝 이야기를 들을 때 쉽게 이해할 수 있습니다.

### 7-8. DeltaTime이 없으면 왜 10배 빨리 도는가 — "프레임 독립"의 수학

빠른 PC 300fps vs 느린 PC 30fps에서 `위치 += 0.01`로 하면 1초에 각각 3.0 vs 0.3 이동 — 10배 차이. 올바른 공식은 `위치 += 속도 * DeltaTime`.

```cpp
FrameTimer timer; timer.Reset(); _f32 elapsed=0;
while(PumpMessage()){
    timer.Tick(); // QueryPerformanceCounter로 직전 호출과의 차이(초)를 잰다
    elapsed += timer.DeltaTime(); // 누적 — 04번 무지개는 이 elapsed로 sin을 돌린다
    device.BeginFrame(RainbowColor(elapsed));
    device.EndFrame(true);
}
// RainbowColor — 6-5: sin에 120° 위상차로 R/G/B를 돌린다
// 300fps든 60fps든 elapsed는 같은 속도로 증가하므로 같은 속도로 순환
```

> **엔지니어 규칙**: 게임 로직·애니메이션에 `DeltaTime` 없이 `1`을 더하는 코드는 버그입니다. 단, 물리 적분은 가변 DeltaTime보다 고정 타임스텝을 쓰는 게 안정적 — 14번 타이머 심화에서 다룹니다.

### 7-9. 엔지니어가 꼭 외워야 할 5가지 오해와 진실

1.  **"BufferCount=2가 더블 버퍼 아닌가?"** — BufferCount 의미는 SwapEffect와 생성 API, 창/전체화면에 따라 다르게 해석해야 합니다. 본 엔진의 `DISCARD` + `BufferCount=1` 구성에서는 `GetBuffer(0)`으로 얻는 백버퍼가 1개이며, Flip Model의 전형인 `BufferCount=2` + `FLIP_DISCARD`를 double-buffering으로 설명하는 Microsoft 샘플도 있습니다. 단순히 "백 개수"로 외우지 않는 것이 안전합니다.
2.  **"Clear 안 하면 자동으로 지워지나?"** — 아닙니다. 렌더 타깃은 자동으로 초기화되지 않습니다. `BeginFrame`이 `ClearRenderTargetView`+`depthSurface.Clear`를 매 프레임 하는 이유(`GraphicDevice.cpp:287`)이며, 의도적으로 이전 내용을 유지하는 패스가 아니라면 Clear가 일반적입니다. 빼면 잔상이 남는 실험이 04번 과제 3번입니다.
3.  **"Begin/End 짝이 안 맞아도 되나?"** — 안 됩니다. `BeginFrame`이 RTV/DSV/뷰포트를 바인딩하고 `EndFrame`이 Present합니다. 중간에 `SetRenderTarget`으로 렌더타깃을 바꿨다 해도 `BeginFrame`이 매 프레임 복구합니다(`GraphicDevice.cpp:283,316`).
4.  **"창 크기 바꾸면?"** — 스왑체인 버퍼 크기가 맞지 않아 `ResizeBuffers`로 RTV/DSV를 재생성해야 합니다. 04번은 고정 크기라 생략, `Window::OnResize`에서 다룹니다.
5.  **"포맷은 왜 R8G8B8A8?"** — 1픽셀 4바이트이므로 논리적인 픽셀 데이터 크기는 800×600×4 ≈ 1.83 MiB(`GraphicDevice.cpp:122`)입니다. 실제 물리 메모리 사용량은 alignment/padding으로 달라질 수 있습니다. HDR이면 `R16G16B16A16_FLOAT`로 바꿔야 하며 스왑체인 포맷과 RTV 포맷을 같이 바꿔야 합니다.

## 8. 핵심 규칙 요약

- [ ] 스왑체인은 애플리케이션이 그리는 백버퍼를 관리하고 `Present`로 표시를 요청하는 장치이며, 실제 경로는 `SwapEffect`에 따라 BitBlt/Flip으로 나뉜다.
- [ ] 개념적 더블 버퍼링 덕분에 깜박임/tearing을 이해할 수 있다 — 원리는 5장에서 본 스캔아웃과 프레젠테이션 동기화.
- [ ] 렌더 타깃은 자동 초기화되지 않으므로 매 프레임 Clear가 일반적이다 (`BeginFrame(color)`). 단, 의도적으로 유지하는 패스도 있다.
- [ ] Initialize 내부 5단계: D3D11CreateDeviceAndSwapChain → RTV → 깊이/DSV → 상태 객체 → 뷰포트.
- [ ] 애니메이션은 `elapsed += timer.DeltaTime()` 누적으로 프레임 독립적이어야 한다.
- [ ] `sin * 0.5 + 0.5` = 0~1 범위 색상 값, 위상 120° 차이 = 무지개 순환.
- [ ] `Present(1,0)`은 프레젠테이션을 VSync에 동기화하도록 요청하며, 실제 블로킹은 queue/DWM 등에 따라 달라진다.
- [ ] 정리 순서: `device.Finalize()` → `window.Destroy()`.

## 10. 다음 단계로
