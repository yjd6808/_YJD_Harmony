# 11. 카메라 좌표계 — 뷰 행렬, WASD 이동과 휠 줌

> 관련 코드: `Projects/sgfr/Sources/sgfr/11_Camera/11_Camera_Main.cpp`, `11_Camera_Function.cpp`
> (엔진: `Projects/sgf/Sources/sgf/Input/InputManager.h`, `Core/FrameTimer.h`)
> 실행: sgfr 실행 후 콘솔 메뉴에서 **11번** 선택
> 선행 학습: 10(월드 변환), 02(윈도우/입력 기초)

## 1. 이 장에서 배우는 것

뷰 행렬 = **카메라 이동의 역변환**이라는 핵심 아이디어로 월드→뷰→투영 변환 체인을 완성하고, deltaTime 기반으로 WASD 이동·휠 줌·R 리셋을 실시간 처리합니다.

## 2. 실행하면 보이는 것

콘솔에 카메라의 비밀(`PrintCameraExplanation`)이 출력된 후, 800×600 창에 회색 **5×5 타일 바닥**이 깔립니다.

- **WASD**: 카메라가 이동합니다. 이때 화면의 타일들이 **반대 방향으로 움직이는 것**처럼 보입니다 (카메라가 오른쪽으로 가면 타일은 왼쪽으로!)
- **마우스 휠**: 확대/축소 (0.2배 ~ 5배 사이)
- **R**: 카메라 위치와 줌을 초기 상태로 리셋
- **ESC**: 종료

줌인 상태에서는 이동 속도가 자동으로 느려져, 화면 기준으로 같은 속도로 이동하는 느낌을 줍니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 카메라는 움직이지 않는다 — 세상이 움직일 뿐

기차 안에서 밖을 보면 **기차가 아니라 세상이 뒤로 지나갑니다.** 카메라도 마찬가지입니다. GPU는 카메라가 "어디에 있는지" 알 필요 없고, **카메라를 원점에 놓고 세상을 반대로 옮긴 좌표**만 알면 됩니다.

- 카메라가 (2, 1)에 있다 → 세상을 (-2, -1)만큼 이동
- 카메라가 2배 확대했다 → 세상을 2배 크게 그린다

이것이 바로 **뷰 행렬 = Translation(-cameraPos) × Scale(zoom)**입니다.

### 3-2. 변환 체인의 4개 좌표계

```
로컬 ─(월드 행렬)→ 월드 ─(뷰 행렬)→ 카메라 ─(투영 행렬)→ NDC ─(뷰포트)→ 픽셀
```

10장에서 첫 화살표(월드)를 배웠고, 이번 장은 두 번째 화살표(뷰)입니다. 11장을 마치면 **전 체인이 완성**됩니다.

### 3-3. deltaTime — "초당 속도"로 움직이기

"1초에 1.5칸"이라고 속도를 정해 두면, 60FPS 컴퓨터에서는 1/60초마다 0.025칸씩, 144FPS 컴퓨터에서는 1/144초마다 0.0104칸씩 움직여 **실제로 걸리는 시간이 동일**해집니다. 이것이 프레임 독립적 움직임입니다. deltaTime이 없다면 고주사율 모니터에서 게임이 두 배 빨라지는 사고가 납니다.

### 3-4. 5×5 타일 — "세상"을 만들어 보기

카메라를 체험하려면 세상에 "움직일 것이" 있어야 합니다. 이 튜토리얼은 회색 타일 5×5개를 바닥에 깔아 세상을 만듭니다. 타일 사이에 틈(간격 0.6, 크기 0.5)을 둔 것은 **카메라가 움직일 때 타일들이 미끄러지는 모습을 또렷이 보여 주기 위한 의도**입니다. 타일이 서로 맞붙어 있으면 화면이 통째로 밀리는 것처럼 보여 움직임을 알아차리기 어렵지만, 틈이 있으면 "타일이 왼쪽으로 하나씩 지나가는" 것이 분명히 보입니다.

그리고 중요한 사실: 타일 25개는 **전부 하나의 정점 버퍼**입니다. 같은 사각형 데이터를 월드 행렬만 바꿔 25번 그립니다. 10장에서 행렬 재사용을 배웠다면, 이제 그 기술로 "많은 물체로 이루어진 세상"을 만들 수 있게 된 것입니다. 이 방식은 이후 배치 렌더러로 진화합니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 뷰 행렬(View) | 월드 좌표를 카메라 기준 좌표로 바꾸는 행렬 | "내 눈앞 3m" 기준으로 바꾸기 |
| 역변환 | 원래 변환을 되돌리는 변환 | 오른쪽으로 3칸 가는 것을 왼쪽으로 3칸으로 |
| 줌(Zoom) | 화면의 확대/축소 배율 | 망원렌즈, 광각렌즈 |
| deltaTime | 이전 프레임에서 지난 시간(초) | 초침이 한 번 뚝하고 움직인 간격 |
| 폴링(Polling) | 매 프레임 키 상태를 물어보는 방식 | "지금 눌렀어?" 매 프레임 확인 |
| 클램프(Clamp) | 값을 최소~최대 범위 안으로 잘라내기 | 화장실 문 안전바 |
| 프레임 독립 | 프레임 속도와 무관하게 시간 기준으로 움직임 | 60번도 144번도 똑같은 거리 |
| 휠 틱(Wheel tick) | 마우스 휠 한 칸 (WheelDelta는 120으로 나눈 값) | 휠 한 톱니 |
| 카메라 좌표계 | 카메라가 원점이고 -Z가 전방인 좌표계 | 카메라의 눈으로 본 세상 |
| WVP | 월드×뷰×투영 결합 행렬 (왼쪽부터 적용) | 카메라 여행 지시서 한 장 |
| LookAt | 눈 위치·바라보는 점·위쪽 벡터로 뷰 행렬을 만드는 함수 | 삼각대를 목표에 맞춤 |
| OrthographicOffCenterLH | 원점이 왼쪽 위인 LH 직교 투영 생성 함수 | 설계도면 좌표 규격 |
| 시야각(FOV) | 카메라가 담는 세로 각도 | 망원/광각 렌즈의 각도 |
| 벽 타기(Wall-cling) | 타이머 누적에 카메라 이동을 더해 원하는 한계로 유지 | 손가락을 벽에 댄 채로 밀기 |
| 렌더 배치 | 같은 셰이더/텍스처의 드로우를 모아 한 번에 처리 | 주문서를 묶어 한 번에 배달 |

표의 첫 줄(카메라 좌표계)이 이 장 전체의 키워드입니다. 카메라가 움직이는 것이 아니라 **모든 월드 좌표가 카메라 반대 방향으로 옮겨질** 뿐이며, 그 사실이 뷰 행렬의 모든 결과를 설명합니다. 기억이 흐려지면 "카메라 고정, 세상이 움직인다" 한 줄만 되새기세요.

## 5. 코드 워크스루

`Camera_Main()`의 흐름입니다.

### 1~3단계: 기본 준비 (10장과 동일)

`PrintCameraExplanation()` → 창/디바이스 → **타일 1장** 분량의 `VertexPC` 정점 4개 + 인덱스 6개로 `VertexBuffer`/`IndexBuffer` 생성 → `CameraShaderSource()`(10번과 동일 구조) 컴파일 + `ConstantBuffer<CbTransform> cbTransform` 생성.

### 4단계: 카메라 상태 변수와 투영

```cpp
vec2 cameraPos = vec2(0.0f, 0.0f);  // 카메라가 바라보는 월드 위치
_f32 zoom = 1.0f;                   // 1보다 크면 확대, 작으면 축소

const _f32 aspect = window.AspectRatio();
const mat4 proj = mat4::OrthographicOffCenterLH(-aspect, +aspect, -1.0f, +1.0f, 0.0f, 1.0f);
```

### 5단계: 렌더 루프 — 입력 처리

```cpp
timer.Tick();
const _f32 dt = timer.DeltaTime();

const _f32 moveSpeed = 1.5f / zoom;   // 줌인 상태에서는 천천히 (화면 기준 속도 일정)
if (input.IsKeyDown('W')) { cameraPos.y += moveSpeed * dt; }
if (input.IsKeyDown('S')) { cameraPos.y -= moveSpeed * dt; }
if (input.IsKeyDown('A')) { cameraPos.x -= moveSpeed * dt; }
if (input.IsKeyDown('D')) { cameraPos.x += moveSpeed * dt; }

const int wheel = input.WheelDelta();  // 이미 120으로 나눈 "틱 단위"! 추가 나눗셈 금지
if (wheel != 0)
{
    zoom *= 1.0f + _f32(wheel) * 0.1f;
    zoom = Clamp(zoom, 0.2f, 5.0f);
}

if (input.IsKeyPressed('R')) { cameraPos = vec2(0.0f, 0.0f); zoom = 1.0f; }
input.NextFrame();
```

- `IsKeyDown`은 **누르는 동안 계속** true (폴링), `IsKeyPressed`는 **막 눌린 프레임에만** true — `NextFrame()`이 이전 상태를 기억하기 때문입니다.
- 휠은 "틱" 단위라 한 틱에 10%씩 배율이 바뀌고, `Clamp`로 0.2~5 범위를 강제합니다.

입력 처리 순서도 규칙이 있습니다. 모든 입력 판정이 끝난 뒤 **루프의 마지막에 `input.NextFrame()`을 호출**해 "이번 프레임 상태"를 "지난 프레임 상태"로 복사합니다. 그래야 다음 프레임에서 `IsKeyPressed`가 정확히 동작합니다. 만약 NextFrame을 건너뛰면, R 키를 눌렀다 뗀 것이 감지되지 않아 카메라 리셋이 일어나지 않습니다. 이 "판정 → NextFrame" 순서는 이후 모든 튜토리얼과 게임 프로젝트에서 동일하게 유지되는 규칙입니다.

### 6단계: 뷰 행렬 생성 — 핵심 한 줄

```cpp
const mat4 view = mat4::Translation(-cameraPos.x, -cameraPos.y, 0.0f) * mat4::Scale(zoom, zoom, 1.0f);
```

카메라 위치의 **반대 부호**로 이동하고, 줌 배율을 스케일로 곱합니다.

### 7단계: 5×5 타일을 "세상"으로 그리기

```cpp
for (int y = -2; y <= 2; ++y)
{
    for (int x = -2; x <= 2; ++x)
    {
        const mat4 world = mat4::Scale(0.5f, 0.5f, 1.0f) * mat4::Translation(x * 0.6f, y * 0.6f, 0.0f);
        CbTransform cb = {};
        cb.worldViewProj_ = world * view * proj;   // 월드 → 뷰 → 투영 순서!
        cbTransform.UpdateAndBind(&device, cb, 0);
        vb.Bind(&device); ib.Bind(&device); shader.Bind(&device);
        device.Context()->IASetPrimitiveTopology(D3D11_PRIMITIVE_TOPOLOGY_TRIANGLELIST);
        device.Context()->DrawIndexed(6, 0, 0);
    }
}
```

같은 VB/IB를 **월드 행렬만 바꿔 25회** 그립니다. 카메라가 이동하면 뷰 행렬이 바뀌고, 모든 타일의 WVP가 함께 바뀌므로 **타일들이 통째로 반대 방향으로 움직이는 것처럼** 보입니다.

타일 색이 4개 정점에 각각 다른 회색(1.0/0.8/0.6/0.4)이라, 타일마다 왼위→오른아래로 부드러운 그라데이션이 생깁니다. 이것은 의도된 것이 아니라 정점 색 보간의 자연스러운 결과로, 타일이 개별적으로 존재한다는 느낌을 강조해 줍니다. 루프의 x/y 순서에 유의하세요 — 안쪽 루프(x)가 먼저 돌아 타일이 가로줄 단위로 그려지지만, 2D라 깊이 테스트가 꺼져 있어 드로우 순서가 화면 결과에 거의 영향을 주지 않습니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. 뷰 변환은 "행렬 3개를 미리 곱한 뒤" 한 번만

이 튜토리얼의 핵심 성능 포인트는 `world * view * proj`를 **CPU에서 미리 합성**해 상수 버퍼로 한 번에 보내는 것입니다. GPU 셰이더는 매 정점마다 1번의 행렬 곱(16 FMA)만 수행합니다. 만약 world/view/proj를 따로 보냈다면 정점마다 3번의 행렬 곱이 필요했을 것입니다. 행렬 곱셈은 CPU 쪽의 SIMD(SSE/AVX) 레지스터에서 64개 float을 처리할 정도로 저렴한 반면, 정점 개수(수십만 개)만큼 곱해지는 쪽은 비싸므로 **미리 합성하는 관례**가 하드웨어 연산량을 3분의 1로 줄입니다.

### 6-2. 상수 버퍼 갱신과 드로우콜의 파이프라인

매 타일마다 `cbTransform.UpdateAndBind`가 호출됩니다. 이는:

1. `Map(D3D11_MAP_WRITE_DISCARD)` — CPU가 GPU 버퍼의 메모리 맵핑 주소에 64바이트를 memcpy
2. `Unmap`
3. `VSSetConstantBuffers(0,...)` + `PSSetConstantBuffers(0,...)`

드라이버는 이를 GPU 명령 버퍼에 "상수 갱신 + 드로우" 기록으로 변환합니다. **드라이버는 CPU에서 동기화하지 않고 명령을 순서대로 큐잉**하므로, GPU가 첫 타일을 그리는 동안 CPU는 벌써 25번째 타일의 상수를 쓰고 있을 수 있습니다(CPU-GPU 병렬 실행). 다만 `Map(DISCARD)`가 드라이버가 새 메모리를 재할당하는 식으로 동작하기 때문에, GPU가 이전 상수를 읽는 중이어도 블로킹 없이 진행됩니다.

이 25회 반복에서 흥미로운 점은 **같은 상수 버퍼를 계속 덮어쓰는** 것입니다. 프레임 내에서 버퍼 내용이 25번 바뀌고, GPU는 각 드로우콜마다 그 시점의 내용을 읽습니다. 명령 버퍼는 순서대로 실행되므로 "상수 갱신 → 드로우"가 항상 일치합니다. 이것이 D3D11의 실행 모델입니다 — 모든 상태와 데이터는 **드로우콜이 실행되는 시점의 값**으로 사용됩니다. 따라서 "버퍼를 갱신하고 바로 그리는" 이 패턴은 GPU와 CPU가 서로 다른 속도로 일해도 항상 올바른 화면을 만듭니다.

### 6-3. NDC와 뷰포트 변환 — 줌의 정체

직교 투영이 끝난 NDC(-1~1)는 **뷰포트 단계**에서 픽셀로 바뀝니다. GPU의 뷰포트 변환 유닛(고정기능)이 `x_pixel = (ndc.x + 1) * width / 2` 같은 보간을 수행합니다. 줌은 그 전 단계인 **뷰 행렬의 Scale**로 이미 적용되었으므로, NDC 상에서 물체가 커졌고 결과적으로 더 많은 픽셀이 그려집니다. 이것이 "줌 = GPU가 픽셀을 더 많이 만들기"라는 뜻으로, 확대할수록 픽셀 처리량이 증가하는 이유입니다.

### 6-4. 타일 25회 드로우와 배치의 서막

25번의 DrawIndexed는 각각 정점 4개를 재처리합니다. GPU 관점에서 같은 버퍼를 반복 바인딩하면 인덱스/정점 캐시가 따뜻해져 성능 손실이 작지만, **드로우콜마다 드라이버가 상태 검증·커맨드 버퍼 기록을 반복**해야 하므로 호출 수가 늘어나면 CPU가 병목이 됩니다. 그래서 실전 엔진은 모든 타일을 **한 번의 드로우콜**(배치 렌더링)로 그립니다. 이 25회 반복이 22장 SceneRenderer/배치 렌더러의 예고편입니다.

### 6-5. WheelDelta의 "틱 단위" — WM_MOUSEWHEEL과 하드웨어

Windows는 마우스 휠 메시지 `WM_MOUSEWHEEL`에 델타 값 ±120(기본 한 틱)을 담아 보냅니다. 이는 1/8도씩 세밀한 휠 회전을 표현하기 위한 고정소수점 값이며, 드라이버가 휠 엔코더의 틱 수를 120으로 환산해 보냅니다. `InputManager::WheelDelta()`는 이 **120을 이미 1로 나누어** 반환하므로, 이 튜토리얼의 `zoom *= 1.0f + wheel * 0.1f`에서 휠 한 틱 = 10% 배율이 정확히 성립합니다. 만약 120을 또 나누면 한 틱에 1/120도밖에 변하지 않아 휠이 죽은 것처럼 느껴집니다.

### 6-6. 뷰 행렬의 계산 비용은 CPU 몫

뷰 행렬은 정점마다 곱해지는 것이 아니라, 매 프레임 **CPU가 한 번** 만들고 `world * view * proj` 합성에 사용됩니다. `Translation(-cameraPos) * Scale(zoom, zoom, 1)`은 4x4 행렬 곱 두 번으로, SSE/AVX 레지스터로 수십 나노초 안에 끝납니다. 합성된 WVP는 상수버퍼로 GPU에 전달되고, GPU는 정점마다 이 하나의 행렬만 곱합니다. 즉 카메라가 움직여도 GPU가 다시 컴파일하거나 셰이더를 바꿀 필요가 전혀 없습니다 — **그저 상수 레지스터 내용이 바뀔 뿐**입니다.

이 구조는 실전 엔진에서도 동일합니다. 카메라 클래스는 `Camera::GetViewProjection()` 같은 함수로 합성 행렬을 만들고, 그리기 전에 한 번 바인딩합니다. 11장의 `cb.worldViewProj_ = world * view * proj`가 바로 그 전형적인 패턴입니다.

### 6-7. 카메라 이동이 "세상이 움직이는 것"으로 보이는 이유

GPU는 카메라라는 개념 자체를 모릅니다. GPU가 아는 것은 "월드 공간에 놓인 삼각형"과 "그걸 화면으로 옮기는 행렬"뿐입니다. 뷰 행렬이 카메라 이동의 역변환이라는 것은, **수학적으로 똑같은 결과**를 두 가지로 해석할 수 있다는 뜻입니다. 카메라가 오른쪽으로 2 이동하면 세상이 왼쪽으로 2 이동한 것과 동일한 화면이 나옵니다. 그래서 이 튜토리얼에서 W를 누르면 타일들이 아래로 내려가 보입니다 — 카메라가 위로 움직였으니, 뷰 행렬은 세상을 그 반대 방향으로 옮긴 것입니다. 이것을 이해하면 3D에서도 같은 원리(13장의 LookAtLH)가 그대로 적용된다는 것이 보입니다.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| 뷰 행렬 | `view = Translation(-cameraPos) * Scale(zoom, zoom, 1)` — 카메라 이동의 역변환 |
| 변환 체인 | `wvp = world * view * proj` — 월드 → 뷰 → 투영 순서 |
| 프레임 독립 | 이동량 = `moveSpeed * dt`, `dt = timer.DeltaTime()` |
| 줌 이동 보정 | `moveSpeed = 1.5f / zoom` — 화면 기준 속도 일정 유지 |
| 휠 틱 | `WheelDelta()`는 이미 120으로 나눈 틱 단위 — **추가 나눗셈 금지** |
| 범위 제한 | `Clamp(zoom, 0.2f, 5.0f)` |
| 폴링 vs 프레스 | `IsKeyDown`(누르는 동안) / `IsKeyPressed`(막 누른 프레임) + `NextFrame()` |
| 직교 투영 | `OrthographicOffCenterLH(-aspect, +aspect, -1, +1, 0, 1)` — 비율 보정 |
| 재사용 | 타일 25개 = 같은 VB/IB + 월드 행렬만 변경 |
| 뷰 합성 비용 | 뷰 행렬은 CPU에서 1회 생성, GPU는 합성된 WVP만 정점마다 곱함 |
| 시간 측정 | `timer.Tick()` 후 `dt = timer.DeltaTime()` — 매 프레임 시작에 |
| 카메라 해석 | "카메라가 움직임" = "세상이 반대로 움직임" (수학적으로 동일) |

표의 키워드들은 13장(3D)에서 거의 그대로 재등장합니다. 특히 `LookAtLH`와 시야각은 3D 카메라에서 원근 투영과 결합하고, 휠 줌은 FOV를 바꾸는 방식으로 발전합니다. "카메라가 움직이는 것이 아니라 세상이 반대로 움직인다"는 비유를 3D에서도 유지하면, 13장의 view/proj 행렬이 낯설지 않을 것입니다.

또한 이 장의 25회 드로우는 배치 렌더링의 예고였습니다. 드로우콜 수를 세는 습관을 여기서부터 길러 두면, 22장 SceneRenderer가 줄이는 비용을 정량적으로 느낄 수 있습니다. 드로우콜 하나에 붙는 부속 호출들(버퍼 바인딩, 토폴로지 설정, DrawIndexed)이 무엇인지 목록으로 기억해 두세요.

카메라 입력 실험도 놓치지 마세요. 키보드(방향 이동), 마우스 휠(줌), 그리고 스페이스바(타이머 일시정지)라는 세 입력이 각각 다른 성격(연속 이동, 불연속 틱, 토글)을 갖는다는 점이 인상적입니다. 이 구분은 28장(입력 처리)에서 이벤트/폴링 모델로 정리되므로, "이 입력은 어떤 성격인가"를 생각하는 습관만 남겨도 충분합니다. 마지막으로 휠 틱의 120 배율은 Windows의 표준 규칙이라, 다른 프레임워크(예: 웹)에서도 같은 값으로 만나게 됩니다.

여기에 더해, 화면 바깥쪽으로 벗어난 타일이 어떻게 보이는지도 눈여겨보세요. 뷰포트 밖의 타일은 GPU의 클리핑 단계에서 잘려 나가므로 화면 밖을 벗어난 물체의 픽셀 셰이더는 실행되지 않습니다. 카메라를 끝까지 밀어 타일 25개 중 일부가 화면 밖으로 사라지는 것을 보며, "클리핑은 비용을 아끼는 하드웨어 장치"라는 인상을 남겨 두면 26장(포스트 프로세싱)의 후처리 풀스크린 쿼드와 대비가 됩니다. 이렇게 이 장 하나에 뷰 변환의 수학, 입력의 성격, 드로우콜 비용, 클리핑까지 네 가지 단면이 담겨 있으니, 마무리로 "카메라 = 세상을 반대로 움직이는 행렬"이라는 한 줄만 확실히 남기고 12장으로 넘어가면 됩니다. 그리고 이 장의 타일 그리드가 "행렬만 바꾸면 같은 그림이 다른 위치에 놓인다"는 사실을 보여 주었다는 점도 함께 기억하세요 — 이것이 이후 모든 렌더러의 토대입니다. 다음 장에서는 이 "행렬을 담는 상자"인 상수버퍼를 본격적으로 다룹니다. 지금까지의 모든 변환 코드가 거기에 정리되어 들어갑니다.

## 8. 직접 해보기 — 실험으로 확인하기

## 9. 다음 단계로
