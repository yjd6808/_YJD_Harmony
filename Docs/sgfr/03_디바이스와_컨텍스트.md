# 03. 디바이스와 컨텍스트 — 만드는 사람과 그리는 사람의 분리

> 관련 코드: `Projects/sgfr/Sources/sgfr/03_DeviceAndContext/` (`03_DeviceAndContext_Main.cpp`)
> 관련 엔진: `Projects/sgf/Sources/sgf/Graphics/GraphicDevice.h`, `GraphicContext.h/.cpp`
> 실행: sgfr 실행 후 콘솔 메뉴에서 **3번** 선택
> 선행 학습: 02. 윈도우와 메시지 루프

## 1. 이 장에서 배우는 것

Direct3D 11의 두 거대한 객체인 **ID3D11Device(공장)**와 **ID3D11DeviceContext(조립 라인)**의 역할 분리를 배우고, sgf v3 엔진이 이를 어떻게 `GraphicDevice`/`GraphicContext`로 나누었는지 확인합니다. 그리고 같은 상태를 반복 설정할 때 **D3D 호출을 생략하는 상태 캐시(바인딩 캐시)**의 원리를 통계 카운터로 직접 실험합니다. 윈도우는 뜨지 않고 콘솔로만 진행됩니다 — "창 없이 디바이스만" 만들 수 있다는 것 자체가 v2.1부터의 큰 변화입니다.

## 2. 실행하면 보이는 것

콘솔에 다음 내용이 순서대로 출력됩니다.

1. 역할 분리 설명 — `ID3D11Device = 공장`, `ID3D11DeviceContext = 조립라인` 요약과 sgf v3 대응 관계
2. `1) 디바이스 초기화 성공 (창 없이 디바이스만 생성됨)`
3. `2) 토폴로지를 [삼각형, 삼각형, 선] 순서로 3번 설정했다.`
4. **실제 D3D 호출 수 : 2 (예상: 2)** / **캐시로 생략된 호출 : 1 (예상: 1)**

즉, 코드로는 3번 호출했지만 GPU에는 2번만 전달되고 1번은 생략됐다는 것이 숫자로 증명됩니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 공장(Device)과 조립 라인(Context)

자동차 회사를 생각해 봅시다. **공장**은 부품(엔진, 바퀴, 유리)을 만드는 곳이고, **조립 라인**은 만들어진 부품을 차체에 끼워 맞추는 곳입니다. 공장이 부품을 만드는 일과 조립 라인이 차를 조립하는 일은 분명히 다릅니다. D3D11도 마찬가지입니다.

- `ID3D11Device` — **만든다.** 정점 버퍼, 텍스처, 셰이더, 상수 버퍼 같은 모든 GPU 리소스를 생성하는 "공장".
- `ID3D11DeviceContext` — **묶고 그린다.** 만들어진 리소스를 파이프라인에 장착(바인딩)하고 `Draw`를 호출하는 "조립 라인".

sgf v3는 이를 그대로 클래스로 나누었습니다. `GraphicDevice::Initialize`가 리소스를 만들고, `device.GetContext()`로 얻는 `GraphicContext`가 바인딩/그리기를 담당합니다.

### 3-2. 상태 캐시 = "이미 해본 일은 건너뛰기"

여러분이 매일 아침 출근할 때 매번 "문을 잠갔나?"를 열 번 확인한다면 낭비일 겁니다. 스마트한 사람은 방금 확인했으면 두 번째부터는 건너뜁니다. GPU도 같습니다. `IASetPrimitiveTopology` 같은 바인딩 호출은 값싸 보이지만, 드로우가 수천 번이 되면 드라이버 검증 오버헤드가 쌓입니다. `GraphicContext`는 "직전에 뭘 묶었는지"를 기억했다가, 같은 것을 다시 묶으라는 명령이 오면 D3D 호출 자체를 생략합니다. 이 장에서는 생략된 횟수를 카운터로 세어 그 효과를 직접 확인합니다.

### 3-3. 왜 v2.1부터 "창 없이 디바이스만" 가능한가

옛날 구조에서는 디바이스를 만들 때 창(스왑체인)까지 강제로 필요했습니다. 하지만 "리소스를 만드는 공장"은 사실 창과 무관합니다. v2.1부터는 디바이스와 창(표면)의 소유를 분리해, 공장만 먼저 세울 수 있게 되었습니다. 2D 게임에서 공구 상자(공장)를 창고(창)보다 먼저 열 수 있는 것과 같습니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| ID3D11Device | GPU 리소스 생성 담당 인터페이스 | 공장 |
| ID3D11DeviceContext | 바인딩/그리기 명령 담당 인터페이스 | 조립 라인 |
| GraphicDevice | sgf의 디바이스 래퍼 (Initialize/Finalize/CreateXXX) | sgf 공장 관리자 |
| GraphicContext | sgf의 컨텍스트 래퍼 (SetXXX/Draw) | sgf 조립 라인 관리자 |
| 바인딩 (Bind) | 리소스를 파이프라인 단계에 장착 | 부품 조립 |
| 상태 캐시 (State Cache) | 직전 상태 기억 후 중복 생략 | 이미 확인한 문잠금 건너뛰기 |
| 토폴로지 (Topology) | 정점을 어떻게 이을지 (삼각형/선/점) | 레고 조립 도면 |
| InvalidateCache | 캐시를 전부 비움 (외부 변경 후 필수) | 확인 기록 새로 초기화 |
| 프리미티브 | 기본 도형 (점/선/삼각형) | 레고 블록 종류 |
| 슬롯 (Slot) | 파이프라인의 장착 위치 번호 | 공구 걸이 번호 |

### 5-1. 역할 분리 안내 출력 (코드 33~39행)

```cpp
printf("  ID3D11Device        = 공장   : 버퍼/텍스처/셰이더 같은 리소스를 '만든다'\n");
printf("  ID3D11DeviceContext = 조립라인: 만들어진 리소스를 파이프라인에 '묶고 그린다'\n\n");
printf("[sgf v3 대응]\n");
printf("  GraphicDevice  -> 생성/수명 담당 (Initialize/Finalize, CreateXXX)\n");
printf("  GraphicContext -> 바인딩/그리기 담당 (SetXXX, Draw/DrawIndexed)\n\n");
```

### 5-2. 창 없이 디바이스만 초기화 (코드 42~51행)

```cpp
GraphicDevice device;
if (!device.Initialize())
{
	printf("그래픽 디바이스 초기화 실패!\n");
	return;
}
GraphicContext& context = device.GetContext();
```

`Initialize()` (인자 없음)는 `D3D11CreateDevice`를 호출해 ID3D11Device와 ID3D11DeviceContext를 만듭니다. 스왑체인/깊이 버퍼가 없어도 디바이스는 멀쩡하게 살아있습니다. `GetContext()`는 디바이스가 소유한 `GraphicContext`의 참조를 돌려줍니다.

### 5-3. 상태 캐시 실험 (코드 54~61행)

```cpp
context.ResetStats();
context.SetPrimitiveTopology(PrimitiveTopology::ptTriangleList);	// (1) 실제 D3D 호출
context.SetPrimitiveTopology(PrimitiveTopology::ptTriangleList);	// (2) 직전과 같음 -> 생략!
context.SetPrimitiveTopology(PrimitiveTopology::ptLineList);		// (3) 달라짐 -> 실제 호출

printf("   실제 D3D 호출 수   : %llu (예상: 2)\n", context.GetApiCallCount());
printf("   캐시로 생략된 호출 : %llu (예상: 1)\n\n", context.GetSkippedCallCount());
```

`GraphicContext::SetPrimitiveTopology`의 내부 구현(`GraphicContext.cpp`)은 다음과 같습니다:

```cpp
void GraphicContext::SetPrimitiveTopology(PrimitiveTopology _topology)
{
	if (_topology == cachedTopology_)	// 직전과 같으면?
	{
		skippedCallCount_ += 1;			// 생략 카운트만 올리고
		return;							// D3D 호출 안 함!
	}
	cachedTopology_ = _topology;
	apiCallCount_ += 1;
	pContext_->IASetPrimitiveTopology(ToD3D11(_topology));	// 진짜 호출
}
```

실행 결과는 정확히 예상대로 **호출 2회 / 생략 1회**가 나옵니다. 첫 번째 삼각형은 캐시에 없어서 호출, 두 번째 삼각형은 캐시와 같아서 생략, 세 번째 선은 달라서 호출 — 이렇게 3번의 요청이 2+1로 갈라집니다.

### 5-4. InvalidateCache 안내 (코드 63~66행)

```cpp
printf("  단, 외부에서 원시 컨텍스트를 직접 만졌다면 InvalidateCache()로 캐시를 비워야 한다.\n");
printf("  (BeginFrame처럼 엔진 내부에서 상태를 바꾸는 지점이 대표적)\n\n");
```

캐시는 "엔진이 마지막으로 묶은 것"을 기억합니다. 그런데 외부 코드가 원시 `ID3D11DeviceContext`를 직접 조작했다면, 엔진은 그 사실을 모르므로 잘못된 생략을 할 수 있습니다. `InvalidateCache()`는 모든 캐시 필드를 nullptr로 밀어버려(토폴로지는 `PrimitiveTopology::Max`), 다음 호출을 무조건 실제로 내려가게 만듭니다.

### 5-5. 정리 (코드 69행)

`device.Finalize()`로 모든 D3D 객체를 해제한 뒤 함수가 반환되고, 런처는 목차로 돌아갑니다.

### 사용된 sgf API 정리

| API | 역할 |
|---|---|
| `GraphicDevice::Initialize()` | 디바이스만 생성 (창 없음, v2.1 경로) |
| `GraphicDevice::Finalize()` | 디바이스 해제 |
| `GraphicDevice::GetContext()` | 소유한 GraphicContext 참조 반환 |

| `GraphicContext::GetSkippedCallCount()` | 캐시로 생략된 호출 수 |
| `GraphicContext::InvalidateCache()` | 바인딩 캐시 전체 무효화 |
| `PrimitiveTopology` 열거형 | ptPointList/ptLineList/ptLineStrip/ptTriangleList/ptTriangleStrip |

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. D3D11 장치 객체의 하드웨어 의미: 디바이스 = GPU 드라이버와의 "계약서"

`D3D11CreateDevice`가 성공하면 드라이버가 GPU 커맨드 프로세서를 초기화하고, 응용 프로그램은 GPU와의 통신 계약(디바이스)을 얻게 됩니다. 이 디바이스는 실제 GPU 하드웨어의 **명령 큐(Command Queue)**와 연결되며, `CreateBuffer` 같은 호출은 CPU가 아닌 GPU 메모리(VRAM 또는 통합 메모리)에 물리적 할당을 합니다. 같은 GPU 하드웨어여도 드라이버에 따라 지원하는 기능 수준(Feature Level 11_0, 11_1 등)이 달라지며, 디바이스 생성 시 이 기능 수준 협상이 이루어집니다.

### 6-2. "만드는 쪽"과 "쓰는 쪽"이 분리된 이유: 커맨드 리스트와 드라이버 스레드

역할 분리는 단순한 설계 취향이 아닙니다. D3D11에서 리소스 생성(ID3D11Device)은 비교적 안전하게 멀티스레드에서 병렬 수행될 수 있지만, 그리기 명령(ID3D11DeviceContext)은 **스레드 단일 소유**를 요구합니다. 즉, 여러 스레드가 동시에 리소스를 만들고, 단일 스레드(렌더 스레드)만 그리기 명령을 내리는 구조가 하드웨어와 API 양쪽에서 자연스럽습니다. sgf가 v3에서 GraphicContext를 별도로 분리한 근거가 여기 있습니다. (그림자 맵 생성처럼 매 프레임 새 리소스가 필요한 경우에도 "공장"은 한 번만 세우고 "조립 라인"만 바쁘게 돌아갑니다.)

### 6-3. 바인딩 호출이 실제로 하는 일: 드라이버의 상태 검증과 명령 버퍼 기록

`IASetPrimitiveTopology` 한 줄은 GPU 하드웨어로 직접 전달되지 않습니다. 내부적으로는 **사용자 모드 드라이버(UMD)**가 해당 상태를 검증하고, 커맨드 버퍼에 "토폴로지 = D3D11_PRIMITIVE_TOPOLOGY_TRIANGLELIST"라는 기록을 추가합니다. 이 기록들이 모이다가 `Present`(04번) 시점에 GPU로 일괄 전송됩니다. 문제는 이 검증이 "같은 상태를 다시 설정해도" 수행된다는 것입니다. 수천 개의 드로우가 각각 같은 토폴로지·같은 셰이더·같은 버퍼를 반복해서 바인딩하면, 드라이버는 같은 검증을 수천 번 반복하고 커맨드 버퍼는 중복 기록으로 지저분해집니다. 상태 캐시가 생략하는 것은 바로 이 낭비입니다. (23번 스테이트 캐시 튜토리얼에서 드로우별 절감 통계를 다시 실험합니다.)

### 6-4. PrimitiveTopology가 IA(Input Assembler) 하드웨어에 도달하는 과정

토폴로지 상태는 D3D11 파이프라인의 첫 단계인 **IA 단계**에 전달됩니다. 하드웨어 수준에서 IA는 정점 버퍼에서 정점을 순차 읽어 프리미티브를 만드는 고정기능 유닛입니다. GPU의 프리미티브 어셈블러는 토폴로지 값에 따라 정점을 묶는 규칙을 바꿉니다 — TRIANGLELIST면 3개씩, LINELIST면 2개씩, POINTLIST면 1개씩. 따라서 토폴로지는 "그리기 해석 규칙"이며, 상태 캐시가 생략 대상으로 삼는 이유는 이 값이 드로우 사이에 거의 변하지 않기 때문입니다.

### 6-5. InvalidateCache가 필요한 실전 시나리오: BeginFrame과 원시 컨텍스트

이 튜토리얼이 주의를 주는 지점은 실전에서 실제로 일어납니다. `GraphicDevice::BeginFrame`은 내부적으로 `ClearRenderTargetView`, `OMSetRenderTargets`, 뷰포트 설정 등 **GraphicContext를 거치지 않는 원시 호출**을 합니다. 만약 GraphicContext가 이전 프레임의 캐시를 계속 기억하고 있다면, "이미 묶였다고 생각하고 생략"해서 잘못된 상태로 드로우가 시작될 수 있습니다. 그래서 08번부터 모든 튜토리얼이 `BeginFrame` 직후 `context.InvalidateCache()`를 호출합니다. 이것이 "외부에서 상태를 건드린 경계에서 캐시를 비운다"는 원칙의 실전 예입니다.

### 6-6. 상태별 캐시의 메모리: 캐시 배열과 비교 연산의 비용

`GraphicContext`는 버퍼/레이아웃/셰이더/래스터라이저/블렌드/깊이/텍스처 SRV/샘플러/상수 버퍼/토폴로지를 각각 캐시합니다(`GraphicContext.h`). 텍스처와 샘플러는 `[ShaderStage][슬롯]` 2차원 배열로 캐시하며, 비교는 포인터 동등성(id3d11 객체 주소) 하나로 끝납니다. 포인터 비교는 CPU 캐시 친화적이어서 수천 번의 비교도 나노초 단위입니다. 반면 드라이버 검증은 이보다 수십~수백 배 비싸므로, "포인터 비교 1회 vs 드라이버 호출 1회"의 교환은 항상 이득입니다.

## 7. 핵심 규칙 요약

- [ ] ID3D11Device = 공장(리소스 생성), ID3D11DeviceContext = 조립 라인(바인딩/그리기).
- [ ] sgf 대응: `GraphicDevice::Initialize/CreateXXX` vs `GraphicContext::SetXXX/Draw`.
- [ ] v2.1부터 `Initialize()`(창 없음)로 디바이스만 생성 가능.
- [ ] 같은 상태를 연속 설정하면 두 번째부터 D3D 호출 생략 (skippedCallCount 증가).
- [ ] 카운터 검증: `ResetStats` → 실험 → `GetApiCallCount`/`GetSkippedCallCount`.

## 9. 다음 단계로

04번에서 `GraphicDevice::Initialize(HWND, w, h)`로 **스왑체인까지 포함한** 전체 초기화를 배우고, 매 프레임 `BeginFrame → EndFrame` 루프가 완성됩니다. 이때 `BeginFrame`이 왜 캐시를 무효화하는지 이 장의 InvalidateCache 원칙이 실제로 적용됩니다. 미리 알면 좋은 것: "공장(디바이스)은 한 번, 조립 라인(컨텍스트)은 매 프레임"이라는 역할 분리는 앞으로 모든 튜토리얼의 전제 조건입니다.
