# 21. 리소스 매니저 — 키로 관리하는 리소스 도서관

> 관련 코드: `Projects/sgfr/Sources/sgfr/21_ResourceManager/` (`21_ResourceManager_Main.cpp`)
> 엔진 코드: `Projects/sgf/Sources/sgf/Graphics/ResourceMgr.h/.cpp`, `IResource.h`
> 실행: sgfr 실행 후 콘솔 메뉴에서 **21번** 선택 (창이 뜨지 않는 콘솔 전용 튜토리얼)
> 선행 학습: 20번(머티리얼 — Add/키 개념 첫 접촉), 03번(디바이스 초기화)

## 1. 이 장에서 배우는 것

모든 공유 리소스(IResource: 텍스처/머티리얼/메시/셰이더 등)를 **`_u64` 키**로 등록·검색·제거하는 리소스 매니저의 내부를 배웁니다. 소유권 이전("소유자 = 수명 결정자"), 경로 중복 로드 방지, 반납된 키의 재사용, 디폴트 리소스 7종의 보호 규칙을 콘솔 출력으로 직접 관찰합니다. 창 없이 실행되는 **헤드리스 모드**(`GraphicDevice::Initialize()` 무인자)도 처음 경험합니다.

## 2. 실행하면 보이는 것

이 튜토리얼은 창이 없습니다. 콘솔에 네 단계가 차례로 출력됩니다.

1. **디폴트 리소스**: 초기화 직후 등록 개수(7), 디폴트 텍스처 키, 디폴트 2D 머티리얼 키, 그리고 `PrintStatus()`가 디버그 출력 창(OutputDebugString)으로 보관 목록 전체를 내보냅니다.
2. **등록/검색/제거**: 빨강/초록 2×2 텍스처를 Add한 키, `Find<Texture>` 성공, `Find<Material>` 타입 불일치 nullptr, `FindKeyByPath("memory://green")` 역조회, 같은 경로 재등록 거부(INVALID_RESOURCE_KEY = 0).
3. **키 재사용**: 빨간 텍스처 Remove 후 새 텍스처 Add가 **반납된 키를 그대로 받는지** 확인합니다.
4. **최종 상태**: `PrintStatus()`로 남은 리소스 목록을 확인하고, `Finalize()`가 전부 소멸시켰음을 알립니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 리소스 매니저 = "도서관 관리자"

게임에는 텍스처/메시/셰이더/머티리얼이 수백 개 있습니다. 각각이 자기 마음대로 만들어지고 지워진다면, 누가 책임지고 지우는지 모르는 **누수(leak)**나, 이미 지운 것을 또 쓰는 **댕글링(낡은 포인터)**이 생깁니다. 리소스 매니저는 도서관 관리자입니다:

- **대출(Add)**: 책을 맡기면 관리자가 청구번호(`_u64` 키)를 발급해 줍니다. **이 순간 책의 주인은 관리자**입니다.
- **검색(Find)**: 청구번호로 책을 찾아줍니다. 타입이 다른 걸 요구하면 "그 책은 그런 종류가 아닙니다"라고 nullptr을 돌려줍니다.
- **반납(Remove)**: 청구번호로 책을 폐기하고 번호를 반환받습니다.
- **보호(디폴트)**: 도서관 기본 비치 도서(디폴트 7종)는 반납·폐기가 금지입니다.

### 3-2. 소유권 이전 = "맡기는 순간 책임도 이전"

`g_cResourceMgr.Add(pChecker)`에 넘기는 순간, 그 포인터의 **수명 책임이 호출자에서 매니저로 넘어갑니다.** 이후 그 리소스는 매니저만 지울 수 있고(Remove), 매니저가 Finalize될 때 일괄 소멸됩니다. 반대로 `Add`가 **거부**되면 소유권은 호출자에게 그대로 남아 있어 호출자가 직접 `delete` 해야 합니다. 이 계약을 "**소유자 = 수명 결정자**"라고 부릅니다.

### 3-3. 키 재사용 = "반납된 사물함 번호"

키는 `AutoIncrementLinkedList<_u64>`라는 발급기가 1씩 늘려가며 만들지만, `Remove`로 반납된 키는 **자유 목록(freeList)**에 들어갔다가 다음 `Add`에서 재사용됩니다. 도서관 사물함 번호처럼, 반납된 13번을 다음 대출자가 다시 받는 것과 같습니다. 이 튜토리얼은 "빨간 키 = 노란 키" 출력으로 그 사실을 증명합니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 리소스(Resource) | GPU 자산: 텍스처/메시/셰이더/머티리얼 등 | 도서관의 책 |
| 키(Key) | 리소스를 가리키는 `_u64` 번호 | 청구번호 |
| 소유권 이전 | 수명 책임이 매니저로 넘어감 | 맡긴 짐의 주인 변경 |
| INVALID_RESOURCE_KEY | 유효하지 않은 키 (= 0) | 없는 청구번호 |
| 경로 인덱스 | 파일 경로 → 키 역방향 색인 | 책 제목 → 청구번호 색인 |
| 헤드리스 모드 | 창 없이 GPU 리소스만 만드는 모드 | 식당 주방만 만들고 홀은 없음 |
| 디폴트 리소스 | 매니저가 자동 준비하는 기본 7종 | 도서관 상비 도서 |
| 프리 리스트(FreeList) | 반납된 키를 보관하는 목록 | 반납 사물함 번호 목록 |
| dbg_new / delete | 디버그용 new/delete 관례 | 영수증 남기는 주문 방식 |

## 5. 코드 워크스루

`ResourceManager_Main()`의 흐름을 따라갑니다.

### 5-1. 헤드리스 디바이스와 디폴트 7종

```cpp
GraphicDevice device;
device.Initialize();                    // 창 없이! 디바이스(공장)만 생성

g_cResourceMgr.Initialize(&device);     // 이 순간 디폴트 7종 자동 등록

printf("초기화 직후 등록 개수: %llu (디폴트 7종)\n", g_cResourceMgr.GetCount());
printf("디폴트 텍스처 키: %llu\n", g_cResourceMgr.GetDefaultTextureKey());
printf("디폴트 2D 머티리얼 키: %llu\n", g_cResourceMgr.GetDefaultMaterial2DKey());
g_cResourceMgr.PrintStatus();
```

`GraphicDevice::Initialize()`의 무인자 버전은 스왑체인 없이 D3D11 디바이스/컨텍스트만 만듭니다. `ResourceMgr::Initialize`는 `CreateDefaults()`(ResourceMgr.cpp:292)를 호출해 다음 7종을 `Add`하고 `defaultKeys_`에 등록합니다:

| # | 리소스 | 디버그 이름 |
|---|---|---|
| 1 | VertexShader 2D (VertexPTC용) | DefaultVS2D |
| 2 | PixelShader 2D | DefaultPS2D |
| 3 | VertexShader 3D (VertexPNT용) | DefaultVS3D |
| 4 | PixelShader 3D | DefaultPS3D |
| 5 | 1×1 흰색 텍스처 | DefaultWhiteTexture |
| 6 | 디폴트 머티리얼 2D (알파+깊이 꺼짐) | DefaultMaterial2D |
| 7 | 디폴트 머티리얼 3D (불투명+깊이 읽기쓰기) | DefaultMaterial3D |

`PrintStatus()`는 `resources_.Size()`와 발급 중인 키 개수, 그리고 각 리소스의 `key=..., type=..., name=...`을 **디버그 출력 창**(OutputDebugStringA)으로 보냅니다.

### 5-2. 등록, 타입 안전 검색, 경로 역조회

```cpp
const _u64 redKey = g_cResourceMgr.Add(pRed);
const _u64 greenKey = g_cResourceMgr.Add(pGreen, "memory://green");  // 경로 별칭

Texture* pFound = g_cResourceMgr.Find<Texture>(redKey);    // 성공 (같은 포인터)
Material* pWrongType = g_cResourceMgr.Find<Material>(redKey); // nullptr! 타입 보호

const _u64 foundByPath = g_cResourceMgr.FindKeyByPath("memory://green");
```

- `Find<T>(key)` 템플릿은 `IResource::GetResourceType() != T::RESOURCE_TYPE`이면 nullptr을 돌려줍니다(ResourceMgr.h:72). 키는 숫자라 타입 정보가 없으므로, **타입 검증은 검색 시점**에 합니다.
- 경로 별칭 `"memory://green"`은 실제 파일이 아니라 데모용 가상 경로지만, `pathIndex_`(경로 → 키 HashMap)에 등록되어 파일 로드와 동일한 규칙(중복 방지)을 적용받습니다.

### 5-3. 중복 경로 거부와 키 재사용

```cpp
const _u64 duplicatedKey = g_cResourceMgr.Add(pDuplicated, "memory://green");
printf("중복 경로 Add = %llu (0 = INVALID_RESOURCE_KEY, 거부됨)\n", duplicatedKey);
if (duplicatedKey == INVALID_RESOURCE_KEY)
{
	delete pDuplicated;   // 거부됐으므로 소유권은 여전히 우리에게 있다
}
```

`Add(리소스, 경로)`는 `FindKeyByPath`가 이미 존재하면 아무것도 하지 않고 `INVALID_RESOURCE_KEY`(=0)를 반환합니다(ResourceMgr.cpp:109). 이때 리소스는 매니저가 받지 않았으므로 **호출자가 직접 `delete`** 해야 합니다 — 소유권 계약의 정반대 사례입니다.

```cpp
g_cResourceMgr.Remove(redKey);   // 이 순간 pRed는 소멸된다! 키는 프리 리스트로
...
const _u64 yellowKey = g_cResourceMgr.Add(pYellow);
printf("새 텍스처 키: %llu (반납한 키 %llu가 재사용되면 성공!)\n", yellowKey, redKey);
```

`Remove`는 ① 디폴트 키 검사(거부 시 `jc_assert`), ② 경로 인덱스 정리, ③ `delete` 후 `resources_`에서 제거, ④ `keyProvider_.Release(key)`로 키 반납(ResourceMgr.cpp:123). 반납된 키는 LIFO 프리 리스트에 들어가 다음 `Acquire`에서 재사용됩니다.

### 5-4. 정리

```cpp
g_cResourceMgr.Finalize();   // 남은 모든 리소스(디폴트 포함) 일괄 소멸
device.Finalize();
```

`Finalize`는 사용자 리소스 먼저(`RemoveAll`), 이어 디폴트 포함 잔여 전부 `ForEachValueDelete`, 경로/디폴트 키 컬렉션 정리, 키 발급기 `Reset` 순으로 수행합니다(ResourceMgr.cpp:66).

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. GPU 리소스의 수명과 참조 카운트

D3D11에서 GPU 리소스(`ID3D11Buffer`, `ID3D11Texture2D`, `ID3D11ShaderResourceView` 등)는 모두 `ID3D11DeviceChild`의 **COM 참조 카운트**로 관리됩니다. 리소스를 만들 때 카운트 1, 바인딩/보관마다 AddRef, 해제 시 Release로 감소하며 0이 되면 해제됩니다. GPU가 명령 큐에서 아직 사용 중인 리소스를 Release하면, 드라이버는 물리 메모리가 즉시 회수되는 것을 막기 위해 **지연 삭제**를 수행합니다 — GPU가 그 명령을 완료한 뒤 실제로 메모리를 반환합니다. 이 때문에 "CPU 쪽에서 delete했다"는 사실만으로는 GPU 메모리가 즉시 사라지지 않고, "참조가 모두 사라졌는가"가 진짜 수명입니다.

그렇다면 왜 포인터 대신 키인가? `Texture* pTex`는 **원시 포인터**일 뿐 참조 카운트를 유지하지 않습니다. `ResourceMgr`가 키로 보관하며 `IResource*`를 들고 있기 때문에 "매니저가 지우기 전까지는 유효"하다는 보증이 성립합니다. 리소스가 지워지면 `Find`는 nullptr이고, `Material::Bind`는 그 nullptr을 조용히 흡수해 assert 후 false를 돌립니다. 즉 키 방식은 **드라이버 수준의 지연 삭제**와 **애플리케이션 수준의 수명 계약** 사이의 어긋남을 코드 구조로 막는 것입니다.

### 6-2. 리소스 종류별 GPU 메모리 형태

이 매니저가 다루는 리소스가 실제 GPU에서는 어떤 것인지 정리하면:

| 리소스 | GPU 메모리 형태 | 해제 시 드라이버가 하는 일 |
|---|---|---|
| Texture | 텍셀 데이터를 담은 `ID3D11Texture2D` + 뷰(SRV) | SRV/텍스처 Release, 텍셀 메모리 반환 |
| Vertex/Index Buffer | `ID3D11Buffer` (DEFAULT/DYNAMIC) | 버퍼 메모리 반환 |
| Constant Buffer | `ID3D11Buffer` (항상 DYNAMIC) | 상수 메모리 반환 |
| Shader | 셰이더 바이트코드가 로드된 셰이더 객체 | 드라이버 셰이더 캐시와 연결 해제 |
| Material | GPU 자산 없음 (상태 desc + 키 조합) | 없음 — CPU 쪽 묶음일 뿐 |

머티리얼은 GPU 메모리를 직접 가지지 않고 상태 desc(블렌드/래스터라이저/샘플러 등은 드라이버가 내부 상태 객체로 변환해 캐싱)만 보관합니다. 그래서 머티리얼의 수명은 순수 CPU 문제이고, GPU 메모리를 가진 텍스처/버퍼/셰이더의 수명 관리가 진짜 중요한 부분입니다.

### 6-3. 키 발급기: AutoIncrementLinkedList와 CPU 캐시 친화성

`Provider<AutoIncrementLinkedList<_u64>>`의 동작은 두 가지 자료 구조의 조합입니다: ① 발급된 키를 오름차순 연결 리스트로 관리(자동 증가), ② 반납된 키를 프리 리스트에 LIFO로 보관. `Acquire()`는 프리 리스트가 비어 있지 않으면 거기서 꺼내고, 비어 있으면 최대값+1을 새로 만듭니다. LIFO로 반납 키를 재사용하는 이유는 **최근에 삭제된 리소스의 캐시 지역성**(같은 메모리 풀 슬롯을 다시 쓰면 캐시 히트 가능성 상승)과, `HashMap`의 키 분포 유지에 유리하기 때문입니다. 키가 오름차순으로 증가하는 동안 컨테이너에 삽입되는 항목들의 해시 분포가 비교적 고르게 유지됩니다. 또한 키가 작을수록 힙 내 접근 패턴이 안정적이라는 점도 있습니다.

### 6-4. 경로 인덱스와 파일 로드의 GPU 경로

`LoadTextureFromFile("...")`은 내부적으로 `FindKeyByPath`로 중복을 검사한 뒤 `Texture::LoadFromFile`(WIC 디코딩 → 픽셀 배열) → `Add(pTexture, 경로)`로 등록합니다(ResourceMgr.cpp:183). 텍스처 생성은 GPU 관점에서 ① CPU에서 WIC 디코딩(압축된 PNG → RGBA8 픽셀 배열), ② `ID3D11Texture2D` 생성(초기 데이터로 **PCIe 버스를 통해 GPU 메모리로 업로드**), ③ SRV(셰이더가 읽을 수 있는 뷰) 생성의 3단계입니다. 같은 경로를 두 번 요청하면 두 번째는 업로드 없이 기존 키만 반환하므로, 대용량 텍스처의 중복 로드(대역폭 낭비 + 메모리 낭비)가 원천 차단됩니다. 이것이 "경로 인덱스"가 존재하는 이유입니다.

## 7. 핵심 규칙 요약

- [ ] 모든 공유 리소스는 `_u64` 키로 등록/검색/제거한다. `Add`에 넘기는 순간 **소유권이 매니저로 이전**.
- [ ] **소유자 = 수명 결정자**: 매니저가 Remove/Finalize로 소멸시킨다. 호출자는 이후 포인터를 잡고 있으면 안 된다.
- [ ] `Find<T>(key)`는 타입까지 검증 — 타입이 다르면 nullptr. 포인터는 절대 손대지 않는다.
- [ ] 경로로 등록한 리소스는 `FindKeyByPath`로 역조회 가능. 같은 경로 재등록은 `INVALID_RESOURCE_KEY`(0)로 거부되고 소유권은 호출자에게 남는다(직접 delete).
- [ ] `Remove`는 리소스 소멸 + 키 반납. 반납된 키는 프리 리스트(LIFO)로 다음 `Add`에서 **재사용**된다.
- [ ] 디폴트 7종(셰이더 4 + 흰 텍스처 1 + 머티리얼 2)은 `Initialize`에서 등록되고 `Remove`가 금지된다. (`defaultKeys_`, jc_assert)
- [ ] `Finalize()` 한 번이면 모든 리소스가 일괄 소멸된다.
