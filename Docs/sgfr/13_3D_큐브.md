- **ESC**: 종료

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 원근 투영 — "멀수록 작게"

사진을 떠올려 보세요. 철로가 먼 곳으로 갈수록 한 점으로 모이는 것처럼, 우리 눈은 가까운 물체는 크게, 먼 물체는 작게 봅니다. 직교 투영(10~11장)은 설계도면처럼 거리와 무관하게 크기가 같지만, 원근 투영은 **카메라 거리로 나누기** 때문에 3D 세계의 깊이감이 살아납니다. `PerspectiveFovLH`의 인자(시야각, 화면비, 근평면, 원평면)가 바로 "카메라가 찍는 뷰 파인더"의 설정입니다.

### 3-2. 깊이 버퍼 — "그리는 순서"의 문제를 푸는 장치

종이 위에 그림을 그릴 때는 나중에 그린 물체가 앞에 보입니다. GPU도 기본적으로 그런데, 3D에서는 **그리는 순서와 앞뒤 관계가 일치하지 않습니다**. 큐브의 뒷면이 나중에 그려지면 앞면을 덮어버리는 사고가 생깁니다.

깊이 버퍼(Z-Buffer)는 **픽셀마다 "지금까지 그려진 것 중 가장 가까운 깊이"를 기억하는 별도의 숫자 메모리**입니다. 새 픽셀을 그릴 때:

1. 새 픽셀의 깊이를 버퍼에 있는 값과 비교
2. **더 가까우면** 그려주고 깊이를 갱신
3. **더 멀면** 그냥 버린다

이 덕분에 드로우 순서와 무관하게 항상 앞에 있는 물체가 보입니다.

### 3-3. 인덱스 36개 — 정점 재활용

정육면체는 꼭짓점이 8개뿐입니다. 6면 × (삼각형 2개 × 3) = 인덱스 36개로 8개의 정점을 재활용합니다. 07장에서 배운 인덱스 버퍼의 힘이 3D에서 꽃을 피웁니다.

### 3-4. 왜 "시계방향"이 앞면인가 — 규칙 하나로 절반을 버리기

게임 캐릭터를 생각해 보세요. 캐릭터의 뒤통수는 어차피 화면에 보이지 않는 경우가 대부분입니다. 그렇다면 **뒤쪽을 향한 삼각형은 아예 그리지 않아도** 됩니다. GPU는 "어느 방향을 향한 삼각형이 앞면인지"를 정점의 감는 순서로 판정하는데, DirectX의 기본 규칙이 **바깥에서 봤을 때 시계방향 = 앞면**입니다. 앞면만 그리면 프리미티브 수가 절반으로 줄어들고, 뒤에서 비쳐 보이는 픽셀 처리도 사라집니다. 이걸 **백페이스 컬링**이라고 합니다.

그래서 큐브의 인덱스 배열이 어지러워 보이는 순서(0,1,2 / 2,1,3 ...)를 갖는 것입니다. 각 면을 **바깥에서 바라보았을 때** 시계방향이 되도록 일부러 고른 순서입니다. 만약 순서를 반대로 뒤집으면 모든 면이 "뒷면"으로 판정되어 큐브가 통째로 사라지는, 초보자들이 가장 많이 겪는 첫 3D 버그가 나타납니다.

## 4. 초보자 용어 사전

| 시야각(FOV) | 카메라가 위아래로 보는 각도 | 사람 눈의 화각 60도 |

| 토글(Toggle) | 켜고 끄는 전환 | 스위치 |

원근 투영은 2D와 3D를 갈라놓는 유일한 새 요소였고, 나머지 3D의 모든 재료(정점, 인덱스, 셰이더, 버퍼)는 이미 익숙한 것이었음을 상기해 보세요. 깊이 버퍼와 컬링이 합쳐진 이유를 이해하는 것이 이 장의 핵심 목표입니다.

## 5. 코드 워크스루

`Cube3D_Main()`의 흐름입니다.

### 1~2단계: 정점 8개 — 무지개색 큐브

정육면체의 8개 꼭짓점을 `VertexPC`(위치+색)로 만듭니다. 각 꼭짓점이 다른 색이라 삼각형 내부에서 색이 보간됩니다.

```cpp
//        4 -------- 5
//       /|         /|
//      0 -------- 1 |      (z가 작은 쪽이 앞면: 0,1,2,3)
//      | 6 -------|-7
//      |/         |/
//      2 -------- 3
const VertexPC vertices[] = {
    { vec3(-0.5f, +0.5f, -0.5f), color(0xFF, 0x00, 0x00, 0xFF) },  // 0: 앞-왼위 (빨강)
    { vec3(+0.5f, +0.5f, -0.5f), color(0x00, 0xFF, 0x00, 0xFF) },  // 1: 앞-오른위 (초록)
    { vec3(-0.5f, -0.5f, -0.5f), color(0x00, 0x00, 0xFF, 0xFF) },  // 2: 앞-왼아래 (파랑)
    { vec3(+0.5f, -0.5f, -0.5f), color(0xFF, 0xFF, 0x00, 0xFF) },  // 3: 앞-오른아래 (노랑)
    // 4~7: 뒤쪽 4개 (+z) — 각각 마젠타/시안/흰색/회색
};
```

### 3단계: 인덱스 36개 — 바깥에서 볼 때 시계방향

```cpp
const _u32 indices[] = {
    0, 1, 2,  2, 1, 3,   // 앞면   (z-)
    5, 4, 7,  7, 4, 6,   // 뒷면   (z+)
    4, 5, 0,  0, 5, 1,   // 윗면   (y+)
    2, 3, 6,  6, 3, 7,   // 아랫면 (y-)
    4, 0, 6,  6, 0, 2,   // 왼면   (x-)
    1, 5, 3,  3, 5, 7,   // 오른면 (x+)
};
```

**인덱스 순서가 곧 면의 방향**입니다. DX11 기본 설정은 "바깥에서 봤을 때 시계방향으로 감긴 삼각형"만 앞면으로 보고, 뒷면은 백페이스 컬링으로 버립니다. 순서를 반대로 하면 큐브가 속이 비어 보이거나 면이 사라집니다.

### 4단계: 셰이더 + 상수 버퍼

`CubeShaderSource()`(Function.cpp)는 `row_major float4x4 gWorldViewProj` 하나만 받아 `mul(float4(position,1), gWorldViewProj)`로 변환하는 단순 셰이더입니다. 이전 장들과 동일 구조입니다.

13장까지 오면서 셰이더가 한 번도 바뀌지 않는 것에 주목하세요. 05장부터 쓴 "위치 + 색" 셰이더는 2D 사각형에도 3D 큐브에도 똑같이 동작합니다. 변환은 전부 CPU가 만든 행렬(상수버퍼)이 담당하므로, 셰이더가 2D용/3D용으로 나뉠 필요가 없는 것입니다. 이것이 "정점은 그대로, 행렬로 움직이는" 설계의 강점입니다. 3D로 넘어와서도 바뀐 것은 행렬의 종류(원근 투영)뿐이며, 코드도 view/proj 생성 두 줄이 추가된 것이 전부입니다. 처음 3D가 이렇게 단순한 이유를 이해하면, 나중에 셰이더가 복잡해지는 이유(조명, 텍스처)도 순서대로 따라올 수 있습니다.

### 5단계: 뷰/투영 행렬

```cpp
// 카메라를 뒤쪽(z = -2.5) 위쪽(y = 1.2)에 두고 원점을 바라본다
const mat4 view = mat4::LookAtLH(vec3(0.0f, 1.2f, -2.5f), vec3::Zero(), vec3::Up());

// 수직 시야각 60도, 화면 비율, 근평면 0.1, 원평면 100
const mat4 proj = mat4::PerspectiveFovLH(jc_math_deg2rad(60.0f), window.AspectRatio(), 0.1f, 100.0f);
```

LH 좌표계에서는 +z가 화면 안쪽이므로 카메라는 **-z 쪽에 배치**합니다. `LookAtLH(위치, 목표, 위방향)`이 한 번에 뷰 행렬을 만들어 줍니다. 인자 하나하나를 보면: 위치는 `vec3(0, 1.2, -2.5)` — 원점에서 약간 위(y=1.2)에 앉아 뒤쪽(z=-2.5)에서 정면을 보는 자세이고, 목표는 `vec3::Zero()`(원점), 위 방향은 `vec3::Up()`(+y)입니다. 이 함수가 내부적으로 하는 일은 11장에서 배운 것과 정확히 같습니다 — "카메라 위치의 역변환 + 카메라 좌표축으로 세상을 다시 세우기"입니다.

LH(Left-Handed) 좌표계를 기억하는 간단한 방법이 있습니다. 오른손을 꼽아 보세요. 엄지=+x, 검지=+y, 중지=+z라고 할 때 오른손 규칙은 중지(앞)가 화면 **밖**을 향합니다. DirectX의 LH는 그 반대로 +z가 화면 **안쪽**을 향합니다. 그래서 카메라가 (-2.5) 지점에 있는 것이 "뒤에서 쳐다보는" 배치가 되는 것입니다. 나중에 다른 그래픽스 API를 만나도 "어느 쪽이 앞인가"만 확인하면 혼동을 피할 수 있습니다.

### 6단계: 렌더 루프

```cpp
// 스페이스바: 깊이 테스트 토글 (문제 상황을 직접 눈으로 확인하는 실험!)
if (input.IsKeyPressed(VK_SPACE))
{
    bDepthTest = !bDepthTest;
    device.SetDepthTest(bDepthTest);
    jc::Console::Write("깊이 테스트: %s\n", bDepthTest ? "ON (정상)" : "OFF (뒷면이 덮일 수 있음)");
}

// 큐브를 두 축으로 천천히 회전 (회전 행렬 두 개를 결합)
const mat4 world = mat4::RotationY(elapsed * 0.8f) * mat4::RotationX(elapsed * 0.5f);

CbTransform cb = {};
cb.worldViewProj_ = world * view * proj;
cbTransform.UpdateAndBind(&device, cb, 0);

vb.Bind(&device); ib.Bind(&device); shader.Bind(&device);
device.Context()->IASetPrimitiveTopology(D3D11_PRIMITIVE_TOPOLOGY_TRIANGLELIST);
device.Context()->DrawIndexed(36, 0, 0);
```

`device.SetDepthTest(bool)`은 내부적으로 깊이/스텐실 상태를 갈아끼웁니다. `DrawIndexed(36, 0, 0)`으로 인덱스 36개(삼각형 12개)를 한 번에 그립니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. 원근 투영의 w 분할 — 하드웨어에서 일어나는 "거리로 나누기"

`PerspectiveFovLH`가 만드는 행렬은 정점을 변환하면서 **z 좌표를 w 성분에 복사**합니다. 셰이더는 `mul`로 클립 공간 좌표 (x, y, z, w)를 만들고, 이후 GPU의 **고정기능 단계인 원근 분할(Perspective Divide)**이 각 성분을 w로 나눕니다: `(x/w, y/w, z/w)`. 예를 들어 z가 10인 정점은 화면에서 10분의 1 크기로, z가 100인 정점은 100분의 1 크기로 그려집니다. 이것이 "멀수록 작게"의 하드웨어 정체입니다.

또한 w 분할 후의 z/w는 **0~1 사이의 비선형 깊이 값**이 되는데, GPU는 이 값을 **수정된 비교 순서**로 씁니다. 드라이버는 근평면이 0.1로 매우 가까우면 원거리 정밀도가 떨어지는 문제(z-fighting)가 생기므로, 근/원평면을 가능한 한 좁게 잡아 깊이 정밀도를 확보하는 것이 실전 팁입니다.

### 6-2. 깊이 버퍼: D24S8 포맷과 비교기 하드웨어

`device.SetDepthTest(true)`가 묶는 깊이 버퍼는 `DepthStencilSurface`가 만든 **D24S8**(깊이 24비트 + 스텐실 8비트) 텍스처입니다. 픽셀 하나에 4바이트가 할당되므로, 800×600 화면은 약 1.9MB, 1920×1080은 약 8.3MB의 깊이 전용 메모리가 사용됩니다.

프레임마다:

1. `ClearDepthStencilView` — 깊이 버퍼를 최대값(1.0)으로 비움
2. 픽셀 셰이더가 픽셀을 만들면 **깊이 테스트 유닛(ROP의 비교기)**이 이 픽셀의 z/w와 기존 깊이값을 `D3D11_COMPARISON_LESS_EQUAL`로 비교 (sgf의 DepthStencilState 기본값)
3. 통과 시 컬러 프레임버퍼와 깊이 버퍼를 **동시에** 씀

여기서 중요한 하드웨어 최적화는 **Early-Z(Hierarchical-Z)**입니다. 대부분의 GPU는 픽셀 셰이더 실행 **전에** 깊이 비교를 수행해 실패할 픽셀은 셰이더를 아예 실행하지 않습니다(성능 절감). 다만 셰이더가 깊이를 임의로 수정하거나 알파 블렌드 같은 조작을 하면 Early-Z가 꺼질 수 있습니다. 이 튜토리얼처럼 "그릴 픽셀은 처음부터 하나"인 경우 깊이 테스트가 꺼지면 **드로우 순서 그대로 덮어쓰기**가 되어, 나중에 그려진 뒷면이 앞면을 덮는 현상이 바로 보입니다.

스페이스바로 끄는 순간의 변화도 설명이 됩니다. 깊이 테스트가 꺼진 상태에서 GPU는 깊이 비교와 쓰기를 건너뛰고 **무조건 컬러만 덮어씁니다**. 큐브가 한 프레임 안에 "앞면 → 윗면 → 옆면..." 순서로 그려지므로, 나중에 그려진 면이 항상 위에 보입니다. 큐브가 회전 중이라 매 프레임 다른 면이 마지막에 그려져, 화면이 마치 "면들이 서로 뒤집혀 덮는" 것처럼 보이는 것입니다. 이 체험이 깊이 버퍼의 존재 이유를 가장 확실하게 가르쳐 줍니다.

### 6-3. 백페이스 컬링 — 래스터라이저의 감는 방향 판정

GPU 래스터라이저는 삼각형의 화면상 감는 방향(시계/반시계)을 계산해 `D3D11_CULL_BACK`이면 뒤집힌 삼각형을 **픽셀 생성 전에** 버립니다. 이 판정은 고정기능 배선이라 프리미티브당 비용이 거의 없고, 보통 **그려야 할 프리미티브의 절반을 제거**합니다(폐쇄된 물체 기준). 큐브의 인덱스를 시계방향으로 맞춘 이유가 이것이며, 실수로 순서를 뒤집으면 모든 면이 "뒷면"으로 판정되어 큐브가 사라져 보입니다.

### 6-4. 정점 8개를 36개로 펼치는 IA 단계

`DrawIndexed(36, 0, 0)`은 **입력 조립기(Input Assembler)**가 인덱스 버퍼를 읽어 정점 번호를 해석하고, 같은 정점을 여러 번 꺼내 삼각형 3개짜리 그룹으로 묶는 과정입니다. GPU는 IA에서 정점 캐시를 운영해, 인덱스로 재방문되는 정점(정육면체에서 한 정점은 평균 4.5개 삼각형이 공유)을 메모리에서 다시 읽지 않고 **정점 캐시(보통 수십 개)**에서 재사용합니다. 그래서 8정점 큐브는 실제 메모리 대역폭이 인덱스 36개 + 정점 8개분만 소비합니다. 이것이 "정점 버퍼 8개, 인덱스 36개" 설계의 하드웨어적 이득입니다.

### 6-5. 회전 결합과 변환의 스레드 병렬화

`RotationY * RotationX`로 만든 월드 행렬은 VS에서 정점마다 16 FMA로 적용됩니다. 8개 정점은 최소 8개 셰이더 스레드로 병렬 실행되며, 실제 게임의 큐브는 수만 정점이 수천 스레드로 병렬 변환됩니다. GPU의 SM(셰이더 멀티프로세서)이 32개 스레드(워프) 단위로 명령을 발행하므로, 정점 처리량이 늘어도 성능이 거의 일정하게 유지됩니다.

### 6-6. 깊이 테스트 토글의 비용 — 파이프라인 플러시

스페이스바를 누를 때마다 `device.SetDepthTest()`가 깊이 스텐실 상태를 바꿉니다. 상태 객체 교체는 드라이버가 내부 파이프라인 구성을 갱신해야 하는 작업이라, 매 프레임 반복하면 GPU가 명령을 처리하는 데 지연이 생깁니다. 실전 게임에서는 "물체 종류에 따라 상태를 미리 정렬해 한 번씩만 바꾸는" 상태 정렬(state sorting) 기법을 씁니다. 이 튜토리얼처럼 토글로 반복 변경하는 것은 학습 목적이며, 실제 프로젝트에서 상태 변경을 줄이는 것이 성능에 좋다는 것을 기억해 두세요.

### 6-7. 깊이 정밀도와 z-fighting — 근평면이 멀어야 하는 이유

원근 투영 후 깊이 값(z/w)은 **가까운 곳에 정밀도가 집중**되는 비선형 분포를 갖습니다. D24S8 포맷은 24비트(약 1600만 단계)로 깊이를 저장하는데, 멀리 있는 물체는 몇 미터 차이도 같은 값으로 반올림되어 두 면이 **번쩍거리며 겹치는 현상(z-fighting)**이 생깁니다. 근평면이 0.1처럼 아주 가까우면 정밀도가 더 희생되므로, 실전에서는 근평면을 최대한 멀리(예: 1.0) 잡아 깊이 정밀도를 확보합니다. 이 튜토리얼의 근평면 0.1, 원평면 100은 학습용 값이고, "깊이 버퍼의 비트 수가 곧 앞뒤 판정의 정밀도"라는 사실을 알고 있으면 이후 큰 씬에서 이상한 렌더링을 만났을 때 원인을 찾기 쉽습니다.

### 6-8. 한 걸음 더 — Early-Z, Hi-Z, Reversed-Z

- **계층적 Z(Hi-Z)**: 깊이 버퍼를 타일 단위로 요약(최소/최대 깊이)해 두고, '이 삼각형은 타일 전체보다 뒤'라면 **픽셀 하나 안 보고 타일째 폐기**합니다.
- **Reversed-Z**: 깊이 정밀도 문제(6-7)의 현대적 해법. 니어=1/파=0으로 뒤집고 float 깊이 버퍼를 쓰면, 0 근처 정밀도가 높은 float 특성 덕에 원거리 Z-파이팅이 극적으로 줄어듭니다.
- **깊이 버퍼 압축**: 깊이는 대역폭을 많이 소모해 GPU가 무손실 압축(평면 방정식 저장 등)을 적용합니다. 27번처럼 깊이를 텍스처로 읽으려면 압축 해제 비용이 조금 듭니다.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| 큐브 구성 | 정점 8개 + 인덱스 36개 (6면 × 삼각형 2 × 3) |
| 인덱스 순서 | 바깥에서 볼 때 **시계방향**이 앞면 (백페이스 컬링) |
| LH 좌표계 | +z = 화면 안쪽, 카메라는 -z에 배치 |
| 뷰 행렬 | `LookAtLH(cameraPos, target, up)` |
| 투영 행렬 | `PerspectiveFovLH(deg2rad(60), aspect, 0.1, 100)` |
| 깊이 버퍼 | 픽셀별 최근접 깊이 기억 → 순서 무관 앞뒤 판정 |
| 깊이 토글 | `device.SetDepthTest(bool)` |
| WVP 결합 | `world * view * proj` (왼쪽부터 적용) |
| DrawIndexed | 인덱스 36개 = 삼각형 12개 |
| 감는 방향 | 시계방향 = 앞면 (DX 기본), 반대로 쓰면 큐브가 사라짐 |
| 백페이스 컬링 | 보이지 않는 뒷면 프리미티브를 미리 버리는 최적화 |
| 깊이 정밀도 | 근평면이 가까울수록 원거리 정밀도 감소 → 실전에선 근평면을 멀리 |

표의 마지막 줄(근평면)은 초보자가 놓치기 쉬운 함정입니다. 근평면을 아주 작게(예: 0.01) 하면 깊이 정밀도가 급격히 나빠져 z-fighting이 생길 수 있습니다. 이 함정을 기억해 두면, 나중에 27장(그림자 매핑)에서 깊이 정밀도 문제를 만났을 때 "13장에서 본 그 함정"으로 쉽게 연결됩니다. 큐브 하나로 깊이 버퍼의 존재 이유, 컬링의 효율, 정점 확장의 구조까지 모두 경험했다는 점이 이 장의 결론입니다. 다음 장부터는 면의 밝기를 계산하는 법선이 추가됩니다. 큐브 정점이 8개에서 24개로 늘어나는 이유가 바로 그때 설명됩니다.
