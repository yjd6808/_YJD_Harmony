# 12. 셰이더 스테이지와 상수버퍼 — b0/b1 슬롯 규약과 16바이트 정렬

> 관련 코드: `Projects/sgfr/Sources/sgfr/Tutorial/12_ShaderStagesAndConstants/12_ShaderStagesAndConstants_Main.cpp`
> (엔진: `Projects/sgf/Sources/sgf/Graphics/Buffers.h` — ConstantBuffer, `GraphicContext.h` — SetConstantBuffer)
> 실행: sgfr 실행 후 콘솔 메뉴에서 **12번** 선택
> 선행 학습: 06(HLSL), 10(상수 버퍼 첫 사용), 11(카메라)

## 1. 이 장에서 배우는 것

상수버퍼가 **셰이더 스테이지별로 따로 바인딩**된다는 사실, v3 엔진의 슬롯 규약(b0 = 프레임 공통 / b1 = 오브젝트별), 그리고 C++ 구조체와 HLSL cbuffer의 메모리 배치를 맞추는 **16바이트 정렬** 규칙을 실습합니다.

## 2. 실행하면 보이는 것

800×600 창에 사각형 두 개가 서로 다른 주기로 "춤을 춥니다":

- **왼쪽 파란 사각형**: 작은 진폭(0.08)으로 천천히 상하로 흔들림
- **오른쪽 주황 사각형**: 큰 진폭(0.2)으로 활발하게 상하로 흔들림
- 두 사각형 모두 왼쪽으로 살짝 치우쳐 떠 있는 형태로, 사인파에 실려 위아래로 요동

둘은 **같은 메시(quad)와 같은 셰이더**를 쓰지만, 오브젝트별 상수버퍼(b1)의 값이 다르기 때문에 다르게 움직입니다. 콘솔에는 "b0(프레임)/b1(오브젝트) 슬롯 규약을 눈으로 확인하세요!" 안내가 출력됩니다. ESC로 종료.

**스스로 실험해 보기**: `left.wobble_`을 0.5로 바꾸거나 `right.tint_`의 색을 바꿔 보세요. 또는 `context.SetConstantBuffer(ShaderStage::ssPixel, 1, ...)` 줄을 잠시 지워 보면 PS가 옛값을 읽어 색이 꼬이는 것을 확인할 수 있습니다. 코드 한 줄로 "어느 스테이지가 이 데이터를 보느냐"가 바뀌는 것이 이 장의 주제입니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 상수버퍼는 "회사 공지 게시판"

픽셀 셰이더와 버텍스 셰이더는 같은 건물의 다른 층에 있는 두 사무실입니다. 사장님(CPU)은 공지를 두 개의 게시판(스테이지별 상수 슬롯)에 **각각 게시해야** 합니다. 한 층에만 게시하면 다른 층은 옛날 공지(또는 빈 게시판)를 보고 일합니다. 그래서 `b1`을 바꿨는데 VS만 바인딩하고 PS는 안 하면, PS는 **이전 오브젝트의 색**을 그대로 읽는 버그가 생깁니다.

### 3-2. b0/b1 — "매 프레임 바뀌는 것"과 "물체마다 다른 것"

- **b0 = 프레임 공통**: 시간, 카메라 위치처럼 한 프레임에 모든 물체가 같은 값. 프레임당 **1번만** 갱신하면 됩니다.
- **b1 = 오브젝트별**: 위치, 색, 크기처럼 물체마다 다른 값. 물체마다 갱신해야 합니다.

갱신 주기가 다른 데이터를 섞어 놓으면, 물체 하나를 그릴 때마다 프레임 공통 데이터까지 통째로 다시 업로드해야 합니다. 분리해 두면 **업데이트 횟수와 업로드 바이트가 최소화**됩니다. 이것이 v3 엔진 전체가 따르는 규약입니다.

### 3-3. 16바이트 정렬 — 박스에 물건 담기

상수버퍼는 HLSL 규칙상 **4개 float(16바이트) 단위로 쪼개져** 저장됩니다. 마치 택배 상자가 16L짜리 칸으로 나뉘어 있고, 물건을 한 칸을 넘겨 담을 수 없는 것과 같습니다. `float` 하나만 담으면 남는 12L는 비어 있고, `vec2 + float`를 담아도 4L가 비고, **color(float4)는 딱 한 칸**에 들어갑니다. C++ 쪽에서 16바이트 배수가 되도록 여백(padding)을 넣지 않으면, HLSL 쪽과 메모리 배치가 어긋나 셰이더가 엉뚱한 값을 읽습니다.

### 3-4. 왜 "한 번에" 모두 바인딩해야 하는가

게임 코드를 짜다 보면 "상수버퍼를 VS에만 바인딩하면 되지 않나?" 하고 생각하기 쉽습니다. 하지만 셰이더는 스테이지마다 별개의 슬롯 상태를 갖기 때문에, **어느 스테이지가 그 데이터를 읽는지에 따라 둘 다 걸어야** 합니다. 이 튜토리얼의 셰이더는 VS가 `gOffset`/`gWobble`을, PS가 `gTint`를 읽습니다. 따라서 b1 하나를 **VS 슬롯 1과 PS 슬롯 1 양쪽에** 걸어야 두 스테이지가 같은 데이터를 봅니다. 한쪽만 걸면 그 스테이지는 옛날 값을 읽습니다.

이것은 엔진 설계에도 영향을 줍니다. 그래서 `ConstantBuffer<T>::UpdateAndBind`(10장)가 내부적으로 `VSSetConstantBuffers`와 `PSSetConstantBuffers`를 **둘 다** 호출하며, 이 장의 v3 방식(`SetConstantBuffer(ShaderStage, ...)`)은 어느 스테이지에 걸지 개발자가 명시적으로 결정하게 합니다. "왜 두 번 걸지?"라는 의문이 이 장에서 풀립니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 셰이더 스테이지 | 파이프라인의 셰이더 단계 (VS = 정점 담당, PS = 픽셀 담당) | 공장의 다른 층 사무실 |
| 상수버퍼(CB) | CPU가 셰이더에 보내는 전역 상수 묶음 | 사장님 공지 게시판 |
| 슬롯(Slot) | 스테이지별 상수버퍼 자리 번호 (b0, b1, b2…) | 게시판 위치 번호 |
| register(bN) | HLSL에서 상수버퍼가 쓸 슬롯을 지정하는 문법 | "b1 게시판에 게시" |
| 바인딩(Binding) | 자원을 특정 스테이지/슬롯에 장착하는 작업 | 게시판에 공지 붙이기 |
| 16바이트 정렬 | 상수버퍼 데이터가 16바이트 단위로 배치되는 규칙 | 16L 택배 칸 |
| 패딩(Padding) | 정렬을 맞추려고 넣는 빈 여분 멤버 | 박스의 스티로폼 |
| 캐시 무효화 | 이전에 기억한 상태가 틀렸다고 표시하기 | "오늘부로 공지 갱신" |
| 프레임 공통 vs 오브젝트 공통 | 매 프레임 변하는 값(b0)과 물체마다 다른 값(b1) 구분 | 전체 공지 vs 층별 공지 |
| 세터(Setter) 계열 호출 | 상태·자원을 장착하는 VSSet/PSSet 함수들 | 공지 붙이는 관리인 |
| GPU 디버그 계층 | 개발 중 오류를 상세히 알려주는 D3D11 계층 | 건물 시공 시 안전 점검반 |
| STAGE_DEMO_SHADER_SOURCE | 이 장의 셰이더를 담은 문자열 상수 | 공사 설계도 한 장 |
| 클리핑(Clip) | 화면 밖에 걸친 도형을 잘라내는 단계 | 사진의 여백 자르기 |

표의 "프레임 공통 vs 오브젝트 공통" 구분이 12장의 핵심 설계입니다. b0는 프레임당 한 번만 갱신하고 b1은 물체마다 갱신하므로, 이후 장들이 오브젝트 수가 늘어날 때 "어느 버퍼를 다시 보낼지" 판단하는 기준이 됩니다.

## 5. 코드 워크스루

`ShaderStagesAndConstants_Main()`의 흐름입니다.

### 1단계: C++ 상수버퍼 구조체 (16바이트 정렬)

```cpp
struct CbFrame    // b0: 프레임에 한 번만 갱신
{
    _f32 time_;          // 누적 시간(초)
    _f32 padding_[3];    // 16바이트 정렬용 여백
};

struct CbObject   // b1: 오브젝트마다 다른 데이터
{
    vec2 offset_;        // NDC 이동량 (VS용)
    _f32 wobble_;        // 춤 진폭 배율 (VS용)
    _f32 padding_;       // 16바이트 정렬용 여백
    vec4 tint_;          // 곱해질 색 (PS용) — HLSL float4와 배치 일치를 위해 vec4 사용
};
```

- `CbFrame`: float 1개 + 여백 3개 = 16바이트 ✓
- `CbObject`: vec2(8) + float(4) + padding(4) + vec4(16) = 32바이트 ✓

상수 버퍼 멤버는 HLSL `float4`와 1:1 대응해야 하므로 색도 `color`(정수 4바이트)가 아니라 **`vec4`**로 선언합니다.

`ConstantBuffer<T>::Create`에는 `static_assert(sizeof(T) % 16 == 0)`이 있어 컴파일 시점에 16바이트 배수를 강제합니다.

### 2단계: 셰이더 소스 — 같은 b1을 VS와 PS가 각자 읽기

```hlsl
cbuffer CbFrame : register(b0)
{
    float gTime;
    float3 gPadding0;
};

cbuffer CbObject : register(b1)
{
    float2 gOffset;
    float  gWobble;
    float  gPadding1;
    float4 gTint;
};

VsOut VSMain(VsIn _in)
{
    float2 wobbled = _in.position.xy + gOffset;
    wobbled.y += sin(gTime * 3.0f + _in.position.x * 4.0f) * gWobble; // b0의 시간으로 춤추기
    ...
}

float4 PSMain(VsOut _in) : SV_Target
{
    return _in.color * gTint;   // 같은 b1을 PS 스테이지에서도 읽는다
}
```

VS는 `gOffset`/`gWobble`(b1)로 이동·진동을, PS는 `gTint`(b1)로 색을 곱합니다. **하나의 상수버퍼를 두 스테이지가 다른 필드만 골라 읽는** 구조입니다. `gTime * 3.0f + position.x * 4.0f`로 사인파 위상에 정점 위치를 섞어 물결처럼 흔들리게 합니다.

이 한 줄이 하는 일을 풀어 보면: 정점의 x 좌표에 따라 위상이 달라지므로(왼쪽 정점은 다른 순간에 흔들림), 사각형이 통째로 오르내리는 것이 아니라 **물결이 좌우로 퍼져 나가는 것처럼** 보입니다. 여기에 왼쪽 사각형은 `wobble_ = 0.08`(작은 진폭), 오른쪽 사각형은 `wobble_ = 0.2`(큰 진폭)를 주었으니, 같은 셰이더를 써도 서로 다른 역동감이 연출됩니다. 오브젝트마다 다른 상수값 하나가 시각적으로 완전히 다른 결과를 만드는 것을 보여 주는 장면입니다.

### 3단계: VS/PS 컴파일 + 메시 + 상수버퍼 2개

```cpp
VertexShader vs; PixelShader ps;
vs.InitializeFromSource(&device, STAGE_DEMO_SHADER_SOURCE);
ps.InitializeFromSource(&device, STAGE_DEMO_SHADER_SOURCE);

Mesh quad;  // VertexPTC 4정점 + 인덱스 6개 (인덱스 포함 Initialize)
ConstantBuffer<CbFrame> frameCb;
ConstantBuffer<CbObject> objectCb;
frameCb.Create(&device); objectCb.Create(&device);
```

여기서 흥미로운 점은 **하나의 셰이더 소스로 VS와 PS를 각각 컴파일**한다는 것입니다. HLSL의 `VSMain`/`PSMain` 진입점이 같은 파일에 있고, `InitializeFromSource`가 내부적으로 셰이더 모델 5 단계의 VS/PS를 각각 컴파일합니다. 진입점 이름만 다르게 컴파일할 수 있다는 사실도 HLSL의 특징입니다. 컴파일이 실패하면(문법 오류 등) `InitializeFromSource`가 false를 반환하므로, 튜토리얼은 "셰이더 컴파일 실패!"를 출력하고 종료합니다. 셰이더 코드를 직접 고쳐 실험하다가 오류가 나면, 이 오류 처리 덕분에 크래시 없이 어디서 잘못됐는지 알 수 있습니다.

### 4단계: 렌더 루프 — b0는 프레임당 1번, b1은 오브젝트마다

```cpp
device.BeginFrame(color(0x0F, 0x0F, 0x1A, 0xFF));	// 어두운 남색 (0.06, 0.06, 0.1)
context.InvalidateCache();   // BeginFrame이 원시 D3D 상태를 건드렸으므로

context.SetVertexShader(&vs);
context.SetPixelShader(&ps);

// (1) b0: 프레임에 딱 한 번만 갱신 + VS 스테이지에 바인딩
CbFrame frame = {};
frame.time_ = elapsed;
frameCb.Update(&device, frame);
context.SetConstantBuffer(ShaderStage::ssVertex, 0, frameCb.Raw());

quad.Bind(context);

// (2) b1: 오브젝트마다 갱신. VS와 PS '두 스테이지 모두'에 바인딩해야 한다!
CbObject left = {};
left.offset_ = vec2(-0.4f, 0.0f);
left.wobble_ = 0.08f;
left.tint_ = vec4(0.3f, 0.8f, 1.0f, 1.0f);		// 파랑 (cbuffer는 vec4)
objectCb.Update(&device, left);
context.SetConstantBuffer(ShaderStage::ssVertex, 1, objectCb.Raw());
context.SetConstantBuffer(ShaderStage::ssPixel, 1, objectCb.Raw());
quad.Draw(context);

CbObject right = {};   // 같은 버퍼에 새 값, 왼쪽과 다른 파라미터
right.offset_ = vec2(0.4f, 0.0f);
right.wobble_ = 0.2f;
right.tint_ = vec4(1.0f, 0.6f, 0.2f, 1.0f);		// 주황 (cbuffer는 vec4)
objectCb.Update(&device, right);
context.SetConstantBuffer(ShaderStage::ssVertex, 1, objectCb.Raw());
context.SetConstantBuffer(ShaderStage::ssPixel, 1, objectCb.Raw());
quad.Draw(context);

device.EndFrame(true);
```

**실험 제안**: `SetConstantBuffer(ShaderStage::ssPixel, 1, ...)` 한 줄을 지워 보면, PS가 이전 오브젝트의 tint(또는 0)를 읽어 두 사각형 색이 꼬이는 것을 직접 볼 수 있습니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. D3D11의 스테이지별 상수 슬롯 — 하드웨어 레지스터 뱅크

D3D11의 상수버퍼는 `ID3D11DeviceContext`의 **스테이지별 슬롯**에 묶입니다. `VSSetConstantBuffers(startSlot, count, ...)`는 VS 스테이지의 슬롯 레지스터를, `PSSetConstantBuffers`는 PS 스테이지의 슬롯 레지스터를 가리킵니다. GPU 아키텍처에서 이 슬롯들은 셰이더 유닛마다 존재하는 **상수 레지스터 파일(Constant Register File)**의 경계 설정으로 구현되며, 각 슬롯이 가리키는 버퍼는 GPU 캐시 계층(L1 상수 캐시 → L2)을 통해 읽힙니다.

중요한 하드웨어 사실: **VS 슬롯에 묶인 버퍼와 PS 슬롯에 묶인 버퍼는 서로 다른 상태**입니다. 같은 버퍼를 양쪽에 묶어야 비로소 같은 데이터를 두 스테이지가 볼 수 있습니다. 한쪽만 묶으면 그 스테이지의 상수 레지스터는 **직전에 바인딩된 값(또는 초기화되지 않은 상태)**을 유지합니다. 이 튜토리얼의 "한쪽만 바인딩하면 다른 쪽은 이전 값을 읽는다"는 주석이 바로 이 하드웨어 동작을 가리킵니다.

이를 기억하는 쉬운 비유는 회사 내부 게시판입니다. 1층(VS) 게시판과 2층(PS) 게시판은 **같은 프린터(CPU)로 출력해도 각각 따로 붙여야** 합니다. 한 층에만 붙이면 그 층 직원들은 아무것도 모르는 채 지난 공지를 보고 일합니다. "바인딩 = 게시판에 공지 붙이기"라는 이미지가 습관이 되면, 이후 버그의 절반은 이 지점에서 해결할 수 있습니다.

### 6-2. 16바이트 정렬의 하드웨어 이유 — 상수 버스 폭

상수 버퍼의 16바이트 정렬 규칙은 단순한 관례가 아니라 **하드웨어 상수 버스(Constant Bus)의 폭**에서 비롯됩니다. GPU의 상수 경로는 4개 float(16B)를 한 번에 싣는 배선으로 설계되어 있으며, 셰이더 명령의 오퍼랜드 필드도 상수 주소를 16바이트 정렬 인덱스로 인코딩합니다. 즉, "cbuffer의 두 번째 16바이트 칸" 같은 표현만 가능하고 "7바이트부터 시작" 같은 비정렬 접근은 존재하지 않습니다. 그래서 `float3 gPadding0`이나 `float gPadding1`처럼 겉보기에 낭비처럼 보이는 여백이, 실제로는 **셰이더가 레지스터를 정확히 한 번에 읽게 만드는 필수 구조**인 것입니다.

`CbObject`에서 `vec2 offset_(8B) + wobble_(4B) + padding_(4B)`가 16바이트로 딱 맞고 `vec4 tint_`가 그다음 칸에 들어갑니다. 만약 padding 없이 두면 컴파일러는 `tint_`를 다음 16B 칸에 배치하거나 HLSL과 배치가 어긋나며, 셰이더의 `gTint`는 `offset_` 일부를 읽는 꼴이 됩니다.

### 6-3. Update와 Map — CPU→GPU 업로드 경로

`ConstantBuffer<T>::Update`는 `Map(..., D3D11_MAP_WRITE_DISCARD, ...)` → `memcpy` → `Unmap`을 수행합니다. 이 버퍼는 `D3D11_USAGE_DYNAMIC`로 생성되어 **CPU 쓰기 접근이 가능한 GPU 버퍼**입니다. `DISCARD`는 GPU가 이전 데이터를 아직 쓰는 중이어도, 드라이버가 **별도 메모리 조각(ring buffer의 다음 항목)**을 넘겨주어 CPU가 절대 블로킹되지 않게 합니다. 그다음 드라이버는 상수 값 자체를 GPU 명령 스트림에 기록해 GPU가 셰이더 실행 직전 상수 레지스터에 로드합니다.

이 튜토리얼이 "프레임당 Update 횟수를 최소화"하는 이유도 하드웨어적: 업로드가 적을수록 PCIe/메모리 대역폭 소모가 적고, 드라이버가 큐잉해야 할 Map 작업이 줄어 CPU와 GPU의 파이프라인이 덜 밀리기 때문입니다. b0(프레임)는 1번, b1(오브젝트)은 2번 — 총 3번의 Update가 이 프레임의 전부입니다.

### 6-4. InvalidateCache가 필요한 하드웨어 이유

`BeginFrame`은 `OMSetRenderTargets`, `ClearRenderTargetView` 같은 **원시 D3D 호출을 내부적으로 수행**하지만, v3의 `GraphicContext`는 그 내부를 모릅니다. 컨텍스트가 "방금 바인딩한 상태"를 캐시에 저장해 두고 있었다면, BeginFrame이 지워 버린 상태와 캐시가 어긋납니다. 예컨대 캐시가 "PS 상수 슬롯1 = old buffer"로 기억하는데 실제 D3D 슬롯은 비어 있다면, 그다음 `SetConstantBuffer` 호출을 **생략해 버리는** 사고가 납니다. `InvalidateCache()`는 캐시를 전부 무효화해 다음 바인딩을 강제함으로써 이 모순을 막습니다.

### 6-5. 슬롯 번호는 곧 GPU 상수 주소의 "베이스 레지스터"

D3D11에서 `SetConstantBuffer(ShaderStage::ssPixel, 1, ...)`이 의미하는 것은 "PS 스테이지의 상수 슬롯 1을 이 버퍼로 교체"입니다. 하드웨어 수준에서 보면, 각 슬롯은 셰이더 유닛의 상수 레지스터 파일 안에서 **시작 주소(베이스 주소)를 가리키는 포인터**입니다. 셰이더가 `gTint`를 읽을 때 컴파일러는 이 베이스 주소에 오프셋을 더해 "슬롯1 + 16바이트 칸" 주소를 상수 캐시에서 읽습니다. 슬롯 번호가 다르면 베이스 주소가 다르므로, 같은 버퍼를 슬롯 0과 슬롯 1에 걸어도 셰이더는 아무 상관없이 그 자리의 내용을 읽습니다.

여기서 중요한 실전 팁이 나옵니다. 상수 레지스터 파일은 크기가 한정되어 있고(하드웨어마다 다르지만 슬롯당 몇 백 바이트 단위), 슬롯을 많이 쓰거나 버퍼가 크면 상수 메모리가 부족해질 수 있습니다. 그래서 v3 엔진이 **b0/b1/b2와 같은 최소 슬롯 규약**을 강제하는 것은, 상수 메모리의 압박을 줄이고 드라이버의 상태 관리도 단순하게 하려는 의도입니다. 슬롯을 임의로 늘리면 곧 상수 메모리 압박과 캐시 미스 증가로 이어집니다.

### 6-6. 업데이트 횟수 최소화가 성능이 되는 이유 — 파이프라인 밀림

프레임당 상수 업데이트 횟수는 CPU-GPU 파이프라인에서 생각보다 중요합니다. `Map`은 CPU가 GPU 버퍼 메모리에 쓰는 것이므로, Map 횟수가 많아질수록:

1. 드라이버가 동기화/메모리 재할당을 관리할 일이 늘고,
2. GPU가 상수 레지스터를 갱신받느라 커맨드 스트림 처리가 밀리고,
3. 상수 캐시 무효화가 잦아져 셰이더가 상수 읽기를 재개해야 합니다.

이 장의 b0/b1 분리는 "프레임당 1번 업데이트되는 데이터"와 "물체마다 업데이트되는 데이터"를 분리해, 같은 오브젝트를 1000개 그려도 **프레임 공통 데이터는 딱 1번**만 업로드하게 만듭니다. 22장의 Renderer3D는 이 규약의 완성형으로, b0(카메라 등)는 장면당 1번, b1(오브젝트)은 물체마다, b2(재질)는 재질마다 업데이트하는 3-슬롯 구조를 갖습니다. 이 장이 그 기초입니다.

### 6-7. 한 걸음 더 — 버퍼 리네이밍과 스칼라 경로

- **버퍼 리네이밍**: `WRITE_DISCARD`로 Map하면 드라이버는 GPU가 아직 읽고 있는 이전 메모리를 그대로 두고 **새 물리 메모리를 몰래 발급**합니다. CPU는 GPU를 기다리지 않고 새 종이에 쓰며, 옛 종이는 GPU가 다 읽은 뒤 회수됩니다.
- **상수버퍼가 싼 이유(스칼라 경로)**: 워프 안 스레드들이 모두 같은 상수 값을 읽으므로, GPU는 이를 벡터 유닛이 아닌 **스칼라 유닛(SALU)과 상수 캐시** 전용 고속 경로로 처리합니다. 텍스처/일반 버퍼 읽기보다 훨씬 저렴합니다.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| 스테이지 분리 | 상수버퍼는 VS/PS 스테이지별로 **각각** 바인딩해야 함 |
| 슬롯 규약 | b0 = 프레임 공통 (프레임당 1회 갱신), b1 = 오브젝트별 |
| 정렬 규칙 | C++ 구조체는 **16바이트 배수**, 부족하면 `padding_`으로 채움 |
| HLSL 대응 | `register(b0)`/`register(b1)`이 슬롯 번호 결정 |
| 스테이지별 사용 | VS는 `gOffset`/`gWobble`, PS는 `gTint` — 같은 b1에서 다른 필드 |
| 갱신 분리 | 주기가 다른 데이터는 다른 CB로 분리해 Update 횟수 최소화 |
| InvalidateCache | BeginFrame 후 반드시 호출 |
| 컴파일 검증 | `static_assert(sizeof(T) % 16 == 0)` |
| 양쪽 바인딩 | 한 오브젝트 CB는 VS/PS 양 슬롯에 각각 `SetConstantBuffer` |
| 슬롯 = 베이스 주소 | 슬롯 번호가 상수 레지스터 파일의 시작 주소를 결정 |
| 확장 | b0(프레임)/b1(오브젝트) → 22장에서 b2(재질)까지 확장 |

표의 핵심은 "슬롯 규약"입니다. b0/b1 구분은 관례가 아니라, 스테이지별·슬롯별로 바인딩되는 하드웨어 상태가 서로 다르기 때문에 생기는 계약입니다. 이후 장에서 상수버퍼가 늘어나도(b2, b3...) 결국은 "어느 게시판에 무엇을 붙였는가" 문제일 뿐이라는 것을 기억하면 길을 잃지 않습니다.

이 장에서 한 번 더 강조할 점은, 셰이더가 정점별·픽셀별로 몇 번 실행되는지 세어 보는 습관입니다. VS는 이 장에서 정점 4개마다, PS는 화면의 픽셀마다 실행됩니다. "같은 상수버퍼를 써도 셰이더 실행 횟수는 그대로"라는 사실이 상수버퍼의 효율성이며, 이 집계 습관이 24장(셰이딩 모델)의 성능 감각으로 이어집니다. 상수버퍼가 없다면 정점마다 행렬을 통째로 버퍼로 보내야 하므로 이 장의 실험이 성립하지 않습니다. 상수버퍼 하나가 셰이더 실행 수백만 회의 공통 데이터를 한 번에 제공한다는 것이 이 장의 결론입니다.
