# 16. SVG 텍스처 — 벡터 vs 래스터, nanosvg 래스터화와 동적 버퍼

> 관련 코드: `Projects/sgfr/Sources/sgfr/16_SvgTextureDraw/16_SvgTextureDraw_Main.cpp`, `16_SvgTextureDraw_Function.cpp`
> (엔진: `Projects/sgf/Sources/sgf/Graphics/Texture.h` — LoadFromSvgFile, `Buffers.h` — 동적 VertexBuffer)
> 실행: sgfr 실행 후 콘솔 메뉴에서 **16번** 선택
> 선행 학습: 15(PNG 텍스처), 12(상수버퍼), 06(동적 버퍼)

## 1. 이 장에서 배우는 것

**벡터(SVG)와 래스터(PNG)의 차이**, GPU가 벡터를 모르기 때문에 **nanosvg 래스터화**를 거쳐 텍스처로 만드는 과정, 그리고 scale 인자로 해상도를 높여도 깨끗한 벡터의 장점을 배웁니다. 매 프레임 크기가 바뀌므로 **동적 정점 버퍼**도 처음 사용합니다.

## 2. 실행하면 보이는 것

콘솔에 벡터 vs 래스터 설명(`PrintVectorVsRasterExplanation`)이 출력된 후, 800×600 창에서 예제 이미지가 **사인파로 크기를 오가며**(0.2~0.9) 그려집니다.

- **nanosvg 설치 시**: 256×256짜리 파란 라운드 사각형 + 노란 원 얼굴 SVG가 **2배 해상도(512×512)**로 래스터화되어 표시됩니다. 확대되어도 계단이 없는 깨끗한 이미지입니다.
- **nanosvg 미설치 시**: CPU로 직접 그린 **그라데이션 노란 원** 텍스처가 대신 표시되며, 콘솔에 "nanosvg 미설치 → CPU로 직접 그린 대체 텍스처로 진행합니다" 안내가 나옵니다.

ESC로 종료.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 벡터는 "설명서", 래스터는 "완성품 사진"

- **PNG(래스터)**: 픽셀 격자 하나하나에 색이 저장된 **완성품 사진**입니다. 확대하면 픽셀이 그대로 커져 계단 현상(깨짐)이 생깁니다. 사진을 10배 확대하면 네모진 점들이 보이는 것과 같습니다.
- **SVG(벡터)**: "중심 (100,100), 반지름 80, 빨간 원" 같은 **도형 설명서(XML 텍스트)**입니다. 크기를 바꾸면 설명서대로 다시 계산해 그리므로 **아무리 확대해도 항상 깨끗**합니다. 벡터 글자(폰트)를 확대해도 깨지지 않는 이유와 같습니다.

### 3-2. GPU는 벡터를 모른다 — 래스터화가 필요하다

GPU 텍스처는 결국 **픽셀 격자**입니다. 그래서 SVG 설명서를 GPU에 그대로 줄 수는 없고, CPU가 "설명서를 읽고 → 원하는 크기의 픽셀 배열로 그려서" 텍스처를 만들어 줍니다. 이 변환을 **래스터화(Rasterize)**라고 합니다.

```
SVG(설명서) → [nanosvg 파싱] → [nanosvgrast 래스터화] → RGBA 픽셀 → GPU 텍스처
```

### 3-3. scale 인자 — "원하는 해상도로 다시 계산"

래스터화는 크기를 정하고 수행하므로, **큰 해상도로 래스터화해 두면 화면에서 확대해도 깨끗**합니다. 15장의 PNG는 256×256으로 고정되어 2배 확대하면 흐려지지만, SVG는 `scale = 2.0`으로 **512×512**로 다시 계산해 언제나 선명합니다. "벡터의 힘"이 여기서 나타납니다.

### 3-4. 동적 버퍼 — 매 프레임 변하는 모양

이 장의 이미지는 매 프레임 크기가 바뀌므로(사인파), 정점 위치도 매 프레임 새로 계산됩니다. GPU 전용 버퍼(DEFAULT)는 한 번 만든 뒤 수정이 안 되므로, **CPU가 매 프레임 갱신할 수 있는 동적 버퍼(DYNAMIC)**를 사용합니다. 이것은 바닥에 못을 박지 않고, 매번 나사를 풀었다 조이는 가변 선반과 같습니다.

### 3-5. 그럼 왜 CPU로 그리나 — 느린 것 같은 래스터화가 장점인 이유

SVG 래스터화가 CPU에서 일어난다면 "느린 것 아닌가?"라고 생각할 수 있습니다. 그러나 중요한 것은 이 작업이 **로딩 시 1회만** 수행된다는 점입니다. 한 번 래스터화해 GPU 텍스처로 올리면 이후 그리기는 GPU가 픽셀을 복붙하듯 처리하므로 아주 빠릅니다.

그리고 이 1회 비용조차 벡터의 장점으로 상쇄됩니다. PNG는 해상도가 고정되어 4K 화면에 쓰면 흐려지므로 **더 큰 PNG를 새로 만들어야** 하지만, SVG는 "설명서"이므로 그냥 **크기만 바꿔 다시 래스터화**하면 됩니다. "설명서를 다시 인쇄하는" 일은 "새 사진을 찍으러 가는" 일보다 훨씬 저렴합니다. 아이콘, 폰트, UI 요소처럼 크기가 다양하게 쓰이는 자산이 벡터로 제작되는 이유가 이것입니다.

### 3-6. 래스터화의 픽셀 루프 — "거리를 재서 색을 정하기"

`CreateFallbackCircleTexture`의 핵심은 **모든 픽셀에 대해 "픽셀 중심 ↔ 원 중심"의 거리를 재고, 그 거리로 알파를 정하는** 이중 반복문입니다:

```cpp
for (int y = 0; y < height; ++y)
    for (int x = 0; x < width; ++x)
    {
        dist = sqrt((x+0.5-center)^2 + (y+0.5-center)^2);
        alpha = Clamp((radius - dist) / 2, 0, 1);
        // dist < radius → alpha 1 (원 안쪽)
        // dist > radius + 2 → alpha 0 (원 바깥쪽)
    }
```

이 "거리 재기"는 픽셀 단위로 수행되므로 512×512 = 26만 번의 제곱근 연산이 일어납니다. CPU가 이 정도의 루프를 도는 데는 몇 밀리초면 충분하고, 그것이 로딩 시 1회뿐이므로 전체적으로 유리합니다. GPU가 벡터를 직접 그릴 때도(테셀레이션) 비슷한 판정을 하되 **픽셀이 아니라 폴리곤의 모서리** 기준으로 커버리지 판정을 한다는 점을 대비해 보면, "그리기 판정이 어디서 일어나느냐"의 차이가 CPU/GPU 분업의 본질임을 알 수 있습니다.

## 5. 코드 워크스루

`SvgTextureDraw_Main()`의 흐름입니다.

### 1단계: SVG 파일 자급자족 — EnsureSampleSvgFile

```cpp
const char* szSvgPath = "sample.svg";   // 실행 폴더 기준 상대 경로

if (EnsureSampleSvgFile(szSvgPath))
{
    bLoaded = texture.LoadFromSvgFile(&device, szSvgPath, 2.0f);   // scale 2.0 = 512x512
}
```

파일이 없으면 `EnsureSampleSvgFile`이 `fopen_s`로 직접 만들어 줍니다. SVG가 사람이 읽을 수 있는 XML 텍스트라는 것을 보여줍니다:

```cpp
fprintf(pFile,
    "<svg xmlns=\"http://www.w3.org/2000/svg\" width=\"256\" height=\"256\">\n"
    "  <rect x=\"16\" y=\"16\" width=\"224\" height=\"224\" rx=\"32\" fill=\"#2d6cdf\"/>\n"
    "  <circle cx=\"128\" cy=\"128\" r=\"72\" fill=\"#ffd166\"/>\n"
    "  <circle cx=\"104\" cy=\"112\" r=\"12\" fill=\"#333333\"/>\n"
    "  <circle cx=\"152\" cy=\"112\" r=\"12\" fill=\"#333333\"/>\n"
    "  <path d=\"M 96 152 Q 128 184 160 152\" stroke=\"#333333\" stroke-width=\"8\" fill=\"none\"/>\n"
    "</svg>\n");
```

파란 라운드 사각형 + 노란 원 얼굴(눈 2개, 입 곡선)입니다. XML 태그 하나하나가 도형 명령입니다 — `rect`는 라운드 처리된 사각형, `circle`은 원, `path`의 `M`(이동)과 `Q`(2차 곡선)는 선 그리기 명령입니다. 이것이 "벡터 이미지는 그림 설명서"라는 말의 실제 모습입니다. 실행 폴더에 `sample.svg` 파일이 생성되어 메모장으로 열어 보면 같은 텍스트를 직접 확인할 수 있습니다.

### 2단계: 텍스처 폴백

```cpp
if (bLoaded) { printf("%s 래스터화 성공! (%d x %d)\n", szSvgPath, texture.Width(), texture.Height()); }
else if (CreateFallbackCircleTexture(&device, &texture)) { ... }
```

- `Texture::LoadFromSvgFile(&device, path, 2.0f)`는 `SGF_HAS_NANOSVG` 매크로로 게이트됩니다. nanosvg 헤더 2개(nanosvg.h, nanosvgrast.h)를 `Projects/sgf/Sources/sgf/_Extern/nanosvg/`에 넣으면 활성화됩니다.
- 없으면 `CreateFallbackCircleTexture`가 CPU로 **안티에일리어싱된 노란 원**을 직접 그립니다:

```cpp
// 픽셀 중심에서 원 중심까지의 거리
const _f32 dx = (x + 0.5f) - center;
const _f32 dy = (y + 0.5f) - center;
const _f32 dist = sqrtf(dx * dx + dy * dy);

// 원 경계에서 2픽셀 정도 부드럽게 알파를 감쇠시킨다.
// 이것이 바로 '안티에일리어싱'의 기본 아이디어다!
_f32 alpha = Clamp((radius - dist) / 2.0f, 0.0f, 1.0f);
pixels[idx + 0] = (_u8)(255.0f * alpha);   // R (노란 원)
// ... A도 같은 alpha → 경계는 반투명
```

경계에서 거리에 비례해 알파가 1→0으로 부드럽게 감쇠해 계단이 사라집니다.

대체 경로도 하나의 학습 자료입니다. `(x + 0.5f)`는 픽셀의 **중심점**을 계산하는 관례적 공식으로, 픽셀 왼쪽 위 모서리가 아니라 중심을 기준으로 원과의 거리를 재야 계단이 고르게 분포합니다. `(radius - dist) / 2.0f`의 `/2`는 "2픽셀 폭의 그라데이션"을 만들기 위한 값이고, 그라데이션이 너무 좁으면(1픽셀) 계단이 보이고 너무 넓으면(8픽셀) 경계가 뿌옇게 보입니다. 안티에일리어싱의 폭은 "뿌옇게 보이지 않는 최소한의 넓이"가 정답이며, 이 숫자를 바꿔 가며 품질이 어떻게 변하는지 실험해 볼 수 있습니다.

### 3단계: 동적 정점 버퍼

```cpp
VertexPTC vertices[4] = {};
const _u32 indices[] = { 0, 1, 2, 2, 1, 3 };
```

```cpp
Shader shader;
shader.CompileFromString(&device, TextureShaderSource(), pLayoutDescs, layoutCount);  // TutorialCommon 공용
```

### 5단계: 렌더 루프 — 매 프레임 정점 갱신

```cpp
timer.Tick();
elapsed += timer.DeltaTime();

// 크기가 0.2 ~ 0.9 사이를 천천히 오가도록 사인파로 계산
const _f32 half = 0.55f + 0.35f * sinf(elapsed * 0.8f);
const _f32 aspect = window.AspectRatio();

// 매 프레임 정점을 새로 계산해 동적 버퍼를 갱신한다. (06번에서 배운 동적 버퍼 활용)
vertices[0] = { vec3(-half, +half * aspect, 0.0f), vec2(0.0f, 0.0f), color::White() };
vertices[1] = { vec3(+half, +half * aspect, 0.0f), vec2(1.0f, 0.0f), color::White() };
vertices[2] = { vec3(-half, -half * aspect, 0.0f), vec2(0.0f, 1.0f), color::White() };
vertices[3] = { vec3(+half, -half * aspect, 0.0f), vec2(1.0f, 1.0f), color::White() };
vb.Update(&device, vertices, 4);

device.BeginFrame(color(0.12f, 0.12f, 0.16f, 1.0f));
texture.Bind(&device, 0);
vb.Bind(&device); ib.Bind(&device); shader.Bind(&device);
device.Context()->DrawIndexed(6, 0, 0);
device.EndFrame(true);
```

`vb.Update(&device, vertices, 4)`은 내부적으로 `Map(D3D11_MAP_WRITE_DISCARD) → memcpy → Unmap`으로 매 프레임 버퍼 내용을 교체합니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. SVG → 픽셀: CPU 래스터화의 하드웨어 위치

SVG는 GPU와 관계없이 **CPU에서** 처리됩니다. nanosvg가 XML 파서로 `<rect>`, `<circle>`, `<path>` 노드를 트리로 만들고, nanosvgrast가 폴리곤을 스캔라인 채움으로 512×512 픽셀 배열에 채웁니다. 이 CPU 래스터화는 부동소수점 연산이 많아 몇 밀리초가 걸리지만 **로딩 시 1회만** 수행되고, 결과물은 `CreateTexture2D`로 GPU 메모리에 올라갑니다. 즉 벡터의 재계산 이득은 "렌더링 시간이 아니라 로딩 시간"에서 옵니다. 런타임에 크기가 바뀌어도 텍스처는 고정 해상도이므로, 진짜 실시간 벡터(폰트, UI)는 GPU의 셰이더가 곡선 방정식을 직접 평가하는 다른 경로(테셀레이션/시그니드 거리 필드)를 씁니다.

### 6-2. scale과 텍스처 메모리 — 4배의 4배

`scale = 2.0`은 256→512로 가로세로가 2배, 픽셀 수는 **4배**(256KB → 1MB)입니다. 텍스처 메모리는 해상도의 제곱으로 늘어나므로, 실전에서 텍스처 아틀라스/압축 포맷(BC 계열)이 중요한 이유가 여기 있습니다. 512×512 RGBA8은 1MB인데, BC7 압축을 쓰면 약 4분의 1로 줄어듭니다. 이 장은 학습용이라 원시 RGBA를 사용합니다.

### 6-3. 안티에일리어싱과 샘플링 하드웨어의 상호작용

`Clamp((radius - dist) / 2, 0, 1)`은 원 경계에서 알파를 0→1로 **그라데이션**시켜, 텍스처 유닛이 경계 픽셀을 샘플링할 때 부분적으로 덮인 원이 투명하게 섞이도록 만듭니다. 화면에서 확대하면 이 알파 그라데이션이 Linear 필터(다음 픽셀 가중 평균)와 결합해 계단을 부드럽게 합니다. 이것은 GPU가 **MSAA 대신 텍스처에 미리 AA를 구워 넣는** 기법으로, 렌더링 시 추가 샘플 비용이 없는 대신 해상도가 부족하면 다시 계단이 보입니다. scale 2.0의 해상도 여유가 이 문제를 보완합니다.

### 6-4. 동적 버퍼의 하드웨어 경로 — Map/DISCARD와 ring buffer

`vb.Update`의 `Map(..., D3D11_MAP_WRITE_DISCARD, ...)`는 CPU가 GPU 버퍼 메모리에 직접 쓰는 **DMA식 접근**입니다. `DISCARD`는 GPU가 지난 프레임의 정점을 아직 쓰고 있어도 드라이버가 **버퍼 내부의 다음 슬롯**을 줘서(더블 버퍼링), CPU는 기다리지 않고 쓰고 GPU는 옛 데이터를 계속 읽습니다. 이 "CPU가 채우고 GPU가 읽는 경마장" 구조는 PCIe/메모리 대역폭을 매 프레임 소모하므로, 동적 버퍼는 "가끔 바뀌는 데이터"에만 쓰고 "매 프레임 전부 바뀌는 배치 데이터"는 상수버퍼·스테이징 기법으로 처리하는 것이 실전 관례입니다. 22장 SceneRenderer가 이 경로를 볼 수 있습니다.

### 6-5. 텍스처 바인딩과 SRV — 셰이더 리소스 슬롯

`texture.Bind(&device, 0)`은 `PSSetShaderResources(0, 1, &srv)`로 **PS 스테이지의 t0 슬롯**에 SRV를 장착합니다. 셰이더의 `Texture2D gTexture : register(t0)`과 슬롯이 일치해야 샘플링됩니다. GPU는 SRV가 가리키는 텍스처를 텍스처 캐시(비디오 메모리의 일부)로 읽어 TMU에 공급합니다. 슬롯 0~7까지 여러 텍스처를 동시에 묶을 수 있어(멀티 텍스처), 이어지는 장들에서 정점 당 여러 UV와 여러 텍스처의 합성이 등장합니다.

### 6-6. 사인파 애니메이션 — CPU 연산의 부하 위치

`sinf(elapsed * 0.8f)`로 half를 매 프레임 계산하는 것은 CPU의 FPU 1회 연산이라 무시할 수 있고, 정점 4개 갱신과 DrawIndexed(6)는 최소 드로우콜입니다. 관심은 "애니메이션 데이터(시간)가 CPU에서 시작된다"는 점입니다. GPU는 명령만 받고 자체 클록을 갖지 않으므로, 시간 개념은 항상 CPU가 만들어 상수버퍼로 보내거나, 정점 갱신(이 장)으로 보냅니다. 이것이 12장의 `gTime`(b0 프레임 공통)이 존재하는 이유입니다.

### 6-7. 동적 버퍼 vs "행렬로 늘리기" — 두 경로의 트레이드오프

크기가 변하는 사각형을 그리는 방법은 이 장처럼 **정점을 매 프레임 새로 계산**하는 것 외에도, **고정된 정점을 상수버퍼의 행렬로 확대/축소**하는 방법이 있습니다(10장 방식). 둘은 하드웨어 경로가 다릅니다.

- 정점 갱신: CPU가 4정점 × 32바이트를 매 프레임 Map/DISCARD로 업로드 → IA가 정점을 읽음. 갱신량은 적지만 Map 호출과 버퍼 쓰기가 매 프레임 발생합니다.
- 행렬 확대: 정점은 한 번만 업로드하고, WVP 행렬(상수버퍼 64바이트)만 매 프레임 갱신 → GPU 셰이더가 확대·축소를 처리. 텍스처 UV는 그대로 0~1이므로 텍스처가 늘어나 보입니다.

16장이 정점 갱신을 택한 이유는 UV를 0~1로 유지해 **텍스처 내용도 함께 커지는** 효과를 주기 위함이 아니라, "크기 변화 = 정점 위치 변화"라는 가장 직관적인 경로를 보여 주기 위함입니다. 실전에서는 UV가 깨지지 않게 하려고 행렬 경로를 더 자주 쓰며, 배치 렌더러(22장)는 매 프레임 정점을 한 버퍼에 모아 한 번에 업로드하는 방식으로 두 세계를 절충합니다.

### 6-8. 안티에일리어싱의 또 다른 얼굴 — 슈퍼샘플링

이 장의 CPU 원은 **알파 감쇠(2픽셀 폭 그라데이션)**로 계단을 부드럽게 합니다. 이것은 "경계를 반투명하게" 하는 기법이고, GPU 렌더링에서 쓰는 다른 계열은 **슈퍼샘플링(MSAA)**입니다 — 픽셀마다 여러 서브샘플 위치(예: 4개)에서 도형을 판정하고 평균을 냅니다. MSAA는 GPU가 픽셀당 여러 번 커버리지 판정을 하므로 대역폭과 ROP 부담이 늘지만, 색상 셰이더는 1회만 실행되어 비교적 효율적입니다. 텍스처에 미리 AA를 구워 넣는 이 장의 방식은 렌더링 비용이 0이지만 해상도가 부족하면 다시 계단이 보입니다. "계단 제거"라는 목표를 두고, 어느 층(텍스처? 렌더타깃? 후처리?)에서 해결하느냐에 따라 기법이 달라진다는 것만 기억해 두세요.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| 벡터 vs 래스터 | SVG = 도형 설명서(확대해도 깨끗), PNG = 픽셀 격자(확대하면 계단) |
| GPU는 벡터를 모른다 | SVG → 파싱 → 래스터화 → RGBA → GPU 텍스처 경로 필수 |
| 래스터화 경로 | `Texture::LoadFromSvgFile(&device, path, 2.0f)` — nanosvg 게이트(SGF_HAS_NANOSVG) |
| scale 인자 | 2.0 = 256→512 해상도(픽셀 4배) |
| 폴백 | nanosvg 없으면 `CreateFallbackCircleTexture` (CPU 그라데이션 원) |
| 동적 버퍼 | `vb.Create(&device, v, stride, 4, true)` → 매 프레임 `vb.Update` |
| 안티에일리어싱 | 경계 알파 `Clamp((radius-dist)/2, 0, 1)` 부드러운 감쇠 |
| 알파 블렌딩 | `device.SetAlphaBlending(true)` — SVG 투명 배경 |
| 셰이더 재사용 | 15장과 동일한 `TextureShaderSource()` |
| SVG 자급자족 | `EnsureSampleSvgFile`이 `fopen_s`로 XML 파일 직접 작성 |
| 동적 vs 행렬 | 정점 갱신(16장) vs 상수버퍼 행렬 확대 — UV 보존은 행렬 경로가 유리 |
| AA 계열 | 알파 감쇠(텍스처) vs MSAA(렌더타깃) — 계층에 따라 기법이 다름 |

표의 "시작 비용"과 "알파 감쇠" 두 줄이 이 장을 요약합니다. 벡터는 준비는 비싸지만 해상도가 자유롭고, 알파 감쇠는 계단 제거의 가장 기본적인 구현이라는 것. 두 개념 모두 이후 장에서 다른 얼굴로 다시 등장하므로, 지금의 이해가 곧 밑거름이 됩니다. PNG(15장)와 SVG(16장)를 모두 경험했으니, "이미지의 형태가 바뀌어도 GPU가 쓰는 것은 결국 픽셀 격자"라는 사실이 가장 중요한 결론입니다. 다음 장에서는 그 픽셀을 읽는 방법(필터·주소 모드)을 조절합니다.
