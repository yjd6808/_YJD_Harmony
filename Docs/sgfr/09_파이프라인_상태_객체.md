# 09. 파이프라인 상태 객체 — 상태를 "값"으로 만들어 들고 다니기

> 관련 코드: `Projects/sgfr/Sources/sgfr/Tutorial/09_PipelineStateObjects/09_PipelineStateObjects_Main.cpp`
> (엔진: `Projects/sgf/Sources/sgf/Graphics/PipelineState.h`, `GraphicContext.h`)
> 실행: sgfr 실행 후 콘솔 메뉴에서 **9번** 선택
> 선행 학습: 05(렌더링 파이프라인), 08(메시와 토폴로지)

## 1. 이 장에서 배우는 것

파이프라인의 4대 상태(래스터라이저·블렌드·깊이·샘플러)를 **독립된 객체**로 만들어 두고, 포인터 하나만 바꿔 그리기 방식을 통째로 교체하는 v3 엔진의 설계를 실습합니다.

## 2. 실행하면 보이는 것

800×600 창에 사각형 두 개가 겹쳐 있습니다. 아래는 **불투명한 파란색 사각형**, 위에는 **알파 0.5의 반투명 주황색 사각형**입니다.

- **1키**: 솔리드(면 채우기) + 뒷면 컬링 — 지금까지 보던 일반 모습
- **2키**: 와이어프레임(선만) + 컬링 없음 — 사각형이 네모난 선 틀로 보임
- **3키**: 불투명 블렌드 — 앞 사각형이 그대로 덮어서 파란색이 거의 안 보임
- **4키**: 알파 블렌드 — 앞 사각형이 반투명해져 파란색과 섞임

콘솔에는 "1/2로 채우기, 3/4로 블렌드를 바꿔보세요!" 안내가 출력됩니다. 초기 상태는 1(솔리드)+4(알파)이므로, 실행 직후부터 반투명 주황이 파란 바닥과 겹쳐 보입니다. 키를 누를 때마다 상태가 즉시 바뀌므로, 어떤 키가 어떤 상태 객체를 가리키는지 감각으로 익힐 수 있습니다.

## 3. 핵심 개념 — 비유로 먼저 이해하기

### 3-1. 상태 객체는 "필기구 세트"다

연필로 그림을 그리다가 붓으로 바꾸려면 펜대 하나를 바꾸는 게 아니라 **붓 전체를 집어 들면** 됩니다. 마찬가지로 그래픽 파이프라인도 "어떻게 그릴지"를 결정하는 설정들이 여럿 붙어 있는데, 옛날 방식(v2)은 `device.SetWireframe(true)`처럼 설정 하나씩 스위치를 눌러 바꿨습니다. 스위치가 10개면 10번 눌러야 하고, 설정이 꼬이기 쉽습니다.

v3 방식은 **스위치들이 이미 맞춰진 붓을 통째로 만들어 두고**, "이제 이 붓으로 그려!" 하듯 객체 하나를 넘겨주는 것입니다. 이것이 **상태 객체(State Object)**입니다.

### 3-2. 4대 상태 객체 — 파이프라인의 "옵션 노브"

| 상태 객체 | 옵션 노브 | 예 |
|---|---|---|
| RasterizerState | 삼각형을 어떻게 채우고, 어떤 면을 버릴지 | 면 채우기 vs 선만, 뒷면 버리기 |
| BlendState | 새 색과 이미 그려진 색을 섞는 공식 | 불투명, 알파 반투명 |
| DepthStencilState | 깊이 테스트 켜기/끄기 | 3D는 켜고, 2D는 끄기 |
| SamplerState | 텍스처를 읽는 방법 | 필터, 주소 모드 (17장에서 자세히) |

### 3-3. 같은 붓은 여러 번 만들어 쓸 필요가 없다 (플라이웨이트 패턴)

상태 객체는 **물건(값)**이므로 복사해서 주고받을 수 있습니다. 그리고 "같은 설정 조합"의 붓은 **하나만 만들어 두고 모든 물체가 빌려 쓰면** 됩니다. 반투명 붓 하나를 모든 물체가 공유하는 것이죠. 이것을 **플라이웨이트(Flyweight) 패턴**이라고 합니다. 각 `RasterizerState` 객체는 자기만의 D3D 상태 객체를 만들어 갖지만(중복 제거는 없음), C++ 쪽에서 **같은 객체를 여러 물체의 드로우에 재사용**하면 GPU 상태 전환 자체가 한 종류이므로 전환이 잦은 렌더러에서 상태 변경 부담이 줄어듭니다. 이것이 23번 스테이트 캐시 튜토리얼의 전제가 됩니다.

### 3-4. 이것이 진짜 배우려는 것: 상태가 "값"이 된다

예전 방식(v2)의 `device.SetWireframe(true)`를 떠올려 보세요. 이 방식은 **명령(동사)**입니다. "와이어프레임 켜! 컬링 꺼!"처럼 하나씩 외치며 현재 상태를 바꿉니다. 그런데 그림 하나를 그릴 때 필요한 설정은 항상 여러 개가 묶여 있습니다. 외치는 방식은 어디서 꼬였는지 모르기 쉽고, 나중에 다시 되돌리기도 번거롭습니다.

v3의 상태 객체는 그 반대입니다. **설정 묶음 자체를 사물(명사)**으로 만들어 두고, "이거로 그려!" 하고 통째로 넘겨줍니다. 사물이므로 배열에 담을 수도, 변수로 저장할 수도, 다른 물체에 붙여 줄 수도 있습니다. 이 장의 실습은 바로 그 가능성의 시작점입니다 — 곧 20장에서 **셰이더 + 상태 + 텍스처를 하나로 묶은 머티리얼(Material)**이 등장해, 이 사물을 통째로 물체에 붙이는 시대가 옵니다. 상태가 값이 되지 않았다면 그런 설계는 애초에 불가능했습니다.

## 4. 초보자 용어 사전

| 용어 | 뜻(쉬운 말) | 비유 |
|---|---|---|
| 파이프라인 상태 | 그리기 전에 정해야 하는 "어떻게 그릴까" 설정 묶음 | 붓의 굵기·색·물성 |
| 래스터라이저 상태 | 삼각형을 면으로 채울지 선으로 채울지, 어떤 면을 버릴지 | 연필 vs 네임펜 |
| 블렌드 상태 | 새 색이 기존 색과 섞이는 공식 | 물감을 덧칠 vs 물감 섞기 |
| 깊이 스텐실 상태 | 깊이 테스트 켜기/끄기 | 앞에 있는 사람만 보이기 |
| 컬링(Culling) | 보이지 않는 뒷면 삼각형을 미리 버리기 | 상자 뒷판 그리지 않기 |
| 와이어프레임(Wireframe) | 면을 채우지 않고 선만 그리는 모드 | 유리 상자의 뼈대 |
| 플라이웨이트 패턴 | 같은 데이터를 여러 객체가 공유해 메모리를 아끼는 설계 | 공용 사물함 열쇠 |
| 상태 캐시 | 이미 바꾼 상태를 기억해 중복 호출을 생략하는 장치 | 이미 한 약속은 안 함 |
| D3D11_RENDER_TARGET_BLEND_DESC | 블렌드 공식 하나를 담는 구조체 (Enable, SrcBlend, DestBlend) | 혼합 공식 작성표 |
| D3D11_CULL_BACK | 뒤집힌(뒷면) 삼각형을 버리는 컬링 모드 | 상자 뒷판 접어 버리기 |
| OMSetBlendState | 블렌드 상태를 파이프라인에 장착하는 호출 | 물감 규칙 게시판 붙이기 |
| RSSetState | 래스터라이저 상태를 장착하는 호출 | 붓 종류 게시판 붙이기 |
| IsKeyDown | 매 프레임 키가 눌렸는지 묻는 폴링 | 매 순간 버튼 확인 |
| SRC_ALPHA | 원본 색의 알파 값 (0.5면 절반 가중치) | 물감의 투명도 |

용어 사전 표의 마지막 세 줄은 18장(블렌드 스테이트)에서 실제 구조체 멤버 단위로 다시 등장하므로, 지금은 "블렌드 공식도 결국 구조체에 담긴 데이터"라는 이미지 정도만 남기면 충분합니다.

## 5. 코드 워크스루

`PipelineStateObjects_Main()` 함수의 흐름을 따라갑니다.

### 1단계: 윈도우·디바이스·컨텍스트 준비

```cpp
GraphicDevice device;
device.Initialize(window.Handle(), window.Width(), window.Height());
GraphicContext& context = device.GetContext();
```

이 튜토리얼부터는 그리기 명령을 `GraphicContext`(작업반장)에게 맡깁니다. `device.GetContext()`가 그 참조를 돌려줍니다.

### 2단계: 셰이더 준비

익명 네임스페이스의 `PASSTHROUGH_SHADER_SOURCE`는 NDC 좌표를 그대로 통과시키는 최소 셰이더입니다. 정점 색의 **알파까지** 그대로 출력하므로, 앞 사각형의 반투명(0.5)이 살아남습니다.

```cpp
VertexShader vs;
PixelShader ps;
vs.InitializeFromSource(&device, PASSTHROUGH_SHADER_SOURCE);
ps.InitializeFromSource(&device, PASSTHROUGH_SHADER_SOURCE);
```

### 3단계: 메시 2개 (인덱스 포함 버전)

`BuildQuadMesh` 헬퍼가 `VertexPTC` 정점 4개 + 시계방향 인덱스 6개 `{0,1,2},{0,2,3}`를 만들어 `Mesh::Initialize`로 메시를 만듭니다. 이번에 `Mesh::Initialize`가 **인덱스까지 받는 버전**으로 등장합니다.

```cpp
Mesh backQuad;  // 불투명 파랑  color(0x33, 0x99, 0xFF, 0xFF)
Mesh frontQuad; // 알파 0.5 주황 color(0xFF, 0x66, 0x33, 0x80)
BuildQuadMesh(&device, &vs, &backQuad, vec2(-0.15f, 0.0f), 0.5f, color(0x33, 0x99, 0xFF, 0xFF));
BuildQuadMesh(&device, &vs, &frontQuad, vec2(+0.15f, 0.0f), 0.5f, color(0xFF, 0x66, 0x33, 0x80));
```

### 4단계: 상태 객체 5개 생성

같은 종류라도 설정 조합마다 따로 만들어 둡니다.

```cpp
RasterizerState rsSolid;        rsSolid.Initialize(&device, CullMode::cmBack, FillMode::fmSolid);
RasterizerState rsWireframe;    rsWireframe.Initialize(&device, CullMode::cmNone, FillMode::fmWireframe);
BlendState blendOpaque;         blendOpaque.Initialize(&device, BlendMode::bmNone);
BlendState blendAlpha;          blendAlpha.Initialize(&device, BlendMode::bmAlpha);
DepthStencilState depthDisabled; depthDisabled.Initialize(&device, DepthMode::dmDisabled);
```

`Initialize(&device, CullMode, FillMode)`처럼 생성 인자가 곧 "설정 값"입니다. 각 객체는 내부적으로 `CreateRasterizerState`/`CreateBlendState`/`CreateDepthStencilState`로 자기만의 `ID3D11RasterizerState`/`ID3D11BlendState`/`ID3D11DepthStencilState` 원본 상태 객체를 만들어 가집니다.

### 5단계: 렌더 루프 — 포인터 교체가 전부

```cpp
RasterizerState* pCurrentRs = &rsSolid;
BlendState* pCurrentBlend = &blendAlpha;

// 키 입력으로 포인터만 갈아끼운다
if (input.IsKeyPressed('1')) { pCurrentRs = &rsSolid; }
if (input.IsKeyPressed('2')) { pCurrentRs = &rsWireframe; }
if (input.IsKeyPressed('3')) { pCurrentBlend = &blendOpaque; }
if (input.IsKeyPressed('4')) { pCurrentBlend = &blendAlpha; }
```

그리기 직전에는 상태를 컨텍스트에 설정합니다.

```cpp
device.BeginFrame(color(0x0F, 0x0F, 0x1A, 0xFF));	// 어두운 남색 (0.06, 0.06, 0.1)
context.InvalidateCache();   // BeginFrame이 원시 D3D 상태를 건드렸으므로 캐시를 비운다

context.SetVertexShader(&vs);
context.SetPixelShader(&ps);
context.SetRasterizerState(pCurrentRs);
context.SetDepthStencilState(&depthDisabled);

context.SetBlendState(&blendOpaque);   // 바닥은 항상 불투명
backQuad.Bind(context);
backQuad.Draw(context);

context.SetBlendState(pCurrentBlend);  // 앞은 선택한 블렌드
frontQuad.Bind(context);
frontQuad.Draw(context);

device.EndFrame(true);
```

`Mesh::Bind(context)`가 정점/인덱스 버퍼·입력 레이아웃·토폴로지를 한 번에 장착하고, `Mesh::Draw(context)`가 `DrawIndexed(6,0,0)`을 호출합니다.

### 키별로 어떤 상태가 바뀌는지 정리

| 키 | 바뀌는 상태 객체 | 결과 |
|---|---|---|
| 1 | `rsSolid` (컬링 ON + 솔리드) | 겹친 사각형이 평범하게 보임 |
| 2 | `rsWireframe` (컬링 OFF + 와이어프레임) | 두 사각형이 선 틀로, 뒷사각형 선도 보임 |
| 3 | `blendOpaque` | 앞 주황이 바닥을 덮어 섞임이 없음 |
| 4 | `blendAlpha` | 앞 주황이 반투명하게 섞임 |

컬링이 켜진 상태(1)에서는 사각형을 뒤에서 보아도 뒷면이 버려지므로, 앞뒤가 구분되지 않는 평평한 사각형은 차이를 느끼기 어렵습니다. 그래서 2키는 컬링을 끄고 와이어프레임을 함께 켜, **"두 사각형이 모두 그려지는"** 상황을 만든 것입니다. 만약 와이어프레임 상태에서 컬링을 켜면 사각형 뒷면이 사라져 반쪽만 보이는 모습을 관찰할 수 있는데, 이 역시 좋은 실험이 됩니다. 블렌드는 앞 사각형의 알파가 0.5라 3/4키 차이가 즉시 눈에 보이므로, "상태 객체 하나가 화면을 완전히 다르게 만든다"는 체감이 확실하게 남습니다.

### 6단계: 정리

상태 객체 클래스에는 `Finalize()`가 정의되어 있지만, 이 튜토리얼은 명시 호출 없이 내부 `ComPtr` 소멸자에 맡깁니다. 메시/셰이더만 명시적으로 정리하면 끝입니다.

## 6. GPU와 DX11, 하드웨어 깊이 보기

### 6-1. D3D11의 상태 객체와 하드웨어 레지스터

D3D11은 상태를 **설명자(DESC) → 상태 객체 → 바인딩** 3단계로 다룹니다. `FillRasterizerDesc`가 채우는 `D3D11_RASTERIZER_DESC`(컬링 모드, 채우기 모드, 앞면 판정 등)를 `ID3D11Device::CreateRasterizerState`에 넘기면, 드라이버는 이 값을 GPU가 이해하는 **구성 비트**로 컴파일해 상태 객체로 만들어 줍니다. 마찬가지로 `D3D11_BLEND_DESC` → `ID3D11BlendState`, `D3D11_DEPTH_STENCIL_DESC` → `ID3D11DepthStencilState`가 만들어집니다.

드로우콜 하나마다 GPU는 파이프라인의 각 단계를 "어떻게 실행할지"를 **상태 레지스터**(컨텍스트에 저장된 설정 비트 모음)에서 읽습니다. 이 레지스터들은 GPU 내부의 스레드 스케줄러와 고정기능 유닛이 참조하는 값이며, CPU가 `OMSetBlendState`, `RSSetState`, `OMSetDepthStencilState` 같은 호출로 덮어쓸 때만 바뀝니다.

### 6-2. 래스터라이저 상태 → 하드웨어 래스터라이저

`ID3D11RasterizerState`는 GPU의 **고정기능 래스터라이저 유닛**(Fixed-Function Rasterizer) 설정입니다. GPU 다이 안의 래스터라이저는 다음과 같은 고정 배선 단계로 구성됩니다:

- **삼각형 셋업(Triangle Setup)**: 정점을 받아 화면 픽셀 좌표로 변환하고, **백페이스 컬링**(CullMode)과 **가로 자르기**(clip)를 수행합니다. 컬링은 삼각형의 감는 방향(winding)을 계산해 앞면/뒷면을 판정하는데, 이것은 GPU가 프리미티브당 수백 클럭이 아니라 **한 사이클에 수십 개 프리미티브를 병렬 판정**할 수 있는 전용 하드웨어 연산입니다.
- **픽셀 생성(Scanline → Edge Walk)**: 채우기 모드가 `D3D11_FILL_SOLID`면 삼각형 내부 픽셀들을, `D3D11_FILL_WIREFRAME`면 **변(edge)에 놓인 픽셀만** 생성합니다. GPU는 선분 픽셀을 밟아가는 브레젠햄류 배선을 쓰기 때문에, 와이어프레임이 "그리는 것"이 아니라 "채우는 픽셀 생성 루틴이 다른 것"으로 처리됩니다. 즉 성능이 같은 것이 아니라 오히려 선별 작업 때문에 하드웨어 효율이 달라질 수 있는 영역입니다.

이 튜토리얼에서 2키(와이어프레임)를 누르면 사각형이 선 틀로 보이는 이유가 바로 이것입니다. 면 내부 픽셀 생성 루틴이 꺼지고, 변 위 픽셀만 래스터라이저가 생성합니다. 컬링이 꺼져 있으므로 앞뒤 상관없이 그려져, 겹친 두 사각형의 선들이 모두 보입니다. 반대로 1키(솔리드+컬링)에서는 뒷면이 버려져 앞 사각형이 바닥을 가립니다.

### 6-3. 블렌드 상태 → ROP(Output Merger) 유닛

`ID3D11BlendState`는 파이프라인 맨 끝 **출력 병합기(Output Merger, ROP)**의 설정입니다. ROP는 그래픽 카드의 **메모리 계층에서 L2 캐시 바로 옆에 있는 전용 유닛**으로, 픽셀 셰이더가 만든 색을 프레임버퍼에 쓰기 전에 섞는 일을 합니다.

`bmAlpha` 모드의 D3D 공식은 `SrcBlend = SRC_ALPHA, DestBlend = INV_SRC_ALPHA`입니다. 즉:

```
final = src * srcAlpha + dst * (1 - srcAlpha)
```

GPU의 ROP는 이 곱셈-덧셈을 픽셀 병렬 유닛(보통 8~16개 채널)으로 처리합니다. 중요한 것은 **블렌딩이 켜져 있으면 ROP가 매 픽셀마다 프레임버퍼의 기존 색을 읽어야 하므로(read-modify-write) 메모리 대역폭이 늘고, 알파 블렌드일 때는 반투명 면들을 멀리 있는 것부터 그려야 한다는 그리기 순서 제약**이 생긴다는 점입니다. 이 튜토리얼의 `bmNone`(불투명)은 기존 색을 읽지 않고 덮어쓰므로 더 빠릅니다.

### 6-4. 깊이 스텐실 상태 → 깊이 비교 유닛

`ID3D11DepthStencilState`는 ROP와 같은 스테이지에 있는 **깊이 테스트 하드웨어** 설정입니다. GPU는 픽셀마다 별도 깊이 버퍼(보통 D24S8)에서 값을 읽어, `D3D11_DEPTH_FUNC_LESS_EQUAL` 같은 비교를 전용 비교기(comparator)로 수행합니다. 비교기는 메모리 대역폭이 비싼 깊이 읽기를 최소화하기 위해 **얼리-Z(Early-Z)** 기능으로 픽셀 셰이더 실행 전에 미리 판정할 수 있습니다. `dmDisabled`는 이 판정을 끄고 항상 덮어쓰는 상태로, 2D 적층 그리기에서 깊이 대신 "그리는 순서"가 앞뒤를 결정하게 만듭니다.

### 6-5. 상태 변경 비용과 스테이트 캐시

상태 바인딩 호출 자체는 비교적 저렴하지만, 드라이버가 상태 객체마다 내부 파이프라인 상태를 다시 조립해야 하므로 **상태 변경이 잦을수록 드라이버 CPU 비용과 GPU 파이프라인 플러시가 늘어납니다.** v3 엔진의 `GraphicContext`는 마지막으로 바인딩한 객체를 `pCachedRasterizer_`, `pCachedBlend_`, `pCachedDepth_` 등에 기억했다가, **같은 객체면 D3D 호출 자체를 생략**하는 스테이트 캐시를 갖고 있습니다. 이 튜토리얼의 `context.InvalidateCache()`는 `BeginFrame`이 원시 `ID3D11DeviceContext`를 직접 건드렸을 수 있으므로 "내가 기억하던 상태는 무효"라고 선언하는 것입니다. (23장에서 심화 실습)

### 6-6. 상태 객체 재사용의 하드웨어 이득

같은 상태 객체를 여러 드로우에 재사용하면, 드라이버가 상태 객체별로 유지하는 내부 컴파일 캐시도 그대로 재사용됩니다. 같은 블렌드 객체 하나를 100개의 드로우에 쓰면 실제 GPU 상태 전환은 한 종류뿐이므로, GPU가 파이프라인 상태를 바꿀 때 비워야 하는 파이프라인 캐시(셰이더/상태 바인딩 캐시)를 덜 흔들게 됩니다. 이것이 "상태를 값으로 만들어 들고 다녀도 느려지지 않는" 이유의 하드웨어 차원의 답입니다.

### 6-7. 상태 전환 비용을 줄이는 스테이트 캐시의 동작 원리

v3의 `GraphicContext`가 구현하는 스테이트 캐시는 "마지막으로 바인딩한 객체를 기억했다가, 같은 객체를 다시 요청하면 D3D 호출을 아예 생략"하는 구조입니다. 예를 들어 한 프레임 안에서 `context.SetBlendState(&blendOpaque)`를 여러 드로우 앞에서 반복 호출해도, 첫 호출에 이미 바인딩했다면 이후 호출은 **캐시 히트로 끝나** 내부적으로 D3D의 `OMSetBlendState`를 부르지 않습니다. 단, 이 장처럼 매 프레임 `BeginFrame` 직후 `InvalidateCache()`를 호출하면 캐시가 비워지므로 **프레임의 첫 바인딩은 항상 실제 호출**이 되고, 절감 효과는 "한 프레임 안에서 같은 객체를 재바인딩할 때" 발생합니다. `GetApiCallCount()`와 `GetSkippedCallCount()`로 이 절감 효과를 숫자로 확인할 수 있고, 23장에서 전용 튜토리얼로 깊이 다룹니다.

이 캐시가 필요한 하드웨어 이유는 명확합니다. `OMSetBlendState`, `RSSetState` 같은 호출은 GPU 명령 버퍼에 상태 변경 기록을 추가하는데, 드라이버는 호출마다 **상태 검증, 중복 체크, 커맨드 인코딩**을 수행합니다. 수천 개의 드로우콜이 있는 게임에서는 이것이 CPU 병목이 될 수 있으므로, "바꿔도 같은 값이면 호출 자체를 줄이는" 것이 곧 GPU 파이프라인을 밀리지 않게 하는 최적화입니다. 다만 이 캐시가 실제 D3D 상태와 어긋나면(예: BeginFrame이 원시 컨텍스트를 직접 만졌다면) 그 후 바인딩 호출이 생략되어 **화면이 이상하게 그려지는** 사고가 나므로, 프레임 시작 시 `InvalidateCache()`로 캐시를 비우는 것이 필수 규칙이 됩니다.

## 7. 핵심 규칙 요약

| 규칙 | 내용 |
|---|---|
| 4대 상태 객체 | Rasterizer / Blend / DepthStencil / Sampler |
| 교체 방법 | `context.SetRasterizerState(&rs)`처럼 **포인터 하나**로 교체 |
| 생성 인자 | `Initialize(&device, CullMode, FillMode)` / `Initialize(&device, BlendMode)` / `Initialize(&device, DepthMode)` |
| 플라이웨이트 | 같은 설정 조합은 **하나의 상태 객체를 재사용** → 상태 전환 부담 감소 |
| Finalize | 상태 객체는 자체 Finalize가 있으나 튜토리얼은 ComPtr 소멸자에 맡김 (메시/셰이더만 명시 호출) |
| InvalidateCache | BeginFrame이 원시 상태를 건드린 뒤 반드시 호출 |
| v2 → v3 | `device.SetWireframe(true)` 스위치 함수 → 객체 교체 방식 |
| 메시 인덱스 | 시계방향 `{0,1,2},{0,2,3}` 6개, `Mesh::Initialize`에 인덱스까지 전달 |

이 표는 앞으로도 계속 참고하게 됩니다. 특히 "포인터 하나로 교체"가 왜 가능한지, 그리고 상태 객체가 값(불변 데이터)으로 존재하는 이유가 23장(스테이트 캐시)에서 숫자로 확인됩니다. 지금은 4개의 상태 객체가 무엇을 담당하는지 큰 그림만 잡으면 18~19장에서 각각을 세부 조절할 때 훨씬 수월합니다.
