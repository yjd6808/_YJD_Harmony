# 그래픽 리소스 소유권 정리 (Device 단일화 + Mesh/Material 키 참조 + 불변 Material)

- 날짜: 2026-09-25
- 상태: 계획 (미구현, 코드 변경 없음)
- 사전 확인: 본 문서 작성 전 실측 코드 대조 완료. 아래 [검증된 현행] 항목은 실제 파일 내용이다.
- 확인 필요: 수정 대상 파일이 5개를 초과하므로 구현 착수 전 별도 승인 필요 (프로젝트 Constraints 2).

## 0. 검증된 현행 (전제)

- `g_cDevice`는 `GraphicDevice` 자체 싱글톤이 아니다. `Application.h:158-160`에서 `sgf::__sSgfApplication->GetDevice()` 매크로이며 실체는 `Application.h:138`의 멤버 `GraphicDevice device_`다.
- `GraphicDevice::Get()` Meyers 싱글톤이 별도로 존재한다 (`GraphicDevice.h:43`, `GraphicDevice.cpp:35-39`). 호출부는 검색 기준 0건이다. 즉 디바이스 인스턴스가 둘 존재할 수 있는 구조다.
- 저수준 생성 함수는 전부 `GraphicDevice*`를 받는다. `Buffers.h:33,58,79`, `Material.h:47`, `Mesh.h:65`, `RenderTarget.h:49,53`, `PipelineState.h:35,61,78,95`, `Texture.h:45,51,57`, `ShaderProgram.h:46,49,81,82`.
- `ResourceMgr::Initialize(GraphicDevice*)`가 `pDevice_`를 보관한다 (`ResourceMgr.h:51,57`). `CreateMaterial`/`MaterialDesc`는 존재하지 않는다 (검색 0건).
- `GameObject`는 기본 Mesh를 `new`하지 않는다. `pMesh_ = nullptr` 빌림이며, 낭비는 `GameObject.cpp:29`의 `pMaterial_(dbg_new Material())` + 객체당 상수버퍼 1개다. 소멸자는 `JC_DELETE_SAFE(pMaterial_)` (`GameObject.cpp:54`).
- `GetMaterial()`은 가변 `Material*` 반환 (`GameObject.h:99`)이며 `Shape3D.cpp:54-58`이 셰이더 키 지정 + `SetBaseColor` + `Initialize`를 직접 수행한다.
- `DrawMesh` 체인은 raw 포인터 전달이다. `Scene.h:79`, `Scene2D.h:71`, `Renderer2D.h:90`, `Scene3D.h:39`.
- `RemoveChild`는 분리만 하며 삭제하지 않는다 (`GameObject.h:59` 주석 "분리 (delete 안 함)"). `RemoveAllChildren` (`GameObject.cpp:102-108`)은 `RemoveChild`를 반복 호출하므로 자식을 `delete`하지 않는다. 부모 소유 주석과 불일치한다.

## 1. GraphicDevice 단일화 + 파라미터 정책

### 1-1. `GraphicDevice::Get()` 제거 (둘 중 하나 제거)

왜: 실제 디바이스(`Application::device_`)와 미사용 싱글톤(`Get()`의 static)이 공존하면 "디바이스는 하나"라는 원칙이 코드로 강제되지 않는다. 사용 구조상 `Application::device_`가 실물이므로 `Get()` 제거가 자연스럽다.

변경 전 (`GraphicDevice.h`):

```cpp
static GraphicDevice& Get(); // 잘 알려진 기본 인스턴스 (Meyers static, 지연 초기화 없음)
```

변경 후 (`GraphicDevice.h`):

```cpp
// 삭제. 디바이스 단일 실체는 Application::device_이며 전역 접근은 g_cDevice 매크로로만 수행한다.
```

변경 전 (`GraphicDevice.cpp`):

```cpp

{
    static GraphicDevice s_instance;
    return s_instance;
}
```

변경 후 (`GraphicDevice.cpp`):

```cpp

```

설명: 삭제 전 `GraphicDevice::Get(` 전체 검색으로 호출부 0건을 재확인한다. 호출부가 생기면 해당 호출부를 `g_cDevice` 또는 주입된 참조로 교체한 뒤 삭제한다. 삭제 후 빌드 1회로 잔존 참조를 확정한다.

### 1-2. 저수준 생성 함수는 파라미터 유지, `*`에서 `&`로 전환

왜: "어떤 디바이스에서 리소스를 만들 것인가"는 명시적 입력이어야 한다. `g_cDevice`로 바꾸면 Application 초기화 전/종료 중 사용 불가, 단위 테스트용 WARP 디바이스 주입 불가, `Application.h` 암묵 의존이 생긴다. `nullptr`가 정상 입력이 아니므로 참조가 적합하다.

적용 대상:

- `VertexBuffer::Create`, `IndexBuffer::Create`, `ConstantBuffer<T>::Create`
- `Texture::LoadFromFile/LoadFromSvgFile/CreateFromMemory`
- `VertexShader/PixelShader::InitializeFromSource/InitializeFromFile`
- `Mesh::Initialize` (+ `InitializeAsXXX` 팩토리군은 `Initialize`에 전달용으로 유지)
- `RenderTarget::Create/CreateDepthOnly`
- `RasterizerState/BlendState/DepthStencilState/SamplerState::Initialize`

### 1-3. 수명 결합 객체의 초기화 주입은 유지

대상: `ResourceMgr::Initialize`, `GraphicContext::InitializeImmediate/InitializeDeferred(/Initialize)`, `BatchRenderer::Initialize`(+ `Renderer2D/3D`継承), `Window::CreateSurface`, `Scene::SetDevice` 주입부.

변경 없음. 최초 1회 주입받아 멤버에 보관하는 구조를 유지한다. 이들까지 `g_cDevice`로 바꾸면 수명 관계가 코드에서 보이지 않게 된다.

### 1-4. `ResourceMgr` 내부 헬퍼의 `_pDevice` 반복 전달 제거 (보관된 의존 사용)

왜: `ResourceMgr`는 이미 `pDevice_`를 보관하므로 내부 헬퍼마다 디바이스를 인자로 받을 필요가 없다. 단, 이는 `g_cDevice` 사용이 아니라 소유 계층의 보관 의존 사용이다.

### 1-5. `g_cDevice` 허용 범위

- 허용: Application 메인 루프(`BeginFrame`/`Present`), 앱 종료 `Finalize`, 튜토리얼·샘플·앱 전용 디버그 도구, 디바이스 단일 정책이 확정된 게임 편의 코드.
- 금지: D3D 래퍼·버퍼·텍스처·셰이더·`Mesh::Initialize` 등 저수준 생성 경로, `ResourceMgr`/`Renderer`/`Context` 내부.
- `GameObject`는 디바이스를 몰라도 되게 변경한다 (§2와 연동. `GameObject::Initialize(GraphicDevice*)`의 Material 초기화 로직 삭제가 최종 형태).

## 2. Mesh/Material의 ResourceMgr 소유 + GameObject 키 참조

### 2-1. `GameObject` 필드를 raw 포인터에서 리소스 키로 전환

왜: "ResourceMgr 소유를 빌린다"면 빌린 포인터 무효화 문제까지 해결해야 한다. 현재 `Mesh*` 보관은 `ResourceMgr::Remove/RemoveAll` 이후 댕글링이 될 수 있다. `_u64` 키+세대 검사는 `ResourceMgr::Find<T>`가 이미 제공한다. 공유 디폴트 오염 방지를 위해 가변 접근도 차단한다.

...

...

### 2-2. 미지정 Material의 렌더 시점 기본값 해석

왜: 생성 시 기본 키를 넣지 않아도 `SetMesh`만으로 그려지게 한다. 2D/3D 선택은 생성 시점이 아니라 메시 포맷이 확정되는 렌더 시점에 가능하다.

변경 전 (`GameObject.cpp::RenderSelf`):

```cpp
if (pMesh_ == nullptr || pScene_ == nullptr)
{
    return;
}
...
pScene_->DrawMesh(pMesh_, pMaterial_, world);
```

변경 후:

```cpp
void GameObject::RenderSelf()
{
    const Mesh* pMesh = g_cResourceMgr.Find<Mesh>(meshKey_);
    if (pMesh == nullptr || pScene_ == nullptr)
    {
        return;
    }
    const mat4& world = (staticLevel_ == StaticLevel::slStatic)
        ? staticWorld_
        : pTransform_->GetWorldMatrix();
    pScene_->DrawMesh(pMesh, ResolveMaterial(*pMesh), world);
}

const Material* GameObject::ResolveMaterial(const Mesh& _mesh) const
{
    if (materialKey_ != INVALID_RESOURCE_KEY)
    {
        return g_cResourceMgr.Find<Material>(materialKey_);
    }
    return _mesh.Is2D()
        ? g_cResourceMgr.GetDefaultMaterial2D()
        : g_cResourceMgr.GetDefaultMaterial3D();
}
```

설명: `GameObject::Initialize`의 `pMaterial_->Initialize(_pDevice)` 블록은 삭제한다. 디바이스를 몰라도 되는 상태가 된다. `DrawMesh` 체인(`Scene/Renderer`)의 인자는 `const Mesh*`/`const Material*`로 변경한다(§2-4와 함께 적용).

### 2-3. `MaterialDesc` + `ResourceMgr::CreateMaterial` 도입 (불변 Material 생성)

왜: `Material::Create()`가 raw 포인터를 반환하면 누가 `Add`하고 실패 시 누가 삭제하는지 모호해진다. 생성·등록·소유권 인수를 한 함수에서 끝낸다.

변경 전: `MaterialDesc` 없음, `ResourceMgr::CreateMaterial` 없음. 사용처는 `Shape3D.cpp:54-58`처럼 직접 변이한다.

### 2-5. 동적 색상은 Material이 아니라 개체별 tint로 분리

왜: 고정 색상(빨강/파랑 프리셋, 재질 테마)과 실시간 색상(피격 점멸, 페이드, HP 변화)은 수명이 다르다. 후자까지 `CreateMaterial`로 만들면 색 변경마다 리소스 폭증이다.

원칙:

- 고정 특성 → `MaterialDesc::baseColor_`
- 개체별 실시간 색상 → `GameObject` tint 또는 `RenderInstanceData`, 최종색 `material.baseColor * instance.tint`

변경 전 (`Renderer2D::DrawMesh` 일부 개념): 머티리얼 상수만으로 색 결정.

변경 후 (체인 전체, 예시):

```cpp
// Scene / Renderer 시그니처에 tint 추가
void DrawMesh(const Mesh* _pMesh, const Material* _pMaterial, const mat4& _world, const color& _tint = color::WHITE);
```

설명: 1차 범위에서는 시그니처에 기본 인자를 두어 기존 호출부를 깨지 않게 한다. `Renderer3D::Draw`는 `Bind` 후 b1(월드)과 함께 tint를 b2에 합성 업로드한다. `Renderer2D::DrawMesh`는 기존 `materialCb_` 갱신 위치에 `baseColor * tint`를 넣는다. 기존 `SetBaseColor` 사용처를 고정/동적으로 먼저 분류한 뒤, 동적 사용처만 tint 경로로 이전한다.

### 2-6. 자식 소유권 불일치 수정

왜: 주석상 부모 소유이나 `RemoveAllChildren`이 삭제하지 않아 누수 가능성이 있다.

변경 전 (`GameObject.cpp`):

```cpp
void GameObject::RemoveChild(GameObject* _pChild)
{
    _pChild->Leave();
    // 리스트에서 분리만 (delete 안 함)
}

void GameObject::RemoveAllChildren()
{
    while (children_.Size() > 0)
    {
        RemoveChild(children_.Last()->pObject_);
    }
}
```

변경 후:

```cpp
void GameObject::RemoveChild(GameObject* _pChild);   // 분리 후 호출자에게 소유권 반환 (delete 안 함)
void GameObject::DestroyChild(GameObject* _pChild);  // 분리 + delete
void GameObject::RemoveAllChildren();                // 모든 자식 delete
```

설명: 소멸자에서 `RemoveAllChildren` 호출 시 자식이 실제로 해제되는지 단위 경로로 확인한다. `Scene.cpp:30,35`의 `root_.RemoveChild/RemoveAllChildren` 호출부가 분리/파괴 중 어느 의미인지 함께 확정한다.

## 5. 미결정 사항 (구현 전 확정 필요)

- 기존 `SetMesh(Mesh*)` raw 포인터 API의 유지 여부. 유지 시 키 역조회(`FindKeyByPointer`)가 필요하므로 삭제를 권장.
- `MaterialDesc` 인터닝 캐시 포함 여부와 해시 범위 (셰이더+상태+텍스처+색상 전체 vs 상태 제외).
- tint 전달 위치: `DrawMesh` 인자 vs `RenderObject`/`RenderInstanceData` 구조체 확장.
- `GraphicContext::Initialize` 하위 호환 래퍼의 삭제 여부 (본 변경과 무관하므로 별도 처리 권장).
