# TCHAR 바인딩 Phase B — jc 경계 감사

- 작성일: 2026-09-08
- 선행: M7 (B안 채택), 1차 char 별칭 이관 완료, Phase A (wchar 수치) 완료
- 이 문서의 용도: Phase C (프로젝트별 별칭 뒤집기) 실행 전 필수 판정표. 코드 수정 없음.

## 1. 규칙 (M7 확정)

- 모듈 안(같은 TU 집합): `const String&` 하나로. A/W 구분 금지.
- 모듈 밖(정적 lib 경계·직렬화·네트워크·파일 포맷): 명시 타입만. `AString`(char, 현 동작 유지) 또는 `WString`(wchar).
- `String`은 경계 헤더에 두지 않는다. 불일치는 컴파일 에러로 난다 (wchar↔char 암묵 변환 없음).

## 2. 핵심 기술 판단

- `BasicString<char, SSO>`와 `BasicString<wchar_t, SSO>`는 둘 다 24B 동일 레이아웃이다.
  위험은 레이아웃이 아니라 **해석**이다. 같은 메모리를 한쪽은 char, 한쪽은 wchar로 읽으면
  조용히 깨진다. 함수 시그니처 불일치는 링커가 잡아주지만(맹글링 상이),
  공유 구조체 멤버의 내용물 해석은 잡아주지 않는다. 그래서 구조체 멤버도 전부 판정 대상이다.
- `StringView`는 char 버퍼 전용으로 남는다. `StringView(const String&)` 생성자는
  `StringView(const AString&)`으로 고정한다 (wchar 바인딩 시 char 버퍼와 섞이면 안 됨).
- `StringConvert.h`는 이미 explicit 설계라 변경 없음. 경계 exemplar로 유지한다.
- `SyncHttpTransport::ToWide(const String&)`는 narrow→wide 변환이라
  파라미터를 `AString`으로 명시해야 한다 (뒤집힌 TU에서 wchar로 읽히면 UTF-8 해석이 깨짐).

## 3. 별칭 정의 위치 (Phase C에서 추가)

```cpp
// String.h (허브)
#ifdef _UNICODE
using TChar = wchar_t;   // windows.h 없이 빌드 매크로만 사용
#else
using TChar = char;
#endif
using String = BasicString<TChar, StringImpl_SSO<TChar>>;
using AString = BasicString<char, StringImpl_SSO<char>>;  // 경계용, 항상 유효
// WString은 StringImpl_SSO.h에 이미 있음
```

## 5. Phase C 실행 절차 (프로젝트별 원자 단위)

1. 해당 프로젝트에 `TChar` 바인딩 별칭 적용 (jc는 빌드 문자셋 그대로. 코드 변경 아님).
2. 컴파일 → 에러가 나는 곳이 정확히 고칠 곳이다 (`""` 리터럴, 서식 문자열, String 멤버 구조체).
3. 리터럴은 `_T()`로 감싼다. 서식 문자열(`"%d"` 등)도 같은 패스에 처리한다.
4. 위 판정표의 [B] 항목을 AString/WString으로 명시한다 (jc는 감사 완료. 하위는 프로젝트별 반복).
5. 빌드 + 전체 테스트. `String=="..."` 비교 테스트가 해석 일치를 증명한다.

순서 원칙: `_T()`를 먼저 까는 것은 금지다 (Unicode TU에서 wchar 리터럴이 char-String에 안 붙는다).
별칭 뒤집기와 같은 단위로만 움직인다. jc → 하위 의존성 순 (이관 때와 동일).

## 6. 가드레일 (영구)

- public 헤더 단독 `String` 사용 금지 CI grep (판정표 [B] 대조).
- 경계 exported 클래스는 `static_assert(sizeof)` (이전에 합의. 레이아웃은 동일하지만 해석 변경 검출용).
- `StringView`는 영원히 char 전용. wchar 뷰가 필요해지면 별도 설계 (이번 범위 밖).

## 7. 재분류 (Harmony 내부 전제, 2026-09-08)

전제: Harmony 프로젝트 간 모듈 이동 + UNICODE 지원 모듈은 문제없다.
근거 3개: (1) 순수 함수 시그니처 불일치는 링커가 시끄럽게 잡는다 (맹글링 상이).
(2) 템플릿은 TU별 인스턴스화 + 맹글링 격리로 조용히 섞이지 않는다.
(3) 프로세스/네트워크 경계(sgs_*, jnetr_*)는 직렬화 바이트라 문자셋과 무관하다.
Unicode 모듈 자체도 로컬 인스턴스화라 문제없다.

### 7.1 해소 — 손댈 필요 없음 (링커·컴파일러가 잡거나, 바이트 경계)

- 순수 함수 시그니처 전부 (#1 CMessage 메서드, #6 IOEngine, #7 File/Directory/Path 함수,
  #8 Http 함수, #10 Logger 함수, #13 Time, #15 Stream, #17 Time, #20 WinApi).
  불일치하면 링크 에러로 드러나니 그때 AString으로 명시한다.
- 템플릿 전부 (DataMap 기본 인자, HashMap/TreeMap/Vector<String>, Properties).
  단, 기본 인자의 String 철자는 AString으로 바꾸지 않는다. 이유: 명시해도 되고 안 해도
  동작이 같고(맹글링 격리), 바꾸면 diff만 늘어난다. 공유 객체 실체가 charset을
  넘나드는 경우만 §7.2로 승격한다.
- 프로세스 경계 모듈 전부 (sgs_*, jnetr_*). 와이어는 바이트다.
- 주석 (#18). `#19 한글 리터럴`은 제외 — 아래 미해소로 승격.
- Unicode 모듈 자체의 로컬 사용 전부.

### 7.2 미해소 — 선제 수정 필요 (조용히 깨짐)

A. 공유 concrete 구조체의 String 멤버 (in-memory 공유. 동일 레이아웃 다른 해석.
   링커가 못 잡는다):
   - #6 IOJob.uri_, IOTypes.uri_/baseAlias_
   - #7 PathResolver 멤버군 (fullPath_/matchedDir_/alias_/defaultAlias_ 등)
   - #8 HttpHeaders.headers_ (TreeMap 멤버 실체)
   - #14 Uri 멤버군 (raw_/host_/path_/query_/fileName_)
   - #5 Env 정적 멤버 (프로세스 전역 singleton 저장소)
   - FileDest/FileSource path_ 멤버, Logger/Thread/Pool/ConsoleMenuItem 이름 멤버
     (객체가 charset 다른 TU를 넘나드는 것. 최악 garbled이지 크래시는 아님. 그래도 명시)
   - #2 DataMap의 String 위치 (키/값 해석 일치. 기본 인자 포함)
   - #4 Property 시스템 Ty 매핑 (데이터 모델 태그)
   - 처방: 전부 AString. 공유되는 저장소는 char 바이트로 고정한다.

B. narrow 전제가 코드에 박힌 곳 (단독 TU에서도 깨짐. 모듈 전제와 무관):
   - #9 `ToWide(const String&)` 파라미터 → AString (UTF-8 디코딩 전제)
   - #13 `StringView(const String&)` 생성자 → AString (char 버퍼 전용)
   - #19 한글 리터럴 멤버 초기화 → AString (UTF-8 바이트 보존)
   - #1 CMessage 와이어 의미 → AString 선제 (WriteString이 Length()를 바이트 길이로
     쓰기 때문에 wchar가 들어오면 프로토콜이 깨진다. 링크 에러를 기다리지 않는다)
   - #12 StaticString 상호변환점 → AString (char 고정 버퍼와 섞임 방지)

C. 판단 보류 (Phase C에서 첫 빌드 에러 보고 결정):
   - `String(0)` / `= nullptr` 관용구 (BasicString에서 동작은 하나 의미가 empty로 바뀜.
     Null 분기가 뒤에 있으면 별도 심사)
   - `Capacity()` off-by-one에 의존한 코드 (NUL 포함 여부. 현재 전수에 없음. 나오면 그때)
