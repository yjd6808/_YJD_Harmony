# 계획: jc::String 구현 후보 성능 비교 및 재설계 (SSO / StringImpl / TLS Pool)

## 날짜
2026-09-05

## 작업 이름
String-구현-후보-성능비교-설계

## 요청 요약
- `Projects/jc/Sources/jc/Primitives/String.h` 현행 구조를 분석하고, 아래 대화에서 나온 설계 방향을 정리한다.
  - `std::string`은 인코딩을 결정하지 않는 "바이트 컨테이너"이며, jc::String도 **UTF-8 바이트 컨테이너**로 명시하고 Windows API 경계에서만 UTF-16(`W` API)으로 변환한다.
  - `String`을 **8바이트 `pCtx_` 하나**로 유지하는 설계(`String → StringImpl*`)의 단점(`new StringImpl`)을 `thread_local` ObjectPool + `StringImpl` 내부 SSO로 완화한다.
  - cross-thread 소멸, owner 스레드 종료 후 소멸 등 TLS Pool의 함정과 해결책(owner 비교 → TLS 반환 / global fallback, 프로세스 lifetime Pool Storage, deferred free queue)을 정리한다.
- **대화에 등장한 모든 String 구현 방식을 `jc_gbench`에서 동일 시나리오로 성능 측정**하여 최종 구조를 데이터로 결정한다.

## 1. 현행 String.h 분석

### 1-1. 구조

```cpp
class String final
{
    char* pBuffer_{};   // 8
    int   len_{};       // 4
    int   capacity_{};  // 4   → sizeof(String) == 16
};
```

- 버퍼는 항상 힙(`dbg_new char[]`)에 있으며, SSO(Small String Optimization)가 없다.
- `pBuffer_ == nullptr`인 **Null 상태**와 `len_ == 0`인 **Empty 상태**가 별도로 존재한다 (`String::Null`, `String::Empty`).
- `DEFAULT_BUFFER_SIZE = 32`, `EXPANDING_FACTOR = 2`.

### 1-2. 현재 확인된 문제점 (String.cpp 기준)

| # | 위치 | 문제 | 영향 |
|---|---|---|---|
| P1 | `String(const char*, int _capacity)` | `expectedCapacity = length * 2` → 문자 100개 문자열이 200바이트를 할당 | 상시 2배 메모리 과할당 |
| P2 | `String(const String&)` | `String(_str.pBuffer_)`로 위임 → `strlen` 재계산 + P1의 2배 과할당. 원본 `len_`/`capacity_`를 전혀 활용하지 않음 | 복사 비용 O(n) 2회(strlen + copy), 내부 NUL 포함 문자열 복사 불가 |
| P3 | `Resize()` | `StringUtil::Copy(strlen 기반)`로 복사 | 내부 NUL 미지원, 불필요한 strlen |
| P4 | `Format()` | `vsnprintf(nullptr,0,...)` 후 같은 `va_list`를 `va_copy` 없이 재사용 | UB (MSVC x64는 우연히 동작) |
| P5 | `String()` 기본 생성자 | Null 상태로 시작 → `operator=` 템플릿 등에서 `Initialize()` 분기 필요, `Source()`가 nullptr 반환 가능 | 호출부마다 `SafeSource()` 분기 |
| P6 | `char& operator[](int) const` | const 메서드가 non-const 참조 반환 | const 안전성 붕괴 |
| P7 | `template <T> operator=` / `operator+` | 임의 T를 `std::to_string`으로 변환 | 의도치 않은 암시 변환 허용 |
| P8 | `int len_` | 2GB 제한, 부호 비교 혼재 | 실사용에선 문제 없음. 설계 재검토 항목 |
| P9 | 인코딩 | 인코딩 개념이 클래스에 없음. `sgf`는 이미 "jc::String은 UTF-8 narrow"로 사용 중(2026-08-22 계획) | `A` API에 그대로 넘기면 ACP(CP949 등)로 해석되어 인도어/이모지 깨짐 |
| P10 | `Source()` / `ExchangeSource()` / `SetLength()` / `GetRangeUnsafe()` | 내부 버퍼를 외부에 직접 노출 (`Source()` 427곳, `SetLength` 17곳, `ExchangeSource` 9곳, `GetRangeUnsafe` 6곳) | SSO 도입 시 포인터 안정성(move 후 dangling) 및 `ExchangeSource`(외부 `new[]` 버퍼 인수) 의미 재정의 필요 |
| P11 | `friend class StringUtil` | `StringUtil.cpp`에서 `pBuffer_`, `len_` 직접 대입 (265, 294~295행) | 내부 표현이 바뀌면 StringUtil 동시 수정 필수 |

> 결론: 현행 구조는 "학습용 operator 클래스"에서 출발했으므로, **할당 정책(P1~P3)** 과 **인코딩 정책(P9)**, **내부 노출(P10~P11)** 세 축을 이번 재설계 범위로 잡는다.

## 2. 설계 방향

### 2-1. 인코딩 정책 (대화 1부)

- `jc::String`은 **UTF-8 바이트 시퀀스를 담는 컨테이너**로 명시한다. `char`는 바이트일 뿐이며 인코딩은 String이 결정하지 않는다.
- 리터럴은 `u8"..."` 또는 컴파일 옵션 `/utf-8` (MSVC) 로 소스 인코딩을 UTF-8로 고정한다. → `Projects/*/Project/*.vcxproj` 에 `/utf-8` 추가 여부는 별도 계획.
- 경계 규칙

```
프로그램 내부           : jc::String (UTF-8)
        ↓
Windows API 호출 시     : StringUtil::Utf8ToWide → std::wstring / WideString (UTF-16)
        ↓
                          xxxW()
```

- `A` API는 현재 ACP(한국: CP949, 인도: 1252/UTF-8 등 환경 의존)로 `char*`를 해석하므로 **jc 내부에서 A API 직접 호출 금지**. 기존 `StringUtil::ToUtf8(const wchar_t*)` 짝으로 `ToWide(const String&)`를 정식 API로 추가한다.
- API 네이밍 정리: `Length()`는 **바이트 길이**임을 문서화하고, 필요 시 `CodePointCount()`를 별도 제공한다 (SSO/Impl 설계와 독립, 후속 작업).

### 2-2. 메모리/레이아웃 후보 (대화 2부 — 성능 테스트 대상)

대화에 등장한 구조를 전부 후보로 등록한다. 후보 코드는 **jc 본체를 건드리지 않고 `jc_gbench` 안에 실험용 헤더로 구현**하고, 벤치마크 결과로 채택안을 고른 뒤 `jc/Primitives/String`으로 이관한다.

| ID | 이름 | 레이아웃 | `sizeof` | 짧은 문자열 힙 할당 | 스레드 고려 |
|---|---|---|---|---|---|
| **S0** | `StringCurrent` (Baseline) | `char* / int len / int cap`, 항상 힙 | 16 | 1회 (32B~) | 없음 |
| **S1** | `StringSso` | `union { heap{ptr,cap}; char sso[23]; } + len`, std::string 스타일 | 24 | 0회 (≤ 23B) | 없음 |
| **S2** | `StringCtx` | `StringImpl* pCtx_` 하나. `StringImpl{ char* buf; len; cap }`을 `new/delete` | 8 | 2회 (Impl + buf) | 없음 |
| **S3** | `StringCtxTls` | S2 + `thread_local ObjectPool<StringImpl>` (같은 스레드 Acquire/Release만 가정) | 8 | 1회 (buf) + pool | same-thread only |
| **S4** | `StringCtxTlsSso` | S3 + `StringImpl` 내부 SSO 버퍼 (`Impl` 64B 슬롯: header 16B + sso 48B) | 8 | 0회 (pool만) | same-thread only |
| **S5** | `StringCtxTlsSsoXThread` | S4 + owner 비교: 같은 스레드 → TLS pool 반환, 다른 스레드 → **global fallback(`delete`)** | 8 | 0회 | cross-thread 안전 |
| **S6** | `StringCtxTlsSsoDeferred` | S4 + 다른 스레드 → **owner의 deferred free queue** 에 push, owner가 `ProcessDeferredFrees()` | 8 | 0회 | cross-thread 안전, owner 종료 시 처리 필요 |
| **S7** | `StringCtxPoolStorage` | S4 + Pool 실체를 **프로세스 lifetime Pool Storage**에 두고 TLS엔 포인터만. owner 스레드 종료 후에도 반환 가능 | 8 | 0회 | cross-thread + owner 종료 안전 |
| **R1** | `std::string` (MSVC) | 참조군 | 32 | 0회 (≤ 15B) | 없음 |
| **R2** | `std::string` + `thread_local` 없음 / `std::pmr::string` (선택) | 참조군 | 32 | - | - |

> S5/S6/S7은 "cross-thread Release 처리 방식"만 다르고 hot path(같은 스레드 생성/소멸)는 S4와 동일해야 한다. 벤치마크에서 이 가정이 실제로 성립하는지(owner 비교 비용, atomic/branch 비용) 확인하는 것이 핵심이다.

### 2-2-1. 후보별 장단점

#### S0. `StringCurrent` — 현행 (`char* / int len / int cap`, 항상 힙)

| 장점 | 단점 |
|---|---|
| 구조가 가장 단순, 디버깅 용이 (natvis 없이도 버퍼가 바로 보임) | 문자 1개마다도 힙 할당 1회. 임시 객체 연쇄(`a + b + c`)에서 할당 폭발 |
| `Source()` 포인터가 Resize 전까지 안정 | `length * 2` 과할당(P1), 복사 시 strlen 재계산(P2) — 구조 자체보다 구현 결함이 큼 |
| 스레드 정책 불필요 (힙 allocator가 이미 스레드 안전) | Null/Empty 이중 상태로 호출부 분기 증가 |
| sizeof 16B로 작음 | 메모리 단편화: 짧은 문자열 수만 개가 개별 힙 블록 |

→ **역할**: 벤치마크 baseline. P1~P4를 고친 "S0-fixed"도 같이 측정해 구조 변경 효과와 버그 수정 효과를 분리한다.

#### S1. `StringSso` — inline SSO (`union { heap; sso[23] } + len`, 24B)

| 장점 | 단점 |
|---|---|
| ≤ 23B 문자열은 힙 할당 0회. 엔진의 이름·키·태그 대부분이 여기 들어감 | `sizeof` 24B로 현행보다 8B 커짐 (확장하려는 32B는 std::string과 동일) |
| 간접 참조 없음 → 컨테이너에서 캐시 지역성 최고, 해시/비교가 객체 자체에서 완결 | **move 시 문자열 바이트를 복사**해야 함 (SSO 상태는 포인터 스와프 불가) → move가 공짜가 아님 |
| 스레드 정책·owner 개념 불필요. 구현·유지보수 부담 가장 낮음 | `Source()` 반환 포인터가 **move/swap 후 dangling** (std::string과 동일한 약속이지만 현재 코드 427곳 점검 필요) |
| std::string / EASTL과 같은 검증된 구조 | union + 플래그 분기가 모든 접근에 들어감 (`isHeap ? ptr : sso`) — 분기 예측이 잘 되어 실측 비용은 작음 |
| 디버깅 쉬움 (natvis 1개로 완결) | SSO 경계(23B) 바로 위의 문자열은 힙으로 넘어가 성능 클리프가 생김 |

→ **적합**: 범용 문자열, 컨테이너 키, 이름. **부적합**: `Source()` 주소를 오래 보관하는 코드.

#### S2. `StringCtx` — `StringImpl*` 8B, Impl은 `new/delete`

| 장점 | 단점 |
|---|---|
| `sizeof(String) == 8`. 구조체/컨테이너 안에서 포인터 하나 크기 | **모든 생성에 힙 할당 2회** (Impl + 버퍼). S0보다 나쁨 |
| move = 포인터 복사 1회, 진짜 공짜 | 모든 접근에 간접 참조 1회 추가 (컨테이너 순회 시 Impl이 메모리 여기저기 흩어짐 → 캐시 미스) |
| Impl 주소가 String 수명 동안 고정 → `Source()` 포인터가 move 후에도 유효 | Impl을 헤더로 노출하지 않으면 디버거에서 문자열이 안 보임 (natvis 필수) |
| 구현 상세(SSO, COW, 인터닝)를 Impl 뒤에 숨길 수 있어 ABI 안정 | Empty 상태에도 Impl이 필요 → `pCtx_ == nullptr`을 Empty로 쓰는 lazy 처리가 없으면 기본 생성자도 할당 |

→ **역할**: "8B 핸들 설계의 순수 바닥". 단독 채택 대상이 아니라 S3~S7이 얼마나 개선하는지 측정하는 기준점.

#### S3. `StringCtxTls` — S2 + `thread_local` free-list pool (same-thread 가정)

| 장점 | 단점 |
|---|---|
| Impl 할당이 pool pop/push → 힙 할당 1회로 감소, mutex/atomic 없음 | **cross-thread 소멸 시 다른 스레드 pool에 반환 → 오동작** (설계상 금지사항이지 컴파일러가 막지 못함) |
| 같은 스레드에서 생성/소멸되는 임시 문자열에 이상적 (Format, operator+) | owner 스레드 종료 시 pool이 파괴되면 살아있는 Impl이 dangling |
| 스레드마다 릭 탐지·통계 가능 (ThreadLocal.h 작성 동기와 동일) | pool에 쌓인 free 슬롯이 다른 스레드에서 재사용 불가 → 스레드 수만큼 메모리 중복 보유 |
| | 문자열 버퍼는 여전히 힙 → 짧은 문자열에도 할당 1회는 남음 |

→ **역할**: TLS pool 효과만 고립해 측정. 엔진 채택은 불가 (정확성 요구 미달).

#### S4. `StringCtxTlsSso` — S3 + Impl 내부 SSO (64B 슬롯)

| 장점 | 단점 |
|---|---|
| ≤ ~44B 문자열은 **힙 할당 0회, pool pop 1회**로 끝. SSO 용량이 S1(23B)보다 크다 | Impl 64B를 문자열마다 소모 → 1글자 문자열도 64B + 8B. S1(24B)보다 메모리 3배 |
| Impl이 pool chunk에 연속 배치되므로 S2보다 간접 참조 캐시 효율이 낫기는 함 | 그래도 간접 참조는 존재. `Vector<String>` 정렬 시 문자열 비교마다 다른 캐시라인 |
| move 공짜 + `Source()` 주소 안정 (S1의 약점 해소) | S3의 cross-thread/owner 종료 문제 그대로 있음 |
| "8B String + 할당 0회" 라는 대화의 목표를 가장 직접적으로 달성 | SSO가 Impl 안에 있으므로 "SSO인데도 포인터를 타야 문자에 도달" — SSO의 지역성 이점 절반 상실 |

→ **역할**: S5~S7의 공통 hot path. S1과의 B1/B9/B10 대결이 이 벤치의 핵심 질문.

#### S5. `StringCtxTlsSsoXThread` — S4 + owner 비교, 다른 스레드는 global fallback

| 장점 | 단점 |
|---|---|
| cross-thread 소멸·owner 종료 후 소멸 모두 **안전** (fallback은 pool을 전혀 안 건드림) | Impl에 `ownerThreadId` 4B + 출처 플래그 추가, `Release`에 `GetThreadId()` 호출(TLS 읽기) + 분기 1회 |
| S6/S7 대비 구현이 가장 단순. 큐·락·lifetime 관리 없음 | **pool chunk 슬롯은 `delete` 불가** → 슬롯을 개별 할당(S5')하거나 chunk 참조카운트가 필요. S5'는 pool의 "연속 배치" 이점을 잃음 |
| cross-thread가 드문 게임 엔진 패턴(네트워크 → 게임 스레드)에 잘 맞음 | cross-thread 소멸된 슬롯은 owner pool로 돌아가지 않음 → producer 스레드 pool이 계속 새 슬롯을 할당 (지속적 producer→consumer 패턴에서 pool 효과 사라짐) |
| 스레드 종료 시 free-list만 버리면 끝 | |

→ **적합**: "가장 현실적인 타협점"(대화 결론). Impl 계열을 채택한다면 1순위 후보.

#### S6. `StringCtxTlsSsoDeferred` — S4 + owner의 deferred free queue

| 장점 | 단점 |
|---|---|
| cross-thread 소멸 슬롯이 **owner pool로 복귀** → 지속적 producer→consumer에서도 pool 효과 유지 (S5의 단점 해소) | owner가 **주기적으로 `ProcessDeferredFrees()`를 호출**해야 함 → 프레임 마다 호출점을 엔진에 박아야 하고, 바쁜 스레드는 큐가 쌓인다 |
| hot path(같은 스레드)는 S4와 동일 | MPSC 큐가 필요 (atomic push). cross-thread 소멸 비용은 S5의 delete보다 싸지만 자체 복잡도 있음 |
| | **owner 종료 후 push는 dangling** (큐가 owner pool 안에 있으므로). `alive` 플래그 읽기 자체가 위험 → **S7 Pool Storage 없이는 단독 성립 불가** |
| | 메모리 해제가 지연되어 피크 메모리 증가, 릭 탐지 시점이 흐릿해짐 |

→ **역할**: S7 위에서만 유효한 최적화 옵션. B12에서 S5와 차이가 작으면 폐기.

#### S7. `StringCtxPoolStorage` — Pool 실체를 프로세스 lifetime에, TLS에는 포인터만

| 장점 | 단점 |
|---|---|
| owner 스레드가 종료돼도 pool이 살아있어 **모든 슬롯이 항상 원래 pool로 복귀**. dangling 시나리오 자체가 없음 | **구현 복잡도 최고**: Pool Storage 싱글턴, 스레드 attach/detach, shared push 경로(lock-free 혹은 SpinLock), 프로세스 종료 시 정리 순서 |
| S6의 deferred queue를 안전하게 얹을 수 있는 유일한 기반 | 스레드가 자주 생성/소멸되는 환경(작업 스레드, 에셋 로딩)에서는 죽은 스레드의 pool이 Storage에 누적 → pool 재사용(스레드 ID 재배정) 또는 GC 정책 필요 |
| 개별 pool 통계/릭 탐지를 중앙에서 일괄 조회 가능 | shared push가 필요하며 이 경로는 락/atomic이 들어가 "동기화 제로"라는 TLS pool의 원래 매력이 부분적으로 후퇴 |
| hot path는 S4와 동일 (TLS 포인터 한 번 더 읽음) | 정적 소멸 순서 문제: 전역 `String` 객체가 Storage보다 늦게 소멸되면 충돌 → Storage를 leak-on-exit로 두는 등 별도 처리 |

→ **역할**: 가장 "올바른" 구조지만 문자열 하나 위해 엔진에 lifetime 관리 계층이 하나 더 생김. 비용 대비 효과가 S5보다 확실히 낫지 않으면 버리고, 이 패턴은 jnet 객체 pool에서 다시 검토.

### 2-3. StringImpl 스케치 (S4~S7 공통)

```cpp
struct StringImpl                     // 64B 슬롯 (cache line 1개)
{
    // ---- header (16B) ----
    char*   pHeap_;                   // SSO 사용 중이면 nullptr
    _u32    len_;
    _u32    cap_     : 31;
    _u32    isHeap_  : 1;
    // ---- owner 정보 (S5~S7) ----
    _u32    ownerThreadId_;           // Thread::GetThreadId()
    ImplPool* pOwnerPool_;            // S7: Pool Storage 내 포인터 (프로세스 lifetime)
    // ---- SSO ----
    char    sso_[SSO_CAPACITY];       // 64 - header 크기, 40~48B

    char*       Data()       { return isHeap_ ? pHeap_ : sso_; }
    const char* Data() const { return isHeap_ ? pHeap_ : sso_; }
};

class String final
{
    StringImpl* pCtx_;                // sizeof(String) == 8
};
```

- 문자열 버퍼(`pHeap_`)는 TLS pool이 아닌 **일반 allocator**(`Memory::Allocate` / `CDefaultAllocator`)에서 받는다. Pool은 `StringImpl` 슬롯만 담당한다(대화 권고).
- 짧은 문자열: pool Acquire 1회로 끝. 긴 문자열: pool Acquire 1회 + heap 1회.

### 2-4. Release 경로 (S5 ~ S7)

```cpp
void StringImplPool::Release(StringImpl* p)
{
    if (p->isHeap_) Memory::Deallocate(p->pHeap_);   // 문자열 버퍼는 항상 일반 allocator

    if (p->ownerThreadId_ == Thread::GetThreadId())
    {
        tls_Pool.Push(p);                             // S3~S7 공통 hot path
        return;
    }

    // ---- cross-thread ----
#if   STRATEGY == S5
    GlobalFallback::Free(p);                          // pool 슬롯이 아닌 별도 경로로 해제 (placement new 된 슬롯을 delete 하면 안 됨 → 슬롯 출처 플래그 필요)
#elif STRATEGY == S6
    p->pOwnerPool_->deferredQueue_.Push(p);           // owner가 주기적으로 ProcessDeferredFrees()
#elif STRATEGY == S7
    p->pOwnerPool_->PushShared(p);                    // Pool Storage는 프로세스 lifetime → owner 종료 후에도 유효. lock-free 또는 SpinLock
#endif
}
```

- **원칙**: "Thread가 종료됐다고 해서 그 Thread가 만든 객체를 다른 Thread가 쓸 수 없게 만들면 안 된다." TLS pool은 **소유 메모리가 아니라 빠른 재사용을 위한 캐시**로 취급한다.
- 스레드 종료 시: 해당 TLS pool의 **free-list만** 정리하고, 살아있는 `StringImpl`은 건드리지 않는다.
  - S5: 살아있는 객체는 나중에 소멸 시 owner ≠ current → global fallback으로 처리. 단, 슬롯이 pool chunk 내부라면 `delete` 불가 → **chunk 단위 참조 카운트**(chunk의 live 슬롯이 0이 될 때 chunk 해제) 또는 **S5' = pool 슬롯을 개별 `Memory::Allocate`로 발급**(pool은 free-list만 캐시)로 해결. 벤치마크에서는 S5'(개별 할당 + free-list 캐시)로 구현하여 단순화한다.
  - S6: owner가 종료되면 deferred queue를 비울 주체가 없음 → 종료 시 queue를 global fallback으로 flush 하고, 이후 push는 `pOwnerPool_->alive == false` 확인 후 fallback. `alive` 접근 자체가 dangling 위험 → **S7 구조(Pool Storage)가 전제되어야 안전**. 즉 S6은 S7 위에서만 성립.
  - S7: Pool Storage(`Process lifetime`) 가 모든 `ImplPool`을 소유. TLS에는 `thread_local ImplPool* tls_pPool` 만 둔다. 스레드 종료 시 `tls_pPool->DetachThread()`(free-list 유지, 이후 반환은 shared path). 프로세스 종료 시 Storage 일괄 정리.

### 2-5. 기존 API 호환 방침 (P10, P11)

| API | 방침 |
|---|---|
| `Source()` / `SafeSource()` | 유지. 단 "move/Resize 이후 포인터 무효" 를 문서화. SSO에서는 `sso_` 주소를 반환하므로 `String` 이동 시에도 `pCtx_` 자체가 이동해 **주소는 유지**됨(S2~S7 장점, S1 단점) |
| `ExchangeSource(char*, int)` | 외부 `new[]` 버퍼를 인수. Impl 계열에서는 `pHeap_`으로 수용 가능. S1은 SSO 크기 이하일 때 복사 후 delete 처리 |
| `SetLength(int)` | 유지 (cap 이내 assert) |
| `GetRangeUnsafe()` | `Tuple<char*,int,int>` 반환 유지, 내부에서 `Memory::Allocate` 사용 |
| `IsNull()` / `String::Null` | **폐기 검토**. Impl 계열에서 `pCtx_ == nullptr`을 Null로 매핑할 수 있으나, 기본 생성자에서 pool Acquire 비용이 발생. 벤치마크 시나리오 B1(빈 문자열 생성/소멸)에서 "기본 생성 시 lazy acquire" vs "즉시 acquire" 두 변형을 측정해 결정 |
| `friend StringUtil` | `pBuffer_`/`len_` 직접 대입 2곳을 `ExchangeSource` / `SetLength` 경유로 교체 후 friend 제거 |
| `char& operator[]() const` | `const char& operator[]() const` + non-const 오버로드로 분리 (P6) |
| `Format()` | `va_copy` 적용 (P4) — 구조와 무관, 선행 수정 |

### 3-3. 시나리오 매트릭스

각 시나리오는 `template <typename TString> static void BM_xxx(State&)` 로 작성하고, 후보별로 `BENCHMARK_TEMPLATE(BM_xxx, StringSso)->Arg(len)` 등록한다.

| B2 | `CopyConstruct` × 데이터셋 | P2(strlen 재계산) 개선 확인 | S1/S4 |

## 7. 리스크 및 비고

- **간접 참조 비용**: `pCtx_` 8B 설계는 모든 접근에 포인터 추적 1회가 추가된다. 컨테이너 시나리오(B9/B10)에서 S1(inline SSO)에 밀릴 가능성이 있으며, 이 경우 "String은 24B inline SSO, StringImpl 계열은 폐기"가 데이터에 기반한 결론일 수 있다. 벤치 설계 단계에서 이 결론도 열어둔다.
- **pool 슬롯 `delete` 금지**: placement new 된 chunk 슬롯을 `delete` 하면 안 되므로 S5의 fallback은 반드시 슬롯 출처를 구분해야 한다(§2-4). 벤치에서는 S5'(슬롯 개별 할당 + free-list 캐시)로 구현하고, 이 단순화가 성능에 미치는 영향을 S7과 비교한다.
- **Deferred queue(S6)의 전제**: owner 종료 후 `pOwnerPool_->alive` 접근이 dangling이 될 수 있어 S7 Pool Storage 없이는 성립하지 않는다. S6 단독은 "S7 위의 최적화 옵션"으로 취급한다.
- **Null 상태 폐기**: `String::Null`, `IsNull()` 사용처를 grep 하여 Phase 7 이관 시 결정. 기본 생성자 pool Acquire 비용(B1 Empty)이 크면 lazy acquire(`pCtx_ == nullptr` = Empty) 유지.
- **`Source()` 427곳**: 시그니처는 유지되므로 컴파일 영향은 없으나, S1 채택 시 move 이후 dangling 가능성을 코드 리뷰로 점검해야 한다. Impl 계열은 이 리스크가 없다는 점이 B9/B10 열화를 감수할 근거가 될 수 있다.
- **Debug 빌드**: `dbg_new`/CRT 메모리 추적과 pool이 겹치면 릭 리포트가 왜곡된다. pool chunk는 프로세스 종료 시 `AtExit` 로 명시 해제해 `_CrtDumpMemoryLeaks` 오탐을 막는다.
- **인코딩 작업은 구조 작업과 독립**: `u8` 리터럴/`/utf-8`/`W` API 전환은 어떤 후보를 채택해도 동일하게 적용 가능하므로 Phase 8로 분리한다.
- **StrForBench 복사본과 원본의 drift**: 벤치 기간 중 누군가 `jc::String` 을 수정하면 `s0` 가 더 이상 baseline 이 아니다. Phase 2 의 “R0 ≈ S0” 검증을 각 Phase 시작마다 반복하고, 어긋나면 `s0` 를 재복사한다.
- **`.inl` 반복 include 방식의 빌드 비용**: 전략 8개 × `String.cpp` 1383줄이 헤더로 들어가 `StringBench_*.cpp` 마다 인스턴스화된다. 컴파일 시간이 문제가 되면 (a) 벤치 중인 전략만 `Core.h` 매크로로 include 하거나, (b) 전략 하나씩 빌드하는 방식(§3-1 대안 3)으로 후퇴한다.
- **`StringUtil` friend 경로 누락**: `StringUtil.cpp:265, 294-295` 처럼 `String` 내부를 직접 만지는 코드는 복사본에서 컴파일이 깨지는 것으로 즉시 드러난다. 조용히 동작이 바뀌는 쪽이 아니라 빌드 실패 쪽이므로 안전하다.

## 8. 사전 권장안 (벤치마크 전 가설 — 액션 RPG 자체 엔진 기준)

벤치마크로 확정하되, 검증할 가설은 미리 적어둔다. 판단 기준은 "게임 엔진에서 String이 실제로 어떻게 쓰이는가"이다.

### 8-1. 엔진에서 String의 실제 사용 패턴

| 용도 | 빈도 | 특징 |
|---|---|---|
| 에셋 경로, 셔이더 소스, 설정 파싱 | 로딩 시점 | 길고(>32B) 생성 횟수 적음. 구조보다 파싱 버퍼 재사용이 중요 |
| GameObject/Component/Bone/Animation 이름 | 프레임별 조회 | 짧고(8~24B) 매우 많음. **문자열 비교가 아니라 해시 비교가 있어야 하는 곳** |
| 디버그/로거/프로파일러 Format | 프레임별 다수 | 임시 객체 생성/소멸 폭발. B1/B6/B7 시나리오가 여기 해당 |
| UI 텍스트 (데미지 숫자, 체업 등) | 프레임별 | 짧음. UTF-8 → 글립 매핑이 본질, String 구조 영향 작음 |
| 네트워크 패킷 내 문자열 (채팅, 닉네임) | 이벤트성 | I/O 스레드에서 생성 → 게임 스레드에서 소멸. **B12 cross-thread가 실제로 발생하는 유일한 곳** |

즉, 엔진 hot path에서는 "짧은 문자열의 생성/소멸/복사"과 "이름 조회"가 지배적이고, cross-thread 이동은 네트워크/로딩 경계에서만 드물게 일어난다.

### 8-2. 권장안

**1순위: S1 (inline SSO, 24B) 를 기본 `jc::String`으로 채택**

- 이유
  - 짧은 이름이 대다수이므로 SSO 하나만으로 힙 할당이 거의 사라진다. 이 시점에서 pool의 추가 이득은 "heap 0회 → pool 1회"가 아니라 "heap 0회 → heap 0회"라 없다.
  - 간접 참조가 없어 `Vector<String>`, `HashMap<String, T>` 순회/해시/복사에서 캐시 지역성이 가장 좋다(B9/B10). 엔진에서 문자열은 단독보다 컨테이너 안에 있는 경우가 압도적이다.
  - 스레드 정책이 필요 없다. owner 스레드, deferred queue, Pool Storage lifetime 같은 **엔진 전체에 영구적으로 남는 복잡도**를 문자열 계열에 넘기지 않는다.
  - EASTL `basic_string`, MSVC/libc++ `std::string`, Godot `String`(COW 별도) 등 검증된 구현이 같은 선택을 했다. Unreal `FString`은 SSO가 없고 대신 `FName`(인턴 이름)으로 hot path를 보완한다 — 아래 3순위 항목과 동일한 시각.
- 포이터 안정성(move 후 `Source()` dangling)은 `std::string`과 같은 약속으로 문서화하고 감수한다.

**2순위: S5 (pCtx_ 8B + TLS pool + Impl SSO + cross-thread fallback) — 조건부 채택**

- 아래 동시 만족 시에만 S1 대신 채택한다.
  1. B1 Tiny/Mid, B6 (임시 객체 연쇄)에서 S1 대비 **2배 이상** 빠름
  2. B9/B10 (컨테이너)에서 S1 대비 **10% 이내** 열화
  3. B11 8스레드에서 선형 스케일, B12 cross-thread 비용이 B1의 3배 이내
- 현실적으로는 1은 만족해도 2에서 실패할 가능성이 높다고 본다. 단, **8B 필드가 Component/ECS 데이터 레이아웃에서 결정적**(예: 64B 정렬 구조체에 이름을 박아야 하는 경우)이라면 그 자리는 아래 `StringId`가 맞고 String이 아니다.

**3순위(가장 효과 큰 보완): `StringId` / `Name` 타입 별도 도입 (이 문서 범위 밖, 후속 계획)**

- 4B/8B 해시(기존 `Hasher` Fnv1a) + 전역 인턴 테이블. 비교 = 정수 비교, 복사 = POD.
- GameObject/Bone/Animation/Material 이름, 이벤트 이름 등 "조회용 이름"은 전부 이 타입으로. `String`은 "사람이 읽는 문자열"로 역할을 좍힐다.
- `pCtx_` 8B 설계가 노릸 "작은 핸들 하나로 문자열을 들고 다니기"는 이 타입이 간접 참조·스레드 문제 없이 더 잘 달성한다.

### 8-3. TLS Pool 아이디어의 올바른 적용 지점

대화에서 나온 `thread_local` ObjectPool + owner fallback 설계는 버릴 것이 아니다. String보다 **네트워크 패킷/메시지 객체, 이벤트, 임시 커맨드** 처림 "크기가 고정이고, 항상 힙에 있어야 하고, 생산 스레드와 소버 스레드가 다른 객체"에 맞다(jnet 측). 이 벤치의 `StringImplPool.h`는 그대로 `jc/Pool/ThreadLocalObjectPool.h`로 일반화해 재사용할 수 있도록 구현한다.

### 8-4. 가설 요약

| 질문 | 가설 | 검증 시나리오 |
|---|---|---|
| SSO가 있으면 pool이 추가로 주는 이득이 있는가? | Tiny/Mid에서는 거의 없음 (S1 ≈ S4) | B1, B6 |
| 8B 간접 참조가 컨테이너에서 얼마나 손해인가? | 20~40% 열화 (S4 < S1) | B9, B10 |
| cross-thread 비용이 게임 엔진에서 의미 있는가? | 발생 빈도가 낮아 S5의 단순 fallback이면 충분, S6/S7은 과설계 | B12, B13 |
| 현행 S0 대비 개선 폭은? | Tiny 생성/소멸 5~10배, 복사 2~3배 (P1/P2 개선 포함) | B1, B2, B14 |

이 가설이 맞는다면 최종 구성은 **`jc::String` = S1** + **`jc::StringId`(별도)** + **TLS pool은 jnet 객체에 적용**이다. 틀리다면(특히 B9/B10에서 S4가 S1과 동률이라면) S5로 가는 것이 맞고, 그 경우 8B 핸들의 포인터 안정성이 덤으로 따라온다.
