## 1. 현황 진단 — 두 개의 소유자, 두 개의 키 체계

### 1.1 소유 구조 비교

| 구분 | GraphicDevice (`GraphicDevice.h:104`~`113`) | ResourceMgr (`ResourceMgr.h:139`~`142`) |
|------|---------------------------------------------|------------------------------------------|
| 보관 | `Vector<VertexShader*>` 등 타입별 Vector | `HashMap<_u64, IResource*> resources_` 단일 맵 |
| 키 | `_u32` index = Vector 위치 (`INVALID_HANDLE = 0xFFFFFFFF`, `GraphicDevice.h:26`) | `_u64` 발급키 (`INVALID_RESOURCE_KEY = 0`, `IResource.h:55`), `Provider<IdProviderReuse<_u64>>` 발급 |
| 생성 | `CreateVertexShader()` 등 내부 `new`+`PushBack` 후 즉시 `context_.Set*()` (`GraphicDevice.cpp:236`~`293`) | `Add(IResource*)` 에서 `keyProvider_.Acquire()`→`SetKey()`→`Insert` (`ResourceMgr.cpp:156`~`166`) |
| 수명 | `Finalize()`에서 역순 `delete` (`GraphicDevice.cpp:68`~`118`) | `Remove()`/`RemoveAll()`/`Finalize()`에서 `delete`+`Release()` (`ResourceMgr.cpp:184`~`222`) |
| 중복 방지 | 없음 | `pathIndex_` 로 경로 중복 로드 방지 (`ResourceMgr.cpp:169`~`181`) |
| 디폴트 보호 | 없음 | `defaultKeys_` HashSet 으로 제거 금지 (`ResourceMgr.cpp:186`~`189`) |
| 조회 | `Resolve*(_u32)` O(1) 인덱스 (`GraphicDevice.cpp:396`~`443`) | `Find(_u64)` HashMap 조회 + `Find<T>()` 타입 검증 (`ResourceMgr.h:75`~`83`) |

```
현재:
  Caller → GraphicDevice.CreateTexture() → _u32 handle → GraphicContext.SetTexture(slot, _u32)
  Caller → ResourceMgr.LoadTextureFromFile() → _u64 key → Material.SetTextureKey(slot, _u64) → Bind 시 Find(_u64)

문제: Texture가 두 곳에 중복 보관될 수 있음. handle vs key 혼용, 소유자 불명확, path 중복 방지 사각지대.
```

### 1.2 핵심 문제 3가지

1. **네임스페이스 충돌** — Device의 `_u32`는 타입별로 0부터 재시작된다. `handle=0`이 VertexShader 0번이자 Texture 0번일 수 있다. 크로스 타입 실수가 컴파일/런타임에 걸리지 않는다. ResourceMgr의 `_u64`는 전역 단일 공간이지만 현재 `ResourceType` 태그는 조회 시에만 검사되고 키 자체에는 인코딩되어 있지 않다 (`IResource.h:58`~`62`).
2. **소유 이중화** — Device가 만든 `Texture`는 Device Vector가 소유, Mgr이 만든 `Texture`는 Mgr HashMap이 소유. `Finalize()` 순서에 따라 dangling/max leak 위험. `Material`이 보관하는 `textureKeys_`는 Mgr 키를 가정하지만 Device 핸들로 만든 텍스처는 바인딩할 수 없다.
3. **정책 불일치** — Mgr은 `IdProviderReuse`로 반납키 LIFO 재사용 (`IdProviderReuse.h:48`~`53`). Device는 재사용 없이 `PushBack`만 하며 삭제 시 구멍을 남기지 않는다 (실제 삭제는 Finalize 일괄만). 즉, Device 쪽은 영구 증가, Mgr 쪽은 재사용 — 댕글링 키가 다른 리소스를 가리킬 위험은 Mgr에만 존재한다.

## 2. 통합 목표와 원칙

### 2.1 목표

- **단일 소유자** — 모든 GPU 리소스(`Texture`, `VertexShader`, `PixelShader`, `Mesh`, `Material` 등 `IResource` 파생)의 소유권을 `ResourceMgr`로 일원화. Device는 소유하지 않는다.
- **단일 키 체계** — `_u64` UID 하나로 모든 리소스를 식별, 타입 인코딩, 전역 유일, 재사용 정책 통일.
- **파사드 유지** — `GraphicDevice`의 public API 형태(`Create*`, `BeginFrame`, `Present`, `GetOrCreateInputLayout`, `Context()`, `States()`)는 그대로 둔다. 내부 구현만 Mgr 위임으로 교체. `sgfr` 튜토리얼/외부 호출부 변경 최소화.

### 2.2 왜 "Device → Mgr" 방향인가

> 질문: “그래픽 디바이스에서 리소스 매니저에 결합되는 방향이 어떤지”

**권장: Device가 Mgr에 의존(위임)하는 방향. 역방향(Mgr가 Device를 소유)도 현재 일부 존재하지만, 저장소 위임은 Device → Mgr 가 맞다.**

- **SRP** — Device는 `ID3D11Device`/`ID3D11DeviceContext`/`SwapChain`/`DepthStencilSurface`/`RenderStates`/`InputLayoutCache`의 **수명·생성·바인딩 캐시** 책임 (`GraphicDevice.h:103`~`122`). Mgr은 **리소스 보관·키 발급·경로 중복 방지·디폴트 보호** 책임. Device가 Vector로 리소스를 보관하는 것은 SRP 위반이다.
- **의존 역전** — D3D 생성 팩토리는 Device에 있어야 하므로 `ResourceMgr::Initialize(GraphicDevice*)` 처럼 Mgr이 Device를 아는 것은 자연스럽다 (`ResourceMgr.h:47`). 반면 리소스 보관은 Mgr이 전문이므로 Device의 생성 함수가 Mgr에 위임하는 것이 자연스럽다. 순환 의존을 끊으려면 **Device의 생성 경로는 Mgr을 호출, Mgr의 생성 경로는 Device의 D3D 팩토리를 호출**로 역할 경계를 명확히 한다.
- **마이그레이션 안정성** — Device 파사드를 유지한 채 내부만 교체하면 `GraphicContext::SetVertexBuffer(_u32)` 같은 기존 핸들 경로를 `SetVertexBuffer(_u64)`로 점진 이관할 수 있다. 역방향으로 Device 저장소를 그대로 두면 통합 효과가 없다.

정리하면:

```
이상적 의존:
  GraphicDevice --생성 위임--> ResourceMgr --D3D 생성--> GraphicDevice::Device()
                <--소유 조회--                  (Device는 D3D Device만 제공)
  GraphicContext --Resolve--> ResourceMgr.Find()  (Device.Resolve* 는 deprecated 경로로 유지 후 제거)
```

## 3. UID 설계 — 상의 2바이트에 resType을 심는 안의 평가

### 3.1 제안 원안

```cpp
resTexture      = 0x0001
resVertexShader = 0x0002
resPixelShader  = 0x0003
resMaterial     = 0x0004
resMesh         = 0x0005
// ...
_u64 key = (resType << 48) | sequence; // 상의 2바이트 = type, 하의 6바이트 = per-type sequence
```

장점:
- 키만 보고 타입 판별 가능 — `Find<T>()`의 HashMap 조회 전 빠른 타입 필터, `PrintStatus()` 디버깅 용이, 직렬화/로그 가독성 높음.
- 타입별 공간 분리 — 키 충돌 원천 방지, per-type 카운터로 디버깅 통계 분리.

단점/주의 (원안 그대로 쓰면 생기는 문제):
1. **baseOffset 없는 IdProvider** — 현재 `IdProvider`/`IdProviderReuse`는 `next_ = INVALID_KEY+1 (=1)` 고정 시작 (`IdProvider.h:32`~`33`, `IdProviderReuse.h:36`~`37`). 타입별 오프셋을 줄 방법이 없다. 제안하신 “IdProvider에서 baseOffset 지정 기능”이 반드시 선행되어야 한다.
2. **단일 Provider로는 타입 인코딩 불가** — 하나의 전역 Provider가 `1,2,3...`을 발급하면 상위 비트에 타입을 OR 할 수 없다. 타입별로 Provider를 나눠야 한다 (아래 5장).
3. **재사용 시 상위 비트 보존 필요** — `IdProviderReuse`의 `freeList_`에 저장된 키가 이미 타입 비트를 포함하고 있어야 재발급 시에도 타입이 유지된다. `Release()`/`Acquire()`가 상위 비트를 제거하지 않도록 해야 한다.
4. **48비트 sequence는 사실상 무한** — 초당 1억 개 생성해도 89년. `_u64` 고갈 걱정은 없음. 다만 `0`은 `INVALID_RESOURCE_KEY`로 예약이므로 per-type 0번은 건너뛰어야 한다.

**결론: 원안 방향은 옳다. 다만 “단일 Provider + 상위 비트 OR”가 아니라 “타입별 Provider + baseOffset”으로 구현해야 한다.**

### 3.2 개선안 — 3가지 레이아웃 비교

| 안 | 레이아웃 | 예시 | 장점 | 단점 |
|----|----------|------|------|------|
| **A. 원안 개선 (추천)** | `[type 16][seq 48]` | `0x0001_0000_0000_0001` | 단순, 최대 65k 타입, 타입당 281조 개, 구현 최소 | generation 없음 — ABA 탐지 불가 |
| **B. Generation 포함** | `[type 16][gen 8][index 40]` 또는 `[type 8][gen 8][index 48]` | `type=1, gen=2, index=1` | 재사용된 키가 이전 핸들과 충돌해도 gen으로 감지 가능 (댕글링 포인터 방어) | 40비트 index도 충분하지만 설계 복잡도↑, 기존 HashMap 기반에선 효과 제한 |
| **C. Strong Handle** | `struct ResourceHandle { _u32 index; _u32 gen; ResourceType type; }` → `_u64` pack | 타입+gen+index 모두 인코딩, 배열 인덱스로 O(1) 조회 | 가장 안전, 디버깅 최적, ECS 스타일 | Mgr를 HashMap에서 `Vector`+`freeList` 기반 dense 배열로 전면 교체 필요 — 변경 범위 큼 |

**권장: 단기 A, 중장기 C.**  
A는 현재 `HashMap<_u64,IResource*>` 구조를 유지하면서 최소 변경으로 타입 TAG를 얻는다. C는 성능·안전 최상이지만 Mgr 내부를 배열 기반으로 재설계해야 하므로 2단계로 진행한다.

### 3.3 타입 ID 할당

`IResource.h:28`~`39`의 `ResourceType` enum을 그대로 쓴다.

```cpp
enum class ResourceType : _u16 {
    rtUnknown = 0,
    rtTexture = 0x0001,
    rtMaterial = 0x0002,
    rtMesh = 0x0003,
    rtVertexShader = 0x0004,
    rtPixelShader = 0x0005,
    rtRenderTarget = 0x0006,
    rtSpriteAnimationClip = 0x0007,
    // 0x0008~0xFFFF 예약
    Max,
};
static_assert((int)ResourceType::Max < 0xFFFF, "type overflow");
constexpr _u64 RESOURCE_TYPE_SHIFT = 48;
constexpr _u64 RESOURCE_TYPE_MASK  = 0xFFFFULL << RESOURCE_TYPE_SHIFT;
constexpr _u64 RESOURCE_SEQ_MASK   = 0x0000FFFFFFFFFFFFULL;
inline ResourceType GetResourceTypeFromKey(_u64 _key) { return ResourceType((_key >> RESOURCE_TYPE_SHIFT) & 0xFFFF); }
inline _u64 MakeKey(ResourceType _type, _u64 _seq) { return ( (_u64)_type << RESOURCE_TYPE_SHIFT) | (_seq & RESOURCE_SEQ_MASK); }
inline bool IsValidKey(_u64 _key) { return _key != INVALID_RESOURCE_KEY; }
```

- `rtUnknown=0`은 `INVALID_RESOURCE_KEY=0`과 자연스럽게 대응.
- `rtMax`까지 8개 타입뿐이므로 16비트 중 3비트만 쓰고 나머지는 예약 — 향후 확장 여지 큼.

## 4. IdProvider 확장 — baseOffset

### 4.1 현재 문제

```cpp
// IdProvider.h:32
next_(TProvider::INVALID_KEY + 1) // 항상 1
// IdProviderReuse.h:36 동일
```

타입별 시작점을 다르게 할 수 없다.

### 4.2 확장 설계 (최소 변경)

```cpp
// IIdProvider.h:26 - INVALID_KEY 유지

// IdProvider.h / IdProviderReuse.h 공통
template <typename TKey>
class IdProvider final : public IIdProvider<TKey> {
public:
    explicit IdProvider(TKey _baseOffset = TProvider::INVALID_KEY + 1)
        : next_(_baseOffset), base_(_baseOffset), acquiredCount_(0) {}
    void Reset() override { next_ = base_; acquiredCount_ = 0; /*Reuse는 freeList_.Clear()*/ }
    // Acquire/Release 동일하되 Acquire 시 next_++ 가 base 영역 내에서만 증가
private:
    TKey next_;
    TKey base_; // 추가
    _sz acquiredCount_;
};

// Provider.h: Provider<T>도 동일하게 baseOffset 전달
template <typename T>
class Provider final : public IIdProvider<...> {
public:
    explicit Provider(TKeyType _base = IIdProvider<TKeyType>::INVALID_KEY + 1)
        : policy_(_base) {}
};
```

`IdProviderReuse`는 동일하게 `base_`를 보관하고, `Release()` 시 들어온 키가 `base_` 이상이고 `next_` 미만인지 검증하는 assert를 추가한다.

> 대안: `baseOffset` 대신 `SetBaseOffset()` setter를 두는 방법도 있으나 생성자 주입이 불변성·스레드 안전에 유리하다. `Reset()`이 base로 복귀해야 하므로 setter는 Reset 이후 재설정 혼란을 야기한다.

### 4.3 타입별 Provider 보유

```cpp
// ResourceMgr.h:142 개선안
// AS-IS: Provider<IdProviderReuse<_u64>> keyProvider_;
// TO-BE:
static constexpr _s32 RESOURCE_TYPE_COUNT = static_cast<_s32>(ResourceType::Max);
Provider<IdProviderReuse<_u64>> keyProviders_[RESOURCE_TYPE_COUNT];

// 초기화 예:
ResourceMgr::ResourceMgr() {
    for (_s32 i = 0; i < RESOURCE_TYPE_COUNT; ++i) {
        // 각 타입의 base = (typeId << 48) + 1
        _u64 base = (static_cast<_u64>(i) << RESOURCE_TYPE_SHIFT) + 1;
        // placement new 또는 별도 Init 필요 — Provider가 base 생성자를 지원하면 가능
        keyProviders_[i] = Provider<IdProviderReuse<_u64>>(base);
    }
}
```

또는 `jc::Vector` 대신 `std::array`로 고정.

발급 시:

```cpp
_u64 ResourceMgr::AcquireKey(ResourceType _type) {
    _s32 idx = static_cast<_s32>(_type);
    jc_assert(idx > 0 && idx < RESOURCE_TYPE_COUNT);
    return keyProviders_[idx].Acquire(); // 이미 type 비트 포함된 키 반환
}
```

`IdProviderReuse`의 freeList 재사용도 같은 type 영역 내에서만 일어나므로 타입 오염 없음.

## 5. 통합 아키텍처 — 3안 비교와 권장안

### 5.1 안 1: 완전 위임 (권장)

**Device는 생성 팩토리 + D3D 소유자, Mgr은 보관·수명 소유자. Device의 Vector 저장소 삭제.**

```
GraphicDevice.CreateTexture(...) {
    Texture* pTex = dbg_new Texture;
    if (!pTex->CreateFromMemory(Device(), ...)) { delete pTex; return INVALID_RESOURCE_KEY; }
    _u64 key = g_cResourceMgr.Add(pTex); // Mgr이 키 발급·보관
    Context().SetTexture(0, key); // _u64 오버로드
    return key;
}
GraphicDevice.ResolveTexture(_u64 _key) {
    return g_cResourceMgr.Find<Texture>(_key); // 위임
}
// GraphicDevice.h:109~113 Vector들 제거, inputLayoutCache_, pDevice_, context_, states_, swapChain_, depthSurface_만 남김
```

- **Facade 유지** — `GraphicDevice::Create*` 시그니처는 반환 타입만 `_u32`→`_u64`로 변경 (또는 오버로드로 점진). 외부에서는 여전히 `GraphicDevice::Get().CreateTexture(...)`로 호출.
- **Context 변경** — `GraphicContext::SetTexture(_u32 _slot, _u64 _key)` 오버로드 추가, 내부에서 `g_cResourceMgr.Find<Texture>(_key)`로 resolve 후 기존 `SetTexture(ShaderStage,slot,Texture*)` 호출. 기존 `_u32` 오버로드는 deprecated로 유지 후 제거.
- **Finalize** — Device는 Vector 삭제 코드(`GraphicDevice.cpp:88`~`117`)를 제거하고 `context_.ClearState()` → `inputLayoutCache_.Clear()` → `depthSurface/swapChain/context/states/pDevice` 해제만 수행. 리소스 해제는 `ResourceMgr::Finalize()`가 전담.

### 5.2 안 2: Mgr이 Device 저장소를 흡수 (비권장)

Device Vector를 Mgr 내부로 이동시키고 Device는 Mgr을 소유(`unique_ptr<ResourceMgr>`). Device가 Mgr의 수명을 관리.  
단점: Mgr이 싱글톤 `g_cResourceMgr`으로 이미 전역 접근되고 있어 소유 관계가 꼬인다. Device Finalize 순서에 Mgr 수명이 묶여 테스트·툴에서 Device 없이 Mgr만 쓰는 케이스가 깨진다.

### 5.3 안 3: 변환 레이어 (과도기)

Device의 `_u32` 핸들과 Mgr의 `_u64` 키를 병존시키고 `HashMap<_u64,_u32>` + `HashMap<_u32,_u64>` 변환 테이블을 둔다.  
단점: 이중 관리가 그대로 남고 변환 비용·동기화 버그가 추가된다. 임시 방편으로는 유용하나 최종안으로는 부적합.

## 6. 세부 설계 — UID 발급 흐름

```cpp
// ResourceMgr.cpp — Add 개선
_u64 ResourceMgr::Add(IResource* _pResource) {
    jc_assert(pDevice_ != nullptr);
    jc_assert(_pResource->GetKey() == INVALID_RESOURCE_KEY);
    ResourceType type = _pResource->GetResourceType();
    jc_assert(type != ResourceType::rtUnknown);
    _u64 key = keyProviders_[static_cast<_s32>(type)].Acquire(); // 이미 (type<<48)|seq
    // 안전망: 상위 비트가 type과 일치하는지 검증
    jc_assert(GetResourceTypeFromKey(key) == type);
    static_cast<ResourceBase*>(_pResource)->SetKey(key);
    resources_.Insert(key, _pResource);
    return key;
}

// 타입 빠른 필터 — Find<T> 최적화 (선택)
template <typename T>
T* ResourceMgr::Find(_u64 _key) {
    if (_key == INVALID_RESOURCE_KEY) return nullptr;
    if (GetResourceTypeFromKey(_key) != T::RESOURCE_TYPE) return nullptr; // HashMap 조회 전 탈락
    auto* pp = resources_.Find(_key);
    if (!pp) return nullptr;
    // 추가 검증: 실제 객체 타입과도 일치해야 함 (위조 키 방어)
    if ((*pp)->GetResourceType() != T::RESOURCE_TYPE) return nullptr;
    return static_cast<T*>(*pp);
}
```

`Remove()`는 타입 추출 후 해당 provider에 `Release(key)`:

```cpp
bool ResourceMgr::Remove(_u64 _key) {
    if (defaultKeys_.Exist(_key)) { jc_assert(false); return false; }
    auto* pp = resources_.Find(_key);
    if (!pp) return false;
    ResourceType type = GetResourceTypeFromKey(_key);
    // 방어: 키의 타입과 객체 타입이 다르면 위조 키
    jc_assert((*pp)->GetResourceType() == type);
    RemovePathEntry(_key);
    delete *pp;
    resources_.Remove(_key);
    keyProviders_[static_cast<_s32>(type)].Release(_key);
    return true;
}
```

`PrintStatus()`는 키에서 타입을 뽑아 `RESOURCE_TYPE_NAMES`와 교차 검증 가능.

## 8. 대안 심층 검토 — 더 좋은 방법이 있는가

### 8.1 Generation 기반 Handle (C안)

```
_u64 = [type 8][gen 8][index 32][unused 16]
```

- `index`는 dense 배열 인덱스, `gen`은 재사용 시 증가. `Find()` 시 `slots[index].gen == key.gen` 검증으로 ABA 완전 방어.
- 장점: `Vector` 인덱스로 O(1) 조회, HashMap 불필요, 캐시 친화.
- 단점: Mgr를 `HashMap`에서 `Vector<Slot>`로 전면 교체, 모든 리소스 조회 코드 변경, 마이그레이션 비용 큼.
- **판정: 장기적으로 가장 우수하나 현 단계에서는 과투자.** A안으로 통합 후, 프로파일링에서 HashMap 조회가 병목으로 확인되면 C안으로 2차 리팩토링을 권장.

### 8.2 Type-Erased 단일 Provider + OR

```cpp
_u64 seq = singleProvider.Acquire(); // 1,2,3...
_u64 key = (type << 48) | seq;
Release(key & SEQ_MASK); // 타입 비트 제거 후 반납
```

- 장점: Provider 1개만 있으면 됨.
- 단점: seq가 타입과 무관하게 증가하므로 타입당 발급량이 불균형해도 시퀀스가 공유되어 디버깅 통계 분리 불가. 재사용 시 seq만 반납되므로 타입 비트가 freeList에 남지 않아 재발급 시 타입 재조합이 필요 — 구현이 더 복잡하고 실수 여지 큼.
- **판정: 비권장. 타입별 Provider가 더 명확.**

### 8.3 Strong Typed Handle (`ResourceHandle<T>`)

```cpp
template <typename T> struct ResourceHandle { _u64 key; };
using TextureHandle = ResourceHandle<Texture>;
```

- 장점: 컴파일 타임에 `TextureHandle`을 `Mesh` 조회에 쓰는 실수를 방지.
- 단점: 기존 `_u64` API와 호환성 추가 작업, `Material`이 `textureKeys_[8]`처럼 heterogeneous 키 배열을 들고 있어 템플릿化가 번거로움.
- **판정: 선택 사항. `_u64`에 타입 비트가 있으면 런타임 검증으로 충분하며, 필요 시 별도 wrapper를 추가하는 것으로 충분.**

## 10. 위험과 대책

| 위험 | 대책 |
|------|------|
| **기존 `_u32` 핸들이 파일/직렬화에 저장된 경우** | `_u32`는 타입별 index였으므로 `_u64`로 복원 불가. 마이그레이션 시점에 저장 포맷 버전을 올리고 `_u64`로 재저장. 과도기에는 `_u32`를 읽어 `_u64`로 변환하는 어댑터 제공 |
| **IdProviderReuse의 LIFO 재사용이 댕글링 키를 다른 리소스로 연결** | 타입 비트로 1차 방어, `Find<T>()`의 타입 검증으로 2차 방어. 필요 시 `IdProvider` (재사용 없음) 로 교체 — `_u64`는 고갈 우려가 없으므로 재사용 없이도 충분하다. `ResourceMgr` 생성자에서 정책 선택 가능하도록 `Provider` 템플릿 인자를 유지 |
| **Device Finalize 순서** | `GraphicDevice::Finalize()`에서 리소스 삭제를 제거하므로 `ResourceMgr::Finalize()`가 먼저 호출되어야 한다. `Director` 또는 앱 종료 시 `g_cResourceMgr.Finalize()` → `GraphicDevice::Get().Finalize()` 순서를 강제. 역순 호출 시 `jc_assert`로 경고 |
| **멀티스레드 발급 경쟁** | 현재 싱글 스레드이므로 문제 없으나, 향후 deferred context에서 리소스 생성 시 `keyProviders_[]`에 mutex 추가 고려. 현 단계에서는 `jc_assert`로 스레드 ID 검증만 |

## 11. 결론 — 권장 조합

- **UID 레이아웃: A안 `[type 16][seq 48]`** — 원안 채택, `ResourceType` 값을 `0x0001`부터 명시.
- **IdProvider: baseOffset 생성자 추가 + 타입별 Provider 배열** — 제안하신 방향 그대로 구현.
- **통합 방향: Device → Mgr 위임 (안 1)** — Device는 파사드·D3D 소유자, Mgr은 단일 저장소·수명 소유자. Device Vector 제거.
- **Facade 유지: 오버로드 점진 이관** — `_u64` 신규 + `_u32` deprecated 병존 후 제거.
- **장기: 필요 시 C안(generation handle)으로 2차 개선** — 현 단계에서는 과도.

이 조합이 변경 범위·위험·성능·디버깅 용이성의 균형이 가장 좋다. 특히 “Device가 Mgr에 결합되는 방향”은 옳은 판단이며, 위 설계대로 Device의 생성 함수가 Mgr에 위임하도록 구현하면 파사드는 그대로 유지하면서 이중 소유 문제가 해소된다.
