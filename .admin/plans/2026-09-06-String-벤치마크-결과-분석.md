# String 구현 후보(S0~S7, R0~R1) 벤치마크 결과 분석

- 날짜: 2026-09-06
- 설계 문서: `.admin/plans/2026-09-05-String-구현-후보-성능비교-설계.md`
- 그래프 스크립트: `.admin/plans/2026-09-06-String-벤치마크-그래프.py` → `string_bench_graphs/*.png` (13장)
- 측정값: 아래 표·그래프는 모두 **CPU Time** 기준. 가로축 후보 순서 `R0, S0, S1, S2, S3, S4, S5, S6, S7, R1`.
- 선행 확인: **R0 ≈ S0** 가 전 항목에서 성립한다(오차 ±5% 이내). 즉 `StrForBench` 복사본은 원본 `jc::String` 의 충실한 baseline 이며, 이후 후보 간 차이는 전부 구조 차이에서 온 것이다.

## 1. 후보 정의 — 기존 문자열 대비 변경점

| ID | 이름 | 레이아웃 / sizeof | 기존(S0/R0) 대비 변경점 |
|---|---|---|---|
| R0 | `jc::String` 원본 (참조군) | `char* + int len + int cap`, 16B, 항상 힙 | 그 자체. `length*2` 과할당, 복사 시 `strlen` 재계산, `Null`(nullptr)과 `Empty` 이중 상태 |
| S0 | `StringCurrent` 복사본 (baseline) | R0 와 동일 16B | R0 를 `s0::StrForBench` 로 복사한 것. `friend StringUtil` 제거, 공개 API 경유로만 동작. 성능은 R0 와 동등해야 함 |
| S1 | `StringSso` (inline SSO) | `union{heap{ptr,len,cap} / sso[23]} + len`, **24B** | 22B 이하는 힙 할당 0회. 그 외 할당 정책(2배 확장)은 S0 와 동일하게 두어 레이아웃 효과만 분리. `Null` 상태 없음(항상 SSO empty). move 는 SSO 상태일 때 바이트 복사 |
| S2 | `StringCtx` (Impl 포인터, pool 없음) | `StringImpl*` **8B**. Impl `{char*,len,cap}` 는 `new/delete` | 모든 생성에 힙 할당 2회(Impl + 버퍼). move 는 포인터 교환이라 공짜. `pCtx_==nullptr` 을 Null/Empty 로 쓰는 lazy acquire. S3~S7 의 바닥 기준점 |
| S3 | `StringCtxTls` (Impl + TLS free-list) | 8B. Impl 슬롯만 TLS pool, 버퍼는 일반 힙 | S2 에서 Impl 할당 1회를 pool pop/push 로 교체. mutex/atomic 없음. **같은 스레드 생성/소멸 가정, owner 검사 없음** (cross-thread 소멸 시 오동작) |
| S4 | `StringCtxTlsSso` (pool + Impl SSO) | 8B. Impl 64B 슬롯 `{pHeap,len,cap,sso[48]}`, SSO_CAP=47 | 47B 이하는 pool pop 1회로 끝나고 힙 할당 0회. move 공짜 + `Source()` 주소 안정. S5~S7 의 공통 hot path |
| S5 | `StringCtxTlsSsoXThread` (owner 비교 + global fallback) | 8B, 64B 슬롯 `{pHeap,len,cap,owner,sso[44]}`, SSO_CAP=43 | S4 + `Release` 시 `owner == GetThreadId()` 비교. 다르면 TLS 반환 대신 `::operator delete` (S5' 단순화안: 슬롯을 chunk 가 아닌 개별 할당으로 발급). owner 종료 후 소멸 안전 |
| S6 | `StringCtxTlsSsoDeferred` (deferred queue, 명시 pump) | 8B, 64B 슬롯, SSO_CAP=43 | S4 + cross-thread 반납을 owner pool 의 inbox(mutex+vector)에 적재. owner 가 `ProcessThreadPoolDeferred()` 로 명시 drain 할 때만 회수. Acquire 시 자동 drain 없음 |
| S7 | `StringCtxPoolStorage` (Pool Storage + 자동 drain) | 8B, 64B 슬롯, SSO_CAP=43 | S6 와 같은 inbox 구조이나 pool 실체가 프로세스 lifetime Storage 에 있고 Acquire 때 자동 drain. owner 종료 후에도 반납 유효. cross-thread + owner 종료 모두 안전 |
| R1 | `std::string` 어댑터 (참조군) | MSVC 32B, SSO 15B | 검증된 표준 구현. 하한선 역할. S1 은 R1 과 적어도 동률이어야 한다는 판단 기준 |

한 줄 요약: **S0→S1 은 "힙→인라인 SSO", S0→S2 는 "값→8B 핸들+이중 할당", S2→S3 은 "Impl new→TLS pool", S3→S4 는 "버퍼 힙→Impl 내 SSO", S4→S5/S6/S7 은 "cross-thread 반납 정책 3종"** 이다. S5/S6/S7 의 같은-스레드 hot path 는 S4 와 동일해야 한다는 것이 설계 가설이며, 아래에서 깨지는 지점을 지적한다.

## 3. 후보군별 결과·원인

읽는 법: 후보군마다 전 항목 성적을 한 표에 모았다. 값은 CPU Time, 굵은 값은 해당 항목 전체 1위다. 항목별 1위 대조는 §3-7, 종합 순위는 §4 참조. 항목 번호(01~13)는 §2·그래프 번호와 동일하다.

왜: 전 항목 R0≈S0(±5%) → 복사본 충실도 검증 통과. 이후 모든 격차는 구조 탓이다. 직접 버퍼라 Append·Find·CopyAssign(/0, `delete` 후 len=0 한 방)에서는 1위권이다. 반면 임시 객체·단발 생성에서는 힙 할당 + P1(2배 과할당) + P2(복사 시 `strlen` 재계산) 때문에 Tiny 생성/복사가 S1/S4 대비 5~8배 느리고, Concat 230ns·Sort 꼴찌권이다. 역할은 baseline이며, 그 이상도 이하도 아니다.

| 06 BinarySearch (us) | 0.267 (R1 다음 2위) |
| 07 Construct /0~/6 (ns) | **6.63** / **7.15** / **13.5** / 71.1 / 106 / 1350 / 73.9 |
| 08 CopyConstruct /0~/6 (ns) | 7.11 / 4.14 / 6.98 / 57.2 / 55.8 / 120 / 55.8 |
| 09 CopyAssign /0~/6 (ns) | 7.11 / **4.14** / 6.63 / 5.86 / 5.86 / 53.0 / 5.86 |

왜: 22B 이하 할당 0회가 전부다. Tiny 생성/복사 1위, Concat 39ns(R0의 6배), CopyAssign은 SSO→SSO `memcpy`로 최상위권이다. Append는 최종 길이가 SSO를 벗어나 S0와 동률 1위이고, Format은 `vsnprintf`(약 600ns)에 가려져 동률이다. Find는 `IsHeap()` 분기 1회분(+1.3ns)만 진다. 약점은 세 가지다. (1) Sort 0.750ms는 S4(0.500ms)에 1.5배 패한다. SSO 이동이 바이트 `memcpy` 23B라 8B 포인터 교환을 못 당한다. (2) Mid(40B)부터 힙으로 추락한다(/3 71.1ns). (3) MT는 전역 힙 경합 탓에 8스레드에서도 37ns에 정체된다. CrossThread/OwnerExit는 전역 힙이라 그냥 안전하다. Empty 이상치(최초 56.2ns)는 2026-09-06 수정으로 해소되어 재측정 6.63ns·2위가 되었다(§7). 한 줄: 스레드 정책 없이 가장 단순하고, 작은 문자열에서는 최강이다.

| 항목 | S2 | S3 |
|---|---|---|
| 01 Append1B (us) | 3.53 (꼴찌) | 3.45 |
| 02 ConcatChain (ns) | 1074 (꼴찌) | 255 |
| 03 Format (ns) | 1283 (꼴찌) | 645 |
| 05 VectorSort (ms) | 0.889 (꼴찌권) | 0.795 |
| 07 Construct /0 (ns) | 105 (꼴찌) | 57.2 |
| 11 MT t1→t8 (ns) | 267 → 78.4 | 173 → 50.2 |
| 12 CrossThread (ns) | 28565 (꼴찌) | 25670 (불안전·참고값) |
| 09 CopyAssign /0 (ns) | 2.89 (유일 선방) | 5.30 |

왜: S2는 "8B 핸들의 순수 바닥"이다. 생성마다 Impl+버퍼 2회 할당이라 전 항목 꼴찌권이다. 유일한 장면 CopyAssign /0(2.89ns)은 `pCtx_==nullptr` lazy 덕에 빈 대입이 아무것도 안 하기 때문이다. S3는 Impl만 pool로 받아도 버퍼 할당이 그대로 남아 전 항목 S0와 동률이다. 즉 **pool을 Impl 슬롯에 걸면 효과가 없다**는 것이 S3의 존재 의의다. 덤으로 둘 다 cross-thread 소멸 시 타 스레드 pool 오염이라 정확성 미달이다. 둘 다 탈락, S2는 기준점 역할 종료.

### 3-4. S4 pool + Impl SSO — hot path 최강 (단독 불안전)

| 항목 | S4 |
|---|---|
| 01 Append1B (us) | 2.57 (Impl 중 1위) |
| 02 ConcatChain (ns) | 50.0 (S1 다음 3위) |
| 03 Format (ns) | **586** (동률 1위) |
| 04 FindCompare (ns) | 12.2 (간접참조 밴드) |
| 05 VectorSort (ms) | 0.500 (자체 1위, R1 다음) |
| 06 BinarySearch (us) | 0.279 (3위) |
| 07 Construct /0~/6 (ns) | **6.28** / 9.63 / 13.7 / **20.4** / 107 / 1381 / **71.5** |
| 08 CopyConstruct /0~/6 (ns) | 6.98 / 7.15 / 6.98 / **9.42** / 60.0 / 123 / 58.6 |
| 09 CopyAssign /0~/6 (ns) | 6.98 / 6.98 / 6.98 / 8.89 / 11.7 / 57.8 / 11.7 |
| 10 Move /0~/6 (ns) | **6.00** / 10.0 / 15.0 / 21.5 / 105 / 1350 / 75.0 |
| 11 MT t1·t4·t8 (ns) | 43.8 / 12.2 / **7.88** |
| 12 CrossThread (ns) | 16009 (2위이나 **불안전·참고값**) |
| 13 OwnerExit (ns) | 1918 (1위이나 **불안전·참고값**) |

왜: SSO 47B가 엔진 이름 대역(8~40B)을 커버하는 것이 전부다. Tiny/Mid 생성·복사·이동 최상위, Sort는 8B 포인터 교환으로 S1 대비 1.5배 우위다. 설계 문서의 우려("S1 대비 20% 열화되면 S1 재검토")를 뒤집은 항목이 바로 Sort다. pool 슬롯이 연속 발급되어 S2 같은 캐시 미스가 없고, Mid 이하 비교가 슬롯 내부에서 끝난다. MT는 무락 TLS free-list라 8스레드 7.88ns 선형 스케일이다. 반면 "pool pop 1회"는 "아무것도 안 하기"보다 비싸서 Concat(50ns)은 S1(39ns)에 패하고, Find는 간접 참조 +3~4ns를 낸다. CrossThread 2위·OwnerExit 1위는 함정값이다. owner 검사가 없어 타 스레드 pool에 반환(free-list 오염·이중 반환 위험)하고, owner 종료 후에는 파괴된 TLS pool을 건드린다. 단독 채택 불가, 반드시 S5/S6/S7 정책과 결합해야 한다.

### 3-5. XThread군 S5 / S6 / S7 — 안전 3종의 정반대 성적표

| 항목 | S4 (참고) | S5 | S6 | S7 |
|---|---|---|---|---|
| hot path 대표 Construct /1 (ns) | 9.63 | 13.5 | 16.9 | 16.0 |
| 05 VectorSort (ms) | 0.500 | 0.586 | 0.594 | 0.558 |
| 11 MT t8 (ns) | 7.88 | 8.63 | 8.77 | 8.81 |
| 12 CrossThread (ns) | 16009⛔ | 20926 | 16392 | **11928** |
| 13 OwnerExit (ns) | 1918⛔ | **3830** | 15067 | 10156 |

왜: 같은-스레드 hot path가 S4와 같아야 한다는 가설이 깨진다. 셋 다 S4보다 느린데, `PoolNewImpl/ReleaseImpl`의 owner 저장·비교(TLS 읽기) 고정 비용 때문이다. 짧은 연산 반복(Append·Concat)에서는 30~60%까지 벌어진다. CrossThread 순서는 S7 > S6 > S5다. S7은 반납이 inbox push 1방 + 다음 Acquire 때 owner가 회수라 pool 효과가 유지되고, S6은 명시 pump 전엔 회수가 안 되며, S5는 반납마다 `delete`라 pool 효과가 사라져 S0 수준으로 회귀한다. OwnerExit 순서는 정반대 S5 > S7 > S6이다. S5는 파괴된 pool을 안 건드려 안전하고 빠르고, S7은 소멸마다 Storage 맵 조회 1회가 타서 2.6배이며, S6은 drain 주체(owner)가 없어 꼴찌다. 결론: 지속 producer→consumer 파이프라인이면 S7, 가끔 owner가 먼저 죽는 패턴이면 S5다. 단일 10% 판정 불가(§4-3의 5).

### 4-3. 설계 문서(§3-6) 판단 기준 대입

1. **정확성**: S3/S4 단독은 B13 정의상 실패이므로 반드시 S5/S6/S7 중 하나의 정책이 붙어야 한다. S6 은 S7 전제 필요.
2. **hot path**: B1 Tiny/Mid 에서 S0 대비 S1 약 8배(/1: 58.6→7.15), S4 약 3~6배(/1: 58.6→9.63, /3: 83.7→20.4). "S0 대비 최소 2배" 충족. std::string 대비는 Tiny 에서 S1>R1, Mid 에서 S4≈R1 로 동등 이상.
3. **컨테이너**: B9 에서 S4(0.500) < S1(0.750), 즉 S1 대비 열화가 아니라 1.5배 우위. "S1 대비 20% 열화 시 S1 재검토" 조건은 발동하지 않는다. B10 에서도 S1(0.267)≈S4(0.279)로 5% 이내.
4. **멀티스레드**: B11 8스레드에서 S4~S7 선형 스케일 확인. B12 cross-thread 비용은 S7 11928ns ≈ B1 Tiny 환산 대비 3배 이내가 아니라 크지만, 단위가 달라(/100 일괄) 직접 비교가 불가하며 상대 순위(S7>S6>S5)는 가설과 일치.
5. **복잡도**: 성능 차이가 10% 이내면 단순한 쪽(S5)을 채택한다. S5 vs S7: hot path·Sort·MT는 5~10% 이내이나 CrossThread(S5 20926 vs S7 11928, 1.75배)와 OwnerExit(S5 3830 vs S7 10156, S5가 2.6배 빠름)가 정반대로 갈린다. 즉 **워크로드가 producer→consumer 지속형이면 S7, owner-종료형이면 S5** 가 유리하며, 단일 기준으로 10% 판정이 불가하다. §5 권장안 참조.

## 6. 권장안 (수치 기반)

1. **기본 `jc::String` 은 S1(inline SSO, 24B)** — Concat·CopyAssign·탐색 최강, 스레드 정책·lifetime 관리가 필요 없고 EASTL/MSVC 와 같은 검증된 선택이다. 단 이관 시 두 가지를 고쳐야 한다: (a) ~~`Initialize(cap)` 의 SSO 판정을 `_capacity` 가 아니라 실제 길이 기준으로 (Empty 힙 할당 버그)~~ → **2026-09-06 수정 완료** (빈 문자열은 capacity 힌트 무관하게 `ToSsoEmpty()`, §7 참조), (b) SSO 경계를 22B → 23B 이상으로(Short 22B 가 경계에 걸려 있음).
2. **8B 핸들이 꼭 필요하면 S5(조건부) 또는 S7(지속 스트리밍)** — Sort·MT·수명주기 전부 S1 을 앞서나 cross-thread 정책이 강제된다. 네트워크 패킷처럼 producer→consumer 가 지속되면 S7, 일반 게임 오브젝트 이름처럼 owner 종료가 문제면 S5.
3. **S2·S3 은 폐기** — S2 는 바닥 기준점으로 역할 종료, S3 은 버퍼 힙 때문에 pool 효과가 없고 불안전하다.
4. **`StringId`(인턴 이름) 별도 도입은 여전히 유효** — 이름 조회가 정수 비교로 바뀌면 Sort·Search 항목 자체가 벤치 대상에서 사라진다(설계 문서 §8-2 3순위).
5. **비교 루틴은 R1 에서 가져올 것** — Sort·Search 에서 R1 이 압도적인 이유는 `memcmp` 계열 비교다. 어느 후보를 채택해도 `Compare` 만 R1 방식으로 교체하면 B9/B10 이 즉시 개선된다.
